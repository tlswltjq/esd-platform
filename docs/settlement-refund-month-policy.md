# 환불 조정 반영 월 A·정책 인터페이스

**2026-11-02 후속 연결 완료:** 아래는 정책만 검증한 당시의 기록이다. 이후 금융 확인 접수·독립 PG 취소 GET·원장/월 합계·역할별 조회를 연결하고 OCI **120건**·check·bootJar를 통과했다. 현재 상태와 남은 비용/이월/지급 범위는 [원장 연결 기록](settlement-refund-ledger-verification.md)을 따른다.

2026-11-02. 사용자는 [결정 42](decisions.md#settlement-refund-posting-month)의 **A: 최초 금융 확인 월이 OPEN이면 해당 월, CLOSED이면 현재 OPEN 월**을 선택했다. [원배분 전액 상계 계산](settlement-refund-allocation-policy.md)의 결정 41과 PG 비용 독립 마감을 유지한다. 이 문서는 월 선택 정책의 구현·검증 범위를 기록한다.

**구현·OCI 검증 완료:** 단위/아키텍처 71·통합/이행 31의 **102건**과 check·bootJar를 통과했다. 정책·입력/결과·Spring 조립이 완료 범위이며 환불 접수·원장 저장·월 합계 갱신은 아직 연결하지 않았다.

## 선택한 동작

| 상황 | 선택 |
|---|---|
| 9월 매출 마감 후 11월 2일 환불 확정·접수 | 11월 반영, 9월 마감 보존 |
| 10월 환불 확인이 11월에 도착, 10월 OPEN | 10월 반영 |
| 같은 지연 도착, 10월 CLOSED·11월 OPEN | 11월 반영, 원래 확인 월 10월과 이월 사유 보존 |
| 확인 월과 현재 월이 모두 CLOSED | 임의 월을 선택하지 않고 충돌 |
| 이미 반영 월이 기록된 환불의 중복·재처리 | 같은 환불/주문/최초 확인 시각이면 최초 결과를 그대로 반환 |
| 기록된 월에 다른 환불·주문·확인 시각을 대입 | 근거 불일치로 거절 |

월은 모두 KST다. 정책은 최초 금융 확인 월을 사용하며 원매출 월이나 재처리 시각으로 바꾸지 않는다. 늦은 직접 성공 응답은 기존 금융 완료를 보강할 수 있지만 새 월 선택의 근거로 사용하지 않는다. 고객 환불 자격·금액, 판매자/플랫폼 상계액과 PG 비용 부담은 변경하지 않는다.

## 구현한 경계

- `RefundSettlementMonthPolicy` 인터페이스를 config에서 `UseConfirmedRefundMonthPolicy`로 조립한다. 정책 안에 설정 바인딩·DB·HTTP·이벤트 소비·시계 읽기를 넣지 않는다.
- `RefundMonthInput`은 환불/주문 ID·금융 확인/접수 시각·확인 월/현재 월의 마감 스냅샷·선행 선택을 받는다. ID·마이크로초 정밀도·확인 전 접수의 거절과 같은 월의 모순된 마감 상태를 생성 시 검증한다.
- `RefundMonthSelection`은 정책 ID·환불/주문·최초 확인/접수 시각·확인 월·반영 월·사유를 불변 값으로 반환한다. 현재 정책 ID는 `REFUND_CONFIRMED_MONTH_V1`, 사유는 `CONFIRMED_MONTH` 또는 `CLOSED_MONTH_ROLLOVER`다.
- 동일 근거의 선행 선택은 정책 버전이나 월 상태가 바뀌어도 그대로 반환한다. 이 결과는 아직 DB에 저장되지 않으며 실제 접수 서비스가 정본을 읽어 입력에 제공하고 원자 저장해야 한다. 정책 결과만으로 DB 중복 저장 방지가 완료됐다고 설명하지 않는다.
- 마감 상태의 잠금·월 전환 경합·Inbox/환불 원장/월 합계 쓰기는 서비스 책임이다. 이번 통합 검사는 실제 DB 행을 잠근 상태로 정책을 호출하지만 실제 환불 접수 서비스는 추가하지 않았다.

원매출·마감 기록을 덮어쓰거나 자동 재마감하지 않는다. 원장에 음수 조정을 저장하는 것과 잔액의 다음 달 이월·판매자 계좌의 실제 회수는 다른 작업이다. 이월/실제 지급·회수 정책은 아직 선택하지 않았다.
