# 성능 측정 — Outbox 릴레이

**상태: 릴레이 처리량 측정·개선 완료. HTTP 경로 재측정 완료(9장). 받는 쪽 측정 완료(12·13장).**
7장의 무효한 비교는 지우지 않고 남긴다 — 무엇이 측정을 망쳤는지가 결론만큼 중요하다.

> **11장의 랙 지표가 틀린 것이었다** (2026-08-14, [D-026](defects.md#d-026)).
> `kafka_consumer_fetch_manager_records_lag` 는 컨슈머가 멈추면 같이 멈춘다.
> 판정을 브로커 오프셋으로 옮기고 다시 쟀더니 — **생산자 지표가 전부 초록인 회차에
> 브로커 랙이 2,285건 남아 있었다**(12장). 예전 도구로는 그 회차가 통째로 초록이었다.

> **8장의 남은 항목은 [perf-tuning.md](perf-tuning.md) 에서 이어진다** (2026-08-10).
> 설정만으로 8-3·8-4 를 재고, 6장의 `138 → 480 events/s` 를 **OCI 에서 다시 쟀다** —
> 같은 개선이 여기서는 `180.7 → 948.7` 이다. 개선폭이 호스트에 따라 달라진다.
>
> **그 측정을 받아 `poll-interval-ms` 를 1000 → 200 으로 적용했다** (2026-08-13, `7574ea2`).
> 종단 p95 1.30s → 0.56s, 대가는 mysql CPU +1.5%p. [README](../README.md) 트레이스 예시에
> `+527ms` 로 찍혀 있던 폴링 대기가 여기서 줄어든다. **상수로 갈 수 있는 것은 여기까지고**,
> 더 내리려면 적응형 폴링이
> 다음 수순이다 — 설계와 함정은 `OutboxRelay#relay` 주석. 같은 측정에서 나온
> `listener.concurrency` 는 **올리지 않기로 했다**(파티션 3개는 확장 여지, 스레드는 1 유지).

측정 도구는 [scripts/perf/](../scripts/perf/), 관련 결함은 [defects.md](defects.md) 참고.

## 1. 무엇을 왜 쟀나

**Outbox 릴레이 처리량**을 주 지표로 잡았다. 근거 셋.

1. **9개 서비스가 공유하는 단일 병목이다.** 여기가 밀리면 결제 완료 → 라이선스 지급 → 정산까지 전 구간이 함께 밀린다
2. **개선 여지가 코드에 드러나 있었다.** `relay()` 가 배치 전체를 `send().get()` 으로 순차 대기했다
3. **[D-013](defects.md#d-013) 수정과 같은 코드를 건드린다.** 순서 보장을 위해 파티션 키로 묶는 작업이 곧 병렬화의 단위를 만든다 — 교정과 성능 개선이 한 수정에 들어갔다

## 2. 측정 환경

| | |
|---|---|
| 호스트 | macOS, 8 GB RAM |
| Docker | 4 GB 할당 |
| 인프라 | MySQL 8.0 · Kafka 3.9 · Redis 7 (컨테이너) |
| 서비스 | catalog(8081) · order(8082) — 호스트에서 `bootRun` |
| 부하 | k6 v2.1.0 (호스트) |

**전체 스택은 띄우지 못했다.** 서비스 9개 + 인프라 8종은 4 GB 를 크게 넘는다.
Elasticsearch·MongoDB·Grafana 를 빼고, 쓰기 경로에 필요한 최소 구성만 올렸다.

서비스를 컨테이너 대신 호스트에서 띄운 이유 — Docker 메모리를 아끼고 재기동이 빠르다.

## 3. 계측

릴레이는 배경 스레드라 **지표가 없으면 관측할 방법이 없다.** 로그는 재현성이 없고,
DB 를 직접 폴링하면 측정이 측정 대상에 부하를 준다.

`OutboxMetrics` 를 추가해 `/actuator/prometheus` 로 노출했다.

| 지표 | 의미 |
|---|---|
| `stove.outbox.published` / `.failed` / `.dead` | 발행 성공·실패·포기 |
| `stove.outbox.relay` | 릴레이 1회 소요시간 (p50/p95/p99) |
| `stove.outbox.batch.size` | 회차당 처리 건수 |
| `stove.outbox.pending` | **적체량 — 우상향이면 유입 > 처리** |

부하 테스트용 임시물이 아니다. 이벤트가 밀리는지, DEAD 로 떨어지는지는
사고가 난 뒤가 아니라 나기 전에 보여야 한다.

## 4. 왜 HTTP 부하로 릴레이를 재지 않았나

처음에는 k6 로 주문을 밀어 릴레이를 포화시키려 했다. 되지 않았다 —
**주문 생성 경로가 훨씬 낮은 지점에서 먼저 포화한다.**

```
목표 400 RPS → 실제 74 RPS,  dropped_iterations 15,795
p95 5.08s,  실패 3.34%
```

catalog 동기 호출과 커넥션 풀 때문에 API 가 먼저 막히고,
그 상태로는 릴레이가 충분히 밀리지 않아 "릴레이가 얼마나 빠른가"를 알 수 없다.

그래서 이벤트를 **DB 에 직접 적재해 적체를 만들고 배수 속도를 재는** 방식으로 바꿨다
(`scripts/perf/relay-drain.sh`). HTTP 경로와 무관하게 릴레이만 측정된다.

## 5. 기준선

20,000건 적재 후 배수.

```
소요        144.9 초
처리량      138.0 events/s
릴레이 1회  p50 0.243s   p95 0.763s   (307회, 배치 최대 200)
```

숫자가 정확히 맞아떨어졌다.

```
주기 = 고정 대기 1.00s + 배치 처리 0.47s = 1.47s
주기당 200건 → 200 / 1.47 = 136 events/s     (측정값 138)
```

병목이 둘로 갈린다.

| 요인 | 비중 |
|---|---|
| 고정 폴링 대기 1초 | **주기의 68% 가 유휴** |
| 배치 직렬 발행 0.47초 | 건당 2.35ms 순차 왕복 |

## 6. 개선

### 개선 1 — 키 단위 웨이브 발행

같은 `partitionKey` 는 순서대로, 다른 키끼리는 동시에 발행한다.

```
이전:  e1 → 대기 → e2 → 대기 → ... → e200 → 대기      (200회 직렬 대기)

이후:  웨이브 1: [키A-1, 키B-1, 키C-1, ...]  ← 동시 발행, 1회 대기
       웨이브 2: [키A-2,        키C-2, ...]  ← 1번이 성공한 키만
```

- **순서** — 앞 이벤트가 못 나가면 같은 키의 뒤 이벤트도 이번 회차에서 보류된다. [D-013](defects.md#d-013) 수정
- **처리량** — 대기 횟수가 *배치 크기* 에서 *최장 체인 길이* 로 줄어든다. 파티션 키가 주문번호라 대부분 길이 1

```
처리량  138.0 → 156.1 events/s   (+13%)
배치 처리 시간  0.47s → 0.28s
```

기대보다 작았다. 배치 처리가 줄어든 만큼 **고정 1초 대기의 비중이 78% 로 올라갔을 뿐**이다.

### 개선 2 — 비울 게 남았으면 다음 폴링을 기다리지 않는다

배치가 가득 찼다는 것은 적체가 더 있다는 뜻이다. 그 상태로 고정 주기만큼 쉬면
쉬는 동안 계속 쌓이기만 한다.

```java
for (int cycle = 0; cycle < properties.maxBatchesPerCycle(); cycle++) {
    int processed = relayOneBatch();
    if (processed < properties.batchSize()) {
        return;   // 배치를 다 못 채웠다 = 적체 해소
    }
}
```

**배치마다 트랜잭션을 따로 연다.** 여러 배치를 한 트랜잭션으로 묶으면
`FOR UPDATE SKIP LOCKED` 락 보유 시간이 그만큼 길어져 API 응답까지 끌어내린다.
한 회차가 스케줄러를 독점하지 않도록 `max-batches-per-cycle`(기본 10) 상한을 뒀다.

```
처리량  156.1 → 480.5 events/s
소요    128.1초 → 41.6초 (20,000건)
```

### 종합

| 단계 | 처리량 | 기준선 대비 |
|---|---|---|
| 기준선 | 138.0 events/s | — |
| + 키 웨이브 발행 | 156.1 events/s | ×1.13 |
| + 연속 배수 | **480.5 events/s** | **×3.48** |

같은 스크립트, 같은 20,000건, 같은 키 분포(전부 다른 키)로 측정했다.

## 7. HTTP 경로 — 유효한 비교를 얻지 못했다

릴레이 개선이 API 에 영향을 주는지 확인하려 k6 를 다시 돌렸더니 **악화**로 보였다.

| 구성 | RPS | p95 | 실패율 |
|---|---|---|---|
| 기준선 (개선 전) | 74.1 | 5.08s | 3.34% |
| 개선 후 `max-batches=10` | 44.8 | 10.0s | 36.1% |
| 개선 후 `max-batches=1` | 46.5 | 8.68s | 31.4% |
| **릴레이 완전 비활성** | **44.9** | **9.9s** | **38.5%** |

마지막 줄이 답이다. **릴레이를 꺼도 같은 숫자가 나온다.**
즉 이 차이는 코드가 아니라 측정 환경에서 왔다.

원인 정황:

- 호스트 메모리 압박 — 측정 중 `pageouts` 150만 관측, 여유 32%
- 첫 기준선은 부팅 직후 유휴 상태에서, 이후 측정은 반복된 빌드·JVM·k6 실행 뒤에 잡혔다
- 실패는 전부 커넥션 풀 고갈이었다
  `Connection is not available, request timed out after 3007ms (total=20, active=20, idle=0, waiting=161)`

**개선 전후를 이 숫자로 비교해서는 안 된다.** 세 구성이 모두 포화 상태이고,
포화 위에서 잰 값은 무엇을 바꾸든 "포화했다"만 알려준다.

### 그래도 유효한 관찰

- **API 가 릴레이보다 훨씬 낮은 지점에서 포화한다.** 45~75 RPS 대 480 events/s.
  쓰기 경로의 병목은 릴레이가 아니라 **catalog 동기 호출 + 커넥션 풀**이다
- 실패 양상이 전부 `HikariCP` 고갈이다. 풀 20개에 대기 161 — 스레드가 커넥션을 기다린다

> **8-1 은 9장에서 수행했다.** 아래 계획은 그 실행 근거로 남긴다.

## 8. 다음에 이어갈 것

### 8-1. HTTP 경로 재측정 (최우선) — ✅ 완료, 9장

**전제 — 여유 있는 호스트에서 다시 잰다.** 지금 환경에서는 무엇을 재도 포화 상태다.

측정 위생 규칙을 먼저 세운다.

- 측정 전 `./gradlew --stop`, 잔여 JVM 정리, `docker compose down -v` 로 초기화
- 각 조건마다 **동일한 초기 상태**에서 시작 (지금은 첫 기준선만 그랬다)
- **포화 이전 구간**에서 비교한다. `RATE=30 DURATION=60s k6 run scripts/perf/order-soak.js` 로
  릴레이 ON/OFF 를 나란히 재면 릴레이가 API 에서 가져가는 몫이 나온다
- 한 조건당 최소 2회 반복해 재현성 확인

### 8-2. 커넥션 풀 병목 규명 — 🔴 이 부하에서 **기각**, 13-5

> **관측 수단이 생겼고, 가설이 틀렸다 (2026-08-14).** `collect-consumer.sh` 가 이제
> `pool_active` 와 **`pool_pending`**(커넥션을 기다리는 스레드 수)을 함께 찍는다.
> 컨슈머를 포화시킨 5회차 전부 **`pending` 0, `active` 최대 5/20** 이었다 —
> 커넥션을 기다린 스레드가 한 번도 없다. **60 RPS + 5 VU 에서 자원 분리는 필요하지 않다.**
> 아래 항목들은 7장의 포화 상태(풀 20개에 대기 161)를 근거로 세운 것인데,
> 그 대기는 포화의 증상이었지 이 구성의 성질이 아니었다.

실패가 전부 풀 고갈이었다. 확인할 것.

- 주문 생성 1건이 커넥션을 얼마나 오래 잡는가 — `PlaceOrderFacade` 는 트랜잭션을 열지 않지만,
  `OrderCommandService` 의 쓰기 트랜잭션 앞뒤로 catalog HTTP 호출(연결 1s + 읽기 2s)이 붙는다
- 풀 크기 20 이 적정한가, 아니면 catalog 응답 지연이 커넥션 점유를 늘리는가
- 릴레이와 API 가 같은 풀을 쓰는 것이 맞는가 — **자원 분리**(별도 DataSource)를 검토

### 8-3. 릴레이 개선의 부작용 확인 — 🔶 절반 완료, [perf-tuning.md](perf-tuning.md) 2절

포화 이전 구간에서 다음을 확인해야 한다.

- 연속 배수가 API 응답에 실제로 얼마나 영향을 주는가 — **아직 확인되지 않았다**
- ~~`max-batches-per-cycle` 의 적정값 — 1·3·10 을 같은 조건에서 비교~~
  → 180.7 / 451.0 / 948.7 events/s. `mbpc=1` 이 개선 전 동작과 같아 **전후 비교까지 나왔다**
- 배치별 트랜잭션 분리가 락 보유 시간을 실제로 줄였는가 (`FOR UPDATE SKIP LOCKED` 대기 관측)
  — **아직**

### 8-4. 아직 손대지 않은 병목 — 🔶 하나 닫힘, [perf-tuning.md](perf-tuning.md) 5절

- **`acks: all` + 단일 브로커** — 배치 처리 0.28초의 상당 부분이 여기일 수 있다. 브로커 3대 구성에서 재측정
  → OCI 에서 같은 배치가 **0.021초**였다. 0.28초는 브로커가 아니라 랩탑이었다
- ~~**`markSent` 대량 UPDATE** — 배치 200건의 커밋 비용. `@BatchSize` / JDBC 배치 설정 확인~~
  → **JDBC 배치 설정으로는 안 움직인다.** 커밋 구간이 비용의 80%인 것은 맞지만
  (배치당 고정 20ms + 건당 0.48ms), 원인은 배치화가 아니다
- **읽기 경로** — store 검색 + Redis 캐시 히트율. Elasticsearch 가 필요해 이번 환경에서는 못 쟀다

## 9. HTTP 경로 재측정 — 유효한 비교를 얻었다

7장이 무효였던 이유는 하나였다. **호스트가 포화였다.**
그 제약을 없앤 뒤 8-1 의 위생 규칙대로 다시 쟀다.

### 9-1. 측정 환경

| | 7장 (무효) | 9장 |
|---|---|---|
| 호스트 | macOS 8GB / Docker 4GB | OCI Ampere A1 — 4코어 **23GB**, aarch64 |
| 스택 | **ES·Mongo·Grafana 제외**, 서비스 2개 `bootRun` | **인프라 9 + 앱 10 전부 컨테이너**, 뺀 것 없음 |
| 스와핑 | `pageouts` **150만**, 여유 32% | swap 사용 **0~1 MiB**, available 15.7GB |
| k6 | 호스트 | 컨테이너(`stove_default` 네트워크). 호스트 포트 미publish |

전체 스택을 동시에 띄운 것은 이때가 처음이다 — 로컬에서는 산술적으로 불가능했다
([decisions.md](decisions.md) 15번).

### 9-2. 한계선 (계단식 20→400 RPS)

| 구성 | RPS | p95 | 실패율 | 최대 VU |
|---|---|---|---|---|
| 릴레이 ON | 132.5 | 466.42ms | **0.00%** | 252 |
| 릴레이 OFF | 133.2 | **84.09ms** | **0.00%** | 63 |

**7장과 가장 크게 다른 것은 실패율이다.** 그때는 세 구성이 31~38% 실패에 p95 8.7~10초였고
원인이 전부 HikariCP 고갈이었다. 그건 코드의 성질이 아니라 포화의 증상이었다.

### 9-3. 판정 — 릴레이 ON/OFF (포화 이전, 동일 초기 상태, 2회 반복)

계단식은 400 RPS 까지 올라가 포화로 들어가므로 한계선 파악에만 쓴다.
비교는 `order-soak.js` 를 **60 RPS 고정**(관측된 한계선의 약 45%)으로,
각 회차마다 `orders` 와 `outbox_event` 를 비우고 order 를 재기동해 돌렸다.

| 조건 | 회차 | RPS | avg | p90 | **p95** | 실패 | **pending** |
|---|---|---:|---:|---:|---:|---:|---:|
| ON | r1 | 60.00 | 21.23ms | 27.71ms | **42.60ms** | 0.00% | **0** |
| ON | r2 | 59.98 | 25.28ms | 26.15ms | **43.12ms** | 0.00% | **0** |
| OFF | r1 | 59.98 | 18.99ms | 17.17ms | **22.37ms** | 0.00% | **5,398** |
| OFF | r2 | 59.97 | 19.08ms | 18.79ms | **24.10ms** | 0.00% | **5,398** |

**두 조건이 서로 다른 숫자를 낸다 — 이번 측정은 유효하다.**
회차 간 편차는 조건 안에서 0.5ms / 1.7ms 인데 조건 사이는 19ms 다. 신호가 잡음보다 크다.

**`pending` 이 그 자체로 대조군 검증이다.** OFF 에서 5,398 은 생성된 주문 수와 정확히 같다 —
이벤트가 하나도 발행되지 않고 그대로 쌓였다는 뜻이고, ON 에서는 0 이다.
**두 조건이 실제로 달랐다는 직접 증거**이고, 7장에는 이 확인이 없었다.

### 9-4. 결론

**릴레이는 쓰기 경로 p95 에 약 19ms(1.85배)를 얹는다. 처리량은 줄이지 않는다.**
60 RPS 에서 두 구성 모두 유입을 실패 없이 소화하므로 RPS 는 같게 나온다 —
**이 비교의 지표는 처리량이 아니라 지연이다.** 7장이 RPS 로 판정하려 한 것 자체가 무리였다.

그리고 그 몫은 부하와 함께 커진다. 60 RPS 에서 19ms 차이가
계단식(최대 400 RPS)에서는 **466ms 대 84ms** 로 벌어지고, 같은 부하를 소화하는 데
필요한 VU 가 63 → 252 로 는다. 8-2 의 가설과 방향이 같다 —
**릴레이와 API 가 같은 커넥션 풀을 쓴다.** 자원 분리를 검토할 근거가 이제 숫자로 있다.

> **남은 한계** — 이것은 릴레이 개선 *전후* 비교가 아니라 릴레이 *유무* 비교다.
> 개선 전 코드로 되돌려 같은 절차를 반복하면 개선이 API 지연에 준 영향까지 나오는데,
> 그건 아직 하지 않았다.

## 10. 이번에 배운 것

**측정 환경이 변하면 그 전후 숫자는 비교가 아니라 무관한 값 두 개다.**

릴레이 처리량(138 → 480)은 짧은 시간 안에 연달아 쟀고 HTTP 와 분리돼 있어 유효하다.
7장의 HTTP 숫자는 몇 시간에 걸쳐 환경이 달라진 상태에서 쟀고, 그래서 쓸 수 없었다.

다행히 "릴레이를 꺼도 같은 숫자" 라는 대조군이 있어 **개선을 성능 저하로 오인하지 않았다.**
대조군이 없었다면 멀쩡한 수정을 되돌렸을 것이다.

**9장에서 같은 교훈을 한 번 더 만났다.** 비교가 도는 중에 같은 호스트에서 CI 를 한 번
띄웠고, 그 회차의 p95 가 59.66ms 로 튀었다(같은 조건의 다른 회차는 42.60 / 43.12ms).
즉시 취소하고 그 회차를 버린 뒤 다시 쟀다.
**측정 중 호스트에 다른 부하를 올리지 않는다**는 것이 7장이 남긴 규칙이었는데,
규칙을 아는 것과 지키는 것은 별개였다. 반복 측정이 그것을 잡아냈다 —
한 조건당 한 번만 쟀다면 오염된 값이 그대로 결론이 됐을 것이다.

## 11. 받는 쪽 — 측정이 생산자 쪽에서 끝나고 있었다

**여태 잰 것은 전부 "보내는 쪽"이었다.** 릴레이가 초당 몇 건 발행하는지는 알아도,
받는 쪽이 그걸 따라오는지는 아무도 재지 않았다.

둘은 같은 숫자가 아니다. 그리고 **차이가 생산자 지표에 전혀 나타나지 않는다** —
발행이 끝나면 `stove_outbox_pending` 은 0 이다. 컨슈머가 밀리면 적체가 브로커로 옮겨갈 뿐인데,
Outbox 만 보면 해소된 것처럼 보인다.

### 11-1. 계측을 새로 하지 않았다

필요한 지표는 이미 전부 노출돼 있었다. 재는 자리가 없었을 뿐이다.

> **이 표의 첫 줄이 틀렸다 (2026-08-14, [D-026](defects.md#d-026)).** `records_lag` 는
> "아직 안 읽은 건수" 가 아니라 **직전 fetch 응답에서 본 건수**다. fetch 가 멈추면 값도 멈춘다.
> 랙 판정은 브로커 오프셋으로 옮겼다 — `scripts/perf/collect-lag.sh` 와 compose 의 `kafka-exporter`.
> 아래 11-2 의 "랙 0" 은 그래서 근거가 되지 못한다(다만 그 결론 자체는 12장에서 다시 확인됐다).

| 지표 | 의미 | 생산자 쪽 대응 |
|---|---|---|
| ~~`kafka_consumer_fetch_manager_records_lag`~~ | ~~아직 안 읽은 건수~~ → **믿을 수 없다. D-026** | `stove.outbox.pending` |
| `kafka_consumer_fetch_manager_records_consumed_total` | 누적 소비 → 증분이 초당 소비량 | `stove.outbox.published` |
| `spring_kafka_listener_seconds_count` / `_sum` | 리스너 처리 건수와 총 시간 → 평균 | `stove.outbox.relay` |
| 위 지표의 `error` 태그 | **예외를 던진 건수** | `stove.outbox.failed` |

마지막 것이 특히 중요하다. 리스너가 던진 예외는 재시도가 흡수하므로
**HTTP 응답에도, 생산자 지표에도, k6 에도 나타나지 않는다.** 여기서만 보인다.

`spring.kafka.listener.observation-enabled: true` 가 이미 켜져 있어서 가능했다 —
[decisions.md](decisions.md) 17번이 트레이스를 이으려고 켠 것인데, 처리시간 타이머가 따라왔다.

### 11-2. 첫 측정 — 결제 콜백 팬아웃 (10 VU, 60초)

`collect-consumer.sh` 를 `payment-callback.js` 와 같은 타임라인으로 돌렸다.

| 컨슈머 | 평균 처리시간 | 초당 소비 | 랙 | 저장소 |
|---|---:|---:|---:|---|
| `download` | **4.8 ms** | 4.5 | 0 | MongoDB |
| `payment` | **8.5 ms** | 10 | 0 | MySQL |
| `order` | **24 ms** | 4.5 | 0 | MySQL |
| `license` | **26 ms** | 4.5 | 0 | MySQL |
| `settlement` | **26 ms** | 4.5 | 0 | MySQL |

**처리시간이 서비스마다 5배까지 벌어진다.** 이 부하에서는 랙이 0 이라 사용자에게 보이지 않지만,
유입이 늘면 가장 느린 셋이 먼저 밀린다. 그리고 그 셋은 `PaymentCompleted` 를 **동시에** 받는다 —
팬아웃 경로의 실질 처리량은 가장 느린 컨슈머가 정한다.

`payment` 이 초당 10건인 것은 두 토픽(`stove.order.v1`·`stove.license.v1`)을 함께 소비하기 때문이다.

> **이 숫자는 한계선이 아니다.** 10 VU 는 컨슈머를 밀지 못하는 부하이고(랙이 계속 0),
> 여기서 얻은 것은 **평상시 처리시간의 서비스 간 격차**다.
> 랙이 쌓이기 시작하는 지점을 찾으려면 유입을 올리며 같은 수집을 반복해야 한다 — 아직 하지 않았다.

> **후속 (2026-08-10, [perf-tuning.md](perf-tuning.md) 4절).** payment 하나에 대해 한계선을 쟀다 —
> **141.1 events/s**(`concurrency=1`), 릴레이 발행 948.7 events/s 의 **6.7분의 1**이다.
> `concurrency` 를 파티션 수인 3 으로 올리면 364.1 events/s 가 된다.
> 그리고 이 절이 판정 근거로 쓰는 `records_lag` 는 **실제 랙 11만 건 동안 0 을 보고했다.**

### 11-3. 왜 컨슈머용 `relay-drain.sh` 를 만들지 않았나

릴레이는 `outbox_event` 에 SQL 로 직접 적재해 적체를 만들 수 있었다.
컨슈머에 같은 짓을 하려면 **Kafka 에 이벤트를 직접 밀어넣어야** 하는데,
그러면 그 이벤트가 가리키는 주문·결제가 DB 에 없다. 리스너가 전부 예외를 던지고
재시도를 소진해 **DLT 가 수만 건 쌓인다.** 측정하려다 운영 지표를 오염시키는 셈이다.

그래서 컨슈머 측은 **실제 경로로 부하를 밀어 재는 방법만** 둔다.
`payment-callback.js` 가 그 경로이고, 유입을 올리는 것이 곧 컨슈머 부하를 올리는 것이다.

> **이 절의 전제 하나가 틀렸다 (2026-08-10).** `relay-drain.sh` 의 합성 페이로드를
> payment 리스너가 실제로 받아 봤더니 **예외가 0건**이었다 — `lines` 가 없어도 `createReady` 가
> 그대로 통과한다. DLT 는 한 건도 쌓이지 않았고 `payment` 행만 생겼다.
>
> 다만 결론은 유지된다. 이유가 달라질 뿐이다 — 위험한 것은 DLT 오염이 아니라
> **의미 없는 행 수만 개**다. [perf-tuning.md](perf-tuning.md) 4절은 합성 적재 대신
> **측정이 남긴 실제 백로그 11만 건**의 배수 속도를 써서 이 문제를 피했다.

## 12. 받는 쪽을 실제로 재다 — 생산자 지표가 전부 초록인 회차의 랙 2,285

11장이 "측정이 생산자 쪽에서 끝나고 있었다"고 적고 컨슈머 지표를 표로 세웠는데,
**그 표의 랙 지표가 틀린 것이었다**([D-026](defects.md#d-026)). 판정 근거를 브로커로 옮기고
같은 질문을 다시 물었다 — **받는 쪽이 보내는 쪽을 따라오는가.**

### 12-1. 측정 환경 — 세 번째 호스트

| | 7장 (무효) | 9장 | **12장** |
|---|---|---|---|
| 호스트 | macOS 8GB / Docker 4GB | OCI Ampere A1 4코어 23GB | **Intel i5-8600 6코어 32GB** |
| Docker | 4 GB | — | OrbStack 15.7 GB |
| 스택 | 일부 제외 | 전부 컨테이너 | **전부 컨테이너** |

**로컬에서 전체 스택이 뜬 것은 이번이 처음이다.** 7장이 "산술적으로 불가능"이라고 적은 것은
그 8GB 랩탑 이야기이고, 이 데스크톱에서는 성립하지 않는다.
[decisions.md](decisions.md) 15번(측정은 원격에서)의 전제가 호스트에 달려 있었다는 뜻이다.

### 12-2. 도구가 먼저 바뀌었다

- **`scripts/perf/collect-lag.sh`** — 랙을 브로커에게 직접 묻는다. 커밋 오프셋이 없는 파티션은
  **0 이 아니라 `unknown` 으로 센다.** 모르는 것을 0 으로 적는 습관이 D-026 을 만들었다
- **`scripts/perf/run-session.sh`** — 부하 + 수집기 넷을 한 타임라인으로 돌리고
  환경·조건 오버라이드·시작 상태(랙 포함)를 `env.txt` 에 남긴다
- **`kafka-exporter`** — 같은 값을 Prometheus 상시 시계열로. 알람 둘이 여기 걸렸다

시작 상태에 **랙**을 넣은 것이 이번 측정을 성립시켰다. `RESET` 은 DB 만 비우므로
앞 회차가 남긴 미소비 메시지가 다음 회차의 시작 상태가 되는데, **DB 만 보면 깨끗해 보인다.**
회차마다 컨슈머 그룹 오프셋을 `--to-latest` 로 되돌려 랙 0 에서 시작했다.

### 12-3. 한계선 — 계단식 20→400 RPS

| | |
|---|---:|
| 처리량 | 121.7 req/s |
| p95 | 1,608.7 ms |
| **실패율** | **0.00%** |
| 릴레이 발행 | 32,862건, 최대 **1,574 events/s** |
| `stove_outbox_pending` | 최대 271 → **최종 0** |
| **브로커 랙 (payment)** | 최대 **27,845** → 최종 **27,474** |

**마지막 두 줄이 이 장의 요지다.** 생산자 지표는 "다 보냈다"(0)이고 실패도 0인데,
브로커에는 27,474건이 밀려 있다. 릴레이가 초당 1,574건을 밀어 넣는 동안
payment 는 초당 31건을 소화했다 — **50배 차이**다.
OCI 에서 잰 격차는 6.7배였다([perf-tuning.md](perf-tuning.md) 4절). 호스트가 다르면 이것도 다르다.

### 12-4. 판정 — listener.concurrency 1 ↔ 3

한계선의 약 절반인 **60 RPS 고정**에서 비교했다(포화 이전). 순서는 `1 → 3 → 1`.
회차마다 `orders`·`outbox_event` 를 비우고 컨슈머 오프셋을 되돌리고 payment 를 재생성했다.

| c | 회차 | RPS | **API p95** | 랙 최대 | **랙 최종** | 소비 최대 | 리스너 평균 |
|---|---|---:|---:|---:|---:|---:|---:|
| **1** | r1 | 59.92 | **209.4ms** | 2,634 | **2,285** | 30.0/s | 52.10ms |
| **1** | r2 | 59.92 | **179.1ms** | 2,565 | **2,119** | 34.0/s | 48.00ms |
| **3** | r1 | 59.82 | **383.5ms** | 1,292 | **325** | 81.7/s | 62.65ms |
| **3** | r2 | 59.76 | **350.1ms** | 1,062 | **210** | 73.3/s | 59.68ms |
| **1** | 재확인 | 59.86 | **232.8ms** | 2,659 | **2,283** | 32.3/s | 52.57ms |

**마지막 줄이 대조군이다.** c=1 재확인의 랙 최종 2,283 이 첫 두 회차(2,285 · 2,119)와 같다 —
측정이 도는 동안 payment 테이블이 계속 커졌는데도 값이 돌아왔으므로, 가운데의 변화는
그 누적이 아니라 **concurrency 때문이다.**

조건 안 편차가 랙 최종 2,119~2,285, 조건 사이는 2,229 대 268 이다. 신호가 잡음보다 훨씬 크다.

### 12-5. 결론 둘

**하나. concurrency 를 파티션 수까지 올리면 소비가 ×2.41 이 된다.**
평균 32.1 → 77.5 events/s. OCI 에서 잰 ×2.55 와 거의 같다 —
**이 배수는 호스트에 별로 의존하지 않는다.** 파티션 3개가 상한이므로 이론 최대 ×3 에 근접한다.

그 결과 랙 최종이 **2,229 → 268 (8.3분의 1)** 로 줄고, c=3 은 60 RPS 를 거의 따라잡는다
(3,600건 중 3,275~3,378 소비). c=1 은 명백히 못 따라간다(1,313~1,482).

**둘. 그 대가가 API 응답에 나온다.** p95 평균 **207ms → 367ms (×1.77)**.
payment 는 주문 생성 경로에 있지도 않은데 그렇다 — 같은 호스트의 CPU 와 커넥션 풀을 나눠 쓴다.
리스너 자신의 평균 처리시간도 50.9 → 61.2ms 로 는다(스레드 간 경합).

> **이 "둘" 은 재현되지 않았다 (13-7).** 같은 비교를 표본 2.5배(9,000건)·부하 150초로 다시 재니
> c=3 값이 c=1 범위 안에 들어갔다 — **차이 없음**이다. 이 60초 측정은 order 재기동 직후라
> JIT·풀 확보 구간이 p95 를 밀어올렸을 가능성이 크다. **아래 12-5 의 ×1.77 은 근거가 약하다.**
> 리스너 처리시간이 느려지는 것(50.9 → 61.2ms)은 두 측정에서 다 관측되므로 그대로 유효하다.

[perf-tuning.md](perf-tuning.md) 는 `concurrency` 를 **올리지 않기로** 결정하면서
"필요할 때 설정 한 줄로 켤 수 있다는 것을 미리 확인해 둔 값"이라고 적었다.
~~이제 그 결정에 가격표가 붙었다 — 컨슈머 처리량 ×2.41 을 사려면 API p95 ×1.77 을 낸다.~~

> **13장이 이 문장을 지웠다.** 대표본 재측정에서 API 차이가 안 나왔고, 커넥션 풀은
> `pending` 0 으로 **병목이 아니었다.** 대가가 있다면 이 부하에서는 안 잡힌다.
> 그리고 13-6 이 이득 쪽을 훨씬 크게 만들었다 — **결제한 사용자가 게임을 받은 비율이
> 50% 대 100% 였다.** 남는 질문은 "올릴 것인가"가 아니라 **"언제 올릴 것인가"** 다.

**어느 쪽인지는 이 표가 아니라 그때의 랙이 말해 준다 — 이제 그걸 볼 수 있다.**

### 12-6. 이번에 배운 것

**초록은 어디가 초록인지까지 말해야 초록이다.**

다섯 회차 전부 이랬다.

```
실패율 0.00%          ✓
checks 100%           ✓
outbox pending 최종 0 ✓
                        ← 여기까지가 예전에 볼 수 있던 전부다
브로커 랙 최종 2,285  ✗
```

**예전 도구로는 이 회차들이 통째로 초록이었다.** 발행이 끝나면 `pending` 은 0 이고,
컨슈머가 던진 예외가 없으니 리스너 지표도 조용하고, 랙 지표는 D-026 때문에 축소된 값을 보고한다.
적체가 브로커로 옮겨간 것뿐인데 **관측 가능한 모든 자리가 해소를 가리켰다.**

9장이 "대조군이 없었다면 멀쩡한 수정을 되돌렸을 것"이라고 적었는데, 여기서는 반대 방향이다 —
**보는 자리가 없었다면 밀리고 있는 것을 정상으로 확인하고 넘어갔을 것이다.**

### 12-7. 이 측정의 한계

- **조건당 2회다**(c=1 은 대조 포함 3회). 위생 규칙의 최소치이고 더 낫지는 않다
- **한계선은 1회만 쟀다.** 60 RPS 를 "절반 이하"로 고른 근거가 그 한 회차에 걸려 있다
- **c=3 의 대가를 API p95 로만 봤다.** 커넥션 풀 점유·DB 락 같은 경로는 이번에도 안 봤다(8-2 는 여전히 열려 있다)
- **payment 하나만 올렸다.** 팬아웃 3종(license·settlement·download)을 함께 올렸을 때의
  합산 대가는 다르다. 11-2 가 보여준 처리시간 격차를 생각하면 그쪽이 진짜 한계선이다
- `dropped_iterations` 임계값(`count<1`)이 5회 중 4회 걸렸다. 실제 유실은 3,600건 중 **0~13건**이라
  판정을 뒤집지 않지만, **임계가 이 시나리오에는 너무 빡빡하다.** 조정하거나 근거를 다시 적어야 한다

## 13. 그 대가를 다시 재다 — 커넥션 풀 가설 기각, 그리고 12장 정정

12장이 "`concurrency=3` 은 소비 ×2.41 을 주고 API p95 ×1.77 을 낸다"고 결론지었다.
그 대가의 원인으로 지목된 것이 8-2 의 오랜 가설 — **리스너 스레드와 HTTP 스레드가
같은 HikariCP 풀을 쓴다** — 였다. 이번에는 그 가설을 직접 겨눴다.

### 13-1. 재기 전에 계측을 하나 더 붙였다

여태 풀 점유는 **지연 숫자로 추정만** 했다. `collect-consumer.sh` 에 두 칼럼을 넣었다.

| | |
|---|---|
| `pool_active` | 지금 빌려 나간 커넥션 |
| **`pool_pending`** | **커넥션을 기다리는 스레드 수 — 이게 판정값이다** |

`active` 가 최대치라도 `pending` 이 0이면 풀은 충분한 것이고, `pending` 이 서면
그때부터 대기가 응답시간에 그대로 실린다. **이 구분이 없으면 "풀이 꽉 찼다"와
"풀이 병목이다"를 영영 못 가른다.**

`payment-callback.js` 에는 엔드포인트별 트렌드를 넣었다. 한 반복이 주문 1회·폴링 N회·승인 1회를
보내는데 **폴링이 건수를 압도해** `http_req_duration` 총계가 사실상 "폴링이 얼마나 빨랐나"가 된다.

### 13-2. 1차는 질문에 답하지 못했다 — 부하가 아무것도 압박하지 않았다

먼저 `fanout` 단독(5 VU · 2분)으로 c=1 · c=3 을 쟀다. 완전히 똑같이 나왔다.

| | c=1 (3회) | c=3 (2회) |
|---|---|---|
| 결제 승인 p95 | 72.4 · 91.9 · 86.5ms | 84.6 · 95.2ms |
| 종단 지연 p95 | 588 · 604 · 604ms | 606 · 614ms |
| 랙 최대 | 2 · 3 · 1 | 2 · 1 |
| **풀 active 최대** | **2·3·2 / 20** | **3·2 / 20** |
| **풀 pending 최대** | **0** | **0** |

**차이가 없는 이유는 영향이 없어서가 아니라 압박이 없어서다.** 풀 20개 중 최대 3개,
기다린 스레드 0, 랙 최대 3. 컨슈머가 노는데 스레드를 늘려 봐야 나눌 일이 없다.
`payment-callback.js` 는 5 VU 고정이라 초당 2.3건만 만든다 — 처음부터 처리량 시나리오가 아니다.

> **이번에 배운 것.** 압박 증거를 같이 찍지 않으면 **음성 결과를 해석할 수 없다.**
> 풀 지표가 없었다면 "차이 없음"만 남고 그게 "영향 없음"인지 "실험 실패"인지 몰랐을 것이다.

### 13-3. 2차 — 컨슈머를 포화시킨 위에서 잰다

[scripts/perf/README.md](../scripts/perf/README.md) 가 적어 둔 대로 겹쳐 돌렸다.
order 를 60 RPS 로 밀어 payment 의 `stove.order.v1` 컨슈머를 포화시켜 두고,
그 위에서 `fanout` 을 겹친다. **리스너 스레드와 HTTP 스레드가 실제로 풀을 놓고 다투는 구성이다.**

회차마다 payment·license·order 를 내리고 컨슈머 오프셋을 `--to-latest` 로 되돌리고
세 스키마를 비운 뒤 재생성했다. 순서는 `1 → 3 → 1`.

### 13-4. 결과

| 회차 | c | 시작 랙 | 지급 | 성공률 | 랙 최종 | 배수/s | 풀 act | **풀 pend** |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| r1 | 1 | 320 | 6/12 | **50%** | 5,756 | 19.0 | 3/20 | **0** |
| ~~r2~~ | 1 | **5,686** | 0/10 | 0% | 11,819 | 16.4 | 2/20 | 0 |
| r1 | 3 | 141 | 36/36 | **100%** | 159 | 52.6 | 4/20 | **0** |
| r2 | 3 | 164 | 36/36 | **100%** | 546 | 51.7 | 5/20 | **0** |
| 재확인 | 1 | 325 | 5/10 | **50%** | 5,741 | 19.2 | 4/20 | **0** |

**대조군이 맞았다** — 재확인의 랙 최종 5,741 이 r1 의 5,756 과 편차 0.3%다.
조건 사이 차이(5,748 : 353)가 조건 안 편차보다 16배 크다.

### 13-5. 판정 하나 — 커넥션 풀은 병목이 아니었다

**다섯 회차 전부 `pending` 0.** `active` 는 최대 5/20. 오염된 회차조차 그랬다.
커넥션을 기다린 스레드가 **한 번도 없다.**

8-2 가 "릴레이와 API 가 같은 풀을 쓰는 것이 맞는가 — 자원 분리를 검토"라고 적어 둔 항목은
**이 부하에서 기각이다.** 자원 분리는 지금 필요하지 않다. 9-4 가 "가설과 방향이 같다"며
지목했던 것이 실은 다른 원인이었다는 뜻이고, 그 원인은 아직 모른다.

> 기각의 범위를 좁혀 둔다 — **60 RPS + 5 VU 에서** 그렇다. 풀 20개가 부족해지는 부하가
> 어디인지는 안 쟀다. 다만 `active` 최대가 5 라 한참 멀다.

### 13-6. 판정 둘 — 사용자 결과를 가르는 것은 랙이다

| | c=1 | c=3 |
|---|---:|---:|
| **결제한 사용자가 게임을 받은 비율** | **50%** | **100%** |
| 2분간 완료 건수 | 6 · 5건 | 36 · 36건 |

**HTTP 실패율 0%, outbox 비어 있음, 그런데 사용자 절반이 물건을 못 받았다.**
12장이 "초록은 어디가 초록인지까지 말해야 초록"이라고 쓴 것의 가장 선명한 사례다.

메커니즘은 산수다.

```
c=1   랙 5,750 ÷ 19/s  ≈ 300초    새 주문 차례까지  →  폴링 한도 60초 초과 → 실패
c=3   랙 1,650 ÷ 52/s  ≈  32초                     →  한도 안 → 성공
```

그리고 컨슈머 배수 속도는 12장과 거의 같다(c=1 19.0/19.2 대 18.2/20.0, c=3 52.6/51.7 대 44.9/46.9) —
**팬아웃 HTTP 부하가 얹혀도 컨슈머 처리량은 영향받지 않는다.**

### 13-7. 12장 정정 — API 대가는 재현되지 않았다

배경 부하 k6 가 **회차당 9,000건**을 남겼다. 12장보다 표본이 2.5배이고 부하 시간이 150초다.

| | p90 | **p95** | p99 |
|---|---:|---:|---:|
| c=1 r1 | 143.5 | **180.8** | 336.4 |
| c=1 재확인 | 132.9 | **160.7** | 294.5 |
| c=3 r1 | 135.6 | **165.5** | 295.4 |
| c=3 r2 | 137.9 | **167.7** | 256.6 |

**c=3 값이 c=1 범위(160.7~180.8) 안에 들어간다.** 조건 안 편차가 조건 간 차이보다 크다 — 차이 없음이다.

12장은 c=1 179~233ms / c=3 350~384ms 로 명백한 차이를 봤다. 두 측정이 어긋난다.

| | 12장 | 13장 |
|---|---|---|
| 표본 | 3,600 | **9,000** |
| 부하 시간 | 60초 | **150초** |
| 재기동 후 워밍업 | 짧다 | 길다 |

**이쪽이 방법론적으로 낫다.** 12장의 60초 측정은 order 재기동 직후라 JIT·풀 확보 구간이
p95 를 밀어올렸을 가능성이 크다. 그래서 **12장 12-5 의 "API p95 ×1.77" 은 근거가 약하다.**
확정하려면 12장의 soak 비교를 150초 이상으로 다시 돌려야 한다.
지금 말할 수 있는 것은 **"대가가 있다면 이 측정으로는 안 잡힌다"** 까지다.

### 13-8. 회차 하나를 버렸다 — 그리고 그걸 잡은 것

`fc1-r2` 는 **시작 랙 5,686** 으로 출발했다. 정상 회차는 배경 부하 5초분인 141~325 다.
컨슈머 오프셋 리셋이 그 회차에서 안 먹었다 — `--reset-offsets` 는 그룹에 활성 멤버가 없어야 하는데,
`docker compose stop` 직후 브로커가 멤버를 아직 떨어내지 않은 경합이다.

그 회차는 랙이 11,819 까지 가 성공률 0% 가 됐다. **c=1 의 대표값이 아니라 버려야 할 회차다.**
평균에 넣었으면 c=1 성공률이 25% 로 잡혀 실제(50%)보다 나쁘게 나왔을 것이다.

이걸 잡은 것은 `run-session.sh` 가 `env.txt` 에 남기는 **시작 랙 한 줄**이다.
`RESET` 은 DB 만 비우므로 앞 회차가 남긴 미소비 메시지는 그대로 남는데, **DB 만 보면 깨끗해 보인다.**
9장이 "각 조건마다 동일한 초기 상태"를 규칙으로 세웠지만, 그 규칙을 **지켰는지 확인하는 수단**은
이번에 처음 생겼다.

### 13-9. 결론

`concurrency=3` 은 이 워크로드에서 **거의 순이익**이다.

| 사는 것 | 내는 것 |
|---|---|
| 지급 성공률 50% → **100%** | 측정 한계 안 (API p95 차이 없음) |
| 완료 건수 6배 | 풀 여유 그대로 (`pending` 0) |
| 랙 최종 5,748 → 353 | |

[perf-tuning.md](perf-tuning.md) 가 "올리지 않기로 했다"고 적은 결정은 **랙이 0인 평상시** 기준이었고,
그 판단은 13-2 가 뒷받침한다 — 한산할 때는 올려도 아무것도 안 변한다.
**밀리는 구간에서는 반대 방향이 맞다.** 그러면 남는 질문은 "올릴 것인가"가 아니라
**"언제 올릴 것인가"** 이고, 그 신호가 랙이다 — 이제 볼 수 있다(`ConsumerLagGrowing`).
