# Store 자동 동기화·복구 계획

2026-11-03 사용자는 일반적인 변경 반영과 시스템이 안전하게 처리할 수 있는 복구는 자동으로 이루어져야 하며, 불가피한 문제에만 사람이 개입해야 한다고 명시했다. 이에 따라 다음 작업을 관리자 수동 갱신 우선에서 **Store 자동 초기화 복구·자동 사본 대조** 우선으로 정렬한다. 동일 버전 교정 A를 선택하고 구현했다. 모듈 검사·실제 여정의 결과와 적용 범위는 아래에 기록한다.

## 변경 전 구현과 공백

| 상황 | 변경 전 구현 | 적용한 보완 |
| --- | --- | --- |
| Catalog 변경 | Outbox·Kafka 변경 이벤트를 Store가 소비하고 상품 잠금·버전 검사로 자동 반영 | 정상 갱신 경로 유지 |
| 짧은 소비 실패 | 공통 재시도 후 소진 시 DLT 보관 | DLT 정책을 유지하며 정본 대조로 안전한 사본 차이를 별도 복구 |
| 초기 동기화 실패 | 시작 시 한 번 실행하고 실패하면 준비 전 503을 유지. 원인 해결 후 재시작 필요 | 원인 해소 뒤 자동 재개하고 전체 초기화 완료 후 조회 준비 |
| 정상 운영 중 누락·구버전 | 주기적 대조 없음 | 보호된 Catalog 정본 조회로 자동 감지·보완 |
| 동일 버전의 내용 불일치 | `StoreProduct.apply`가 충돌로 거절. 시작 시 동기화를 반복해도 같은 충돌 | 선택한 A에 따라 직접 조회·검증한 정본으로 교정 |

변경 전 시작 전용 `CatalogSynchronizationRunner`를 주기 실행 스케줄러로 교체했다. 기존 `ApplyCatalogProduct`의 이벤트 반영과 `StoreProduct`의 충돌 검사는 유지하며 정본 교정 경로를 추가했다. Catalog의 `/internal/v1/store-products`는 숨김 상품도 포함한다. 공개 검색 결과의 부재나 공개 상세 404를 상품 삭제 근거로 사용하지 않는다.

## 확정한 방향

[결정 66](decisions.md#store-automatic-reconciliation-first)에 따라 정상 변경은 이벤트로 신속히 반영하고, 일시 장애·초기화 실패·안전하게 판별 가능한 사본 불일치는 자동 복구한다. 수동 재동기화 버튼과 관리 API를 먼저 만들어 자동 복구를 대신하지 않는다. 자동 처리의 진행·실패 근거와 사람이 개입할 예외를 관측할 수 있어야 한다.

이는 모든 DLT의 무조건 재투입, 어떤 사본 충돌이든 강제 덮어쓰기, 불완전한 초기 사본 공개, 다른 업무 모듈의 자동 재처리 정책 변경을 승인한 것이 아니다. 기존 License P3 등 별도 합의는 유지한다.

## 선택한 동일 버전 교정과 대안

예를 들어 Catalog와 Store의 catalogVersion은 둘 다 12지만 정본 가격은 1,000원, 사본 가격은 2,000원인 경우다. 기존 반영 함수는 충돌을 발생시키므로 별도 교정 경로가 필요했다.

| 대안 | 동작 | 개발·운영·고객 관점의 트레이드오프 |
| --- | --- | --- |
| A. 정본 검증 후 자동 교정 — 추천 | 직접 조회한 Catalog 정본의 응답·상품 식별자를 검증하고 같은 버전의 사본 내용도 교정 | 운영 개입과 잘못된 표시 지속을 줄인다. 교정 전후 근거·동시 갱신 보호가 필요하며 복구 경로가 추가된다 |
| B. 누락·구버전만 자동 보완 | 동일 버전 불일치는 기록·알림 후 운영자가 처리 | 기존 반영 규칙을 활용하기 쉽지만 안전하게 복구할 수 있는 내용 차이에도 운영 개입이 필요하다 |

A는 Kafka의 동일 버전 충돌 검사를 느슨하게 만드는 선택이 아니다. 직접 조회해 검증한 정본을 바탕으로 사본을 교정하는 경로를 구분한다. 교정 도중 더 최신 이벤트가 반영되면 이를 과거 상태로 되돌리지 않아야 한다. 상품 식별자 불일치·Store가 더 높은 버전인 경우·정본 자체의 모순은 이번 동일 버전 선택과 별도로 판단한다. 사용자는 차이를 설명받은 뒤 A 실행을 지시했다. [결정 67](decisions.md#store-canonical-same-version-repair)에 따라 구현·검증한다.

## 설계·검증 기준

1. 선택한 자동 교정 범위와 실패 분류를 기록한다.
2. 초기화 재개와 운영 중 대조의 작업 상태·중복 실행·재시도·재시작 복구를 설계한다. 기존 준비 상태와 대조 작업 상태를 분리한다. 초기화 전 503과 Catalog 일시 장애 중 이미 준비된 사본의 조회라는 기존 계약은 유지한다. 새로 확인된 모순 항목의 조회 처리는 별도로 정한다.
3. 변경 종류별 허용 지연과 대조 비용을 기준으로 재시도·대조 주기를 정한다. 주기와 무관한 일률적 즉시 반영을 보장하지 않는다.
4. 정상 Kafka 반영과 정본 대조의 경합·중복·역순, 숨김/판매 상태, 초기화 실패 후 무재시작 복구, Catalog 장애·회복, 안전하게 판별할 수 없는 응답의 처리를 검증한다.
5. 합의 뒤 로컬에서 편집하고 `ssh sng` OCI 격리 자원에서 TDD·관련 단위/통합·실제 여정을 실행한다. 기존 공유 자원·PG 상태·이전 검증 자료를 보존한다.


## 구현 범위

- `CatalogSynchronizationScheduler`를 config에서 조립해 시작 직후부터 실행한다. 초기화가 실패하면 자동 재시도하고, 한 차례 전체 대조가 성공한 뒤 공개 조회 준비 상태가 열린다. Catalog 장애 중 이미 준비된 사본의 조회는 유지한다.
- 정상 변경의 Kafka 반영은 `ApplyCatalogProduct`의 기존 동일 버전 충돌 검사와 상품 잠금을 유지한다. `ReconcileCatalogProduct`는 직접 Catalog port를 조회한 뒤 `CanonicalProduct`의 코드·필수 값과 상품 ID/코드/최초 공개일을 검증해 정본 교정을 수행한다. HTTP 호출 중 Store DB 트랜잭션을 유지하지 않는다.
- 누락은 INSERTED, 정상적인 구버전 보완은 UPDATED, 같은 catalogVersion의 내용 교정은 REPAIRED로 기록한다. 변경과 `store_reconciliation`의 전후 JSON·정본 조회 시각·기록 시각은 같은 트랜잭션으로 확정한다. 같은 상태의 반복 대조는 새 교정 이력을 만들지 않는다. V4는 감사 테이블을 추가하고 기존 사본을 보존한다.
- HTTP 응답이 늦어 그동안 더 높은 버전이 Kafka로 반영됐다면 행 잠금 뒤 확인한 최신 사본을 보존한다. 상품 식별 충돌, 새 catalogVersion에서 콘텐츠 버전의 역전·불변 콘텐츠의 모순은 자동 덮어쓰지 않는다. 사본 삭제·강제 버전 하향·DLT 원본 재투입은 수행하지 않는다.
- 정본 HTTP 경계는 필수 필드·정수 금액/버전·명시적 노출 값·코드 일치·페이지 메타데이터를 검증한다. 구 이벤트를 위한 공통 스냅샷의 기본값을 정본 HTTP 응답의 누락 필드에 적용하지 않는다. 네트워크/5xx/429는 일시 접근 실패로 분류하고 제공사 메시지·URL·키를 경고나 오류 분류에 복사하지 않는다.
- 전체 Catalog 접근 장애는 현재 대조를 중단하고 다음 재시도로 넘긴다. 개별 상품의 계약/식별 오류는 기록하면서 나머지 상품의 처리를 계속한다. 실패한 대조는 재시도하며 완전한 초기화 전에는 503을 유지한다.

### 실행 설정과 관측

| 설정 | 기본값 | 의미 |
| --- | --- | --- |
| STORE_SYNC_ENABLED | true | 자동 초기화·대조 실행 |
| STORE_SYNC_POLL_INTERVAL_MS | 1000 | 실행 기한 확인 간격 |
| STORE_SYNC_RETRY_DELAY | PT5S | 실패한 대조 종료 후 다음 재시도까지의 간격 |
| STORE_SYNC_RECONCILE_INTERVAL | PT1M | 성공한 전체 대조 종료 후 다음 정기 대조까지의 간격 |

기본 간격은 변경 가능한 구현 설정이다. Kafka 변경 전파가 정상 경로이며, 전체 대조의 소요 시간·장애·부하를 포함한 갱신 지연 SLA가 아니다. 여러 상품의 대조는 각각의 시점에서 수행되므로 전체 Catalog의 원자적 스냅샷 전환을 보장하지 않는다.

프로세스 내 겹친 대조는 하나로 합친다. 진행 위치·타이머·준비 상태는 메모리에 두고 재시작 시 전체 대조를 다시 수행한다. 교정 이력은 DB에 보존한다. 여러 인스턴스의 전역 단일 스캔·내구 커서/임대는 이번 범위가 아니며, 상품별 DB 잠금·삽입 경합 재시도·버전 검사로 변경을 보호한다. 규모가 커지면 측정에 따라 스캔 비용·범위·변경분 계약을 고도화한다.

Micrometer에 `stove.store.sync.ready`, `running`, `runs{result=success|failure}`, `last.success.timestamp`, `last.scanned`, `last.changed`, `last.failed`, `last.skipped.newer`를 등록하고 상품 코드·실패 유형의 경고를 남긴다. 지표 어댑터는 도메인 상태 공급자만 받고 서비스와 프레임워크 객체의 조립은 config에서 맡는다. 기존 관리 엔드포인트의 접근 정책은 유지하며 실제 경보 전송·대시보드/스크레이프 배포는 별도 운영 범위다.

## 검증 기록

최초 OCI 인수 테스트 6건 중 **5건이 예상대로 실패**했다. 같은 버전의 내용 교정·무재시작 복구·준비된 사본 유지·개별 실패 후 나머지 복구·요청 코드 대조의 부재를 확인했다. 최신 버전 보호는 기존에도 통과했다.

최종 `:apps:store:check :apps:store:bootJar :e2e:compileTestJava`는 **106.55초**, 단위/아키텍처 **70건**·통합/이행/OpenAPI **25건**, 합계 **95건 통과·실패/오류/건너뜀 0건**이다. V3→V4의 기존 행 보존과 빈 감사 이력, HTTP 필수 필드/금액/페이지·일시 장애 분류, 자동 재시도 기한·로컬 중복 실행, 늦은 HTTP 응답과 최신 이벤트, 감사 실패 시 실제 DB 변경의 롤백을 검증했다. OpenAPI 응답 변경은 없고 기존 스냅샷과 일치했다.

검증 중 지표 어댑터의 서비스 직접 참조와 포트 패키지의 예외 클래스 배치를 아키텍처 규칙에 맞췄다. 감사 실패 주입에 사용하려던 MySQL 트리거는 binary log의 SUPER 권한 제약으로 생성되지 않았다. 전역 DB 설정을 변경하지 않고 같은 트랜잭션의 변경을 flush한 뒤 감사 저장 실패를 주입해 롤백을 확인했다.

실제 9개 서비스의 `runtime-auto` 여정은 **485.92초·11단계 통과·실패/오류/건너뜀 0건**이다. Kafka 리스너를 끈 Store에서 사본 한 행을 삭제하고 다른 행의 가격·노출/제목을 변조했다. 자동 대조가 누락을 INSERTED로 복원하고 같은 **catalogVersion 16을 유지한 채 가격 1→2,500, listed=true→false**로 교정했으며 REPAIRED 전후 감사를 확인했다.

Catalog 장애 중 새로 시작한 Store는 503을 유지했다. Catalog 복구 후에는 **Store PID 2464933을 그대로 유지**하면서 자동 초기화·조회가 회복됐다. 이미 준비된 Store의 Catalog 장애 중 조회 유지, 기존 심사/출시·철회·판매/노출/다운로드 제어·영구 보유권·최신 ZIP·새 주문도 함께 통과했다. 실제 여정은 관측 시간을 줄이기 위해 정기 대조 2초·재시도 1초·기한 확인 100ms를 사용했고 운영 기본값과 구분한다.

입력 **1,545개**의 SHA-256과 최종 Store 게이트·실행 작업본이 일치한다. 게이트 이후 코드/테스트/실행 입력 변경은 0개다. 9개 bootJar에 테스트 클래스/라이브러리와 제거한 시작 전용 Runner가 포함되지 않았음을 확인했다. 변경 없는 다른 모듈의 전체 검사는 반복하지 않았다.

기존 **컨테이너 23개·볼륨 57개**의 ID·시작 시각·재시작 횟수·실행/건강 상태·포트·마운트를 보존했다. 전용 앱 프로세스와 네트워크는 모두 정리했다. 임시 키·발급 URL 파일은 수집에서 제외하고 실행 디렉터리에서도 정리했다. 외부 PG 호출은 **0건**이며 결제 결과는 기존 계약 픽스처다.

원자료는 Git 제외 `runs/store-auto-20261103/results/`, OCI `/tmp/esd-store-auto-20261103.unkipb4j`에 보존한다. `final-evidence-summary.json`, `final-check-xml/store`, `runtime-auto-evidence/checks`, `automatic-reconciliation.json`, `automatic-recovery.json`, 입력 해시와 실행 전후 자원 기록으로 재확인할 수 있다. 새 실제 PG 거래·공유 배포·G4 전체 완료로 확대하지 않는다.

2. 초기화 지연·대조 실패 지속·수집 중단을 구분해 경보와 복구 시 자동 해제를 검증한다. 이미 준비된 조회의 가용성과 정본 대조의 성공 여부를 구분하며, 마지막 대조 시각만으로 상품별 갱신 지연을 보장하지 않는다.
3. `ssh sng` 격리 환경에서 실제 수집·장애·회복과 기존 조회 유지를 확인하고 운영자가 볼 상태와 다음 행동을 기록한다.

경보 임계값·허용 지연은 다음 작업에서 필요한 정책으로 설명하고 선택한다. 이번 커밋으로 운영 수집/경보의 구현·공유 배포를 완료한 것으로 보지 않는다. 이어 전체 일반화의 G5 계정 복구·상태·운영 권한을 점검한다. Auth에는 현재 비밀번호를 확인하는 변경 API가 있으며 비밀번호 분실 복구는 별도 범위다.
