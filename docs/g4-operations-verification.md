# G4 출시·상점·보유자 운영 여정

2026-11-03 사용자의 “공백을 점검하며 실행한다” 지시에 따라 **9개 실제 서비스의 10단계 운영 여정을 모두 통과**했다. [단일 심사·명시적 철회 구현](project-review-withdrawal-verification.md) 이후의 연결 범위를 다룬다. G4 전체의 남은 공백은 마지막 절에 구분한다.

## 목적과 기존 공백

기존 검증은 출시·철회, Store 사본, 판매/노출/다운로드 제한, 구매자의 다운로드를 각각 확인했다. 그러나 철회한 업데이트가 현재 공개본에 영향을 주지 않는지, 이후 자동 공개가 기존 보유권과 제한 정책을 보존하는지, 숨김 사본이 HTTP 초기 동기화로 복구되는지를 하나의 최신 실행본으로 대조한 기록은 없었다.

선택지는 기존 독립 검증만 유지하는 방법과 여러 서비스를 연결하는 전용 여정을 추가하는 방법이다. 독립 검증은 빠르고 실패 원인을 좁히기 쉽지만, 서비스 간 설정·배포·사본 전파 문제를 놓칠 수 있다. 전용 여정은 프로세스 재시작과 인프라가 필요하고 느리지만, 고객과 운영자가 실제로 받는 상태를 확인할 수 있다. 이번에는 모듈 검증을 그대로 유지하면서 G4 경계에 필요한 전용 여정을 추가한다.

## 범위와 실행 방식

- 실제 서비스: Auth·Gateway·Studio·Review·Catalog·Store·Order·License·Download 9개.
- 결제: Order의 실제 `OrderPlaced`를 읽고 보호된 내부 승인 접수 API를 호출한 뒤 `OrderPaymentCompleted` 계약 픽스처를 전달한다. 이후 OrderPaid 발행·License 지급·Download 조회/ZIP 전송은 실제 서비스다. Payment 실행·외부 PG 승인/취소·환불 검증 결과로 확대하지 않는다.
- 환경: 사용자가 지정한 `ssh sng` OCI의 새 작업 디렉터리·Compose 프로젝트·DB·루프백 포트. 코드 편집은 로컬에서 수행한다. 기존 컨테이너·볼륨과 이전 검증 원자료를 보존한다.
- 저장소 권한: Review 읽기 계정, 체크인한 정책의 Download 읽기/태그 기반 거절 계정, Catalog 태그 전용 계정을 분리한다. 발급 URL의 만료 전 여부를 확인한 뒤 실제 GET 200/403을 대조한다.
- 재시작: Catalog 자동 공개 워커만 일시 정지하여 공개 전 철회를 재현한다. 실제 제품에 고정 대기시간을 추가하지 않는다. Store의 자체 격리 사본만 비운 뒤 Kafka 리스너를 끄고 HTTP 초기 동기화를 검증한다.

## 실행 행렬

| 단계 | 확인할 결과 |
| --- | --- |
| 1. 최초 공개·구매 근거 | Store 검색/상세와 Catalog 일치, 실제 Order 승인 접수→결과 픽스처→OrderPaid→영구 보유권→원본 ZIP. 미보유자/비로그인/위조 소유자 헤더 거절 |
| 2. 업데이트 철회·재요청 | 심사 철회 후 같은 자료 재심사, 출시 철회 후 같은 승인본 재요청. 자동 공개 대기 중 작업본을 바꿔도 현재 상점/다운로드 유지 |
| 3. 자동 공개 복구 | Catalog 재시작 후 살아 있는 요청만 공개. 상품 ID·최초 공개일·기존 보유권 유지, 다운로드만 새 공개 빌드로 변경 |
| 4. 판매·노출 제어 | 판매자 중지/관리자 제한/독립 숨김. 새 주문과 기존 주문 승인 접수의 차이, 확정된 승인 영수증 재전송, 운영 권한, 기존 보유자 접근 |
| 5. 다운로드 독립 제어 | 기존 버전의 만료 전 URL 차단. 제한 상태에서 새 버전 공개 후 제한 유지. 해제 뒤 최신 ZIP·이전 URL 복원, 판매/노출 정책과 보유권 보존 |
| 6. 사본 재구축 | 자체 Store 사본을 비우고 Kafka 없이 HTTP 동기화. 보이는 상품과 숨김 상품의 최신 행을 DB·API 양쪽으로 대조 |
| 7. Catalog 장애 | 이미 준비된 Store는 보이는 상품을 계속 조회하고 숨김을 유지. 새 URL은 503, 이미 발급된 URL과 보유권은 유지 |
| 8. 장애 중 Store 재시작 | 초기 동기화에 실패한 Store는 `STORE_NOT_READY` 503 |
| 9. 원인 복구 후 재시작 | Catalog 복구 후 HTTP 동기화로 두 노출 상태를 모두 복원 |
| 10. 노출 재개·새 주문 | Kafka 소비를 켜고 노출을 복원. 최신 승인본 가격/버전으로 새 주문, 기존 보유자의 최신 ZIP 접근, 미지급자의 다운로드 거절 |

## 재현

현재 소스가 있는 지정 OCI 격리 작업본에서만 실행한다.

```sh
CI=true STOVE_TEST_MINIO_IMAGE=stove/minio:review-withdrawal-20261103 \
  python3 tools/verification/verify-g4-operations.py
```

`G4_TEST_PORT_OFFSET` 기본값은 43000이다. 앱 포트와 Docker의 실제 공개 포트를 대조해 기존 자원과 충돌하면 실행 전 거절한다. 인프라 포트는 이를 제외하고 할당한다. `:e2e:g4OperationsE2eTest`는 각 단계에서 정확히 1건 실행·건너뜀 0건을 요구하며 기본 E2E와 분리한다. 키와 발급 URL을 담은 실행 파일은 전용 디렉터리에만 보관하고 요약에는 넣지 않는다.

## 실행 결과

최종 실행 `runtime-g4-final`은 **459.95초**, 단계별 JUnit XML의 합계는 **10건 통과·실패/오류/건너뜀 0건**이다. 위 행렬의 모든 단계가 각각 1건씩 실행됐다. 9개 bootJar와 실제 실행본을 대조하고 JAR 안에 테스트 클래스·테스트 라이브러리가 들어가지 않았음을 확인했다.

- 입력 **1,525개**의 SHA-256과 실행 작업본이 일치한다. 선행 단일 심사·철회 검증본과 달라진 입력은 `e2e/build.gradle`, 새 여정 클래스, 결제 계약 픽스처, 실행 스크립트의 **4개 파일**뿐이다. 업무 모듈 운영 코드의 추가 결함은 이번 여정에서 발견하지 않았다. 선행 모듈 검증 **695건**은 이전 기록으로 유지하며 이번 실행 수에 합산하지 않는다. 변경 없는 모듈의 전체 check는 반복하지 않았다.
- Store를 비운 뒤 HTTP로 재구축한 사본과 장애 복구 후 사본 모두, 보이는 대조 상품 1행과 숨긴 최신 빌드 `3`의 상품 1행이 존재했다. 공개 API에서는 숨긴 상품이 404이며 검색·목록의 총개수 계산에서도 빠졌다.
- 기존 **컨테이너 23개·볼륨 57개**를 보존했다. 컨테이너 ID·시작 시각·재시작 횟수·실행/건강 상태·포트·마운트를 실행 전후 대조했다. 두 실행에서 만든 네트워크와 검증용 앱 프로세스는 모두 정리했다. 이전 검증 디렉터리도 보존했다.
- 외부 PG 호출은 **0건**이다. 결제 결과 픽스처는 1건이며 실제 승인/환불 성공 근거가 아니다. 임시 키와 발급 URL을 담은 파일은 수집에서 제외하고 전용 실행 디렉터리에서도 정리했다.

원자료는 Git 제외 로컬 `runs/g4-operations-20261103/results/`, OCI `/tmp/esd-g4-operations-20261103.i_h5csm4`에 있다. `final-evidence-summary.json`, `runtime-g4-final-evidence/phases.json`, 단계별 JUnit XML, `rebuilt-projection.json`·`recovered-projection.json`, `resources-before.json`·`resources-after-final.json`으로 집계와 보존을 재확인할 수 있다. 초기 검증 오류 기록은 최종 통과 기록과 함께 보존했다. 공유 배포·G4 전체 완료를 선언하지 않는다.

## 점검 중 보완한 검증 공백

1. 결제 픽스처도 실제 `OrderPlaced`의 식별자·구매자·금액을 읽고 현재 보호된 승인 접수 계약을 통과시킨다. PG 앱을 추가하거나 Order의 과거 PENDING 결과 수용 경로로 우회하지 않는다.
2. 기존 구매권뿐 아니라 원주문의 상품·제목·버전·금액·생성 시각·원래 기한도 업데이트 전후 대조한다. 공개본의 현재 조건과 구매 당시 조건을 구분한다.
3. 빈 Store의 404만으로 숨김 복원을 판단하지 않는다. 보이는 대조 상품의 긍정 응답과 숨긴 최신 사본의 실제 DB 행을 함께 확인한다.
4. 과거 URL의 403 전에 만료까지 시간이 남았는지 확인한다. Download 계정의 파일 변경·태그 변경 거절과 Catalog 계정의 파일 읽기·변경 거절도 확인한다. 검증용 앱도 루프백 주소에 바인딩한다.
5. 첫 실행에서 새 검증의 잘못된 헤더 import와 타 창작자 자원의 기대값을 바로잡았다. `ReadCatalogListing.seller`는 기존 계약상 타 소유자의 자원을 `NOT_FOUND` 404로 숨긴다. 잘못된 역할은 403이다. 이 차이를 운영 코드 결함이나 새 정책 변경으로 처리하지 않았다.
