## 실제 역할·심사와 다운로드

준비 단계의 실제 Auth·Gateway ADMIN/두 MEMBER 로그인·PKCE S256·BFF 쿠키, 관리자 반려·고객 재심사와 네 단계의 ACTIVE·ZIP 유지 근거는 [준비 기록](g2-refund-role-journey-preparation.md)에 있다. 이번 실행은 그 세션·같은 환불·같은 2차 회차와 준비한 requestId를 사용했다. 별도 서명 JWT·직접 Bearer를 만들어 관리자 권한을 대신하지 않았다.

- 실행 직전 해당 PG의 미취소·TEST·원승인 구성을 재조회하고, 같은 미판정 2차 심사·ACTIVE·환불 실행 0건을 대조했다. 신규 결제 승인 작업자는 계속 꺼두고 전용 환불 실행·조회·동일 키 재시도 작업자만 활성화했다.
- 실제 ADMIN의 회차 지정 승인과 동일 명령의 반복 영수증을 확인했다. 최초 반려·재심사 이력과 최초 환불 접수 시각은 유지됐다. License 정지 요청·Payment 환불 실행·성공 취소는 각각 1건이다.
- 정지 뒤 본인의 신규 ticket은 403이다. 타인의 ticket도 403·라이브러리 상세 404, 비로그인 ticket은 401이다. 본인의 라이브러리는 항목을 삭제하지 않고 SUSPENDED로 제공한다.
- 정지 전에 발급한 같은 URL은 정지 뒤·만료 전에도 GET 200으로 원본 167바이트를 수신했다. SHA-256은 `90e86dc0bc5963256d673f378b11c8756c22282e6063511803889ffa29fc701c`로 원본과 같다.
- 해당 URL의 만료 시각은 22:53:50.337226219 KST다. 자연 만료 뒤 22:54:10 KST의 같은 URL은 MinIO HTTP 403·AccessDenied·`Request has expired`로 거절됐다. 업무/PG/스토리지 시각이나 기존 URL을 바꾸지 않았다. 서명 URL은 수집본에 포함하지 않았다.

원래 Order의 PG 승인 쌍은 P2 이전 이벤트의 미기록 값이므로 NULL을 유지한다. 대신 새 취소 이벤트가 Order 환불 사본에 승인 8,976/24와 확인 취소 9,000/24를 전달했고, 고객·관리자 조회가 이 사본을 사용한다. 원승인 이벤트·과거 Order 결과를 받은 것처럼 값을 채우지 않았다. 이는 P2의 과거 NULL 보존과 완료 상세 보완을 실제 거래에서 확인한 결과다.

## 관측 도구 보정

운영 코드·스키마·정책은 수정하지 않았다. 다음은 검증 도구의 오류와 수정이며 제품의 환불 실패로 집계하지 않는다.

1. 송신 준비 시각의 관측 SQL이 실제 컬럼 `first_cancel_prepared_at`과 다른 이름을 사용했다. 당시 PG는 이미 CANCELLED, 업무는 COMPLETED였다. 저장된 승인·중복 영수증을 사용해 GET/DB 관측만 재개했다.
2. MySQL CLI 기본 문자셋으로 한글 Outbox payload를 읽으며 디코딩이 실패했다. 관측 클라이언트에 `--default-character-set=utf8mb4`를 지정했다. 그 전에 저장한 정지 후·만료 전 ZIP 수신 근거도 보존했다.
3. 최종 집계가 준비 DB 요약에 없는 접수 시각 키를 참조했다. 준비 때 저장한 원래 고객 응답의 시각과 비교하도록 바로잡았다. 최종 성공 기록이 없어서 정리 도구는 변경 전에 멈췄고, 집계 통과 뒤 정상 정리했다.

이 과정에서 새 승인 명령·취소 키·후속 금융 시도를 만들거나 업무 자료/시각을 수정하지 않았다. 보정 뒤 최초 완료 시각·원구매·성공 취소 ID·금액·실행 본문·최초 준비와 PG 취소 한 건이 그대로임을 재대조했다. 도구 보정 기록은 원자료의 `observation-tool-corrections.json`에 있다.

**이후 재개 기준은 환불 후 자료가 있는 새 경로다.** 이전 `/tmp/esd-g2-journey-20261030.LeytgmUN`의 보존 원자료는 해시가 같은 **환불 전 구매 검증 스냅샷**이다. 외부 PG는 이번에 허가한 취소로 이미 변경됐으므로 그 과거 스냅샷을 현재 업무 상태처럼 다시 기동하지 않는다. 이번에 성공한 승인·취소 스크립트를 반복 실행하지 않는다.

## 남은 범위

이번에 완료한 것은 최신 실제 역할별 **수동 환불 한 건**이다. R3의 재현 가능한 공급자 실패/응답 유실과 실제 정지·복구·명시적 재시도, 최신 자동 환불 여정의 남은 검증을 별도로 구분한다. 추가 TEST 구매·취소는 이번 한 건의 허가를 확대해 자동 실행하지 않는다. 지급 누락 복구·환불 후 재구매·G3 정산 조정과 G2 전체 종료는 [전체 계획](platform-generalization-plan.md)을 따른다.
