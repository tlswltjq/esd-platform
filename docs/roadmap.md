# 로드맵 — 기능 일반화와 이후 고도화

**목표 (2026-10-29 사용자 결정):** MVP 상태의 전 기능을 일반적인 사용 수준으로 고도화한 뒤, 엣지 케이스·성능 관점으로 추가 고도화한다.
모듈별 남은 작업은 각 `.kiro/specs/<모듈>/tasks.md`, 단계별 검증 결과는 [근거 색인](evidence.md), 정책 선택은 [결정 기록](decisions.md)과 [판단 색인](judgment-index.md)을 따른다.
이 문서는 단계의 정의·순서·완료 조건만 다룬다. 진행 경위는 적지 않는다.

원문(2026-11-06까지의 날짜별 진행 기록 포함): [platform-generalization-plan.md](https://github.com/tlswltjq/esd-platform/blob/0cc225bf/docs/platform-generalization-plan.md)

## 1. 단계의 정의

| 단계 | 완료 기준 |
|---|---|
| MVP 완료 | 제한된 범위의 핵심 계약을 구현하고 검증을 통과함. 11개 모듈 모두 완료(2026-10-13~10-18) |
| 기능 일반화 | 역할별 정상 업무가 끝까지 이어지고, 일상적인 실패·취소·재진입·사후 처리를 지원함. 상태·근거·다음 행동을 조회하고 운영자가 정해진 절차로 처리할 수 있음 |
| 엣지 케이스·성능 고도화 | 일반화된 계약을 대상으로 희귀한 교차 경합·복합 장애·대규모 재구축·다중 인스턴스·부하·비용을 측정하고 개선 |

- 대상은 게임 스토어 **백엔드**다. 재현 가능한 API 여정과 운영 절차가 기본 완료 기준이며, 전용 화면·실제 은행 송금은 별도 범위다.
- 단일 상품 주문·KRW·단일 PG·전체 ZIP·수동 심사는 현재 제품 범위로 유지한다. 장바구니·다중 통화·부분 환불·쿠폰·델타 패치·DRM이 없다는 이유로 일반화 실패로 보지 않는다. **기능 수보다 선택한 기능의 전체 업무를 완성한다.**
- 중복 결제 방지·권한·금액 검증·업무 변경과 이벤트의 원자성·불확실한 금융 결과 보존은 매 단계의 필수 조건이며 나중으로 미루지 않는다.

## 2. 단계와 순서

각 단계는 최소 계획 → 필요한 정책 선택 → TDD·구현 → 관련 통합/여정 검증 → 기록 순서로 진행한다. 기간·완료율은 임의로 산정하지 않는다.

| 단계 | 범위 | 완료 조건 | 상태 (2026-11-07) |
|---|---|---|---|
| G1 | Payment·Order 일반 결제 생명주기 | 시도 실패/미확정·미접수와 주문 종료 구분, 결제창 이탈/재진입·안전한 종료. 성공·시도 실패·재진입·응답 유실을 Order 결과/다음 행동까지 검증 | 실제 TEST 여정 완료(10-29). 종료 판정은 그 기록과 흉내 서버를 넓힌 실제 스택 여정으로 한다([결정 119](decisions.md#g1-exit-verification)). 여정에 넣을 이탈/재진입 조합은 [결정 120](decisions.md#g1-reentry-scope)으로 정했다. 보류 건 재조회 간격은 [결정 122](decisions.md#approval-review-requery-interval), 고객 안내는 [결정 123](decisions.md#approval-review-customer-notice)으로 정했다. confirm 기한이 지난 접수 승인은 [결정 124](decisions.md#confirm-window-expired-hold)로 보류에 올린다. G1 정책 결정은 모두 정했고, 다음 구현이 남았다. 흉내 서버 확장·여정(31분 대기 야간 작업 포함), 접수 전 PAY_PENDING 만료 의심 재현, 재조회 간격·고객 안내·기한 지난 승인 보류 구현 |
| G2 | 구매·환불·보유권 전체 여정 (Auth·Gateway·Order·Payment·License·Download) | 최신 격리 스택·실제 역할별 인증으로 구매/지급/다운로드, 자동/수동 환불·반려, 확정 실패 뒤 복구/재시도. 지급 확인 누락 복구와 재구매 정책 | 재구매(P4) 결정 89~98 구현(보관함·등록)과 실제 스택 15단계 검증(PR #116, PG 환불 결과만 주입 — 결정 100). PG 취소 구간까지의 여정은 PortOne 흉내 서버로 확인(결정 111, 매일 밤 CI). 실제 PortOne 확인은 전용 테스트 가맹점 뒤로 미룸. Order 측 지급 확인 누락은 진입 시각 기준 감지·경보·안내로 정했다([결정 125](decisions.md#license-grant-wait-detection)). 그 구현과 환불 조사 이후 조치·종결 결정이 남음 |
| G3 | 현재 PG와 Settlement 연결·환불 조정 | 거래/비용·지급 자료 출처와 미확정 비용 모델, 원매출·환불 조정·판매자/플랫폼 순액·마감 전후 반영. 모의 수령과 실제 수령 구분 | 진행 중 |
| G4 | 창작·심사·공개·탐색 일반 운영 (Studio·Review·Catalog·Store) | 수정/업데이트·판매 중지/재개·요청 철회, 목록 사용성, 기본 분류/필터·사본 대조. 새 구매 허용과 기존 보유자 접근까지 검증 | 주요 정책 구현·검증 완료. 허용 지연 SLA·운영 경보/화면은 별도 |
| G5 | 계정·공통 운영 마무리 | 계정 복구/상태/운영 권한, 서비스 자격증명·접근 범위, 비밀 설정·웹훅, 대기/실패 지표·원본 재처리·백업/복구. 역할별 전체 여정의 최신 단일 기준 | 진행 중. 계정 변경 후 토큰·세션 정리, 역할 경계·서비스 소유권, 서비스 접근키, 지표 수집·운영 재처리·비밀 주입, 백업·복구 완료(PR #110~#114). 운영 API 구조(3절 열린 논의)·역할별 전체 여정의 단일 기준 남음 |
| G6 | 엣지 케이스·성능 고도화 | 아래 일반화 완료 판정 충족 후 | 대기 |

G1~G4에 필요한 계정·권한·지표·기본 복구는 해당 단계에 함께 구현한다. G5는 공통 운영을 전체적으로 닫는 단계이며 보안을 그때까지 유예한다는 뜻이 아니다.

## 3. 열린 논의 (구현 기대값으로 먼저 확정하지 않는다)

- **운영 API 구조 (G5):** 운영 전용 진입점, 업무 관리자/인프라 운영 권한, 감사 기록의 소유, 공통 라이브러리 HTTP 자동 등록 방식. 별도 Admin 모듈 신설은 합의하지 않았다.
- **할인·행사의 기한:** 주문 생성 마감/승인 진행 기한과 PG 혜택 조건의 관계. 판매 중지 시 기존 주문 기한 유지(결정 47)를 모든 혜택의 유효기간 연장으로 해석하지 않는다.
- **선물하기 (제품 확장 검토):** 보관함(결정 90·93)을 이용해 받는 사람을 바꾸는 흐름. 범위·환불·정산 연결은 미정이다.

## 4. G3 계약 원칙

- 거래·PG 비용·지급 자료는 확인 가능한 공급자 근거(API·파일)를 사용한다. 자료가 없으면 해당 대사를 미완료로 표시한다.
- 비용이 미확정이면 0원으로 만들거나 모의 비용으로 대체하지 않는다.
- 원매출·확정 마감을 덮어쓰지 않고 감사 가능한 조정으로 반영한다. 플랫폼 PG 비용 전액 부담 정책은 사용자 변경 전까지 유지한다.
- Settlement의 포트는 Settlement가 소유한다. Payment를 정산 조회 프록시나 실행자로 만들지 않는다.

## 5. 일반화 완료 판정

| 여정 | 결과까지 확인할 것 |
|---|---|
| 가입/로그인·계정 복구 | 본인 인증·역할, 복구/상태 변경 후 세션·토큰 정책과 감사 |
| 자료 생성→심사→출시→검색 | 불변 심사/출시 근거, 공개 정보·판매 가능 상태의 일관성, 수정과 재출시 |
| 구매 성공→지급→다운로드 | 실제 사용자 인증, 서버 결제 확인, Order·Payment·License·저장소 연결 |
| 결제 실패/이탈→재진입 또는 종료 | 실패와 미확정 구분, 동일 상품 구매 제한 해소/이어 결제, 늦은 승인과 중복 청구 방지 |
| 자동/수동 환불·반려 | ADMIN 경로·결정 이력·실제 정지 선행·PG 확인·고객 상태·신규 다운로드 제한 |
| 환불 확정 실패→복구→재시도 | License 복구 전 재시도 차단, 새 정지와 시도, 원래 자격/구매 보존 |
| 지급 확인 누락·처리 중단 | 원래 근거의 재전달/복구로 진행, 운영자가 대상·사유·다음 행동 확인 |
| 구매/환불→매출·월 마감 | 같은 공급자의 거래·비용 근거, 환불 조정·판매자 순액, 마감 뒤 조정, 미확정 자료 명시 |
| 업데이트·판매 중지/재개 | 신규 구매와 기존 보유자 다운로드가 각각 합의한 정책을 따름 |

공통 조건:
1. 필수 여정이 API·사용자/운영자 절차로 재현되고, 미완료 건의 주체와 다음 행동이 명확하다.
2. 관련 단위·통합·여정 검증이 통과하고 금전·보유권·정산의 중복/위조·근거 없는 전이가 없다.
3. 실행한 소스·설정·마이그레이션·공급자·역할·검증 범위를 기록한다. 코드만 최신인 상태를 최신 런타임 검증으로 보지 않는다.
4. 지원하지 않는 LIVE 결제/지급·전용 화면은 명시하고, 필수 일반 업무를 "후속"으로 남긴 채 완료 표시하지 않는다.
5. 남은 백로그가 새 제품 범위·희귀 예외·성능/규모 개선 중 무엇인지 구분돼 있다.

## 6. 이후 고도화

일반화가 끝나면 실제 사용 패턴과 목표 부하·허용 지연을 정하고 현재 버전의 지연·처리량·DB/PG 호출 수·대기열·복구 시간을 측정한다. 과거 [실험 기록](experiments.md)의 수치를 현재 시스템의 보장으로 쓰지 않는다.
이어 병목과 영향 순으로 다중 워커/임대·Kafka 소비/릴레이·쿼리/인덱스·검색·큰 파일 경로를 개선하고, 희귀 동시 금융 결과·장시간 외부 장애·DB 유실·재구축을 검증한다. 검색 엔진 교체·캐시·새 인프라는 측정이나 실제 요구가 있을 때 선택한다.
