# Studio 목록 페이지 계약

2026-11-03 [G4 운영 여정](g4-operations-verification.md) 이후의 첫 일반화 공백이다. 기존 API 직접 전환과 페이지 번호 방식을 선택해 구현했다. 최종 모듈 검사와 실제 여정 결과는 아래 검증 절에 기록한다.

## 변경 전 동작과 문제

| 목록 | 변경 전 조회 |
| --- | --- |
| `GET /api/v1/studio/projects` | JWT sub 소유 프로젝트를 ID 내림차순으로 전부 반환 |
| `GET /api/v1/studio/projects/{id}/builds` | 소유권 확인 후 해당 프로젝트의 빌드를 ID 내림차순으로 전부 반환 |
| `GET /api/v1/studio/projects/{id}/review-requests` | 소유권 확인 후 심사 요청 이력을 ID 내림차순으로 전부 반환 |
| `GET /api/v1/studio/projects/{id}/release-requests` | 소유권 확인 후 출시 요청 이력을 ID 내림차순으로 전부 반환 |

변경 전 `ReadProjects`와 각 Repository는 위 목록을 제한 없는 `List`로 조회했다. 프로젝트 응답은 상점 페이지 본문과 현재/진행 중 요청도 포함하며, 요청 조회를 프로젝트마다 추가 수행한다. 심사 요청에는 불변 스냅샷도 있다. 이력이 늘수록 행 개수뿐 아니라 응답 본문과 추가 조회 비용도 증가한다. 단순히 전체 목록을 읽고 Java에서 자르는 방법으로는 DB 조회량이 제한되지 않는다.

철회 영수증 목록은 이미 `page`·`size`로 DB 조회를 제한하지만 페이지 정보 없이 배열을 반환한다. 위 네 목록과 달리 무제한 조회로 분류하지 않는다. 이번 계약과의 응답 통일 범위는 별도로 점검한다. Review 심사 목록과 Catalog 작업 목록도 이미 조회량을 제한한다.

## 확정한 선택

**응답 전환 A — 기존 API를 페이지 응답으로 바로 전환한다.** 사용자는 기존 API 교체와 새 API 병행 운영의 개발·운영·호출부 영향을 비교한 뒤 A를 선택했다. [결정 64](decisions.md#studio-list-page-direct-transition)를 따른다.

기존 호출부와 테스트를 함께 수정한다. 기존 전체 배열을 반환하는 별도 호환 경로와 신규 페이지 경로를 병행하는 B는 선택하지 않았다. 이 결정만으로 페이지 번호/커서, 응답 필드, 정렬/필터, 기본·최대 크기를 확정하지 않는다.

## 페이지 방식 선택과 비교

| 방식 | 사용 예 | 이점 | 비용·주의점 |
| --- | --- | --- | --- |
| 페이지 번호 | 1페이지에서 5페이지로 이동 | 임의 페이지 이동·총개수 안내가 쉽고 현재 Review/Store 조회 방식과 익숙한 사용성을 공유 | 총개수를 제공하면 count 조회가 필요하다. 깊은 페이지는 앞부분을 건너뛰는 비용이 커지고 조회 사이 새 항목이 추가되면 위치가 달라질 수 있다 |
| 커서 | 마지막으로 받은 항목 다음부터 이어 받기 | 불변 정렬 키와 인덱스를 활용하면 깊은 목록을 이어 읽기 좋고 새 항목 추가에 따른 위치 변화가 적다 | 특정 페이지로 바로 이동하기 어렵다. 총개수는 별도 계산이 필요하고 커서·정렬/필터 조합의 검증을 관리해야 한다. 전체 탐색의 단일 시점 일관성을 자동 보장하지 않는다 |

2026-11-03 사용자는 **페이지 번호 방식 A**를 선택했다. [결정 65](decisions.md#studio-list-numbered-pages)를 따른다. 구현 기준은 page=0·size=20, 최대 100, ID 내림차순, `items/page/size/totalElements/totalPages`다. 기존 항목 정보를 유지하고 새 필터·임의 정렬은 추가하지 않는다. 범위 오류와 JPA 정수 offset 초과는 400으로 거절한다. 철회 영수증은 기존 제한 조회를 유지한다.

## 선택과 무관하게 필요한 구현·검증

- 소유자와 프로젝트 조건, 선택한 필터·정렬, 조회 한도를 DB 쿼리에 적용한다. 정렬 동률에는 유일한 키를 사용한다.
- 기존 단일 심사/출시와 작업본에 독립적인 진행 중 요청 조회를 보존한다. 페이지에 보이지 않는 요청도 진행 중 한도에 포함된다.
- 현재 단건 조회·명령 재전송·심사/출시·철회의 업무 계약은 목록 전환의 부수 효과로 바꾸지 않는다.
- 목록에서 필요한 필드와 상세에서 읽을 필드를 점검하고, 프로젝트별 추가 조회가 페이지 크기에 비례해 불필요하게 반복되지 않도록 구성한다. 응답 축약은 별도 계약으로 명시한다.
- 빈 목록·경계 입력·마지막 구간·소유권 격리·상태 변화·정렬 동률, 공개 OpenAPI와 현재 E2E 호출부를 확인한다. 전체 요청 이력을 가정하는 검증은 선택한 페이지 계약에 따라 탐색한다.
- 합의 뒤 로컬에서 편집하고 사용자가 지정한 `ssh sng` OCI 격리 자원에서 관련 TDD·통합/계약 검사와 필요한 여정을 실행한다. 이미 검증한 변경 없는 모듈 전체를 반복하지 않는다.


## 구현한 계약

네 GET 목록의 `ApiResponse.data`는 다음 구조다. `items`의 항목 정보는 기존 응답과 같다.

```json
{
  "items": [],
  "page": 0,
  "size": 20,
  "totalElements": 0,
  "totalPages": 0
}
```

- 기본 page=0·size=20, 최대 size=100, ID 내림차순이다. 음수 페이지, 범위 밖 크기·숫자가 아닌 인자, JPA가 표현할 수 없는 정수 offset은 400이다. 정상 범위의 마지막 이후 페이지는 빈 items와 실제 총건수를 반환한다.
- `StudioPage` 생성 시 값 범위를 검증하고 Repository의 `Pageable`로 DB에서 조회량을 제한한다. 소유자 조건과 프로젝트 조건을 count 조회에도 적용한다.
- 프로젝트 페이지는 연결된 현재 요청과 프로젝트 전체의 진행 중 요청을 심사/출시별로 각각 한 번에 읽는다. 작업본 버전과 현재 요청의 일치 여부는 기존 의미대로 판단하고, 진행 중 요청은 작업본 버전과 독립적으로 표시한다.
- 단건·명령·철회 영수증의 기존 계약은 유지한다. 새 필터·정렬·목록 항목 축약은 이 변경에 포함하지 않는다.
- `ReviewJourney.listItems`가 필요한 페이지를 순회하며 기존 E2E의 이력 조회를 새 계약에 맞췄다. G4 실제 여정에는 네 목록의 size=1 페이지 이동·총건수·권한/소유권 검사를 추가했다.

## 검증

변경 전 실제 HTTP/MySQL 인수 테스트 **10건이 예상대로 실패**했다. 전체 배열 응답과 무시되는 page/size가 원인이었으며 픽스처/기동 오류로 실패한 것이 아니다. 구현 후 같은 인수 테스트와 Studio 단위·아키텍처 검사, E2E 컴파일을 통과했다.

최종 `:apps:studio:check :apps:studio:bootJar :e2e:compileTestJava`는 **104.74초**, 단위·아키텍처 **75건**과 인프라 통합 **28건**의 **103건 통과·실패/오류/건너뜀 0건**이다. OpenAPI를 OCI에서 갱신한 뒤 최종 검사에서는 갱신 플래그 없이 일치를 확인했다.

새 인수 테스트는 소유 프로젝트 23개 중 기본 20개만 DB에서 실제 객체로 읽는지, 페이지별 중복 없는 ID 순서와 총건수, 네 목록의 경계·소유권, 다른 작업본 버전의 진행 중 요청을 확인한다. 연결 요청이 있는 프로젝트 5개 조회는 실제 Hibernate 통계로 **SQL 최대 4회**를 검증했다. 이는 대규모 부하 벤치마크 결과가 아니다.

실제 Auth·Gateway를 포함한 9개 서비스의 최종 G4 연결 여정도 **10단계 모두 통과**했다. 네 목록을 size=1로 넘기는 동작·총건수·ID 순서·잘못된 크기·미인증/잘못된 역할·타 소유자 경계를 실제 Gateway에서 확인했다. 출시/철회·현재 공개본·영구 보유권·판매/노출/다운로드 제한·Store 복구와 새 주문도 유지됐다. 최종 실행 `runtime-pagination-final`은 **463.15초**다.

입력 **1,529개**와 실행본의 해시를 대조했다. 선행 G4 검증본에서 달라진 입력 20개는 Studio·E2E와 G4 실행 도구뿐이다. 최종 Studio 게이트 이후 바뀐 실행 입력은 아래 기동 보완 도구 한 파일이며, 업무 코드·테스트·OpenAPI는 같은 입력으로 실제 여정을 통과했다. 다른 모듈의 변경 없는 전체 검사는 반복하지 않았다. 9개 bootJar에 테스트 클래스·라이브러리가 포함되지 않았음을 확인했다.

기존 컨테이너 **23개·볼륨 57개**의 ID·시작 시각·재시작 횟수·실행/건강 상태·포트·마운트를 보존했다. 검증용 앱 프로세스와 두 실행의 자체 네트워크는 모두 정리했다. 임시 키·발급 URL 원문은 증거 수집에서 제외하고 해당 파일도 정리했다. 외부 PG 호출은 **0건**이며 결제 결과는 기존 G4 계약 픽스처다.

원자료는 Git 제외 `runs/studio-pagination-20261103/results/`, OCI `/tmp/esd-studio-pagination-20261103.k8fanecf`에 보존한다. `final-evidence-summary.json`, `final-check-xml/studio`, `runtime-pagination-final-evidence/checks`, 입력 해시와 실행 전후 자원 JSON으로 재확인할 수 있다. 공유 배포·G4 전체 완료와 구분한다.

### 실제 기동에서 발견한 검증 도구 공백

첫 실행은 업무 검증 전 8개 JVM의 동시 기동 중 Studio DB 최초 접속 기한을 넘겨 종료됐다. 다른 서비스의 최초 접속도 짧은 기한에 근접했다. 실패 로그를 보존하고 실행 도구에서 애플리케이션 계정·DB의 TCP `SELECT 1`을 확인한 뒤 두 서비스씩 건강 상태를 확인하며 기동하도록 보완했다. 같은 업무 코드·JAR로 전체 여정을 통과했다. 업무 테스트 실패를 자동 재시도로 통과시키거나 애플리케이션 DB 시간 설정을 늘린 결과가 아니다. 이 기록은 다수 서비스 동시 배포의 기동 복원력 검증 완료를 뜻하지 않는다.

다음 G4 작업은 Store 사본 대조/재동기화의 기본 운영 계약과 최소 분류/필터의 범위다. Studio의 새 검색·상태 필터·목록 요약/상세 분리는 필요에 따른 별도 확장으로 남긴다.

커밋 준비에서 신규 테스트 5개 파일의 마지막 빈 줄만 제거했다. 검증본과의 차이가 파일 끝 개행 정리뿐임을 대조했으며 업무 코드·테스트 로직·실행 계약은 그대로다. 기록은 Git 제외 `runs/studio-pagination-20261103/commit-whitespace-check.json`에 보존했고 이 형식 정리만으로 전체 검증을 반복하지 않았다.
