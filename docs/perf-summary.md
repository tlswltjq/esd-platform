# 성능 측정 요약

> 이 문서는 **요약 레이어**다. 원본 측정 기록은 [performance.md](performance.md) ch5–14와 [perf-tuning.md](perf-tuning.md)에, 측정 방법론은 [measuring.md](measuring.md)에 있다.

## 한 줄

Outbox 릴레이와 Kafka 컨슈머의 처리량을 측정하고 튜닝했다. **이 문서가 주장하는 것은 처리량 수치가 아니라, 그 수치를 만든 비용 구조와 그것을 알아내는 데 쓴 측정 방법이다.**

## 측정 환경

| | |

> 아래 주장은 모두 (a) 동일 환경 내 비교이거나 (b) 환경에 독립적인 비용 모델이다.

## 주장 1 — 계측을 믿지 않고 시스템 밖에서 판정했고, 그 덕에 계측의 거짓말을 잡았다

**관측.** Spring Actuator의 `records_lag`가 **0**을 보고하는 동안, 브로커에는 실제로 **113,517건**이 미처리 상태로 쌓여 있었다. (결함 D-026)

**의미.** 앱이 내는 지표만 봤다면 "적체 없음"으로 판정하고 컨슈머 실험 전체가 조용히 무효가 됐을 것이다. 틀린 결론이 아니라 **틀린 줄도 모르는 결론**이 나왔을 상황이다.

**대응.** 판정 지표를 SUT(system under test) 밖에서 뽑는 원칙으로 전환. `collect-lag.sh`가 브로커의 committed offset과 log-end offset을 직접 질의한다. → measuring.md 규칙 3

**한계.** 이 불일치의 근본 원인(Micrometer 바인딩 시점 / 리밸런스 중 metric 리셋 등)은 아직 규명하지 않았다. 회피했을 뿐이다.

## 주장 2 — 내 가설을 내 데이터로 기각했다

**가설.** 컨슈머 처리량 정체의 원인은 HikariCP 커넥션 풀 고갈이다.

**설계.** `pool_active`(사용 중)만으로는 판정할 수 없다고 보고 `pool_pending`(커넥션을 기다리는 스레드 수)을 함께 수집했다. active에 여유가 있어도 pending이 뜨면 경합이고, pending이 0이면 경합이 아니다.

**결과.** 전 런에서 **pending = 0**, 최대 active 5/20. → **가설 기각.**

| 조건 | 사용자 성공률 | 최종 브로커 lag |
|---|---|---|
| `concurrency=1` | 10–50% | 5,741–5,756 |
| `concurrency=3` | 100% | 159–546 |

처리량 차이는 실재했으나(×2.41–2.55) **원인은 커넥션 풀이 아니었다. 현재 원인은 미규명 상태로 남겨두었다.**

**부수 소득.** 같은 실험에서 "c=3의 API p95 비용 ×1.77"이라는 이전 결론(ch12)도 뒤집혔다. 표본을 60초/소수에서 9,000건으로 늘리자 유의한 차이가 사라졌다 — ch12의 워밍업 오염이 유력하다. *(미해결 항목으로 아래 참조)*

**재현.** ch13을 ch14에서 독립 반복. 소비율 2% 이내 일치, 브로커 lag 재현성 1.1% 편차.

## 주장 3 — 배율이 아니라 비용 모델을 산출했다

릴레이 배치 처리 시간을 분해한 결과:

```
배치 처리 시간 ≈ 20ms (고정) + 0.48ms × 건수
```

**이 모델이 설명하는 것 세 가지:**

1. **이론 상한** — 약 2,080 events/s. 현재 최적 조합(batch 400 / mbpc 10)에서 1,315 events/s로 상한의 63%.

2. **환경별 배율 차이** — 동일한 `mbpc=1→10` 변경이 8GB 랩탑에서 **×3.08**, Ampere에서 **×5.25**. 이 변경은 *고정 비용*을 제거하므로 고정:변동 비율이 다른 호스트에서 배율이 달라진다. 모델의 예측과 일치한다.

3. **계측의 사각지대** — 타이머로 관측되던 구간(release 로직)은 전체 배치 시간의 **12–30%**에 불과했다. 나머지는 commit 단계 오버헤드로, 기존 instrumentation이 보지 못하던 영역이었다.

> **그래서 배율은 헤드라인이 아니다.** ×5.25는 Ampere에서만 참이다. 모델은 두 호스트 모두를 설명하고, 아직 측정하지 않은 호스트도 예측한다.

### 적용된 튜닝

| 항목 | before | after | 효과 | 상태 |
|---|---|---|---|---|
| `max-batches-per-cycle` | 1 | 10 | ×5.25 (Ampere 기준) | **적용** |
| `poll-interval-ms` | 1000ms | 200ms | e2e p95 1.30s → 0.56s<br>런간 편차 46% → 0.4% | **적용** |
| `listener-concurrency` | 1 | 3 | ×2.55 | 보류 (비상용 노브) |
| `batch-size` | 200 | 400 | ×1.35 | 후보 (락 점유 비용 미측정) |
| JDBC batching | 50 | 200 | **없음** | 기각 |

마지막 줄이 중요하다. **효과 없음도 결과로 기록한다.** actuator `/env`로 설정이 실제 적용된 것을 확인한 뒤 측정했고, 그럼에도 변화가 없었다. 가설 공간을 좁히는 음성 결과다.

`poll-interval` 항목의 **런간 편차 46% → 0.4%** 는 평균 개선만큼 중요하다. 폴링 주기가 길면 요청이 주기 경계 어디에 떨어지느냐에 따라 결과가 튀는데, 그 분산 자체가 사라졌다.

## 알고 있는 한계

**1. 릴레이 개선분의 상당 부분은 사용자에게 도달하지 않는다.**
릴레이 948.7 events/s vs 컨슈머 141.1 events/s — **6.7배 비대칭**. 시스템 처리량은 `min(릴레이, 컨슈머)`이므로 141/s를 넘는 릴레이 개선은 적체 위치를 outbox에서 Kafka로 옮길 뿐이다. **현재 binding constraint는 컨슈머 쪽이다.**
(컨슈머 141/s는 Order·License·Settlement의 24–26ms/건으로 설명된다 — 스레드당 약 40/s.)

**2. e2e 중앙값은 아직 측정 불가.**
측정 도구가 0.5초 주기로 상태를 폴링하므로 중앙값이 ~528ms에 고정된다. p95 개선(1.30s → 0.56s)은 유효하나 중앙값 개선은 관측되지 않았다 — 개선이 없어서가 아니라 **해상도가 부족해서**다.

**3. 릴레이가 API에 더하는 19ms의 내역이 미규명.**
60 RPS에서 릴레이 ON p95 42.6–43.1ms vs OFF 22.4–24.1ms. 커넥션 풀은 아니다(pending 0). 코드 경로별 분해는 미실시.

**4. ch12와 ch13·14의 결론이 충돌한다.**
c=3의 API p95 비용이 ch12에서는 ×1.77, ch13·14에서는 유의차 없음. 표본 수와 워밍업 오염이 유력하나 **아직 닫지 않았다.**

**5. 측정 호스트에 다른 워크로드가 상주한다.**
OCI 인스턴스는 별도 프로덕션 스택(일시 중지 상태)과 self-hosted CI 러너를 함께 갖고 있다. 런 시작 전 CI 중단과 load < 1.5를 확인하지만 이는 **사전 점검이지 연속 감시가 아니다.**

측정 기록에는 버린 런도 남아 있다. 폐기 사유:

- 호스트 메모리 스와핑 (150M pageouts) — ch7
- 대조군 부재로 비교 불가 — ch7

- offset 리셋 실패 (bash 변수 섀도잉) — ch14에서 발견, 이후 pre-flight 검증 추가

## 측정 규칙 (요약)

전문은 [measuring.md](measuring.md). 핵심만:

- **대조군이 다른 숫자를 내는 것을 먼저 확인**한 뒤 비교한다.
  예: 릴레이 OFF일 때 pending 5,398건 = 주문 수와 정확히 일치, ON일 때 0. 조건이 실제로 달랐다는 증거.
- 판정 지표는 SUT 밖에서 뽑는다.
- 부하 모델은 arrival-rate. VU 고정 모델은 응답이 빨라지면 유입도 같이 줄어 병목을 숨긴다. *(단 e2e 완료 시간 측정은 VU 모델이 적절)*
- 포화점 탐색(ramp)과 비교 측정(고정 부하)을 분리한다.
- 조건당 최소 2회. **조건 내 분산이 조건 간 차이보다 작아야** 비교가 성립한다.
- 설정이 실제로 적용됐는지 매 런 확인한다.
- 결과와 같은 폴더에 `env.txt`를 남긴다.
- 측정 중 호스트에 다른 워크로드를 두지 않는다.
