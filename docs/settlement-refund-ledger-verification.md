# G3 전액 환불 원장·월 합계 연결

2026-11-02. [원배분 전액 상계 A](decisions.md#settlement-full-refund-allocation)와 [최초 금융 확인 월·마감 시 현재 OPEN 월 A](decisions.md#settlement-refund-posting-month)를 실제 Settlement 접수·저장·조회에 연결한다. 앞선 [계산 정책 92건](settlement-refund-allocation-policy.md)과 [월 정책 102건](settlement-refund-month-policy.md)은 정책만 검증한 단계이며, 이번에는 환불 원장과 월 합계의 원자 저장을 검증한다.

## 처리와 책임

1. Payment의 기존 `RefundPaymentConfirmed`를 `settlement-confirmed-refund` 그룹에서 소비한다. `SettlementRefundMapper`가 봉투의 ID·종류·주문 키와 본문을 검증하고 `ConfirmedRefund` 내부 입력을 만든다. 늦은 `RefundExecutionSucceeded`는 최초 금융 확인을 보강하는 사건이므로 두 번째 금액 조정으로 소비하지 않는다.
2. `RecordConfirmedRefund`가 기존 원장 중복을 먼저 확인한다. 동일 근거는 PG 장애·월 마감 이후에도 최초 기록을 반환한다. 다른 본문·다른 환불로 원래 주문을 다시 상계할 수 없다.
3. 원매출과 정산이 보관한 PG 원승인에 주문·결제·구매자·금액·통화·거래를 대조한다. `core.port.PgRefunds`와 PortOne 읽기 어댑터로 같은 결제를 직접 GET하고 전액 취소·성공 취소 ID 전체·합계·기존 지급 구성을 확인한다. PG 조회 중 업무 트랜잭션을 유지하지 않는다. Payment HTTP·DB를 읽거나 환불 명령을 보내지 않는다.
4. 같은 트랜잭션에서 원매출·해당 월을 잠그고 배분 A와 월 정책 A를 적용한다. Inbox·환불 원장/취소 근거·월 환불 합계를 함께 저장한다. 금융 확인 월이 CLOSED이면 현재 OPEN 월을 잠그며, 월 경계가 바뀌거나 반영 가능한 월이 없으면 임의로 저장하지 않는다.
5. 월 마감은 매출 원장 합계와 환불 원장 합계를 각각 월 행과 비교한다. 원매출·기존 CLOSED 월·최초 closedAt은 보존한다. PG 비용 확정과 독립적으로 판매자 금액을 마감하는 기존 계약을 유지한다.

`SettlementRefund`에는 최초 금융 확인/접수 시각, 환불·시도·요청/원매출 식별자, 당시 판매자/상품 스냅샷, 원래 배분 정책·금액, 두 정책 ID, 금융 확인 월·실제 반영 월·선택 사유와 독립 조회한 취소별 근거를 불변 저장한다. 제공사가 취소 행의 시각을 보고하지 않으면 NULL을 보존하고 전체 취소 시각과 구분한다. 취소 근거의 공급자·ID는 전체 원장에서 한 번만 사용한다.

## 9,000원 예시와 조회

원매출 총액 9,000원·고객 실결제 8,976원·확인된 외부 혜택 24원이라면 원래 판매자 8,100원·플랫폼 900원을 그대로 상계한다. 현재 요율로 재계산하거나 혜택 24원만큼 판매자 몫을 줄이지 않는다.

| 상황 | 매출 합계 | 환불 합계 | 판매자 순배분 |
|---|---:|---:|---:|
| 같은 OPEN 월에서 판매·전액 환불 | 9,000 | 9,000 | 0 |
| 9월 판매 마감 뒤 10월 환불만 반영 | 10월 0 | 10월 9,000 | 10월 -8,100 |

기존 월 `paidAmount`·`platformFeeAmount`·`sellerPayoutAmount`·`recordCount`는 매출 총합 의미를 유지한다. 환불은 양수인 `refundAmount`·`refundedPlatformFeeAmount`·`refundedSellerPayoutAmount`·`refundCount`로 따로 제공하고, 각각을 차감한 `netPaidAmount`·`netPlatformFeeAmount`·`netSellerPayoutAmount`가 순액이다. 순액은 음수일 수 있다. 음수 표시는 자동 이월·계좌 회수·송금 실행을 뜻하지 않는다.

| 경로 | 권한·정보 |
|---|---|
| GET `/api/v1/settlements/me/refunds` | CREATOR JWT sub의 환불 조정 목록. 상품·음수 조정액·확인/접수 월과 사유. 구매자·PG 실행 정보 미노출 |
| GET `/api/v1/settlements/refunds` | ADMIN 판매자/반영 월 필터·페이지 목록과 정책/출처 요약 |
| GET `/api/v1/settlements/refunds/{refundId}` | ADMIN 최초 금융 입력과 직접 검증한 공급자/취소별 근거 상세 |

Gateway의 기존 CREATOR `/me/**`·ADMIN 정산 경로가 이 경로를 포함한다. Gateway 코드는 변경하지 않았다. 목록은 취소 컬렉션을 읽지 않고 상세만 함께 조회하여 페이지 조회의 컬렉션 fetch join을 피한다. Settlement 공개 명세는 12개 경로·13개 연산이다.

환불이 있는 월의 PG 비용 반환 출처는 아직 연결하지 않았다. 따라서 전체 `pgFeeAmount`·`platformNetAmount`는 NULL이고 `pendingPgCostCount`에 환불 건수를 포함한다. 원매출에서 확인된 비용 부분합 `confirmedPgFeeAmount`와 매출 비용 전체가 확인됐을 때의 `salePgFeeAmount`를 보존한다. 환불만 있는 월도 비용 반환 미확정이며 0원 확정으로 표시하지 않는다.

## 지연·실패와 복구

환불이 원매출보다 먼저 도착하면 Inbox·원장·월 합계에 아무것도 기록하지 않고 기존 Kafka 재시도/DLT 경로로 남긴다. 원매출을 먼저 복구한 뒤 원래 금융 확인 이벤트의 ID·본문·키·종류를 유지해 재처리한다. 최초 금융 확인 월은 보존하되 실제 접수 시 그 월이 CLOSED이면 합의한 현재 OPEN 월을 적용한다. 이 단위는 자동 의존성 대기 큐나 별도 환불 운영 HTTP를 추가하지 않는다.

원매출도 지연됐다면 PortOne의 완전한 `CANCELLED` 응답에서 원래 승인·지급 구성과 전액 성공 취소 합계를 함께 검증해 원매출을 접수할 수 있다. 이후 원래 금융 확인 이벤트로 환불을 기록한다. 부분 취소·진행 중 취소·불명확한 채널/거래/지급 구성은 완전한 전액 취소로 취급하지 않는다. SIMULATED 공급자의 환불 읽기 계약은 아직 없으므로 명시적으로 503이며 모의 취소 근거를 생성하지 않는다.

## 이행과 검증 범위

V10은 환불 헤더·취소 근거 테이블, 원매출 연결 FK/업무 유일 키와 월 환불 합계 4개 열을 추가한다. 기존 월은 환불 합계 0에서 시작하며 과거 원매출·거래/비용·명세·마감과 V1–V9 체크섬을 보존한다. 이행이 과거 환불 원장을 추정 생성하거나 다른 모듈 자료를 삭제하지 않는다.

코드·문서는 로컬에서 편집하고 실행은 `ssh sng`의 `/tmp/esd-g3-portone-20261031.uPXeH2Dl/refund-ledger-20261102/work`에서 수행했다. 앞선 월 정책 검증본을 서버 안에서 격리 복사하고 Settlement 변경 소스 34개(신규 19개 포함)와 해시 메타데이터만 동기화했다. 이전 검증본의 302개 소스 해시도 보존됐다.

1. 새 원장/월 반영 테스트를 먼저 전송해 타입이 없는 컴파일 Red를 확인했다. 실제 운영 거래의 손실을 재현한 Red는 아니다.
2. 서비스·이행·어댑터·조회 구현 뒤 단위/아키텍처·통합 컴파일 및 원장/중복/롤백 집중 검사를 통과했다.
3. PG HTTP·이행·순서 역전/Kafka 사례를 확장할 때 테스트 도우미가 `SendResult` 대신 `RecordMetadata`를 반환한 컴파일 오류를 수정했다. 이후 관련 검사는 통과했다. 업무 조건을 완화하거나 기대 금액을 바꿔 통과시키지 않았다.
4. 신규 API에 맞춘 OpenAPI 갱신을 별도 명령으로 수행·회수했다. 최종 게이트는 선택 필터나 명세 갱신 플래그 없이 실행했다.

```sh
CI=true ./gradlew :apps:settlement:check :apps:settlement:bootJar --console=plain
```

| 최종 검사 | 사례 | 결과 |
|---|---:|---|
| 단위·아키텍처 | 77 (아키텍처 39 포함) | 실패·오류·건너뜀 0 |
| 업무·HTTP·MySQL/Kafka 통합 | 41 | 실패·오류·건너뜀 0 |
| V5 이후·V8→V9→V10 이행 | 2 | 실패·오류·건너뜀 0 |

신규 6개 단위 검사는 Mapper·취소 전체 합계/ID·원매출 보존·환불만 있는 음수 순액·두 원장 마감 합계를 다룬다. 신규 통합 12개는 저장/공개 조회의 권한·정보 제한, 마감 뒤/지연 환불과 최초 월 보존, 중복 동시 접수·월 마감 경합, 취소 ID 재사용 차단, 실제 Inbox flush 후 예외의 전체 롤백, 독립 PG 읽기·지급 구성 대조·취소 후 원매출 지연 접수와 잘못된/불완전 취소 거절을 다룬다. Kafka 사례는 원매출 부재의 DLT를 관측하고 원매출 접수 뒤 동일 사건을 재처리하며, 중복 금융 확인·늦은 직접 성공 보강 사건까지 소비 오프셋이 전진한 뒤 원장/월 조정이 한 번임을 확인했다. 이행 2개는 기존 검사를 확장했으며 새 사례 수에 가산하지 않았다.

검증 원자료는 로컬 `runs/g3-refund-ledger-20261102/collected/`의 Red/집중/확장/명세 갱신/최종 로그, 최종 XML, 전송/전체 소스 명세, 전후 자원 스냅샷과 `verification-summary.json`이다. 최종 **321개 소스/Gradle 입력 해시**가 로컬·OCI에서 일치했다. JAR SHA-256은 `7c91d7881cc939fb52ac3935cd2a88993ec7dfc0bc27bdb47d505b07ee700023`이다.

Testcontainers 종료 뒤 기존 컨테이너 **23개**의 ID·실행/건강 상태·최초 시작 시각·재시작 수·마운트 및 볼륨 **57개**가 전후 동일했다. Spring HTTP 서버·실제 MySQL/Kafka·루프백 PG 계약 픽스처 검증이며, 별도 전체 플랫폼 앱 여정·실제 PortOne 조회나 금융 동작은 실행하지 않았다. 최종 검증 뒤에는 문서만 수정했다.

실제 PortOne 거래·기존 런타임 갱신, 은행 입금·판매자 송금/회수, PG 비용 반환과 지급 자료 출처, 음수 잔액의 자동 이월은 이번 범위에 포함하지 않는다. P4 재구매는 계속 후속 논의이며 G2·G3 전체 완료를 뜻하지 않는다.
