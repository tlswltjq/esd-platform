## 첫 단위 작업과 배경

첫 단위는 **매출·판매자 정산·PG 거래/비용/지급 대사의 책임 경계를 검토하고 현재 PortOne 연결 계약을 정하는 것**이다. 이어 전액 환불 조정과 마감 전후 반영을 한 쟁점씩 진행한다. 실제 은행 입금·판매자 송금이나 재구매 정책을 먼저 추가하지 않는다.

예를 들어 상품 9,000원의 결제 성공을 확인했지만 실제 PG 수수료 자료를 아직 확인하지 못한 경우다. 결제 성공·매출 발생 근거와 비용 확인 시점은 구분해야 한다. 미확인 비용을 0원 또는 기존 모의 PG 수수료로 채우면 플랫폼 순액을 잘못 확정할 수 있다. 이 예시는 정책 검토 상황이며 실제 제공사의 특정 계정에 항상 비용 조회 기능이 없다는 진단이 아니다.

## 분리 전 도메인의 결합

- `PgCost`가 공급자 거래 식별·시각과 PG 비용을 함께 소유하고 `PgPayment`가 비용을 필수로 요구한다. 현재는 거래가 확인돼도 비용 근거가 없으면 유효한 입력으로 표현할 수 없다.
- `SettlementSale`은 원매출·판매자/플랫폼 배분과 PG 비용·플랫폼 잔여액을 함께 소유한다. `SellerMonthlySettlement`도 판매자 금액과 플랫폼 부담 비용·잔여액을 함께 합산한다.
- 기존 정책은 PG 비용 전액 플랫폼 부담이다. 따라서 판매자 몫의 계산과 PG 비용 확정은 독립시킬 수 있지만 현재 모델이 이를 결합하고 있다.
- `PgReceiptItem`은 외부 명세를 매출에 포함된 `PgPayment/PgCost` 전체와 대조한다. 거래 연결과 비용 대사가 한 비교에 들어 있어 불일치 원인을 분리하기 어렵다.
- `SettlementTotals`는 결제액·배분·비용을 한 보존식으로 묶고 여러 금액에 비음수 조건을 둔다. 이 구조를 그대로 환불 조정까지 확대할지 재검토해야 한다. 원래 매출을 덮어쓰지 않는 조정 근거의 표현이 필요하다.

## 책임 분리 후보

다음은 사용자가 선택한 **하나의 Settlement 모듈 내부 책임 분리**다. 새 마이크로서비스·회계 ERP·복식부기 시스템 도입을 전제하지 않는다. 이번 구현은 원매출과 비용의 분리까지이며 표에 있는 환불 조정 자체는 아직 구현하지 않았다.

| 책임 | 소유할 사실 | 다른 책임과 연결 |
|---|---|---|
| 매출·배분 근거 | 원구매·검증한 승인·불변 판매자·플랫폼 정책·판매자/플랫폼 배분, 원매출을 참조하는 환불 조정 | 원래 주문/결제 키로 외부 거래·조정을 연결한다. PG 비용 확정을 원매출 접수의 필수 조건으로 묶지 않는 안이다. |
| 판매자 정산 | 판매자에게 배분한 매출과 조정의 기간별 합계·확정 근거 | 판매자 금액의 계산과 마감 조건을 소유한다. PG 비용은 기존 전액 플랫폼 부담 정책에 따라 별도 비용 책임이 소유한다. 계산 가능과 실제 지급 허용은 구분한다. |
| PG 거래·비용·지급 대사 | 공급자가 확인한 거래·비용과 지급 명세, 내부 원거래와의 연결·차이 | 거래 확인·비용 확인·명세 대사를 구분한다. 명세 일치와 실제 은행 수령도 구분하며, 이번 범위에 실제 은행 연동을 추가하지 않는다. |

조회 응답은 위 사실을 조합할 수 있다. 한 화면에서 보여준다는 이유로 모든 값을 한 엔티티·한 확정 시점에 다시 묶지 않는다. 기존 Order·Payment·Catalog의 완료 계약은 기준으로 유지하고, Settlement 공개 계약을 바꾸는 경우 관련 Gateway·명세·검증 도구를 함께 대조한다. 다른 모듈 DB를 직접 수정하는 방향으로 옮기지 않는다.

### 금액으로 보는 차이

기존 MVP의 설명용 플랫폼 수수료 10%·PG 비용 전액 플랫폼 부담을 적용한 **할인 없는 10,000원 예시**다. 실제 사업 요율·할인 정산 기준의 신규 합의가 아니다.

| 관측 시점 | 원매출 | 판매자 배분 | 플랫폼 몫 | PG 비용 | PG 비용 차감 후 플랫폼 잔여액 |
|---|---:|---:|---:|---:|---:|
| 승인·원구매·배분 근거 확인, PG 비용 미확인 | 10,000 | 9,000 | 1,000 | 미확정 | 미확정 |
| 이후 PG 비용 300원 확인 | 10,000 | 9,000 | 1,000 | 300 | 700 |

이 예시에서 PG 비용 확인은 판매자 배분 9,000원을 다시 정하는 사건이 아니다. 플랫폼 잔여액은 다른 비용·세금을 고려한 회계상 순이익이 아니다. 후속 선택 39에 따라 판매자 금액이 검증되면 PG 비용 미확정 상태에서도 지난 월을 마감하며 실제 송금 조건은 별도다.

## 공급자 자료 조사와 확인 수준

- [PortOne 결제 API](https://developers.portone.io/api/rest-v2/payment), [대사 API](https://developers.portone.io/api/rest-v2/reconciliation), [전체 API 분류](https://developers.portone.io/api/rest-v2)를 확인했다. 대사 API의 현재 공개 목록은 정산일/거래일 기준 부가세 보고서 두 종류이며, 파트너 정산 API도 별도 분류다. API 이름만 보고 거래별 실제 PG 수수료·플랫폼으로의 실제 입금과 같은 자료라고 간주하지 않는다.
- 기존 G2 실제 TEST 승인/취소 수집본은 금액 요약이며 PG 수수료 근거가 보존되어 있지 않다. 요약에 해당 필드가 없다는 사실만으로 전체 제공사 API의 기능 부재를 단정하지 않는다.
- 현재 TEST 채널/계정에서 거래별 비용과 PG 지급 자료를 어느 API·명세/보고서로 확보할지, 조회 권한·거래 연결 키·자료 확정 시점을 추가 확인해야 한다. 아직 없는 근거를 모의 PG 값·추정 수수료로 대신하지 않는다.
- 9,000원 총액, 8,976원 PG 실결제, 24원 할인은 기존에 구분한 금액이다. 할인 24원을 PG 수수료로 간주하지 않는다. 할인 부담과 판매자 정산 기준의 확장은 해당 쟁점에서 별도로 설명한다.

### 2026-10-31 추가 확인: 현재 토스페이의 혜택·TEST 정산

[토스페이 공식 FAQ](https://docs-pay.toss.im/faq-v2)는 승인 응답의 `discountedAmount`에 토스 포인트·즉시할인이 포함되며 이 혜택은 토스 부담이고 수수료는 결제 요청 금액을 기준으로 계산한다고 설명한다. [정산 상세 API](https://docs-pay.toss.im/reference/settlement/detail)의 `amount`도 실결제·토스 부담·포인트 사용 금액을 합한 수수료 부과 대상 금액이다. 따라서 고객의 실결제액 8,976원을 플랫폼 수령액이나 판매자 배분 기준으로 그대로 치환할 근거가 없다. 토스페이와 토스페이먼츠·토스쇼핑의 계약/문서를 혼용하지 않는다. [현재 PortOne 토스페이 연동](https://developers.portone.io/opi/ko/integration/pg/v2/tosspay-v2)과 기존 TOSSPAY_V2 관측을 기준으로 대조한다.

이는 현재 채널의 일반 계약에 대한 문서 근거다. 기존 TEST 거래에서 24원 할인과 취소의 `easyPayDiscountAmount=24`를 확인했지만 실제 지급이나 모든 할인/포인트 조합을 관측한 것은 아니다. 특히 토스페이 정산 상세 API는 **Test API Key의 결제는 실제 지급되지 않아 정산 대상이 아니며 빈 목록·0원 합계를 반환한다**고 명시한다. 이 빈 목록/합계를 거래 수수료 0원·플랫폼 수령 완료로 해석하지 않는다. PortOne 결제 조회의 TEST 검증과 실제 비용·지급 명세의 검증을 분리한다. 실제 LIVE 연결·자금 이동·새 금융 호출을 이번 조사로 승인한 것으로 해석하지 않는다.

## 첫 설계 선택 — 기존 통합 모델을 확장할지 책임을 분리할지

앞선 A/B는 비용이 없는 매출의 반영 시점을 중심으로 한 미결 제안이었다. 도메인 변경 가능성을 반영해 **책임 경계부터 먼저 선택**한다. 아래 두 안 모두 외부 거래·구매 근거를 대조하며 PG 비용을 임의로 확정하지 않는다.

| 선택 | 변경 방향 | 개발·운영·판매자 비용 |
|---|---|---|
| ① 기존 통합 모델 확장 | 매출·월 합계·PG 대사의 현재 결합을 유지하며 비용 미확정 상태를 추가한다. | 초기 변경을 좁힐 수 있다. 여러 계산·합계·마감·대사에서 미확정 분기가 필요하고 판매자 금액과 플랫폼 비용의 결합을 관리해야 한다. |
| ② 책임 분리 모델 — 추천 | 위 세 책임을 같은 Settlement 모듈 안에서 나누고 거래/조정 근거로 연결한다. 매출·판매자 배분과 PG 비용의 확정 시점을 나눠 표현한다. | 초기 모델·스키마·조회 계약 정비 범위가 크다. 운영자는 판매자 정산과 PG 대사의 상태·차이를 구분하고 후속 환불·늦은 비용도 해당 책임에서 다룰 수 있다. |

Codex는 **②**를 추천했다. 기존 PG 비용 전액 플랫폼 부담 정책에서는 판매자 배분과 PG 비용이 서로 다른 확정 근거를 가지며 후속 환불 조정·늦은 자료·명세 대사에서도 이 구분이 필요하기 때문이다. **사용자는 ② 진행을 선택했다.** 별도 선택 이유는 덧붙이지 않았으므로 위 추천 이유를 사용자 이유로 기록하지 않는다.

활동과 PG 지급의 구분은 외부 공급자의 보고 체계에서도 참고할 수 있다. [Stripe Balance 보고서](https://docs.stripe.com/reports/balance)는 활동과 잔액을, [Payout reconciliation](https://docs.stripe.com/reports/payout-reconciliation)은 지급 회차와 거래 집합의 대사를 설명한다. [Adyen 대사 안내](https://docs.adyen.com/reporting/settlement-reconciliation/)도 거래/비용과 배치/은행 명세 수준을 구분한다. 이를 PortOne의 현재 계정에서 같은 API·자료를 제공한다는 근거로 사용하지 않으며, 위 책임 분리는 이 프로젝트 정책에 맞춘 설계 제안이다.

## 선택한 판매자 월 마감과 다음 정책

판매자 금액은 PG 비용과 독립적으로 마감한다. 미확정 비용과 그에 의존하는 플랫폼 잔여액은 NULL·상태·미확인 건수로 표현한다. 늦은 비용은 별도 PG 기록에 저장하며 판매자 배분·월 합계·최초 closedAt은 그대로 유지한다. 지난 KST 월만 마감하고 마감 후 지연 매출은 현재 OPEN 월에 넣는 기존 계약을 유지한다.

외부 혜택의 배분 범위는 아래 A안을 선택했다. 총액 9,000원·PG 실결제 8,976원·할인 24원을 구분하고 공급자 계약·검증한 채널과 거래를 근거로 배분한다. 플랫폼 쿠폰·판매자 부담 프로모션의 규칙을 이 선택으로 정하지 않는다. 이어 비용 출처·환불 조정 등 남은 항목을 하나씩 설명하고 선택을 기다린다.

### 외부 PG 혜택이 판매자 배분에 미치는 범위 — A 선택

첫 대상은 현재 지원하는 TOSSPAY_V2의 외부 결제 혜택이다. 플랫폼 쿠폰·판매자 할인·공동 부담 프로모션의 정책을 함께 확정하지 않는다. 주문 금액은 주문에서 확정해 PG에 요청한 금액이며 상품 정가와 같다고 일반화하지 않는다. PG 비용 전액 플랫폼 부담과 비용에 독립적인 판매자 월 마감은 기존 선택을 유지한다.

설명용 플랫폼 수수료 10%에서 외부 부담 혜택을 판매자에게 차감하지 않으므로 주문 9,000원 → 플랫폼 몫 900원·판매자 8,100원이다. 고객 실결제 8,976원·외부 혜택 24원은 별도 지급 구성 근거로 보존한다. 수수료/실제 수령 자료가 없으면 해당 값은 계속 미확정이다. 사용자 선택에 따라 이 배분 계약을 구현·검증한다.

| 안 | 배분 기준과 미확인 혜택 처리 | 개발·운영·판매자/고객 비용 |
|---|---|---|
| A — 추천 | 공급자 계약과 검증된 채널·거래를 근거로 외부 부담이 확인된 혜택은 주문 금액 기준으로 배분한다. 부담이 불명확한 할인 거래는 배분 확정을 보류하고 근거를 확인한다. | 현재 토스페이를 명확히 연결하고 미지원 할인 규칙을 임의 계산하지 않는다. 새 할인 유형은 계약 확인이 필요하고 해당 거래의 판매자 금액 확정이 늦어질 수 있다. 지원한 외부 혜택의 사용 여부로 판매자 금액을 줄이지 않는다. |
| B | 외부 PG 혜택은 부담 근거 확인 여부와 무관하게 주문 금액 기준 판매자 배분을 보장하고, 사후 부족액은 플랫폼이 부담한다. | 배분 기준은 일관되고 판매자 지연이 적다. 플랫폼이 확인하지 못한 할인 차액까지 보장하는 추가 사업 정책과 별도 손익/차이 추적이 필요하다. |

두 안은 현재 토스 부담 혜택이 확인된 사례의 배분 결과가 같다. 쟁점은 **부담이 확인되지 않은 외부 할인까지 플랫폼이 보장할지**다. A의 계약 확인은 채널/혜택 유형의 근거를 관리한다는 뜻이며 매번 사람의 판정을 받는 절차를 전제하지 않는다. 근거 미확인 거래의 배분 확정과 PG 비용 미확정은 서로 다르다. 이미 검증된 판매자 금액의 마감을 PG 비용 때문에 보류하는 정책으로 되돌리지 않는다.

Codex는 A를 추천했다. 현재 지원 범위를 실제 공급자 계약에 맞춰 연결하고 확인하지 않은 차액 보장이나 일반 프로모션 엔진까지 확장하지 않기 때문이다. **사용자는 A를 선택했다.** 별도 선택 이유는 덧붙이지 않았으므로 추천 이유를 사용자 이유로 기록하지 않는다. Settlement 자신의 PortOne 읽기 어댑터, 총액·실결제·외부 혜택 근거 보존/대조와 주문 금액 배분을 연결한다. 실제 PG 비용/지급 자료와 환불 조정은 후속 단위다.

- 플랫폼 쿠폰·판매자/공동 부담 할인 확장. 이미 선택한 외부 부담 혜택 A와 구분하며 현 지원 범위의 완료를 막는 선행 조건으로 삼지 않는다.
- 비용 근거의 출처와 미확정 표시/후속 확정, 운영 확인 흐름. 추정값·0원으로 확정을 대신하지 않는다.
- PG 수령/실제 판매자 지급 조건. 이미 선택한 비용 독립 월 마감 조건은 다시 묻지 않는다.
- 환불 조정의 확정 출처, 플랫폼 수수료·PG 비용 반환/부담과 원매출 연결.
- 마감 전후·지연 도착의 조정 반영 월. 기존 매출/비용/명세·검증 자료의 보존과 필요한 스키마 이행 방법.

이 항목들을 경계 선택 하나로 모두 승인한 것으로 해석하지 않는다. P4 재구매와 운영 API 전체 구조 분리는 후속 논의로 유지한다.

## 전액 환불의 판매자·플랫폼 배분 — A 선택

현재 `OrderEventListener`는 OrderPaid만 반영하며 환불 조정 경로가 없다. 예를 들어 주문 총액 9,000원을 판매자 8,100원·플랫폼 중개 수수료 900원으로 배분한 뒤 고객 전액 환불이 완료되면 정산에도 별도 조정이 필요하다. 기존 원매출·배분 스냅샷은 보존한다. 여기서 논의하는 수수료는 플랫폼이 받는 중개 수수료이며 외부 PG에 내는 비용과 다르다. 기존 고객 환불 총액/혜택 계약은 유지한다.

| 안 | 전액 환불 조정 | 이 원매출·환불만 합친 결과와 비용 |
|---|---|---|
| A — 추천 | 판매자 -8,100원·플랫폼 중개 수수료 -900원으로 원배분 전액을 상계한다. | 판매자와 플랫폼의 원매출 배분이 각각 0이다. 원래 배분 스냅샷을 정확히 반전해 요율 변경·반올림 차이를 피한다. 반환되지 않은 실제 PG 비용이 있다면 기존처럼 플랫폼 부담으로 별도 반영한다. |
| B | 플랫폼 중개 수수료 900원을 유지하고 판매자에 -9,000원을 조정한다. | 이 거래의 판매자 배분 잔액은 -900원·플랫폼 중개 수수료는 900원이다. 환불에도 중개 수수료를 부과하는 별도 판매자 정책과 음수 배분/회수의 처리가 필요하다. |

두 안 모두 고객의 기존 전액 환불 결과는 유지한다. 차이는 환불로 취소된 매출의 플랫폼 중개 수수료를 판매자에게 남길지다. **2026-10-31 사용자는 A를 선택했다.** 별도 선택 이유는 밝히지 않았고 교체 가능한 정책의 인터페이스 적용 현황을 질문했다. [결정 41](decisions.md#settlement-full-refund-allocation)과 [계산 정책·현재 인터페이스 점검](settlement-refund-allocation-policy.md)을 따른다. 2026-11-02 소스 7개 전송 승인을 받아 계산 인터페이스·구현·테스트의 OCI 92건·check·bootJar를 통과했다. 원래 배분 A를 다시 묻지 않는다.

배분 A의 계산 정책은 OCI 검증까지 완료했다. 환불 완료 근거의 이벤트/외부 대조와 원매출 연결, 취소 후 지연 접수, 마감 전후 조정 월·음수 월 합계·실제 송금/회수 조건은 이어서 한 쟁점씩 구체화한다. PG 비용 반환은 제공사 근거 없이 0원으로 바꾸지 않으며 PG 비용 독립 판매자 마감과 확인된 외부 혜택 A는 다시 묻지 않는다.

## 2026-11-02 환불 조정의 반영 월 — A 선택

원배분 전액 상계 A의 계산 정책은 92건으로 검증했지만 환불 조정 원장·월 반영은 아직 연결하지 않았다. 이번 질문은 **금융 완료로 검증된 환불 조정을 어느 판매자 월에 반영할지**다. 고객의 전액 환불 자격/금액·원래 판매자/플랫폼 상계액·PG 비용 플랫폼 부담·비용 독립 월 마감은 기존 선택을 유지한다.

현행 매출은 OrderPaid 발생 시각의 KST 월을 우선하고, 그 월이 CLOSED이면 접수 시점 현재 OPEN 월에 반영한다. 마감은 원장과 월 합계를 대조해 최초 CLOSED/closedAt을 보존한다. 환불에는 아직 대응 경로가 없으며 현재 월 합계는 양수 매출만 표현한다.

예를 들어 9월 주문 총액 9,000원·판매자 8,100원·플랫폼 수수료 900원을 반영한 뒤 9월을 마감했고, 11월 2일에 전액 환불이 금융 완료로 확정됐다. 기존 결정 41의 조정액은 총액 -9,000원·판매자 -8,100원·플랫폼 -900원이다. 다음 두 안을 비교한다.

| 안 | 월 반영 규칙 | 개발·운영·판매자/고객 관점 |
|---|---|---|
| A — 추천 | 최초 금융 완료 확인 시각의 KST 월에 환불 조정을 반영한다. 그 월이 이미 CLOSED이면 접수 시점 현재 OPEN 월에 반영한다. 최초 반영 월은 중복/재처리로 바꾸지 않는다. | 사례에서는 9월 확정본을 유지하고 11월에 조정한다. 기존 지연 매출과 같은 마감 경계를 사용하고 판매자는 현재 명세에서 과거 주문의 환불 조정을 추적한다. 서로 다른 월의 매출·환불은 원매출 연결로 함께 조회해야 한다. |
| B | 원매출이 반영된 월에 환불 조정을 귀속시킨다. 이미 마감한 월이면 기존 마감본을 보존하면서 정정 회차·수정 명세를 추가한다. | 사례에서는 9월의 정정 명세가 생긴다. 원매출 월의 최신 순액으로 볼 수 있지만 마감 버전·변경 고지·확정본 간 차이 대사가 필요하다. 기존 마감 행/원매출을 덮어쓰는 안은 아니다. |

A의 경계 예시는 다음과 같다. 11월 판매·11월 환불이면 같은 월에서 상계한다. 10월 31일 최초 금융 완료가 확인됐지만 11월에 늦게 도착한 환불은 10월이 OPEN이면 10월, CLOSED이면 현재 OPEN 월인 11월에 반영하고 실제 확인 시각과 지연 반영 사유를 함께 보존한다. 뒤늦은 `RefundExecutionSucceeded` 보강 사건이나 운영 재처리 시각으로 최초 금융 확인 월·배분·반영 월을 다시 정하지 않는다.

이는 우리 판매자 정산의 반영 기준 제안이다. [토스페이 정산 명세](https://docs-pay.toss.im/reference/settlement/detail)는 지급일/거래 승인일 조회 기준과 결제·환불 거래를 따로 제공한다. 외부 명세의 날짜·실제 입금이나 세무 신고 기간을 위 판매자 월과 같은 사실로 간주하지 않는다.

두 안 모두 원구매·원매출·최초 마감 근거와 고객의 전액 환불을 보존한다. 월의 환불 조정이 -8,100원이라는 계산만으로 판매자 계좌에서 즉시 회수하지 않는다. 음수 월 잔액의 이월·상계/실제 지급·회수는 별도 정책이며 이번 질문에서 확정하지 않는다.

Codex는 A를 추천했다. 기존 매출의 지연 반영/마감 계약과 맞고, 과거 확정본을 보존하며 현재 명세에서 조정을 추적할 수 있기 때문이다. **사용자는 A를 선택했다.** 별도 선택 이유는 덧붙이지 않았으므로 추천 이유를 사용자 이유로 기록하지 않는다. [결정 42](decisions.md#settlement-refund-posting-month)에 따라 교체 가능한 월 선택 정책·검증된 입력/불변 결과·Spring 조립을 구현하고 최신 OCI 102건·check·bootJar를 통과했다. [결과 기록](settlement-refund-month-policy.md)을 따른다. 실제 환불 접수·원장·월 합계 쓰기는 다음 연결 단위다. 같은 월 반영 정책을 다시 묻지 않는다.

## 2026-11-02 전액 환불 원장 연결 완료

계산/월 정책의 후속으로 기존 `RefundPaymentConfirmed` 접수·원매출/독립 PG 취소 대조·불변 조정 원장·월 합계·판매자/관리자 조회를 연결했다. OPEN 확인 월 또는 마감 시 현재 OPEN 월에 저장하고 기존 매출 총합·마감본을 보존한다. 원매출보다 앞선 금융 확인의 DLT 원본 재처리와 완전 취소 뒤 지연 원매출 복구도 검증했다. 최신 OCI **120건**·check·bootJar 및 실제 PG/런타임 미적용 범위는 [원장 연결 기록](settlement-refund-ledger-verification.md)을 따른다.

이제 남은 G3 계약은 실제 PG 비용·환불 비용 반환·지급 자료 출처와 해당 대사다. 음수 잔액의 자동 이월·실제 지급/회수는 별도 미결 정책이며 같은 전액 환불 배분/월 선택을 다시 묻지 않는다. 아래는 첫 책임 분리/승인 읽기 단계의 구현 경계를 보존한 기록이다.

## 앞선 책임 분리·승인 읽기의 구현과 검증 경계

`SettlementSale`·`SellerMonthlySettlement`는 원매출·배분과 판매자 합계를, 새 `PgTransactionRecord`·`PgFeeRecord`는 승인 거래와 확인된 비용을 소유한다. `PgEvidence`는 비용 없이도 검증한 거래를 표현한다. ADMIN 조회는 이 사실을 조합하며, ADMIN의 거래 재조회는 외부 PG GET으로 확인한 근거만 추가한다. 기존 비용을 덮어쓰거나 판매자 마감을 변경하지 않는다. 명세 대사는 미도착 매출·비용 대기·거래 불일치·비용 불일치를 구분한다.

V8은 기존 매출에서 거래·확정 비용을 분리 복사하고 원래 비용 열을 `legacy_*`로 보존한다. 기존 명세의 불일치 값을 검증된 거래/비용의 정본으로 승격하지 않는다. 원매출·판매자 배분·월 마감·과거 마이그레이션 체크섬을 보존한다.

외부 계약은 Settlement `core.port`, HTTP 구현은 `adapter`, 설정/조립은 `config`에 유지한다. 첫 단위는 모의 PG HTTP 어댑터로 검증했고 후속 A 단위에서 PortOne TEST 원승인 읽기 어댑터를 조건부 조립했다. PortOne 비용·지급 자료와 환불 조정, 일반 할인 부담 정책은 후속 범위다. 새 읽기 연결의 검증은 루프백 HTTP·실제 DB이며 실제 제공사 사용자 여정과 구분한다.

합의 범위의 TDD → 관련 단위·아키텍처 → 실제 DB/Kafka·PG HTTP 계약 → 판매자/관리자 조회의 사실·미확정 표시를 검증한다. 코드·문서는 로컬에서 편집하고 빌드·테스트·서비스 실행은 `ssh sng`의 새 격리 환경에서 수행한다. 기존 P3 원자료·공유 자원을 보존하며 실제 새 PG 금융 동작·은행 입금·판매자 송금은 별도 범위다.
