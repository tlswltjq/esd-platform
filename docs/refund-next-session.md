# 전액 환불 — 다음 세션의 공통 지시와 작업

2026-10-28. 사용자가 이번 세션 종료 후 공통 지시사항과 다음 작업을 명시하도록 요청해 작성했다. 현재 구현·검증 상태는 [인계 요약](refund-session-handoff.md), 단계별 근거는 [PG·환불 검증 기록](pg-test-integration-plan.md)에서 확인한다. Git의 현재 상태와 원자료를 우선 대조하고 이 문서의 작성 시점을 최신 실행 결과로 오해하지 않는다.

## 먼저 읽고 확인할 것

1. 저장소 루트 [AGENTS.md](../AGENTS.md)를 읽는다. 완료된 열한 모듈의 계약, core.port/adapter/config 경계, 외부 이벤트 Mapper, 서비스의 Inbox·잠금·업무·Outbox 조율, 내부 입력 검증, 명시적 Java 타입·import 규칙을 따른다.
2. [현재 인계](refund-session-handoff.md)와 `git status`, `git log`, 원격 브랜치 상태를 대조한다. 사용자 변경을 되돌리지 않는다.
3. 해당 쟁점의 [결정](decisions.md#full-refund-policy), [테스트 계획](testing.md#order-full-refund-tdd), [미결 질문](domain/open-questions.md#q9)을 읽는다. 과거 “후속” 기록은 작성 당시의 상태이며 현재 정책을 덮어쓰지 않는다.
4. 검증 원자료는 Git 제외 `runs/`에 있다. 폴더명에 `current`가 붙은 파일은 경로를 적은 일반 파일일 수 있다. 새 checkout에 원자료가 없다면 검증 기록과 원자료 부재를 구분하고 성공을 추정하지 않는다.

## 사용자와 진행하는 방식

- 사용자는 전액 환불을 직접 설계하며 배우려 한다. 한 번에 핵심 쟁점 하나를 다룬다. 배경, 쉬운 구체적 사례, 선택지, 개발·운영·고객 비용, Codex의 추천과 이유를 설명한다.
- 정상 흐름부터 설명하고 결제/환불/이용권 상태가 어디에 저장되는지, 누가 어떤 요청을 보내는지를 연결한다. 결제 성공 화면, 서버 조회, 웹훅, DB 저장, 환불 접수, 실제 정지, 실제 취소, 실제 복구를 구분한다.
- 사용자가 선택과 이유를 말할 시간을 준다. 선택의 반례와 놓친 비용을 검토한다. 미결 정책을 테스트 기대값이나 구현으로 먼저 확정하지 않는다.
- `다음`, `Continue`는 작업·논의를 이어가라는 뜻이다. 특정 미결 정책의 A/B 선택으로 해석하지 않는다. 이미 선택한 정책과 허가받은 실행을 다시 묻지 않는다.
- 합의 뒤 TDD의 실제 Red → Green → 필요한 회귀/인프라 검증 → 결과 기록은 Codex가 수행한다. 검사 실패의 원인·수정과 실제 실행 범위를 남긴다. 전체 환불 완료나 실제 PG 검증을 부분 테스트 결과로 대신 주장하지 않는다.
- 코드를 짧게 바꾸는 것뿐 아니라 모듈 간 결과 전달·동시 요청·재전송·롤백과 사용자에게 보이는 상태를 확인한다. 변경과 무관한 검사를 이유 없이 반복하지 않는다.

## 실행 환경과 보존할 자료

- 사용자가 승인한 인프라 검증은 **`ssh sng` OCI의 격리 환경**이다. 별도 DB·포트·컨테이너를 사용하고 기존 자료를 보존한다. 로컬 코드 편집·빌드·서비스 실행과 OCI 인프라 검증의 범위를 기록한다.
- 마지막 공유 기준은 컨테이너 23개·볼륨 57개다. 실행 전 실제 목록을 다시 읽고 ID·시작 시각·재시작 횟수·상태와 볼륨을 비교한다. 전체 prune, 공유 compose down, 임의 DB 초기화는 하지 않는다.
- `.env.portone-test`와 `runs/**/private.json`은 Git 제외·권한 600인 비밀 설정이다. 실제 API Secret·웹훅 Secret·비밀번호·Bearer를 출력하거나 커밋·문서·OCI 소스 묶음에 넣지 않는다. 저장된 자격 증명을 다시 요청하지 않는다.
- 외부 PG는 PortOne V2의 `tosspay_v2` **TEST** 채널이다. 모의 PG 환불 계약을 추가 구현하는 방향으로 되돌아가지 않는다. 실제 PG 테스트에도 서버 재조회·금액/주문 대조가 필요하다.
- 기존 실제 환불 완료 거래의 결제/환불 스크립트를 다시 실행하지 않는다. 별도 오래된 9,000원 PAID는 보호하며 자격 시각을 바꾸거나 임의 환불하지 않는다. 새 금융 동작은 해당 작업에서 합의한 범위를 확인한다.
- 공개 HTTPS 웹훅은 OCI IP와 로컬 Payment를 SSH로 연결한 검증 환경이다. 로컬 앱·터널이 필요하며 상시 운영 배포로 설명하지 않는다.
- 이 문서 작성 시 사용자는 누적 완료 작업·문서 정리의 커밋과 푸시를 요청했다. 다음 세션에서는 실제 Git 결과를 확인한다. 새로운 미결 정책까지 포괄 승인한 것으로 해석하지 않는다.

## 이번 세션 완료: 고객의 명시적 재시도 HTTP 계약 연결

2026-10-28 사용자는 이전 실패 시도 ID를 명시하는 첫 번째 안의 실행을 선택했다. `POST /api/v1/orders/{orderNo}/refund/retries`가 `previousAttemptId`를 받아 기존 `RequestRefundRetry`에 연결된다. 고객 환불 조회의 `retryableAttemptId`는 확정 실패·실제 복구가 끝난 현재 시도에만 제공한다. 최초 접수와 동일 요청의 반복은 HTTP 202와 같은 refundId·previousAttemptId·재시도 receivedAt을 반환한다. Location은 기존 환불 조회이며 응답은 no-store다. 후속 정지·PG 완료를 접수 응답으로 판단하지 않는다.

로컬 Order 308·Gateway 100건, OCI Order 308·통합 124건 및 Gateway 100·Redis 통합 1건을 통과했다. 초기 Gateway CSRF 기대값과 OCI 중복 구매 픽스처 오류를 보정했으며 최종 OCI는 명세 갱신 플래그 없이 전체 재실행했다. [상세 기록](pg-test-integration-plan.md#2026-10-28-고객-명시적-재시도-http-첫-번째-안)을 따른다. 기존 실제 검증 런타임은 갱신하지 않았고 추가 PG 환불도 실행하지 않았다.

이미 합의한 조건은 다시 열지 않는다.

- 이전 실행의 검증된 FAILED와 실제 License ACTIVE/복구 완료가 모두 필요하다.
- 고객의 명시적 요청만 새 attemptId를 만든다. 같은 명시적 재시도의 반복은 한 후속 시도로 수렴한다.
- refundId·첫 접수 시각·원래 자동 환불 자격·이전 실패 이력을 보존한다. 새 시도는 다시 실제 정지를 거친다.
- 결과 미확정, 관리자 반려 REJECTED, 운영 중단 403/INVALID_REQUEST는 이 재시도 대상이 아니다. 기존 요청의 결과 조회/같은 키 재전송과 구분한다.
- MEMBER sub/소유권·동시 중복·타인/없는 주문·실제 복구 전 거절·Outbox 롤백·Gateway 경로·명세를 검증한다. 실제 추가 환불은 독립적으로 선택한 테스트 사례에서만 수행한다.

## 추천하는 다음 작업: Payment 운영 중단 재개 HTTP 계약

Payment 내부 `RequestRefundCancellationResume`를 관리자 HTTP로 연결하는 계약을 한 쟁점씩 논의한다. 확정 실패 뒤 고객이 새 시도를 만드는 위 API와 달리, 운영 중단 재개는 원래 PG 키·본문·최초 준비 시각·3시간 창을 유지한다. 먼저 기존 중단/재개 입력·영수증과 권한·감사 기록·응답 유실/동일 지시 재전송 의미를 설명하고 사용자 선택 뒤 구현한다. 이 추천을 새로운 운영 정책이나 실제 금융 동작의 승인으로 해석하지 않는다.
