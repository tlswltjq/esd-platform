## 이번 세션 완료: 고객의 명시적 재시도 HTTP 계약 연결

2026-10-28 사용자는 이전 실패 시도 ID를 명시하는 첫 번째 안의 실행을 선택했다. `POST /api/v1/orders/{orderNo}/refund/retries`가 `previousAttemptId`를 받아 기존 `RequestRefundRetry`에 연결된다. 고객 환불 조회의 `retryableAttemptId`는 확정 실패·실제 복구가 끝난 현재 시도에만 제공한다. 최초 접수와 동일 요청의 반복은 HTTP 202와 같은 refundId·previousAttemptId·재시도 receivedAt을 반환한다. Location은 기존 환불 조회이며 응답은 no-store다. 후속 정지·PG 완료를 접수 응답으로 판단하지 않는다.

로컬 Order 308·Gateway 100건, OCI Order 308·통합 124건 및 Gateway 100·Redis 통합 1건을 통과했다. 초기 Gateway CSRF 기대값과 OCI 중복 구매 픽스처 오류를 보정했으며 최종 OCI는 명세 갱신 플래그 없이 전체 재실행했다. [상세 기록](pg-test-integration-plan.md#2026-10-28-고객-명시적-재시도-http-첫-번째-안)을 따른다. 기존 실제 검증 런타임은 갱신하지 않았고 추가 PG 환불도 실행하지 않았다.

이미 합의한 조건은 다시 열지 않는다.

- 이전 실행의 검증된 FAILED와 실제 License ACTIVE/복구 완료가 모두 필요하다.
- 고객의 명시적 요청만 새 attemptId를 만든다. 같은 명시적 재시도의 반복은 한 후속 시도로 수렴한다.
- refundId·첫 접수 시각·원래 자동 환불 자격·이전 실패 이력을 보존한다. 새 시도는 다시 실제 정지를 거친다.
- 결과 미확정, 관리자 반려 REJECTED, 운영 중단 403/INVALID_REQUEST는 이 재시도 대상이 아니다. 기존 요청의 결과 조회/같은 키 재전송과 구분한다.
- MEMBER sub/소유권·동시 중복·타인/없는 주문·실제 복구 전 거절·Outbox 롤백·Gateway 경로·명세를 검증한다. 실제 추가 환불은 독립적으로 선택한 테스트 사례에서만 수행한다.

## 2026-10-29 완료: 잘못된 승인 중단과 새 심사 복귀

사용자는 **A안: Order가 Payment 실행 요청을 저장하기 전까지만 관리자 중단 허용**, **B안: 중단·필요한 실제 이용권 복구 뒤 같은 환불의 새 심사 회차로 복귀**를 선택했다. 이 두 선택을 다시 묻지 않는다. 과거 승인/중단과 최초 접수·자격·원구매를 보존하며 고객에게 재신청을 요구하지 않는다. 관리자 정정은 고객 재심사의 요청 주체/7일 신청 기한을 적용하는 고객 신청이 아니다.

합의한 계약을 구현·검증했다. ADMIN POST `/api/v1/admin/refunds/{refundId}/approval-stops`는 requestId·현재 승인 reviewId·필수 사유와 JWT sub를 저장하고 202 최초 영수증을 반환한다. 중단과 정지 완료는 같은 주문 잠금으로 순서를 결정한다. 실행 요청이 먼저 저장됐다면 실제 PG 송신 전이어도 거절한다. 중단이 먼저 저장됐다면 늦은 정지 완료를 PG 요청 대신 승인 정정 복구로 연결하고, 실제 복구 완료 전 새 판정을 받지 않는다. 정지 요청 전에는 바로 새 심사로 복귀한다. 새 회차 판정은 기존 후속 판정 API를 사용하며 과거 명령 재전송은 이후 회차를 바꾸지 않는다.

Order V22·License V9, 관리자 감사/고객 정보 제한, 중복/동시성·실제 flush 롤백·각 모듈 DB/Kafka·명세를 검증했다. 최종 OCI 전체 967건 및 기존 23개 컨테이너·57개 볼륨 보존 결과와 실제 런타임/PG 미적용 범위는 [승인 중단 검증 기록](pg-test-integration-plan.md#2026-10-29-잘못된-승인-중단과-새-심사-복귀)을 따른다. 실제 ADMIN 계정/운영 화면/두 실제 서비스의 전체 사용자 검증은 후속이다.

## 2026-10-29 완료: 장기 미확정 고객 안내와 준비 이벤트

사용자는 **A안: 고객 조회에 결과 확인 지연 안내 추가**, **A안: Payment의 진행 근거를 이벤트로 Order가 보관**을 선택했고 구현·검증했다. 이 두 선택은 다시 묻지 않는다. 기존 PROCESSING과 최초 자격·금융/이용권 정책을 유지하고 고객에게 별도 재신청이 필요하지 않음을 안내한다. 고객 조회 때 Payment HTTP를 호출하지 않는다.

Payment는 실제 최초 준비 시각과 원래 3시간 경계를 RefundExecutionPrepared로 준비 트랜잭션의 Outbox에 한 번만 저장한다. Order는 봉투/본문/키·구매/실행/정지를 검증한 근거와 Inbox를 원자 저장한다. 준비는 실제 송신/성공 근거가 아니다. 현재 환불·시도가 미확정인 경우에만 경계부터 processingNotice(code/message/since)를 표시하고 완료·실패/복구·새 시도에서는 오래된 안내가 나오지 않는다. 준비 정보가 없으면 접수/실행 요청 시각으로 추정하지 않고 안내를 null로 둔다.

Order V23·Payment V26와 기존 준비 사실 backfill·기존 12개 경로/14개 연산·기존 응답 필드 보존을 검증했다. 최종 OCI 전체 1193건 및 공유 23개 컨테이너·57개 볼륨 보존의 범위는 [지연 안내 검증 기록](pg-test-integration-plan.md#2026-10-29-장기-미확정-고객-안내와-준비-이벤트)을 따른다. 실제 런타임/금융 동작·고객 화면·실제 PG 장애 전체 검증은 추가하지 않았다.

## 2026-10-29 완료: 장기 미확정 운영 조회와 조사 기록

사용자는 **A안: 목록·상세 조회와 조사 기록 API**를 선택했고 구현·검증했다. 이 선택은 다시 묻지 않는다. Payment의 ADMIN `/api/v1/admin/refund-delays`에서 원래 준비 + 3시간 이상의 현재 미확정 시도를 조회하고, 상세·페이지 조사 이력과 `/{attemptId}/investigations` POST를 제공한다. 운영자 신원은 JWT sub, 확인 내용은 필수/최대 500자, 시각은 서버에서 기록한다. 같은 명령·대상·운영자·내용은 결과 확정 뒤에도 최초 영수증으로 수렴한다. 과거 기록은 수정하지 않고 완료 뒤에도 조회하며 새 추가는 현재 미확정에만 허용한다.

조사 기록은 PG 호출·결과 조회 깨우기·송신 재개·중단 해제·실패/복구·새 키/시도·원래 3시간 초기화를 수행하지 않는다. 조회/송신 예약과 lease는 저장된 일정이며 PG GET 성공 근거가 아니다. V27 데이터 보존·명령 경합·실제 flush 롤백·권한/명세와 최종 OCI 615건, 컨테이너 23개·볼륨 57개 보존의 범위는 [운영 조회·조사 기록](pg-test-integration-plan.md#2026-10-29-장기-미확정-운영-조회와-조사-기록-a안)을 따른다. 실제 런타임·ADMIN/운영 화면·PG 장애 전체 검증은 추가하지 않았다.

## 환불 개별 백로그: 조사 이후 조치와 종결 기준

이 항목은 전체 계획의 우선순위에 따라 재개한다. 조사한 사실을 토대로 어떤 후속 조치가 필요한지 한 쟁점씩 정한다. 현재 미확정과 전액 환불은 확인됐지만 우리 실행 귀속이 미확정인 건을 구분하고, 조사 기록 저장과 금융/이용권 조치·조사 종결을 같은 뜻으로 쓰지 않는다. 기존 결과 조회와 원래 3시간 경계를 유지하며 시간만으로 실패/복구/새 금융 동작을 추가하지 않는다. 쉬운 사례·대안·개발/운영/고객 비용·추천을 설명하고 사용자 선택을 기다린다. 실제 추가 금융 동작은 별도로 합의한 사례에서만 검증한다.
