# 상점 장르 분류·필터 계획

2026-11-03 합의한 플랫폼 장르 목록·심사 제출 시 1~3개·코드 수정/배포 관리·선택 중지 시 기존 근거 보존과 복수 장르 AND 검색을 구현·검증했다. Studio→Review→Catalog→Store의 계약·공개 사본·정본 교정·명세/호출부를 함께 연결했다. 최신 관련 검사 **676건**과 실제 9개 서비스 **12단계**가 통과했다.

사용자는 개발 중이고 보관 중인 데이터가 없다고 명시했다. [결정 74](decisions.md#genres-use-new-contract-without-legacy-data)에 따라 장르 없는 과거 자료를 위한 호환 경로 없이 새 계약으로 통일한다. 복수 장르 검색은 선택한 장르를 모두 포함하는 AND(결정 75)다.

## 변경 전 계약과 공백

- `SearchStoreProducts`는 제목 검색·NEWEST/PRICE_ASC/PRICE_DESC 정렬·번호 페이지를 제공한다. `StoreProductRepository.search`는 최종 listed 조건과 제목으로 DB에서 필터하고 총건수를 계산한다. 가격 정렬은 가격 범위 필터와 구분한다.
- Studio의 `Project`·`StorePage`, 공통 `ProjectSnapshot`·`CatalogProductSnapshot`, Catalog/Store 공개 사본에는 장르 자료가 없다. Store에 필터 조건만 추가해서 장르별 탐색을 완성할 수 없다.
- 작업본은 미완성 상태로 저장하고 `Project.requireReady()`에서 새 심사 제출의 제목·소개·내용·썸네일·빌드 준비를 검사한다. `RequestProjectReview`는 먼저 같은 명령의 재전송·활성 요청·현재 승인본을 처리하므로 새 요청의 필수 조건과 과거 요청의 재전송을 구분해야 한다.
- 장르가 없는 상품은 장르별 탐색에서 발견하기 어렵다. 자유 입력만 사용하면 유사어·오탈자와 부적절한 분류의 관리가 필요하다.

## 확정한 정책

[결정 68](decisions.md#platform-defined-product-genres)에 따라 플랫폼이 정한 장르 목록에서 창작자가 선택한다. 자유 태그를 이번 최소 분류의 기본 방식으로 도입하지 않는다. 이후 [결정 71](decisions.md#genres-managed-through-code-deployment)에서 기준 목록은 코드에 정의하고 코드 수정·배포를 통해 변경하기로 선택했다. 상품별 선택값은 업무 데이터로 저장하며, 배포 없이 기준 목록을 바꾸는 관리자 기능은 이번 범위에서 제외한다.

[결정 69](decisions.md#genres-required-on-new-review)에 따라 작업본은 장르 없이 저장할 수 있으나 새 심사를 제출할 때는 장르 선택을 요구한다. 같은 접수 명령의 재전송과 새 요청은 기존대로 구분한다. 장르 없는 구 계약의 승인본을 허용하는 경로는 결정 74에 따라 추가하지 않는다.

[결정 70](decisions.md#one-to-three-product-genres)에 따라 새 심사 제출 시 서로 다른 장르 1~3개를 선택한다. 작업본은 미선택 저장을 허용하며 선택할 때의 상한은 3개다. 중복 코드를 여러 장르로 세지 않는다. 대표 장르·선택 순위는 이번 구현 범위에 추가하지 않는다. 복수 검색은 결정 75의 AND 조건을 적용한다.

[결정 73](decisions.md#retired-genres-preserve-existing-evidence)에 따라 장르 선택을 중지해도 알려진 코드와 기존 상품의 표시/검색·이미 제출한 심사·승인본 출시는 유지한다. 새 심사 제출은 현재 선택 가능한 장르만 허용한다. 이는 새 계약으로 생성된 자료에 적용하며 장르 없는 자료를 허용하는 예외가 아니다.

[결정 74](decisions.md#genres-use-new-contract-without-legacy-data)에 따라 새 심사·출시·공개 계약은 장르 1~3개를 요구한다. 기존 데이터 전환을 위한 구 계약 호환은 구현·테스트의 요구로 삼지 않는다. 입력·이벤트·픽스처·명세를 함께 새 계약에 맞춘다.

## 확정한 검색 조건과 구현 범위

[결정 75](decisions.md#store-multiple-genres-match-all)에 따라 검색에서 액션과 RPG를 함께 선택하면 두 장르를 모두 지정한 상품만 찾는다. 장르 조건은 기존 제목 검색·최종 노출 조건과 함께 DB 페이지/총건수 계산 전에 적용한다. 조건을 지정하지 않으면 기존처럼 모든 노출 상품을 조회한다. 알려진 선택 중지 장르는 기존 상품의 검색에 계속 사용할 수 있고, 알 수 없는 코드·중복·빈 코드는 400으로 거절한다.

대표 장르·선택 순위·장르 계층은 이번 범위에 추가하지 않고 상품의 장르를 동등한 분류로 다룬다. 이는 추가 기능을 도입하지 않는 구현 범위이며 사용자가 대표 장르를 별도로 선택했다고 기록하지 않는다. 가격 범위·판매 상태 등의 추가 필터도 별도 범위다.

### 최초 장르 목록 — 확정

[결정 72](decisions.md#initial-ten-product-genres)에 따라 **액션·어드벤처·RPG·전략·시뮬레이션·퍼즐·스포츠·레이싱·리듬·비주얼 노벨**의 10개로 시작한다. 복합 장르는 선택한 1~3개로 표현한다. 예를 들어 액션 RPG는 액션과 RPG를 선택할 수 있다. 세부 특성을 위한 자유 태그나 장르 계층은 이번 범위에 포함하지 않는다.

이는 이 프로젝트에서 선택한 초기 목록이며 외부 표준으로 간주하지 않는다. 구현에서 식별 코드와 표시명을 일관되게 정의하고 선택 중지의 결정 73에 맞춰 과거 근거와 새 선택을 검증한다.

### 선택 중지의 처리 — 확정

Review는 제출 스냅샷을 불변 근거로 저장하고 Catalog는 같은 버전의 출시 근거가 다르면 충돌로 거절한다. 장르 목록을 바꿀 때 과거 코드까지 제거하면 기존 JSON의 읽기·이벤트 재전달·Store 정본 대조가 영향을 받을 수 있으므로, 목록 변경과 기존 근거의 유효성을 구분해야 한다.

선택한 A에 따라 코드는 보존하고 신규 선택만 중지한다. 기존 공개 상품의 표시/검색·이미 제출한 심사·승인본의 출시는 유지하고, 새 심사 제출은 선택 가능한 장르만 허용한다. 과거 근거와 새 선택의 유효성 검사를 나눈다. 이번에는 추가만 지원하는 B는 선택하지 않았다.

선택 중지의 변경 수단은 코드 수정·배포다. 장르 없는 구 계약의 호환 경로는 결정 74에 따라 추가하지 않는다.

### 상품별 장르 수정 — 기존 계약 적용

`Project.update()`는 상점 정보가 달라지면 contentVersion을 올린다. `RequestProjectRelease`는 현재 작업본 버전의 승인 결과를 요구하고 승인 시점의 스냅샷으로 출시를 요청한다. 장르도 이 상점 정보에 포함해 작업본 수정→새 버전의 심사 승인→출시 요청으로 공개본에 반영한다. 같은 빌드를 유지하며 장르를 수정할 수 있고, 제출된 과거 근거는 보존한다. 이는 기존 상점 정보의 승인/출시 계약을 적용하는 설계이며 사용자가 별도 즉시 변경 경로를 선택했다고 기록하지 않는다.

### 장르 도입 전 자료의 전환 — 새 계약으로 통일

처음에는 장르 없는 과거 심사 자료를 보존한다는 전제로 과거 승인 인정과 장르 보완 후 새 심사를 비교했다. 사용자는 그 논의가 필요한 이유를 확인한 뒤 개발 중이고 보관 중인 데이터가 없다고 명시했다. 과거 승인 인정 A안을 합의한 것으로 보지 않으며, 보존할 자료를 위한 호환 경로 없이 새 계약으로 통일한다.

작업본은 미선택을 허용하고 심사·출시·공개 자료는 알려진 장르 1~3개를 요구한다. 장르 누락의 기본값·과거 자료 판별 예외·구 계약 공개 상품의 유지 검증은 추가하지 않는다. 향후 선택 중지된 알려진 장르의 자료 보존은 별도 합의인 결정 73대로 유지한다. 이 계약 정리는 공유 자원 삭제 작업으로 확대하지 않는다.

## 구현·검증 범위

- Studio 작업본·입력/조회와 심사 준비 검사, Review 불변 근거·조회/판정, Catalog 불변 출시 근거·공개 사본/이벤트, Store 조회 사본·DB 필터/총건수·정본 대조의 영향을 함께 점검한다.
- 모듈별 외부 이벤트 매핑에서 새 자료를 검증하고, 작업본 변경과 승인/출시 근거의 기존 버전 의미를 보존한다. 정상 Kafka 반영과 직접 정본 교정의 새 장르 자료도 대조한다.
- 장르 필수 계약의 누락·빈 목록·중복·알 수 없는 코드·상한 초과를 경계별로 검증한다. 선택 중지 전 제출한 알려진 코드의 읽기·이벤트 재전달·출시는 유지하고 새 심사 제출은 거절하는 것을 검증한다. 장르 없는 구 계약의 호환 픽스처는 추가하지 않는다.
- 로컬에서 편집하고 사용자 지정 `ssh sng` OCI의 격리 자원에서 관련 TDD·아키텍처·이행·통합 및 필요한 실제 여정을 실행한다. 기존 자원·증거를 보존하고 변경하지 않은 범위의 전체 검사는 반복하지 않는다.

선행 Store 95건·실제 여정 11단계는 [자동 복구 완료 기록](store-auto-reconciliation-plan.md)을 따른다. 이전 실행 건수를 최신 676건에 다시 합산하지 않으며 이 기능을 G4 전체 완료로 해석하지 않는다.

## 구현 내용

- 기준 목록과 선택/보존 규칙은 공통 이벤트 계약의 작은 `GenreCatalog` 값 객체로 정의한다. 실행 중 다른 서비스에서 목록을 내려받는 의존성은 추가하지 않는다. Studio CREATOR 조회 `/api/v1/studio/genres`와 Store 익명 조회 `/api/v1/storefront/genres`는 코드·표시명·선택 가능 여부를 제공한다.
- Studio V27의 `studio_project_genre`와 Store V5의 `store_product_genre`에 중복 없는 장르 집합을 저장한다. Catalog·Review의 장르는 기존 불변 JSON 근거에 포함한다. 기존 SQL 이력은 수정하지 않는다.
- 상품 장르는 순위 없는 집합이다. 입력 순서만 바꿔도 버전이 증가하거나 같은 스냅샷이 충돌하지 않도록 정렬한 불변 목록으로 전달한다. 상품별 행 잠금과 같은 트랜잭션에서 장르 관계를 저장하며 페이지 조회에는 컬렉션 배치 로딩을 사용한다.
- HTTP 정본과 Kafka 반영·동일 버전 교정은 장르도 검증·비교·저장한다. 입력 장르의 누락·알 수 없는 코드·중복·상한 초과를 기존 자료로 보완하는 경로는 없다.
- 이후 목록에 코드를 추가할 때는 수신 서비스가 코드를 인식하도록 먼저 배포하고 새 제출의 선택지를 연다. 선택 중지해도 코드는 보존하고 이미 제출한 근거는 읽기·출시할 수 있다.

## 검증 기록
