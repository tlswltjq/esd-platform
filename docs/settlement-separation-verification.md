# G3 첫 단위: 정산 책임 분리·PG 비용 독립 월 마감

2026-10-31. [결정 38](decisions.md#settlement-responsibility-separation)의 같은 Settlement 내부 책임 분리 ②와 [결정 39](decisions.md#seller-close-independent-of-pg-cost)의 판매자 금액 독립 마감을 구현·검증했다. 두 선택을 다시 묻지 않는다. 기준 HEAD는 `70d2176`이며 이전 P3 작업을 포함한 미커밋 변경을 보존했다. 이번 작업은 G3 첫 구조 변경의 완료이며 G3 전체 완료는 아니다.

**후속 완료:** 같은 날짜에 [외부 부담 혜택 A·PortOne 원승인 읽기](settlement-external-benefit-verification.md)를 연결하고 최신 전체 84건을 검증했다. 아래 75건과 소스/JAR 해시는 첫 단위 당시 기록이다. 현재 PortOne 어댑터 유무와 최신 범위는 후속 기록을 기준으로 한다.

## 결과와 구체적 사례

할인 없는 10,000원 원매출에 기존 모의 플랫폼 수수료 10%를 적용하면 판매자 몫은 9,000원이다. PG 비용 자료가 없더라도 승인 거래·원구매·Catalog 소유자와 배분을 검증해 매출을 저장하고 지난 판매자 월을 마감한다. 이후 PG 비용 300원을 확인하면 플랫폼 잔여액 700원을 조회할 수 있으며 원매출·판매자 배분·월 합계·최초 마감 시각은 변하지 않는다. 이 예시는 실제 할인 거래의 배분 기준이나 사업 요율을 새로 합의한 것이 아니다.

| 책임 | 구현 |
|---|---|
| 원매출·배분 | `SettlementSale`에 OrderPaid 전체 구매 근거·불변 판매자·플랫폼 정책/배분·PG 거래 참조를 보존한다. PG 비용/플랫폼 잔여액은 소유하지 않는다. |
| 판매자 월 합계·마감 | `SellerMonthlySettlement`와 `SettlementTotals`는 결제액·플랫폼 몫·판매자 몫·건수만 소유한다. 비용 확인 없이 지난 월을 마감한다. |
| PG 승인 거래 | 새 `PgTransactionRecord`가 결제/주문 키·금액·통화·공급자 거래 ID/시각·최초 접수 시각을 보존한다. `PgEvidence`는 비용 없이도 거래를 표현한다. |
| 확인된 PG 비용 | 새 `PgFeeRecord`가 거래와 일치하는 확정 비용·최초 확인 시각·접수 주체를 보존한다. 비용 미확정이면 행이 없다. 확인된 0원은 별도 확정 행이다. |
| PG 명세 대사 | 기존 `PgReceipt`·항목의 원본은 유지하고 매출 미도착·거래 불일치·비용 대기·비용 불일치를 구분한다. 비용 대기만으로 모의 수령을 확정하지 않는다. |

매출 접수 서비스가 Inbox·PG 거래·있으면 비용·매출·판매자 월 합계를 하나의 트랜잭션으로 조율한다. 기존 전체 구매 내용 대조 후 중복 수렴, 외부 조회 중 업무 트랜잭션 금지, 업무 키 충돌 재시도와 월 잠금을 유지한다. 늦은 비용은 같은 원매출의 재처리에 섞지 않고 별도 거래 확인 경로로 기록한다.

## HTTP·조회 계약

- CREATOR의 내 매출·월 조회는 기존 배분 정보와 JWT sub 범위를 유지한다. 구매자·PG 비용·운영 정보를 추가 노출하지 않는다.
- ADMIN 매출은 `pgTransaction`, `pgCostStatus`와 nullable `pgCost`·`platformNetAmount`를 제공한다. 비용 미확정이면 두 금액은 NULL이다.
- ADMIN 월 조회는 `pgCostStatus`(CONFIRMED/UNCONFIRMED/PARTIAL), `confirmedPgFeeAmount`(확인된 부분합), `pendingPgCostCount`를 제공한다. 미확인 건이 있으면 전체 `pgFeeAmount`·`platformNetAmount`는 NULL이다. 빈 월은 기존처럼 건수·금액 0이다.
- 새 ADMIN `POST /api/v1/settlements/pg-transactions/{paymentId}/refresh`는 이미 접수한 거래를 공급자 GET으로 재조회한다. JWT sub를 비용 최초 접수 주체로 기록한다. 동일 거래 검증·거래 행 잠금 뒤 비용을 한 번만 저장한다. 확인된 비용이 바뀌면 충돌로 보존하며 응답에 비용이 빠졌다고 기존 비용을 지우지 않는다. PG 승인·취소·송금은 수행하지 않는다.
- 기존 Gateway의 ADMIN `/api/v1/settlements/**` 라우팅을 사용한다. Gateway 소스는 변경하지 않았다. 명세는 기존 8개 경로/9개 연산에서 9개 경로/10개 연산으로 갱신했다. 관리자 비용 숫자는 미확정 시 NULL이 될 수 있으므로 호출자는 새 상태와 함께 해석해야 한다.

목록 조회는 페이지 내 PG 거래/비용을 일괄 조회하고 판매자 월 비용은 묶어 집계한다. 판매자 합계 조회와 비용 조합은 읽기 트랜잭션 안에서 수행한다. 성능 부하 검증을 수행한 결과는 아니다.

## V8 데이터 이행

[V8 SQL](../apps/settlement/src/main/resources/db/migration/V8__separate_pg_evidence_and_seller_allocation.sql)은 기존 `settlement_sale`의 검증된 거래·확정 비용만 새 두 테이블로 복사한다. 비용의 과거 접수 주체는 `MIGRATED_V8`로 명시하며 실제 관리자 신원을 만들지 않는다. 외부 명세에 있는 불일치 자료를 거래/비용 정본으로 승격하지 않는다.

기존 매출의 PG 시각·정책·율·비용·플랫폼 잔여액과 월 비용·잔여액 열은 nullable `legacy_*`로 이름을 바꿔 보존한다. 현재 모델은 이 열을 읽거나 갱신하지 않는다. 신규 비용 미확정 행은 NULL이며 0원으로 채우지 않는다. 원매출·배분·월 키·금액·건수·마감 상태/시각과 PG 명세는 보존하고 배분 전용 금액 제약·거래 연결 FK를 추가한다. V1–V7 파일과 체크섬은 변경하지 않았다.

실제 MySQL의 V7에 매출 2개(플랫폼 잔여액 음수 사례 포함), CLOSED 월, 비용이 불일치하는 과거 명세를 넣고 V8로 이행했다. 이름이 바뀐 과거 열을 대응시킨 매출 전체·월 전체와 명세 헤더/항목이 이행 전과 같고, 새 거래 근거·비용이 매출에서 정확히 복사됐음을 확인했다. 기존 V5 원장/Inbox의 이행·대소문자 키 검사도 최종 게이트에 포함했다. 공유 DB에는 이행을 적용하지 않았다.

## 남은 범위와 다음 논의

현재 Settlement 설정은 여전히 모의 PG HTTP 어댑터를 조립한다. `PgEvidence`가 PORTONE_TEST를 표현할 수 있어도 실제 PortOne 조회 어댑터·확정 비용 출처·지급 자료 연결을 구현한 것은 아니다. 확정 `PgCost`와 지급 명세는 기존 SIMULATED 계약을 유지한다.

다음은 총액 9,000원·PG 실결제 8,976원·할인 24원처럼 할인 포함 거래의 판매자 배분 기준과 할인 부담을 한 쟁점으로 논의한다. 비용 출처, 전액 환불의 판매자/플랫폼 조정·PG 비용 반환, 마감 전후 조정 월, 실제 송금 조건은 별도 선택이 필요하다. 원매출을 덮어쓰는 환불 조정이나 임의 할인/비용 계산을 이번에 추가하지 않았다. P4 환불 후 재구매와 운영 API 구조는 후속 논의로 유지한다.
