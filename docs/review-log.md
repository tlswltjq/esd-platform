# 리뷰 기록 — 지적별 판정

코드 리뷰가 낸 지적을 **한 건씩 확인하고 판정한 기록**이다.
[defects.md](defects.md) 가 "무엇이 틀렸었나"를 적는다면 여기는 **"무엇을 지적받았고 그중
무엇이 사실이었나"**를 적는다. 고친 것만 남기면 넘긴 지적이 다음 리뷰에서 다시 올라오고,
그때 같은 판단을 처음부터 다시 하게 된다.

**규칙**

- 지적은 **전수로** 적는다. 고친 것도, 넘긴 것도, **틀린 지적도** 적는다.
- 판정 근거는 코드에서 확인한 사실로 쓴다. "그럴 것 같다"는 판정이 아니라 보류다.
- 넘긴 지적에는 **다시 올라왔을 때 판단을 뒤집을 조건**을 적는다.

### 부분 수용 — 8번

**지적** `PropertyReferenceException` 을 전역 400 으로 받으면, 서버가 만든 잘못된
`Sort.by("...")` 까지 400 이 되어 5xx 알람이 울리지 않는다.

**사실이다.** 다만 그것은 D-024 가 **알고 고른 맞바꿈**이다 — 반대쪽은 클라이언트 오타 하나가
공개 경로에서 500 을 만드는 상태이고, 그것이 D-015·D-020 계열의 결함 자체였다.

정책은 유지하되 **잃은 것만 되돌렸다.** 안전망이 이제 타입명을 로그에 남긴다.
클라이언트 오타와 서버가 만든 잘못된 정렬을 가르는 단서가 그것뿐이다.
원본 메시지를 통째로 싣지는 않는다 — 거기에는 요청 문자열이 들어 있다(2번과 같은 이유).

**다시 볼 조건** — 내부 `Sort.by(...)` 를 문자열 상수로 조립하는 코드가 catalog 밖에서 늘어나면,
그때는 안전망이 아니라 **호출부에서** 막아야 한다.

### 넘긴 지적과 근거

**9. 안전망이 엔티티 속성명을 흘릴 수 있다** — catalog 는 `ProductSort` 가 표를 통과한
**엔티티 이름**을 Spring Data 에 넘기므로, 표가 썩으면 예외가 그 이름을 들고 온다.
그러나 (a) 응답에는 타입명이 나가지 않고, (b) 표가 썩는 것은 `ProductSortKeysTest` 가 전수로
잡는다. 남는 노출은 `id` 같은 이름 한 단어다.
**다시 볼 조건** — 안전망이 실제로 catalog 요청을 받기 시작하면(=화이트리스트가 빠진 경로가 생기면).

**10. 두 계층의 400 문구가 다르다** — 두 겹 설계의 결과다. 코드는 양쪽 다
`INVALID_REQUEST` 이고, **문구는 계약이 아니다.** 커밋된 OpenAPI 스냅샷도 메시지를 약속하지 않는다.
**다시 볼 조건** — 클라이언트가 메시지 문자열로 분기하는 것이 발견되면.

**11. 화이트리스트가 강제되지 않는 관례다** — 사실이지만, 클라이언트 `Pageable` 을 받는
엔드포인트는 **저장소 전체에 `ProductController#list` 하나뿐이다**(store 의 검색은
`PageRequest.of(page, size)` 를 서비스가 직접 만든다). 규칙보다 대상이 먼저 늘어야 한다 —
지금 규칙을 세우면 대상이 하나인 규칙이 하나 더 생길 뿐이고, 그것이 D-021 이 남긴 교훈이다.
**다시 볼 조건** — 두 번째 엔드포인트가 클라이언트 `Pageable` 을 받는 순간.
그때는 `common:web` 의 인자 리졸버 자리가 맞다.

**12. 컨텍스트를 하나 더 띄운다** — 사실이다(`@AutoConfigureMockMvc` 가 컨텍스트 키를 바꾼다).
`CatalogContextTest` 가 이미 `RANDOM_PORT` 로 떠 있으므로 `TestRestTemplate` 로 옮겨탈 수는 있다.
옮기지 않는 이유는 이 클래스가 **상태 코드와 응답 계약**을 읽는 테스트라 MockMvc 의 표현이
그대로 값이기 때문이다. 비용은 CI 한 회차에 컨텍스트 한 번이다.
**다시 볼 조건** — 같은 이유로 컨텍스트를 더 띄우는 클래스가 생기면, 그때 묶는다.

**13. `PageRequest.of` 재조립** — offset 이 `page × size` 가 아닌 `Pageable` 구현을 넘기면
윈도가 밀린다. 그러나 **그런 호출자가 없고**, `Pageable` 인터페이스에는 `withSort` 가 없어
일반 해법이 깔끔하지 않다(`PageRequest` 로 좁히면 그 자체가 같은 가정이다).
**다시 볼 조건** — keyset/offset-scroll 래퍼가 들어오면.

### 사실이 아니었던 지적 — 14번의 일부

지적은 javadoc 의 전수 대조 테스트 이름이 틀렸다는 것이었고, **`ProductSort` 는 실제로 틀렸다**
(`ProductSortTest` → `ProductSortKeysTest`). 고쳤다.

같은 지적이 `ProductQueryService.java:64` 와 `ProductSortTest` 의 javadoc 도 같은 혼동을
갖고 있다고 했는데, **둘 다 아니다.** 앞은 `{@link ProductSort}` 를 가리키고(클래스가 맞다),
뒤는 `ProductControllerTest`·`ProductLookupTest` 를 가리킨다(둘 다 실재하고 문맥도 맞다).

### 조사 방법 — 무엇으로 판정했나

- **지적의 좌표를 먼저 확인한다.** 파일·줄을 열어 지적이 말하는 코드가 실제로 그 자리에 있는지
  본다. 14번의 절반이 여기서 떨어졌다.
- **주장을 코드로 되짚는다.** 5번은 `ProductView` 와 `ProductResponse` 의 레코드 컴포넌트가
  지금은 **같다**는 것까지 확인했다 — 즉 **현재 버그가 아니라 다음 변경에서 열리는 구멍**이다.
  그 구분을 판정에 적었다.
- **규칙이 막는지 직접 본다.** 5번의 수정(테스트가 `api` 의 DTO 를 참조)은 계층 규칙에 걸릴 수
  있어 `CatalogArchitectureTest` 를 확인했다 — `ImportOption.DoNotIncludeTests` 라 걸리지 않는다.
- **고친 뒤에는 테스트가 잡는지 되돌려 본다.** 꼬리표를 지우면 단위 3건, `apply` 가 정렬을
  떨어뜨리면 통합 5건이 빨개지는 것을 확인했다. 되싣기 방어를 빼면 로그를 읽는 테스트만 빨개진다.

### 고치다가 새로 만든 것

8번을 고치면서 안전망의 로그를 `e.getMessage()` 전문으로 바꿨다가 되돌렸다 —
**그 메시지 안에 요청 문자열이 들어 있어서**, 2번에서 막은 로그 줄 위조를 같은 커밋에서
다시 열 뻔했다. 속성 이름만 `EchoedInput` 을 통과시키고 타입은 따로 싣는 형태로 고쳤다.

응답 본문으로는 이것을 잡을 수 없다는 것도 그때 드러났다 — **JSON 직렬화가 개행을
이스케이프하므로 막지 않아도 응답에는 날 개행이 없다.** 그래서 테스트가 로그 어펜더를 붙인다.

### 남은 것

- e2e(`TrackACreatorFlowTest`)는 로컬에서 돌리지 않았다. 전체 스택이 필요하고,
  이 변경이 건드린 `?sort=productId,desc` 는 통합 테스트가 덮는다.
- 기본 정렬이 `id desc` 로 정해졌다. **관측 가능한 동작 변경**이고, 근거는
  [D-025](defects.md#d-025) 에 있다. OpenAPI 스냅샷은 정렬 기본값을 약속한 적이 없어 변화가 없다.
