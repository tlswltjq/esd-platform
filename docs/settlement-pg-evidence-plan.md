# G3 PG 비용·환불 비용 반환·지급 자료의 수집 경로

2026-11-02. 전액 환불의 원배분 상계·월 선택과 [환불 원장/월 합계 연결 120건](settlement-refund-ledger-verification.md) 다음 단위다. 현재 코드와 공식 문서를 대조한 뒤 사용자는 **A: 토스페이 공식 정산 API 자동 수집**을 선택했다. [결정 43](decisions.md#tosspay-statement-api-source)을 따르며 아래 A/B 표는 선택의 배경이다. 실제 계정 설정·LIVE 금융 실행은 이 선택에 포함하지 않는다.

## 확인할 사실과 예시

고객에게 9,000원을 전액 환불했고 판매자/플랫폼의 원배분도 상계했다는 사실만으로 PG 수수료의 반환까지 확인된 것은 아니다. 예를 들어 승인 때 수수료 300원·그 수수료의 부가세 30원이 발생했다면 환불 때 각각 얼마나 반환됐는지를 별도 자료에서 확인해야 한다. 이 금액은 설명용이며 현재 TEST 거래의 관측값·사업 요율이 아니다.

판매자 월 마감과 환불 조정은 이미 선택한 계약대로 계속 처리한다. 비용 자료가 없으면 미확정이며 요율 추정·0원으로 대신하지 않는다. 판매자 배분/월 선택 A와 플랫폼 전액 PG 비용 부담을 다시 묻지 않는다. PG 지급 보고와 실제 은행 입금의 확인도 구분한다.

토스페이와 토스페이먼츠는 다른 연동 계약이다. 이 조사는 현재 `TOSSPAY_V2` 채널 기준이다. 기존 계정의 LIVE 권한/가맹점 키·정산 조회 동의·내려받을 수 있는 실제 파일은 이번에 확인하지 않았다. 콘솔 설정·거래/정산 조회·자금 이동은 실행하지 않고 공개 공식 문서만 조회했다.

## 현재 구현과 맞지 않는 부분

- `PortOnePaymentHttpClient`/`PortOneRefundHttpClient`는 승인·전액 취소와 지급 구성의 확인을 담당한다. PG 수수료·VAT·지급 보고를 생성하지 않는다.
- `PgCost`는 SIMULATED 거래의 비음수 수수료·율·정책만 표현하며 수수료 부가세나 환불 반환 행은 없다. 실제 명세에 요율이 없다고 모의 요율을 채울 수 없다.
- `PgSettlement`/`PgReceiptItem`은 양수 승인 항목과 모의 비용, `SIMULATED_PAID`를 전제한다. 실제 토스페이의 결제/환불 부호·수수료/VAT·조회 페이지와 지급일 보고를 그대로 수용할 수 없다.
- `ReconcilePgReceipt`도 SIMULATED 조회·대사/모의 수령에 한정돼 있다. 실제 PG 명세를 넣고 모의 수령 완료로 표시하는 방식으로 확대하지 않는다.
- PORTONE_TEST의 명세 공급자는 명시적 미연동 503이다. 기존 환불 월 조회의 비용/플랫폼 잔여액 NULL을 유지한다.

## 선택한 자료 수집 경로 — A

| 안 | 동작 | 개발·운영·고객 관점 |
|---|---|---|
| **A — 토스페이 공식 정산 API 자동 수집 (추천)** | Settlement가 가맹점/조회일/기준을 지정해 페이지 전체를 읽고 원본 행·합계를 보존한다. PortOne 승인/취소 근거와의 연결을 대조한다. | 조회 어댑터·페이지/재수집 처리가 필요하다. 운영자의 반복 내려받기/등록을 줄이고 비용 확인 지연을 추적하기 쉽다. 고객/판매자의 기존 환불·마감 계약은 그대로다. 실제 가맹점 조회 권한과 거래 키 매핑은 실제 연결 전에 검증해야 한다. |
| **B — 토스페이 파트너스 공식 엑셀 명세 접수** | 운영자가 내려받은 공식 명세를 접수하고 원본·등록 주체·중복 근거를 보관해 같은 업무 대사에 연결한다. | API 권한 연동 대신 실제 파일 형식/범위 검증·업로드 처리가 필요하다. 운영자의 정기 제출과 누락 관리가 생기며 비용 확정이 제출 시점에 영향을 받는다. 파일 형식은 실제 명세를 확인한 뒤 정한다. |

두 안 모두 외부 명세의 승인 비용과 환불 반환을 근거로 삼는다. 임의 금액 수기 확정·미확인 비용의 0원 처리·실제 지급 완료 추정은 제안하지 않는다. A 선택은 SFTP·엑셀 보조 경로의 일괄 구현이나 LIVE 결제/취소 실행을 승인하는 뜻이 아니다. 일반 정산 API 밖의 차액 정산 등은 별도 출처 확인이 필요하다.

추천은 A다. 현재 일반화 목표에서 반복 비용/지급 대사 업무를 자동화하기 좋고 조회 계약이 공개돼 있기 때문이다. **현재 TEST에는 실지급 자료가 없으므로**, A를 선택하면 공식 응답 계약을 따르는 루프백 픽스처와 OCI MySQL/Kafka로 수집·대사를 검증하고 실제 거래의 비용은 미확정으로 유지한다. 실제 명세 연결/검증은 가맹점 키·권한·대응하는 실거래 자료가 확보된 별도 단계다. TEST를 LIVE로 자동 전환하지 않는다.

## 선택 뒤 구체화할 범위

선택한 출처의 원본 보관·가맹점/통화/거래 연결 키, 결제·환불·수수료/VAT의 부호/합계 검증, 중복/충돌·미도착/불일치 대사와 조회 범위를 구체화한다. 실제 PortOne 결제/취소 ID와 토스페이 거래/payToken/주문번호 간 대응을 이름 유사성만으로 확정하지 않는다. 기존 원매출·환불·CLOSED 월·모의 명세는 보존한다. 실수령 판단·세무 처리·음수 잔액 자동 이월/송금·P4 재구매는 이번 경로 선택에 포함하지 않는다.

A의 수집·원본/거래 근거·대사·관리자 조회·주기 재수집을 구현하고 OCI **144건**·check·bootJar를 통과했다. [355개 해시·자원 보존과 정확한 범위](settlement-pg-evidence-verification.md)를 따른다. 앞선 120건과 이번 검증을 구분하며 실가맹점 자료/LIVE 승인 접수·비용 월 귀속/요약 통합·추가 비용 자료·실수령은 후속이다.
