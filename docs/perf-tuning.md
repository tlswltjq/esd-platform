# 설정 튜닝으로 얻은 개선 수치

**측정일 2026-08-10. 코드는 한 줄도 고치지 않았다** — 전부 환경변수 오버라이드다.

[performance.md](performance.md) 가 "다음에 이어갈 것"으로 남겨 둔 8-3 · 8-4 · 11-2 를 숫자로 닫고,
간판 수치(138 → 480 events/s)를 **그 문서가 스스로 무효 선언한 환경이 아닌 곳에서** 다시 잰다.

측정 도구는 [scripts/perf/](../scripts/perf/) 를 그대로 쓴다. 새로 만든 것은 조건을 갈아 끼우는
셸 루프뿐이고, 그것도 리포에 넣지 않았다 — 측정 절차는 재현 가능해야 하지만
일회성 스윕 스크립트까지 코드가 될 필요는 없다.

---

## 0. 왜 설정만으로 전후를 잴 수 있나

`OutboxRelay` 의 개선 2("비울 게 남았으면 다음 폴링을 기다리지 않는다")는
`max-batches-per-cycle` 로 켜고 끌 수 있다.

```java
for (int cycle = 0; cycle < properties.maxBatchesPerCycle(); cycle++) {
    int processed = relayOneBatch();
    if (processed < properties.batchSize()) return;
}
```

**`max-batches-per-cycle = 1` 은 개선 전 동작과 같다** — 한 배치를 비우고 다음 폴링을 기다린다.
그래서 코드를 되돌리지 않고도 개선 전후를 **같은 호스트, 같은 시각, 같은 데이터**로 비교할 수 있다.
performance.md 10장이 "측정 환경이 변하면 그 전후 숫자는 비교가 아니라 무관한 값 두 개"라고
적은 그 함정을 구조적으로 피한다.

같은 방식으로 나머지 조건도 전부 설정이다.

| 주제 | 노브 | 어느 절 |
|---|---|---|
| 1. 릴레이 처리량 | `STOVE_OUTBOX_MAXBATCHESPERCYCLE` | 2절 |
| 2. 종단 지연 | `STOVE_OUTBOX_POLLINTERVALMS` | 3절 |
| 3. 컨슈머 처리량 | `SPRING_KAFKA_LISTENER_CONCURRENCY` | 4절 |
| 4. 배치 커밋 비용 | `STOVE_OUTBOX_BATCHSIZE` · `SPRING_APPLICATION_JSON` | 5절 |

`SPRING_APPLICATION_JSON` 은 `hibernate.jdbc.batch_size` 처럼 **밑줄이 든 키**를 주기 위한 것이다 —
환경변수 이름 규칙(`_` → `.`)으로는 표현할 수 없다.

performance.md 9장과 같은 곳이다. 로컬에서는 전체 스택이 산술적으로 안 뜬다.

## 2. 주제 1 — 릴레이 처리량: 간판 수치를 유효 환경에서 다시 잰다

### 무엇이 문제였나

performance.md 6장의 `138 → 480 events/s (×3.48)` 는 **7장이 스스로 무효 선언한 그 랩탑**
(8GB / Docker 4GB, `pageouts` 150만)에서 나왔다. 10장이 "릴레이 처리량은 짧은 시간 안에
연달아 쟀고 HTTP 와 분리돼 있어 유효하다"고 변호했지만, **호스트가 다르면 개선폭 자체가 달라진다**는
것까지는 확인되지 않았다.

### 결과 — 2만 건 적재 후 배수, 조건당 2회

| max-batches-per-cycle | 회차 1 | 회차 2 | 평균 | mbpc=1 대비 | 배수 소요 |
|---|---:|---:|---:|---:|---:|
| **1** (개선 전 동작) | 180.7 | 180.7 | **180.7** | ×1.00 | 110.7초 |
| **3** | 456.6 | 445.4 | **451.0** | ×2.50 | 43.8 / 44.9초 |
| **10** (현재 기본값) | 975.6 | 921.7 | **948.7** | **×5.25** | 20.5 / 21.7초 |

전 회차 `failed 0 · dead 0`. 회차 간 편차는 최대 5.5%(mbpc=10)이고 조건 간 차이는 ×2.5~5.3 이다 —
**신호가 잡음보다 훨씬 크다.**

### 랩탑과 나란히 놓으면

| | 랩탑 (6장) | OCI (이번) |
|---|---:|---:|
| 개선 전 | 156.1 events/s | 180.7 events/s |
| 개선 후 | 480.5 events/s | **948.7 events/s** |
| **개선폭** | **×3.08** | **×5.25** |
| 배치 200건 발행 시간 | 0.28초 | **0.021초** |

**같은 코드 개선이 호스트에 따라 ×3.08 과 ×5.25 로 다르게 나온다.** 이유는 마지막 줄에 있다.

이 개선이 없애는 것은 **고정 폴링 대기**다. 그러니 이득은 주기에서 대기가 차지하는 비중에 비례한다.

```
랩탑 : 주기 1.28초 = 대기 1.00 + 배치 0.28    → 유휴 78%
OCI  : 주기 1.02초 = 대기 1.00 + 배치 0.021   → 유휴 98%
```

느린 호스트에서 잰 개선폭은 **과소평가**였다. 배치 처리가 빠른 기계일수록 고정 대기가
더 크게 남고, 그것을 없애는 개선의 값도 커진다.

### 적정값 — 8-3 이 남긴 질문

8-3 은 `max-batches-per-cycle` 의 1·3·10 을 같은 조건에서 비교하라고 적어 뒀다.

`3` 이 `1` 의 정확히 ×2.5, `10` 이 ×5.25 다. **10 을 줘도 10배가 되지 않는다** —
증가가 선형이 아니라 포화한다. 그 이유는 주제 4 에서 밝힌다.

## 3. 주제 2 — 종단 지연: 트레이스에 보이던 `+527ms`

### 무엇을 재는가

`e2e_fulfillment_latency` — **결제 승인 응답에서 라이브러리에 라이선스가 보이기까지**의 벽시계 시간.
`http_req_duration` 과 `stove_outbox_pending` 이 둘 다 초록인데 이 값만 큰 상황이 실재한다.

README 의 트레이스 예시에 `+527ms` 가 "Outbox 폴링 지연"으로 찍혀 있다. 고정 주기 1초는
평균 0.5초를 그냥 기다리는 시간이므로 계산과 맞는다. **그런데 주기를 줄여본 적이 없었다.**

### 결과 — 5 VU · 2분, 조건당 2회

| poll-interval-ms | 회차 | avg | med | p90 | **p95** | max | **완료 건수** | 성공률 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| **1000** (현재) | r1 | 693ms | 528ms | 1.05s | **1.30s** | 1.68s | 252 | 100% |
| **1000** | r2 | 1014ms | 1032ms | 1.05s | **1.06s** | 1.73s | 198 | 100% |
| **200** | r1 | 543ms | 526ms | 551ms | **563ms** | 1.23s | **285** | 100% |
| **200** | r2 | 541ms | 526ms | 544ms | **561ms** | 1.22s | **286** | 100% |

**얻은 것 셋.**

1. **꼬리가 줄었다** — p95 1.30s / 1.06s → 0.563s / 0.561s. p90 은 1.05s → 0.55s
2. **처리량이 늘었다** — 같은 5 VU 로 2분에 완료한 건수 198~252 → 285~286.
   한 반복이 덜 기다리니 더 많이 돈다
3. **예측 가능해졌다** — 회차 간 편차가 1000ms 에서 46%(693 vs 1014), 200ms 에서 **0.4%**.
   1초 주기에서는 이벤트가 주기 어디에 떨어지느냐가 결과를 흔든다

### 측정 도구가 결론을 가린 자리

중앙값은 528 → 526ms 로 **거의 그대로**다. 개선이 없어서가 아니다.

네 회차 전부 `min` 이 **517~522ms** 다. 이 바닥값은 시스템이 아니라 측정 도구에서 온다 —
`payment-callback.js` 의 `POLL_INTERVAL_S = 0.5` 다. 지급 여부를 0.5초마다 확인하므로
그보다 짧은 지연은 **관측할 수 없다.**

그래서 이 측정이 말할 수 있는 것은 꼬리와 완료 건수까지다.
**중앙값의 진짜 개선폭은 이 도구로는 잴 수 없다.** 재려면 폴링 간격을 줄여야 하는데,
그건 시나리오 코드를 고치는 일이라 이번 범위 밖이다.

### 대가

| | mysql CPU | 릴레이 호출 |
|---|---:|---:|
| poll 1000ms | 7.7% / 6.8% | 0.75 / 0.51 회/초 |
| poll 200ms | 8.9% / 8.7% | 1.21 / 1.23 회/초 |

**약 +20%.** 주기를 5분의 1로 줄였는데 CPU 는 20%만 는다 —
빈 폴링(`lockPendingBatch` 가 0건을 돌려주는 회차)이 싸기 때문이다.
꼬리 지연 절반을 CPU 20%로 사는 거래이고, 이 부하에서는 남는 장사다.

> 릴레이 호출 지표(`stove_outbox_relay_seconds_count`)는 **빈 배치를 세지 않는다**
> (`relayOneBatch` 가 빈 배치에서 `recordRelay` 를 건너뛴다). 위 숫자는 폴링 횟수가 아니라
> **실제로 일한 횟수**다. 빈 폴링의 비용은 mysql CPU 로만 보인다.

## 4. 주제 3 — 컨슈머 처리량: 리포가 적어 놓고 안 잰 것

### 근거는 이미 코드에 있었다

```
처리량이 필요하면 concurrency 를 올린다. 파티션 수까지는 안전하다
                          — common/archunit EventOrderingRules, docs/event-ordering.md 5절
```

모든 토픽이 3파티션(`KAFKA_NUM_PARTITIONS: 3`)이고, 리스너 `concurrency` 는 **기본값 1**이다.
쓸 수 있는 병렬도의 3분의 1만 쓰고 있었고, **한 번도 측정되지 않았다.**

### 무엇으로 쟀나 — 실제 백로그

합성 이벤트를 밀어 넣지 않았다. 주제 1 을 재는 동안 payment 를 내려 두었더니
`stove.order.v1` 에 **11만 건**이 남았고, 그것이 빠지는 속도를 그대로 쟀다.
표본이 크고 컨슈머가 이미 정상 상태라 이쪽이 낫다.

순서는 `1 → 3 → 1`. 마지막이 첫 번째와 같아야 한다 — 측정 중 payment 테이블이 계속 커지므로,
그 효과를 배제하려면 대조가 필요하다.

### 결과 — 90초 창, 컨슈머 그룹 오프셋 증분

| listener concurrency | 소비 처리량 |
|---|---:|
| 1 (첫 측정) | 141.1 events/s |
| **3** | **364.1 events/s** |
| 1 (재확인) | 144.3 events/s |

**×2.55.** 파티션 3개가 상한이므로 이론 최대 ×3 에 근접한다.
c=1 두 회차가 141.1 / 144.3 (편차 2.3%)로 일치하니, 테이블이 13만 행까지 커진 효과는
차이를 만들지 않았다 — **×2.55 는 concurrency 때문이다.**

### 이 숫자가 드러낸 비대칭

| | events/s |
|---|---:|
| 릴레이 발행 (mbpc=10) | **948.7** |
| 컨슈머 소비 (concurrency=1) | **141.1** |

**6.7배.** performance.md 11장이 "측정이 생산자 쪽에서 끝나고 있었다"고 적은 그 자리에
숫자가 들어간다. 발행이 끝나면 `stove_outbox_pending` 은 0 이므로 **생산자 지표만 보면
해소된 것처럼 보이지만**, 적체는 브로커로 옮겨갔을 뿐이다.

concurrency 를 3 으로 올려도 364 : 949 로 여전히 2.6배 차이다.
팬아웃 경로의 실질 처리량은 릴레이가 아니라 **가장 느린 컨슈머**가 정한다.

### 덤으로 나온 결함 후보 — 랙 지표를 믿을 수 없다

실제 랙이 **113,517건**인 동안, actuator 의
`kafka_consumer_fetch_manager_records_lag` 합계는 **0** 을 보고했다.

```
# 컨슈머 그룹 오프셋 (권위 있는 값)
payment  stove.order.v1  p0  lag 40194
payment  stove.order.v1  p1  lag 38803
payment  stove.order.v1  p2  lag 34520

# 같은 시각 actuator
lag 합계 0
```

`scripts/perf/collect-consumer.sh` 와 performance.md 11-1 이 이 지표를 **랙의 주 판정 수단**으로
쓰고 있다. 이 상태로는 "랙 0" 이 "밀리지 않았다"의 근거가 되지 못한다.
**적체가 쌓여도 지표가 0 이면 사고는 관측되지 않는다.**

판정은 `kafka-consumer-groups.sh --describe` 로 해야 한다. 결함으로 등록할 값이 있다.

## 5. 주제 4 — 릴레이 배치의 커밋 비용 (8-4)

### 여섯 회차가 한 모델에 맞는다

주제 1 의 결과를 배수 시간으로 다시 쓰면 이렇게 된다. 배치 200건, 2만 건이므로
회차 수는 `100 / mbpc` 이고, 한 회차는 `고정 대기 1초 + mbpc × (배치 1회 비용 b)` 다.

```
T = 100/mbpc + 100·b
```

| mbpc | 측정 T | 역산한 b |
|---|---:|---:|
| 1 (r1/r2) | 110.7 / 110.7초 | 0.107 / 0.107초 |
| 3 (r1/r2) | 43.8 / 44.9초 | 0.105 / 0.116초 |
| 10 (r1/r2) | 20.5 / 21.7초 | 0.105 / 0.117초 |

**b 가 여섯 회차에서 0.105~0.117초로 일정하다.** 모델이 맞는다는 뜻이다.

### 그런데 타이머는 0.021초만 본다

`stove.outbox.relay` 가 보고한 배치 1회 평균은 **0.021~0.024초**다. b 의 20%다.
나머지 80%는 어디 있나 — 코드에 답이 있다.

```java
private int relayOneBatch() {
    Integer processed = transactionTemplate.execute(status -> {
        long startedAt = System.nanoTime();
        List<OutboxEvent> batch = repository.lockPendingBatch(properties.batchSize());
        publishPreservingOrder(batch);
        metrics.recordRelay(System.nanoTime() - startedAt, batch.size());   // ← 커밋 전
        return batch.size();
    });
}
```

**`recordRelay` 는 트랜잭션 커밋 전에 찍힌다.** 타이머가 재는 것은 락 선점 SELECT 와 발행까지고,
`markSent` 로 더럽혀진 200개 엔티티의 flush 와 커밋은 그 밖이다.

즉 **배치 1회 0.105초 중 0.084초(80%)가 타이머에 안 보이는 커밋 구간**이다.
performance.md 8-4 가 "`markSent` 대량 UPDATE — 배치 200건의 커밋 비용"이라고 적어 둔 항목에
이제 숫자가 붙었다.

### 이것이 만드는 상한

모델을 `mbpc → ∞` 로 보내면 고정 대기가 사라지고 `200 / b` 만 남는다.

```
200 / 0.105 ≈ 1,905 events/s      (배치 크기를 200 으로 둔 채)
```

**`max-batches-per-cycle` 을 아무리 올려도 이 선을 못 넘는다.** mbpc=10 이 948.7 인 것은
이미 상한의 절반이라는 뜻이고, 그래서 10 을 줘도 10배가 안 나온 것이다.

그래서 다음 질문이 갈린다 — b 를 줄일 수 있나. 아래 두 절이 그것을 두 방향에서 친다.

### 그래서 JDBC 배치를 올려 봤다 — 효과 없음

`application.yml` 은 `jdbc.batch_size: 50` 과 `order_inserts: true` 를 뒀는데,
`markSent` 는 UPDATE 이고 **`order_updates` 는 없다.** 이것이 첫 번째 의심이었다.

환경변수 이름 규칙으로는 `hibernate.jdbc.batch_size` 의 밑줄을 표현할 수 없으므로
`SPRING_APPLICATION_JSON` 으로 줬다.

```json
{"spring":{"jpa":{"properties":{"hibernate":{
  "jdbc":{"batch_size":200},"order_updates":true,"batch_versioned_data":true}}}}}
```

| 조건 | 회차 1 | 회차 2 |
|---|---:|---:|
| 기준 (`batch_size:50`, `order_updates` 없음) | 21.6초 / 925.9 events/s | 21.6초 / 925.9 events/s |
| 튜닝 (`batch_size:200` + `order_updates`) | 20.5초 / 975.6 events/s | 20.5초 / 975.6 events/s |

조건 안에서는 회차가 완전히 일치하는데, **이 1.1초를 설정 덕으로 돌릴 수 없다.**
주제 1 에서 아무 설정 없이 잰 같은 mbpc=10 이 20.5초와 21.7초를 오갔다 —
차이가 조건 간 차이와 같은 크기다.

설정이 정말 실렸는지는 따로 확인했다. `management.endpoints.web.exposure.include` 에
`env` 를 더해(이것도 환경변수다) 애플리케이션에게 직접 물었다.

```
spring.jpa.properties.hibernate.jdbc.batch_size
  → {"property":{"source":"spring.application.json", ...
spring.jpa.properties.hibernate.order_updates
  → {"property":{"source":"spring.application.json", ...
```

**바인딩됐고, 그런데도 안 변했다.**

**결론: `markSent` 의 JDBC 배치화로는 배치당 0.086초가 설명되지 않는다.**
8-4 의 가설 하나가 닫혔다. 부정적 결과지만 다음 후보를 좁힌다는 점에서 값이 있다.

### 그러면 그 비용은 건당인가 배치당인가

`batch-size` 와 `max-batches-per-cycle` 을 **곱이 일정하게** 바꾼다.
회차당 처리량이 2000건으로 같으므로, 달라지는 것은 **배치 수**뿐이다.

| batch-size | mbpc | 회차당 | 배치 수 | 소요 | 처리량 | 타이머 평균 |
|---|---|---|---:|---:|---:|---:|
| 100 | 20 | 2000 | 200 | 22.6초 | 885.0 events/s | 0.0191초 |
| **200** | 10 | 2000 | 100 | 21.6초 | 925.9 events/s | 0.0239초 |
| **400** | 5 | 2000 | 50 | **18.5초** | **1081.1 events/s** | 0.0310초 |

`릴레이 타이머 (N회)` 가 200 / 100 / 50 으로 정확히 나온 것이 설정이 실제로 걸렸다는 증거다.

**배치 수가 적을수록 빠르다.** 배치당 비용을 배치 크기로 회귀하면

```
배치 1회 비용 b ≈ 0.027초 + 0.00036 × (배치 크기)
                  ^^^^^^^   배치마다 고정으로 드는 27ms
```

즉 20ms 안팎이 **건수와 무관하게 배치마다 붙는다** — 트랜잭션 시작·커밋, 락 선점 쿼리 왕복이다.
배치를 200 에서 400 으로 키우면 이 고정비를 무는 횟수가 절반이 되고,
그래서 같은 회차당 처리량인데도 빨라진다.

### 재현 확인, 그리고 더 키워 보기

| batch-size | mbpc | 회차당 | 배치 수 | 측정 | 처리량 |
|---|---|---|---:|---|---:|
| 100 | 20 | 2000 | 200 | 22.6초 | 885.0 |
| **200** | **10** | **2000** | **100** | 21.6 / 21.6 / 21.6 / 20.5 / 20.5 / 21.7초 | **925.9 ~ 975.6** ← 현재 기본값 |
| 400 | 5 | 2000 | 50 | 18.5 / 19.5 / 19.4초 | 1025.6 ~ 1081.1 |
| **400** | **10** | **4000** | **50** | **15.2 / 15.3초** | **1307.2 ~ 1315.8** |
| 800 | 5 | 4000 | 25 | 15.3초 | 1307.2 |

**`batch-size: 400` + `max-batches-per-cycle: 10` 이 기본값보다 40% 빠르다.** 두 회차가 15.2 / 15.3초로 일치한다.

`400×10` 과 `800×5` 가 **15.3초로 같다** — 회차당 이벤트 수가 4000 으로 같으면 배치를
어떻게 쪼개든 같다는 뜻이다. 배치당 고정비는 400 을 넘어가면 이미 무시할 만해진다.

### 비용 구조 — 여섯 조건이 한 식에 들어간다

`T = cycles × (1 + mbpc × b)` 에서 b 를 역산하면

| 배치 크기 | b (배치 1회) | 건당 | 그중 타이머가 보는 몫 |
|---|---:|---:|---:|
| 100 | 0.063초 | 0.63ms | 0.019초 (30%) |
| 200 | 0.116초 | 0.58ms | 0.024초 (21%) |
| 400 | 0.188~0.206초 | 0.47~0.52ms | 0.030초 (15%) |
| 800 | 0.412초 | 0.52ms | 0.049초 (12%) |

```
b ≈ 0.020초 + 0.00048 × (배치 크기)
    ^^^^^^^   배치당 고정      ^^^^^^^ 건당 0.48ms
```

**건당 0.48ms 중 발행(타이머)은 0.06ms 뿐이다.** 나머지 0.42ms 는 커밋 구간이고,
JDBC 배치 설정으로는 움직이지 않았다. 이 건당 비용이 설계의 진짜 상한을 만든다.

```
mbpc·배치 → ∞  ⇒  1 / 0.00048 ≈ 2,080 events/s
```

### 주의 — 이 개선에는 안 잰 대가가 있다

`OutboxRelay` 의 주석이 배치마다 트랜잭션을 나눈 이유를 이렇게 적어 뒀다.

> 여러 배치를 한 트랜잭션으로 묶으면 `FOR UPDATE SKIP LOCKED` 락 보유 시간이 그만큼 길어져,
> 같은 커넥션 풀을 쓰는 API 응답까지 끌어내린다.

**배치를 키우는 것도 락 보유 시간을 늘린다.** 400건짜리 트랜잭션은 200건짜리보다
두 배 오래 행을 잡고 있고, 그 영향은 이번에 재지 않았다.
그래서 이것은 **권고가 아니라 후보**다 — 9장 절차(포화 이전 고정 부하에서 API p95 비교)로
대가를 재고 나서야 기본값을 바꿀 수 있다.

## 7. 정리 — 무엇을 포트폴리오에 적을 수 있나

### 검증된 개선 — 그대로 적어도 되는 것

| 주제 | 전 | 후 | 배수 | 회차 | 코드 변경 |
|---|---:|---:|---:|---|---|
| 릴레이 처리량 (연속 배수) | 180.7 events/s | **948.7 events/s** | **×5.25** | 조건당 2회 | 없음 (설정) |
| 컨슈머 처리량 (concurrency 1→3) | 141.1 events/s | **364.1 events/s** | **×2.55** | 1→3→1 대조 | 없음 (설정) |
| 종단 지연 p95 (폴링 1000→200ms) | 1.30s / 1.06s | **0.56s** | **약 ½** | 조건당 2회 | 없음 (설정) |
| 종단 완료 건수 (같은 5 VU · 2분) | 198~252건 | **285~286건** | ×1.2~1.4 | 조건당 2회 | 없음 (설정) |

### 대가를 아직 안 잰 후보

| 주제 | 전 | 후 | 배수 | 안 잰 것 |
|---|---:|---:|---:|---|
| 릴레이 배치 크기 (200→400, mbpc 10) | 925.9~975.6 events/s | **1,307~1,316 events/s** | ×1.35~1.42 | 락 보유 시간이 API p95 에 주는 영향 |

### 숫자보다 값이 나갈 수 있는 것 넷

1. **개선폭은 호스트에 의존한다** — 같은 개선이 랩탑에서 ×3.08, OCI 에서 ×5.25.
   고정 대기를 없애는 개선이라 배치 처리가 빠른 기계일수록 이득이 크다.
   **느린 기계에서 잰 개선폭은 과소평가였다**
2. **측정 도구의 해상도가 결론을 가릴 수 있다** — 종단 지연 중앙값이 안 변한 것처럼 보인 이유는
   k6 시나리오의 폴링 간격 0.5초였다. `min` 이 네 회차 모두 517~522ms 로 같았던 것이 단서다
3. **지표가 0 이라고 적체가 없는 게 아니다** — 실제 랙 11만 건 동안
   `records_lag` 는 0 을 보고했다
4. **부정적 결과도 범위를 좁힌다** — JDBC 배치 튜닝은 효과가 없었지만(바인딩은 확인),
   그 덕에 배치당 고정비 20ms 와 건당 0.48ms 라는 비용 구조가 드러났다.
   **어디를 고쳐야 하는지는 안 되는 것을 지워서 알아냈다**

## 8. 이어서 할 것

- **배치 크기의 대가 측정** — `batch-size: 400` 이 40% 빠르지만 락을 두 배 오래 잡는다.
  9장 절차(포화 이전 고정 부하에서 API p95 비교)로 대가를 재야 기본값을 바꿀 수 있다
- **랙 지표 결함 등록** — `kafka_consumer_fetch_manager_records_lag` 가 0 을 보고한 조건을
  좁혀 [defects.md](defects.md) 에 올린다. `collect-consumer.sh` 의 판정 근거가 걸려 있다
- **컨슈머별 한계선** — 이번에 잰 것은 payment 하나다. 11-2 가 보여준 처리시간 격차
  (download 4.8ms ~ settlement 26ms)를 생각하면 팬아웃 3종이 함께 밀릴 때가 진짜 한계선이다
- **커넥션 풀 (8-2)** — 9-4 가 남긴 "릴레이와 API 가 같은 풀을 쓴다" 가설은 이번에도 안 건드렸다
- **건당 0.42ms 의 정체** — 커밋 구간이 JDBC 배치로 안 줄었다. Hibernate 더티체킹인지,
  MySQL 행 잠금·리두인지 가려야 상한 2,080 events/s 를 올릴 수 있다

## 9. 측정을 어떻게 돌렸나

전부 [scripts/perf/](../scripts/perf/) 의 기존 도구다. 조건을 갈아 끼우는 것만 셸 루프로 감쌌다.

```bash
# 조건 = compose 오버라이드 한 장. 코드도 yml 도 건드리지 않는다.
cat > /tmp/ovr.yml <<'EOF'
name: stove-apps
services:
  order:
    environment:
      STOVE_OUTBOX_MAXBATCHESPERCYCLE: "1"
EOF
docker compose -f docker-compose.apps.yml -f docker-compose.apps.ci.yml \
               -f docker-compose.apps.e2e.yml -f /tmp/ovr.yml \
               up -d --force-recreate order

./scripts/perf/relay-drain.sh 20000 mbpc1-r1
```

**설정이 실제로 걸렸는지 매 회차 확인했다.** `docker inspect` 로 환경변수를 보고,
`hibernate.*` 처럼 env 이름 규칙으로 표현할 수 없는 것은 `SPRING_APPLICATION_JSON` 으로 주고
`/actuator/env` 로 바인딩 소스까지 확인했다 — 노출 목록도 환경변수로 열었다.
**세 조건이 조용히 같은 값으로 돌면 비교가 통째로 거짓이 된다.**

컨슈머 랙은 actuator 를 믿을 수 없어 `kafka-consumer-groups.sh --describe` 로 쟀다(4절).

측정이 남긴 것은 전부 지웠다 — 합성 이벤트 오프셋을 끝으로 옮기고,
`ORD-PERF-*` / `ORD-CONS-*` 행과 `outbox_event` 를 비웠다. 정리 후 랙 0, 합성 행 0,
앱 10종 healthy 를 확인했다.
