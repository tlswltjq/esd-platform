# 전체 기능 일반화 계획과 환불·Payment 평가

2026-10-29 작성. 사용자 목표는 **MVP 상태의 전 기능을 일반적인 사용 수준으로 고도화한 뒤, 엣지 케이스와 성능 관점으로 추가 고도화**하는 것이다. 이 문서는 그 목표에 맞춘 현재 평가와 권장 실행 순서다. 세부 업무 정책은 각 작업 시작 시 사용자와 결정하며, 계획 수립을 미결 정책의 구현 승인으로 해석하지 않는다.

평가 기준 코드는 `7f96c3a`다. 이 커밋에 장기 미확정 환불의 운영 조회·조사 기록까지 포함했다. 이번 작업은 코드·계약·기존 검증 근거를 읽은 평가와 계획 수립이며, 전체 서비스 재검증·배포·추가 PG 거래는 수행하지 않았다.

## 1. 일반적인 사용 수준의 정의

대상은 현재 재작성 완료한 열한 모듈과 이들이 제공하는 게임 스토어 **백엔드**다. 별도 대형 프론트엔드, 미완료·제거된 구 기능의 전부 복원, 실제 은행 송금까지를 묵시적으로 추가하지 않는다. 사용자·운영자가 재현 가능한 API 여정과 운영 절차를 기본 완료 기준으로 삼는다. 전용 화면은 별도 범위로 확정한다.

| 단계 | 완료 기준 |
|---|---|
| MVP 완료 | 제한된 범위의 핵심 계약을 구현하고 해당 검증을 통과함. 기존 완료 기록의 의미를 유지 |
| 기능 일반화 | 역할별 정상 업무가 끝까지 이어지고, 일상적인 실패·취소·재진입·사후 처리를 지원함. 상태·근거·다음 행동을 조회하고 운영자가 정해진 절차로 처리할 수 있음 |
| 엣지 케이스·성능 고도화 | 일반화된 계약을 대상으로 희귀한 교차 경합·복합 장애·대규모 재구축·다중 인스턴스·부하·비용을 측정하고 개선 |

일상적인 결제 실패, 결제창 이탈, 환불 후 정산 반영, 판매 중지, 비밀번호 분실은 일반화 단계에서 검토할 업무다. 중복 결제 방지·권한·금액 검증·업무 변경과 이벤트의 원자성·불확실한 금융 결과 보존도 매 단계의 필수 조건이다. 이 안전성을 나중 단계로 미루지 않는다.

단일 상품 주문·KRW·단일 PG·전체 ZIP·수동 심사는 현재 제품 범위로 유지할 수 있다. 장바구니·다중 통화·부분 환불·쿠폰·추천·델타 패치·DRM이 없다는 이유만으로 일반화 실패로 평가하지 않는다. 기능 수를 늘리는 것보다 선택한 기능의 전체 업무를 완성한다.

## 2. 환불 기능 평가

**선택한 전액 환불 범위에서 업무·정합성 처리는 MVP보다 상당히 확장됐다. 남은 우선 과제는 정산·보유권·운영 사용 흐름의 연결이다.**

| 평가 축 | 확인한 현재 상태 | 판단 |
|---|---|---|
| 고객 업무 | 접수·조회·자동 자격, 수동 승인/반려, 반려 뒤 고객 재심사, 확정 실패·실제 복구 뒤 명시적 재시도, 지연 안내 | 주요 고객 API와 일반 업무를 이미 지원 |
| 실행·이용권 | 지급 확인 → 실제 정지 → PG 실행, 완료 근거 보존, 확정 실패 뒤 실제 복구, 잘못된 승인 중단/복구 후 새 심사 | 모듈 간 책임과 주요 안전 조건이 잘 갖춰짐 |
| 금융 불확실성 | 같은 키/본문·원래 3시간, 내구 조회/재송신, 오류별 중단·재개, 전액 취소와 실행 성공 귀속 구분 | 이미 상당한 예외 처리를 구현. 이 방향의 무제한 확장은 우선순위를 낮춤 |
| 운영 API | ADMIN 심사·중단 조회/재개·장기 미확정 조회·불변 조사 기록 | 운영 기능은 있으나 실제 Auth ADMIN·Gateway·서비스를 잇는 최신 전체 여정은 미완료 |
| 프로젝트 전체 결과 | 환불 완료 후 매출/수수료/판매자 몫 조정 없음. 재구매 정책 미결. 이전 PAID의 지급 확인 누락 복구도 남음 | 일반화 단계의 주요 공백 |
| 검증·적용 | 모듈 DB/Kafka·경합/롤백·명세 검사와 실제 TEST 자동 환불 1건의 과거 근거. 최신 관리자 확장 전체 E2E·실제 운영 화면은 미검증 | 코드·통합 검사·전체 여정·실행 중인 버전을 구분해야 함 |

근거는 [현재 환불 인계](refund-session-handoff.md), [운영 조회·조사 기록 검증](pg-test-integration-plan.md#2026-10-29-장기-미확정-운영-조회와-조사-기록-a안), [환불 테스트 계획](testing.md#order-full-refund-tdd)이다. 최근 실행은 Payment 304/통합 196·Gateway 114/Redis 통합 1의 615건이며, 앞선 Order·License·공통 Kafka 검사와 중복 합산하지 않는다.

따라서 다음 작업을 조사 종결 상태·담당 배정·희귀 PG 응답 정책의 추가 설계로 자동 연결하지 않는다. 기존 미결 질문은 보존하되, 아래 G1~G3의 일반 업무 완성을 먼저 진행한다. 긴 미확정에 대한 실제 지원 절차는 필요하지만 새 금융 명령을 추가하는 정책과 분리한다.

## 3. Payment 모듈 평가

**모의 PG MVP를 넘어 PortOne TEST 승인·웹훅·환불을 갖췄지만, 실제 제공사 결제의 일반적인 생명주기와 정산 연결은 아직 부분 구현이다. 환불의 성숙도를 Payment 전체의 성숙도로 확대할 수 없다.**

1. `ReadPaymentCheckout`은 본인 PENDING 결제의 고정 식별자·금액으로 결제창 정보를 제공한다. `PortOnePgHttpGateway`는 서버 재조회에서 구매·금액·채널을 대조하고 승인 근거를 만든다. 서명 웹훅은 재조회를 깨우며 자체 성공 판정으로 쓰지 않는다.
2. 현재 PortOne 어댑터는 **PAID 이외의 상태를 모두 PgUnavailable로 처리**한다. `ResolvePayment`는 이를 PENDING·재조회 예약으로 유지한다. 모의 PG의 최종 거절 처리는 있지만, 그 사실이 PortOne의 검증된 결제 실패 처리까지 구현됐다는 의미는 아니다.
3. Order는 같은 상품의 PENDING·PAID 주문을 차단한다. 따라서 결제창 이탈·실패·미접수와 불확실한 통신 오류를 구분하고, 이어 결제/안전한 종료/새 주문으로 이동하는 계약이 필요하다. **브라우저 닫기나 시각 경과만으로 실패 확정하는 해법은 채택하지 않는다.**
4. PortOne 승인 결과는 현재 PG 비용을 미확정(null)으로 남긴다. Settlement는 SIMULATED 공급자·확정 비용만 수용하고 모의 PG 어댑터로 조립된다. 현재 두 모듈이 같은 실제 공급자 계약으로 끝까지 연결됐다고 평가할 수 없다.
5. `PORTONE_TEST`·TEST 채널 검증이 명시돼 있다. LIVE 결제·실제 PG 지급 자료·은행 입금·판매자 송금의 준비 완료를 뜻하지 않는다. 기능 일반화의 우선 검증 채널은 TEST로 유지하고 LIVE 전환은 별도 계약·설정·운영 검증 항목으로 둔다.

| 코드 근거 | 관찰 |
|---|---|
| [PortOnePgHttpGateway](../apps/payment/src/main/java/com/stove/payment/adapter/pg/PortOnePgHttpGateway.java) | PAID만 승인 결과로 변환, 비용 미확정, TEST 채널·주문/금액 검증 |
| [ResolvePayment](../apps/payment/src/main/java/com/stove/payment/core/service/ResolvePayment.java) | 오류와 미확정 결과를 PENDING으로 보존·재예약 |
| [ReadPaymentCheckout](../apps/payment/src/main/java/com/stove/payment/core/service/ReadPaymentCheckout.java) | 본인·공급자·PENDING 조건의 결제창 정보 조회 |
| [CreateOrder](../apps/order/src/main/java/com/stove/order/core/service/CreateOrder.java) | PENDING·PAID의 동일 상품 새 주문 차단 |
| [SettlementConfiguration](../apps/settlement/src/main/java/com/stove/settlement/config/SettlementConfiguration.java) · [PgCost](../apps/settlement/src/main/java/com/stove/settlement/core/domain/PgCost.java) | 모의 PG 조립과 SIMULATED·확정 비용 전제 |

이 관찰은 현재 코드의 범위 평가다. 실제 PortOne의 실패/만료 상태·재결제 가능 조건·정산 자료 제공 범위는 구현 착수 시 공식 계약과 사용 가능한 TEST 근거로 확인한다. 미확인 필드나 공급자 기능을 계획의 확정 사실로 만들지 않는다.

## 4. 열한 모듈의 일반화 공백

아래의 추가 기능은 권장 범위다. 기존에 합의한 계약은 유지하고, 판매 중지·재구매·계정 복구 등 새로운 정책은 해당 단계에서 확정한다. 완료된 MVP를 다시 재작성하는 계획이 아니다.

| 모듈 | 현재 확인한 기능 | 일반화 단계에서 닫을 범위 | 이후로 둘 확장 |
|---|---|---|---|
| Auth | 가입·역할·OIDC, RTR, 현재 비밀번호 확인 후 변경, 초기 운영 계정 생성 | 실제 역할별 접근 절차, 분실 비밀번호 복구와 계정 상태/권한 관리의 최소 계약·감사 | 소셜 로그인 다수·고급 MFA/인증 플랫폼 |
| Gateway | BFF·CSRF·토큰 릴레이·권한 라우팅, 관리자 API 경로 | 최신 API의 실제 역할별 여정·오류/진행 응답, 외부 웹훅의 재현 가능한 실행 구성 | 대규모 트래픽 제어·복잡한 배포 토폴로지 |
| Studio | 자료·전체 ZIP·썸네일, 버전·심사/출시 요청·재요청·이력 | 창작자의 평상시 수정/업데이트·요청 철회 정책, 프로젝트/빌드/요청 목록의 페이지 계약 | 대용량 분할 업로드·다중 채널·CI 배포 |
| Review | 불변 스냅샷·빌드 열람·수동 승인/반려 | 심사 목록/상태 조회의 사용성, 진행 중 요청 철회/보류 필요성 및 창작자 통지 계약 | 자동 심사·다단계 관문·정교한 담당 배정/SLA |
| Catalog | 현재 공개본·과거 출시 근거·상세/빌드/소유자 정본 | 판매 가능/중지/재개 정책과 Order의 실제 구매 허용 판단, 공개본 변경 이력 | 예약 출시·복잡한 롤백/다중 채널 |
| Store | 제목 검색·가격/최신순·페이지·상세, 초기 동기화 | Catalog 판매 상태 반영, 최소 분류/필터의 제품 범위 확정, 관리자가 수행할 기본 사본 대조/재동기화 | Elasticsearch·개인화·대규모 무중단 재색인 |
| Order | 단일 상품·불변 구매/청구액·본인 조회·결제 결과·환불 | 미결제 재진입/안전한 종료, 환불 후 재구매 정책, 고객에게 일관된 현재 진행/다음 행동 제공 | 장바구니·다중 통화·복잡한 할인 조합 |
| Payment | 모의 PG·PortOne TEST 승인/웹훅·내구 환불·관리자 복구/조사 | 검증된 결제 실패와 미확정 구분, 일반적인 결제 이탈/재진입, 같은 공급자로 정산까지 연결 | 다중 PG·다중 워커 최적화·처리량 향상 |
| License | 원구매 근거·상품 보유권·라이브러리·정지/복구 | PAID 후 지급 누락의 근거 기반 복구, 환불 완료/재구매 정책과 권한·구매 이력 연결 | 선물·기간제·기기/좌석 권한 |
| Download | 현재 공개 ZIP·권한/빌드 대조·HEAD·만료 URL, 정지 시 신규 접근 거절 | 결제/지급 대기·정지·파일 없음의 구분, 업데이트·판매 중지 정책과 기존 보유자 접근의 전체 여정 | 델타 패치·다중 플랫폼·CDN/DRM 최적화 |
| Settlement | 모의 PG 거래/비용·판매자 배분·월 마감·지급 명세 대사 | 현재 공급자 거래/비용 자료, 환불 조정·마감 전후 반영·판매자 순액 조회 | 실제 은행 송금 자동화·복잡한 세무/다중 PG |

Studio·Review·Catalog의 책임 경계는 유지한다. 예를 들어 판매 가능 상태는 Catalog의 정본에서 정의하고, Store에 복사하며, Order가 구매 시 정본 계약으로 확인한다. 공개 노출 중지와 기존 구매자의 다운로드 금지를 같은 정책으로 간주하지 않는다. 분류·필터가 필요하면 Studio의 자료 → Catalog 공개 계약 → Store 조회를 함께 설계한다.

현재 구현의 구체적인 근거는 [Studio](studio-simplification-plan.md), [Review](review-simplification-plan.md), [Catalog](catalog-mvp-plan.md), [Store](store-mvp-plan.md), [Auth/BFF](auth-bff.md), [License](license-mvp-plan.md), [Download](download-mvp-plan.md), [Settlement](settlement-mvp-plan.md) 완료 기록과 각 모듈 소스다. 문서의 당시 제외 범위를 현재 미구현으로 일괄 복사하지 않고, 이후 환불 확장을 대조했다.

## 5. 권장 실행 순서와 단계별 완료 조건

기간·완료율을 임의로 산정하지 않는다. 각 단계는 최소 계획 → 필요한 정책 선택 → TDD·구현 → 관련 통합/여정 검증 → 완료 기록 순서로 진행한다. 이미 통과한 다른 기능의 전체 재검사는 변경 범위와 의존성에 맞춰 선택한다.

| 순서 | 작업 묶음 | 의존성·완료 조건 |
|---|---|---|

G1~G4에서 필요한 계정·권한·지표·기본 복구는 해당 단계에 함께 구현한다. G5는 그 공통 운영을 전체적으로 닫는 단계이며 보안을 그때까지 유예하는 뜻이 아니다. G2의 재구매가 허용되지 않는 정책으로 정해져도 일관된 안내·거절과 이력 보존을 검증하면 해당 정책의 완료가 가능하다. 허용 시에는 구매 근거/보유권 세대와 과거 이벤트로부터 새 권한을 보호하는 계약까지 포함한다.

### G1에서 바로 시작할 구체적 작업

**첫 쟁점은 PortOne에서 검증된 결제 실패를 Payment·Order에 어떻게 확정 반영할지다.** 현재 존재하는 모의 PG 실패 모델·OrderPaymentFailed를 대조하고, 실제 제공사 응답의 식별자·원구매·금액·확정성을 확인한다. 결제창을 닫은 사실·404·타임아웃을 이 실패 근거에 섞지 않는다.

이후 고객이 PENDING 주문으로 돌아왔을 때 기존 결제를 이어갈 조건과 종료할 조건을 정한다. 기존 정책은 확정 FAILED 뒤 새 requestId의 새 주문이며, 같은 주문에서 새 결제 시도를 허용할지는 별도 선택이다. 만료/종료를 추가한다면 늦은 승인의 처리와 PG에서 더 결제되지 않음을 보장할 수 있는 경계를 함께 정한다. 보장할 수 없는 건은 미확정·조회/운영 확인으로 남긴다.

산출물은 결제 상태별 근거/다음 행동 표, API·이벤트 변경, 고객용 오류/진행 계약, 단위·DB/Kafka·PG HTTP 계약 검사, 필요한 TEST 채널 여정 기록이다. 단위 테스트 수 증가를 기능 완료 조건으로 삼지 않는다.

### G3에서 먼저 정할 계약

- 실제 사용 가능한 결제 거래·PG 비용·지급 자료의 공급자/입수 경로. API 또는 파일 등 확인 가능한 근거를 사용하고, 공급자 자료가 없으면 해당 대사를 미완료로 표시한다.
- 승인 시 비용 미확정과 후속 비용 확정. 비용이 없다고 0원으로 만들거나 모의 PG 비용을 실제 비용으로 대체하지 않는다.
- 전액 환불의 원매출 연결, 판매자 배분·플랫폼 수수료의 조정과 실제 PG 비용 반환 여부. 현재 플랫폼 전액 부담 정책은 사용자 변경 전까지 유지한다.
- 마감 전 환불과 마감 뒤 조정의 귀속/상계. 원매출·확정 마감을 덮어쓰는 대신 감사 가능한 조정 방식을 합의한다.
- 환불 확인 사실의 발행 주체와 수신 계약. Settlement의 포트는 Settlement가 소유하고 Payment를 조회 프록시나 정산 실행자로 만들지 않는다.

실제 은행 입금·판매자 송금·세무 업무는 별도 외부 계약과 범위 확정이 필요하다. 이를 지원하지 않는 상태에서는 해당 기능을 완료로 표기하지 않는다.

## 6. 일반화 단계의 전체 완료 판정

아래 행렬을 최신 계약으로 실행하고 근거를 남긴다. 공급자 응답 픽스처, 실제 모듈 간 처리, 실제 TEST 금융 동작을 각각 구분한다. 역할·금액·구매 출처·내구 기록의 정합성은 모든 행에서 유지해야 한다.

| 여정 | 결과까지 확인할 것 |
|---|---|
| 가입/로그인·계정 복구 | 본인 인증·역할, 복구/상태 변경 후 세션·토큰 정책과 감사 |
| 자료 생성→심사→출시→검색 | 불변 심사/출시 근거, 공개 정보·판매 가능 상태의 일관성, 수정과 재출시 |
| 구매 성공→지급→다운로드 | 실제 사용자 인증, 서버 결제 확인, Order·Payment·License·저장소의 연결 |
| 결제 실패/이탈→재진입 또는 종료 | 실패와 미확정의 구분, 동일 상품의 구매 제한 해소/이어 결제, 늦은 승인과 중복 청구 방지 |
| 자동/수동 환불·반려 | 최신 ADMIN 경로·결정 이력·실제 정지 선행·PG 확인·고객 상태·신규 다운로드 제한 |
| 환불 확정 실패→복구→고객 재시도 | 실제 License 복구 전 재시도 차단, 새 정지와 시도, 원래 자격/구매 보존 |
| 지급 확인 누락·일상적 처리 중단 | 원래 근거의 재전달/복구로 진행, 운영자가 대상·사유·다음 행동 확인 |
| 구매/환불→매출·월 마감 | 같은 공급자의 거래·비용 근거, 환불 조정·판매자 순액, 마감 뒤 조정, 미확정 자료의 명시 |
| 업데이트·판매 중지/재개 | 신규 구매와 기존 보유자 다운로드가 합의한 각각의 정책을 따름 |

공통 종료 조건은 다음과 같다.

1. 각 필수 여정이 API·사용자/운영자 절차로 재현되고, 일상적인 미완료 건의 주체와 다음 행동이 명확하다.
2. 현재 계약의 관련 단위·통합·여정 검증이 통과하고 금전·보유권·정산의 중복/위조·근거 없는 전이가 없다.
3. 실행한 소스·설정·마이그레이션·공급자·계정 역할·검증 범위를 기록한다. 코드만 최신인 상태를 최신 런타임 검증으로 보고하지 않는다.
4. 실제로 지원하지 않는 LIVE 결제/지급·전용 화면 등은 명시돼 있고, 필수 일반 업무를 “후속”으로 남긴 채 완료 표시하지 않는다.
5. 남은 백로그가 새로운 제품 범위·희귀 예외·성능/규모 개선인지 구분돼 있다.

기존 `e2e/`에는 재작성 전 API를 사용하는 테스트도 남아 있고 기본 빌드의 전체 여정 실행과도 구분된다. 구 시뮬레이터·쿠폰/정산 경로를 새 요구사항으로 복원하지 않는다. 현재 완료 모듈의 계약과 `tools/verification` 실행 근거를 기준으로 유효한 인수 시나리오를 선정·갱신한다.

## 7. 이후 고도화의 순서

일반화가 끝나면 먼저 실제 사용 패턴과 목표 부하·허용 지연을 정하고, 현재 버전의 종단 지연·처리량·DB/PG 호출 수·대기열·복구 시간을 측정한다. 과거 [성능 기록](performance.md)의 수치를 현재 시스템의 보장으로 쓰지 않는다.

그다음 병목과 영향에 따라 다중 워커/임대·Kafka 소비/릴레이·쿼리/인덱스·검색·큰 파일/다운로드 경로를 개선한다. 희귀 동시 금융 결과·재투입 순서·장시간 외부 장애·DB 유실·보존/재구축도 영향 순으로 검증한다. 검색 엔진 교체·캐시·새 인프라는 측정이나 실제 기능 요구가 있을 때 선택한다.

환불의 조사 종결·담당 배정·추가 알림, 부분 환불·다중 PG 같은 항목은 각각 운영 고도화 또는 제품 범위 확장으로 분류한다. 현재 지연 조회와 안전한 결과 확인은 유지하며, 시간 경과만으로 실패·복구·새 PG 키를 만드는 정책으로 바꾸지 않는다.
