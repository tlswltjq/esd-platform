# G3 PG 비용의 업무 반영 월 연결과 지급일별 대사

**후속 테스트 정비:** 현재 기본 검증은 [테스트 경계 정비·176건](settlement-test-boundaries-verification.md)을 따른다. 아래 167건은 당시의 합성 LIVE DB 검증 기록이며 원자료를 보존한다. 이후 운영 제약을 해제하던 픽스처를 제거하고 계약 검사와 현재 허용 입력의 DB 검사를 분리했다. 정상 LIVE 입력과 비용 저장/SQL 집계의 전체 DB 성공 검증은 아직 공백이다.

2026-11-02. 사용자는 판매 월과 PG 지급일이 다를 수 있는 이유, 두 기준의 조회와 기술 설계를 확인한 뒤 `실행`을 지시했다. [결정 45](decisions.md#pg-cost-business-month-and-payout-date)를 적용한다. 비용 부담·판매자 마감·전액 환불 배분/월 정책은 기존 합의를 유지한다.

## 구현

기존 `SettlementSale.settlementMonth`와 `SettlementRefund.settlementMonth`를 업무 반영 월로 재사용한다. 실제 거래 발생 월이나 수집일로 다시 계산하지 않는다. PG 원본의 `dueDate`는 PG가 보고한 지급일이며 토스페이 공식 문서상 계좌 입금일이다. 이전 논의의 ‘지급 예정일’ 표현을 바로잡았고 독립 은행 실수령 확인과 구분한다.

V12는 `settlement_pg_cost_posting`과 지급일/미완료 재대사 인덱스를 추가한다. 기존 원본·판매자 월·이행 파일은 변경하지 않는다. 원본 PG 정본 거래(`source_entry_id`)를 유일 키로 하며 원매출·선택적 환불·판매자·업무 반영 월·`LINKED_BUSINESS_MONTH_V1`·검증 명세 ID·최초 검증 시각을 불변 저장한다. 수수료·VAT·지급일은 기존 정본 원본을 참조한다.

나중에 검증한 같은 결제 묶음에서 `AMBIGUOUS_PAYMENT` 또는 `EXCESS_REFUND`가 발견되면 기존 연결의 `check_code`를 갱신한다. 원본·업무 반영 월·최초 검증 기록은 유지하고 해당 연결은 현재 확정 비용 집계에서 제외한다. 월 금융 조회는 다시 미확정으로 표시하며 지급일 항목은 충돌 코드와 기존 연결을 함께 보여준다. 근거가 약한 IDENTITY_UNVERIFIED 등의 관측만으로 기존 검증 연결을 덮어쓰지 않는다.

`ReconcilePgStatement`는 기존 명세 잠금 뒤 같은 가맹점·환경·결제 토큰의 정본 거래를 정렬 잠금하고 매출/환불·원승인·상점/채널·거래 키·금액을 대조한다. 대사와 비용 연결은 같은 트랜잭션에서 저장한다. 이전 연결은 내용만 대조하고 최초 월·검증 명세/시각을 보존한다. `source_entry_id` 유일 제약과 정본 잠금으로 서로 다른 DUE/SETTLE 수집본의 동시 첫 연결도 하나로 수렴한다.

여러 PG 환불 행은 내부 전액 환불과 관측 합계가 일치해야 한다. 새 관측으로 합계가 완성되면 해당 결제 묶음의 과거 행도 함께 연결한다. 명세 항목의 상태는 각 명세 재대사 때 갱신되며 지급일 항목 조회는 저장된 비용 연결을 함께 표시한다. 부분 관측으로 환불 비용 확인을 완료하지 않는다.

HTTP 수집은 기존처럼 업무 트랜잭션 밖에서 수행한다. 원본은 선행 커밋하므로 연결 저장 실패 뒤에도 보존된다. 설정된 수집 주기의 마지막에 `ReconcilePendingPgStatements`가 저장된 RECEIVED/PENDING을 한 번에 최대 100개씩 ID 커서로 재대사한다. 실패를 격리하고 다음 순회에서 재시도하며, 원본 수집 lookback 밖의 날짜도 PG 재호출 없이 처리한다. 스케줄은 기존 `enabled`·`scheduled-enabled`가 켜진 경우에만 실행되며 실제 런타임 설정은 바꾸지 않았다.

## 조회와 금액 의미

| 조회 | 기준과 제공 범위 |
|---|---|
| 기존 ADMIN GET `/api/v1/settlements/months` | 업무 반영 월의 매출 비용과 환불 비용 반환을 조합. 기존 판매자 마감본은 보존 |
| 새 ADMIN GET `/api/v1/settlements/pg-payouts` | `merchantId`·`environment`·`month` 필수. 원본 보고 지급일 월별 거래액·수수료·VAT·순액과 연결 건수·수집된 DUE 일자 수 |
| 새 ADMIN GET `/api/v1/settlements/pg-payouts/items` | 같은 범위의 정본 거래 페이지. 보고 지급일·금액·대사 코드·업무 반영 월·비용 연결 ID·검증 명세 ID |

Gateway의 기존 ADMIN 정산 범위가 새 경로를 포함한다. Settlement의 GET ADMIN 규칙을 명시적으로 추가했고 CREATOR·MEMBER/익명에 공개하지 않는다. 조회 기준은 `PG_REPORTED`이며 지급일 조회는 수집본 헤더의 합계를 누적하지 않고 중복 없는 정본 거래를 집계한다. 명세 수집 범위 전체가 월 전체를 보장하는 것은 아니다. `collectedPayoutDayCount`와 관측 거래 수를 제공하고 `MATCHED_REPORTED`는 관측 거래의 내부 연결이 일치한다는 뜻이다. 은행 잔액·실수령 완료·월 전체 자료 완비를 뜻하지 않는다. 미관측은 `NO_EVIDENCE`, 수집한 DUE의 빈 관측은 `EMPTY_REPORTED`로 구분한다.

기본 금융 요약의 `pgFeeAmount`는 매출 비용(수수료+VAT)에서 확인된 환불 반환(수수료+VAT)을 뺀 순비용이다. `platformNetAmount`는 환불 조정 후 플랫폼 몫에서 그 순비용을 뺀 금액이다. 환불만 반영된 월은 순비용과 플랫폼 잔여액이 음수일 수 있다. 미확인 거래가 있으면 두 값은 NULL로 둔다.

기존 `confirmedPgFeeAmount`·`salePgFeeAmount`는 승인 비용의 부분합/확인 총액 의미를 유지한다. `refundPgFeeReturnAmount`·`confirmedRefundPgFeeReturnAmount`, 승인 VAT·반환 VAT, `confirmedNetPgCostAmount`를 추가한다. VAT 총액도 미확인이면 NULL이다. 명시적으로 보고된 반환 0원은 근거가 확인된 0원으로 구분한다. 기존 모의 비용은 기존 저장소에서 조합하며 실제 비용 원장으로 복사하지 않는다.

이 확인 범위는 현재 수집 경로가 보고한 수수료·VAT 및 반환이다. 일반 API 밖 카드 차액 정산·별도 비용 자료를 포함한 최종 회계 이익·세무 처리를 보장하지 않는다.

## 검증 방법과 증거 경계

로컬에서 코드·문서를 편집하고 모든 Gradle·서비스·DB/Kafka 검증은 `ssh sng`의 `/tmp/esd-pg-cost-posting-20261102.pLSbPcJ4/work`에서 수행했다. 이전 아키텍처 검증본을 별도 디렉터리로 복사하고 공유 서비스·이전 검증본은 수정하지 않았다. 실행 원자료는 Git 제외 `runs/g3-pg-cost-posting-20261102/`에 보존한다.

먼저 `PgCostPostingTest`만 전송해 미구현 타입 두 개가 없는 컴파일 Red를 확인했다. 최초 구현 뒤 단위·아키텍처와 통합 컴파일을 통과했다. 첫 집중 통합은 새 ADMIN 경로 등록 누락과 합성 LIVE 픽스처의 FK 변경 순서로 13건 중 6건이 실패했다. ADMIN GET 규칙을 추가하고 픽스처는 매출을 같은 트랜잭션에서 원래 ID·값으로 재삽입하여 FK를 보존하도록 고쳤다. 수정 뒤 집중 13건이 통과했으며, 이후 lookback 밖 지연 근거 재대사와 동시 최초 연결을 보강했다.

첫 전체 게이트 165건 성공 뒤 최종 검토에서, 뒤늦은 충돌 관측이 기존 비용 연결을 확정 집계에서 보류하지 않는 문제를 발견했다. 두 실제 DB/HTTP 회귀 사례를 변경 전 구현에 실행해 **두 건 모두 AssertionFailedError**를 확인했다. 현재 대사 상태를 보존하는 비용 연결·집계를 보완해 전체 게이트 **167건**을 다시 통과했다. 선행 165건 성공 증거는 별도 `first-gate-evidence.tar.gz`에 보존한다.

**실제 LIVE 승인 접수·가맹점 매핑·실명세 검증은 없다.** 운영 `PgEvidence`·`PgFunding`·V9 CHECK는 여전히 TEST 계약이다. 성공 대사의 DB 검증은 명시적 합성 미래 LIVE 근거 픽스처이며, 테스트 전용 컨테이너 안에서 V9 funding CHECK를 일시 제거하고 합성 원매출/승인에 LIVE 값을 넣는다. FK는 유지하고 각 테스트 종료 시 자료를 정리한 뒤 원래 V9 CHECK를 그대로 복원한다. 이 픽스처는 실제 LIVE 입력 경로를 검증한 것이 아니며 운영 스키마·허용 계약을 완화하지 않는다. 현재 TEST 거래는 실제 비용 미확정으로 유지된다.

주요 검증은 다음과 같다.

- 마감된 10월 매출의 늦은 비용 330원을 10월 금융 조회에 연결하고, 같은 거래를 11월 지급일 조회에서 한 번 집계. 판매자 마감본 전체 동일.
- DUE/SETTLE 재수집·동시 최초 재대사 후 비용 연결 단일화와 최초 검증 기록 보존.
- 여러 환불 행의 전체 합계 전에는 미확정, 완성 뒤 과거 행까지 연결. 환불 조정 월의 반환 220원·VAT 20원과 음수 순비용·플랫폼 잔여액 확인.
- 명시적 반환 0원과 미도착 NULL 구분, 미연결 원본의 지급일 조회 노출, ADMIN·CREATOR·익명 경계 및 범위/월 검증.
- 실제 DB CHECK로 비용 INSERT 실패를 주입해 대사 변경 롤백·원본 보존을 확인하고 저장 원본 재대사로 복구.
- 수집 lookback 밖의 날짜와 실패한 원본의 재대사에 PG HTTP 호출이 추가되지 않음.
- 늦은 모호한 승인·초과 환불 관측 시 최초 비용 연결/검증 기록 보존과 현재 확정 보류.
- V1–V11 체크섬과 기존 매출·비용·마감·모의 명세·불변 PG 원본/페이지/연결 자료를 V12에서 보존.
- OpenAPI 19개 경로·21개 연산과 기존 경로·필드 보존. 명세 갱신 실행과 최종 비갱신 검증을 구분.

## 최종 게이트

최종 실행은 필터와 명세 갱신 옵션 없이 `CI=true ./gradlew :apps:settlement:check :apps:settlement:bootJar --console=plain`이다. 최종 게이트는 **105개 단위·아키텍처 + 62개 통합·이행 = 167건**을 통과했고 실패·오류·건너뜀은 0건이다. 아키텍처는 47건이며 통합 62건에는 과거 DB 이행 2건이 포함된다. 실행 명령 경과 시간은 105.961초다. 이전 집중 성공이나 명세 갱신 실행의 같은 검사를 최종 수에 중복 합산하지 않는다.

최종 소스·Gradle·명세 **1,316개**의 SHA-256이 로컬과 OCI에서 일치한다. 이전 아키텍처 검증 작업본의 **1,304개**도 원래 해시를 보존한다. bootJar SHA-256은 `58c654f4547fc31875c51ae51e696c6abb726d8c12e4093acb79a46883aeffb6`이다. 최종 게이트 뒤에는 문서만 편집했다.

전후 Docker 스냅샷이 완전히 같다. 기존 컨테이너 **23개**의 ID·시작 시각·재시작·실행/건강 상태·마운트, 볼륨 **57개**를 보존했고 새 잔여 자원은 없다. 원자료는 `runs/g3-pg-cost-posting-20261102/collected/`의 최종 XML·실행 명령·로그·manifest·`verification-summary.json`이다.

실제 제공사 조회·승인·취소·은행 실입금 확인·판매자 송금·기존 런타임 배포는 수행하지 않는다. API 밖 비용 자료·음수 잔액 이월/회수·P4 재구매와 G3 전체 완료는 별도다.
