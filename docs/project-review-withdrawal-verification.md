# 단일 심사·출시와 명시적 철회 구현·검증

2026-11-03 구현·관련 검증 완료. 기준은 `5c08fb1`과 이번 작업의 로컬 변경이다. [정책·분석](project-review-withdrawal-analysis.md), [결정 53~63](decisions.md#review-withdrawal-first-committed-result)을 따른다. 모듈별 최종 검사 695건과 실제 역할별 여정 3건을 통과했다. G4 전체 완료·공유 환경 배포를 뜻하지 않는다.

## 적용한 동작

- Studio는 프로젝트의 모든 버전을 통틀어 진행 중 심사와 출시를 각각 1건으로 제한한다. 철회 처리 중에도 유지한다. 다음 버전의 편집·심사는 이전 출시 처리 중에 진행할 수 있다.
- 현재 작업본의 요청과 버전에 독립적인 activeReviewRequest·activeReleaseRequest를 구분한다. 현재 버전과 일치하는 승인 스냅샷으로만 출시한다. 승인 자체는 공개를 수행하지 않는다.
- 제출은 requestId·contentVersion, 철회는 requestId·명시적 대상 요청·선택 reason을 받는다. 같은 명령은 같은 요청·영수증으로 수렴하고, 충돌 본문은 거절한다. 오래된 명령을 재전송해 현재 작업본을 새로 제출하지 않는다.
- 철회는 202 내구 접수와 no-store 영수증 조회를 제공한다. PENDING에서 WITHDRAWN 또는 DENIED로 확정되며 실제 정본 결과·행위자·시각·사유를 보존한다. 조회는 소유자와 명시적 대상에 제한한다.
- Review는 검토 착수 후에도 최종 판정 전 철회를 허용한다. 승인·반려·철회 중 먼저 커밋된 결과를 유지한다. 동일 자료의 새 심사는 허용하지만 철회한 과거 요청을 다시 열지 않는다.
- Catalog는 출시 원본과 Inbox를 먼저 내구 접수한 뒤 자동 작업으로 공개한다. 공개본·결과/상품 Outbox·작업 완료를 원자 저장한다. 실패는 같은 요청으로 재개하고 재시도 근거를 ADMIN 읽기 전용 API로 제공한다.
- 공개 전 철회가 먼저 확정되면 해당 요청은 공개하지 않는다. 공개가 먼저 확정되면 결과를 유지한다. 출시 철회 뒤 같은 승인본을 새 명령으로 다시 출시할 수 있다.
- 업데이트의 새 공개가 확정되기 전까지 기존 공개본을 유지한다. 철회와 재출시는 기존 판매·노출·다운로드 제어를 초기화하지 않는다.

### DB 이행

Studio V26은 명령/영수증 테이블과 활성 심사·출시의 nullable 생성 열 유일 키를 추가한다. Review V11은 활성 심사 유일 키·철회 감사/의사·요청 잠금을, Catalog V15는 공개 작업·철회 이력·요청 잠금을 추가한다.

기존 활성 심사·출시가 프로젝트별로 여러 건이면 유일 키 이행이 실패한다. 과거 이력은 삭제하거나 임의로 최신 한 건을 선택하지 않는다. 기존 데이터 보존·중복 거절·최종 종료 후 다음 요청 허용을 실제 MySQL로 검증한다. 이번 실행은 격리 테스트 DB의 이행이며 공유 업무 DB를 전환하지 않는다.

적용 전 각 업무 DB에서 다음 조회 결과가 비어 있는지 확인한다. 충돌이 있으면 정본 결과·미완료 명령·Outbox를 대조해 별도 전환한다. Studio V26은 여러 DDL 문장이므로 일부 적용 뒤 실패한 경우 무조건 repair 후 재실행하지 않고 실제 스키마를 먼저 대조한다.

~~~sql
-- Studio DB
SELECT project_id, COUNT(*) FROM studio_review_request
WHERE status='REQUESTED' GROUP BY project_id HAVING COUNT(*)>1;
SELECT project_id, COUNT(*) FROM studio_release_request
WHERE status='REQUESTED' GROUP BY project_id HAVING COUNT(*)>1;
-- Review DB
SELECT project_id, COUNT(*) FROM project_review
WHERE status='REQUESTED' GROUP BY project_id HAVING COUNT(*)>1;
~~~

### 호출부·배포 순서

심사/출시 POST의 requestId·contentVersion은 새 필수 본문이다. 기존 본문 없는 호출부는 함께 교체해야 한다. 소유자·승인본은 서버 근거로 정하고 본문에서 신뢰하지 않는다.

Review/Catalog의 새 철회 요청 소비자와 Studio의 새 결과 소비자를 모든 대상 인스턴스에 준비한 뒤 철회 명령 경로를 사용한다. 구 소비자가 새 이벤트를 모른 채 처리 완료하지 않도록 한다. 원본 재전달은 eventId·요청 ID·버전·키·불변 스냅샷을 유지한다. 실제 공유 환경 배포는 별도 작업이다.

### TDD와 대상 검증

Review 도메인의 WITHDRAWN을 사람의 판정으로 허용하던 검사, Studio의 명령 종류/최종 결과 검증, 결과 이벤트 ID 재사용, 다른 버전의 진행 중 출시 중복 접수를 먼저 실패로 재현하고 후속 Green을 확인했다. 초기 동기화에서 실제 Java build 패키지를 누락한 컴파일 실패와 트랜잭션 밖 Mockito spy 설정 실패는 기능 Red로 세지 않는다.

### 실제 역할별 여정과 재시작

최신 `runtime-config-boundary`는 165.59초에 성공했다. Auth·Gateway·Studio·Review·Catalog와 전용 MySQL·Redis·Kafka·MinIO만 실행했다. 실제 PKCE 로그인한 창작자·다른 창작자·심사자·관리자 및 비로그인 요청을 사용했다. 새 PG 승인·취소 같은 금융 동작은 없다. 이전 성공 여정의 원자료도 보존하며 합산하지 않는다.

1. 자동 공개 작업만 중지한 상태에서 심사 철회·동일 자료 재신청·과거 버전 심사 차단·승인 후 비공개·출시 철회·같은 승인본 재출시를 확인했다. 이전 출시 처리 중 다음 버전 편집·심사는 허용하고 새 출시는 409로 거절했다.
2. Catalog 프로세스를 종료하고 자동 공개를 켜서 재시작했다. 저장된 요청의 공개 재개와 철회된 요청의 비공개 유지, 제출 당시 승인본의 공개를 확인했다. 이후 다음 버전을 명시적으로 요청해 업데이트 공개까지 확인했다.
3. 자동 공개를 켠 상태에서 기존 승인·출시·공개본 교체·작업본 분리 여정도 통과했다.

각 단계는 별도 테스트 JVM에서 1건씩 실행하고 XML을 단계별로 보존했다. 0건·건너뜀은 성공으로 인정하지 않는다. Review 읽기 전용 스토리지 계정의 실제 업로드·삭제 거절도 확인했다.

첫 실행의 포트 충돌은 서비스 여정 시작 전 인프라 준비 실패였다. 자체 자원을 정리했고 Docker 할당 포트를 피하는 스크립트로 보완해 새 격리 환경에서 다시 검증했다. 기존 공유 컨테이너를 중단하거나 포트를 변경하지 않았다.

## 보장 범위와 후속

공개 작업 중지는 공개 전 철회와 경합의 상태 일관성을 검증하기 위한 제어다. 기본 200ms poll은 최소 철회 유예시간이 아니며 사용자가 실수를 알아차리고 취소할 시간을 보장하지 않는다. 이미 공개된 상품을 되돌리거나 기존 URL/진행 중 다운로드를 자동 회수하는 기능도 아니다.

업데이트는 같은 프로젝트에서 반복 심사·출시한다. DLC에 공통 절차를 재사용하는 방향은 보존하되 별도 상품/프로젝트·본편 관계·구매/권한·환불·버전 호환 정책은 이번에 구현하지 않았다. 신규 자동 검사·검증 결과 해시 캐시·예약 출시도 후속 범위다.

이 검증을 Store·Order·Download까지 실행한 G4 전체 여정, 전체 일반화 완료, 실운영 배포나 실제 PG 금융 검증으로 확대하지 않는다. 현재 S3 확인은 기존처럼 Project 잠금 트랜잭션 안에서 수행하며 고비용 자동 검사나 성능 최적화를 새로 도입하지 않았다.
