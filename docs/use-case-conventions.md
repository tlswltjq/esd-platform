# 유스케이스 클래스 작성 규칙

[문서 목록](README.md) · [아키텍처](architecture.md)

`apps/*`의 `core.service`에 있는 업무 처리 클래스는 유스케이스 단위로 구성한다. 신규 클래스와 책임을 재구성하는 클래스부터 아래 규칙을 적용한다. 기존 클래스는 관련 기능을 변경할 때 점진적으로 정리하며, 이름만 맞추기 위해 전체 모듈을 일괄 변경하지 않는다.

## 책임의 경계

SRP의 판단 기준은 **변경 이유가 하나인가**다. 하나의 유스케이스를 완성하는 검증·도메인 변경·저장·이벤트 기록은 같은 클래스에서 조율할 수 있다. 메서드나 처리 단계마다 클래스를 만들지는 않는다.

- 업무 목적과 정책의 변경 이유가 다르면 별도 유스케이스로 분리한다. 가입, 비밀번호 변경, 운영자 계정 초기화가 이에 해당한다.
- 같은 업무에서 초기 값만 다른 경우에는 한 클래스의 명시적인 메서드로 표현할 수 있다. 크리에이터 가입과 일반 회원 가입은 현재 초기 역할만 다르므로 함께 둔다.
- 한 흐름에 별도 심사나 추가 검증 정책이 생겨 독립적으로 변경되기 시작하면 분리한다.
- 여러 유스케이스에서 반복되거나 독립적으로 변경되는 정책은 별도 협력 객체로 추출한다. 단순 위임만 하는 클래스를 의무적으로 만들지 않는다.

도메인 상태와 불변식은 `core.domain`에서 표현하고, 유스케이스 클래스는 필요한 도메인 객체·리포지토리·포트의 호출을 조율한다. 외부 연동 구현은 `infrastructure`에 두고 `core.port`를 통해 호출한다.

## 클래스와 메서드 이름

유스케이스 클래스는 **동사 + 대상**의 PascalCase 이름을 사용하며 `Service` 접미사를 붙이지 않는다. 이름으로 업무 동작을 드러내고, `core.service` 패키지로 계층을 표현한다. Spring 빈 등록에는 필요한 `@Service`를 그대로 사용한다.

| 업무 | 클래스 | 공개 진입점 |
|---|---|---|
| 계정 가입 | `RegisterAccount` | `registerCreator()`, `registerMember()` |
| 비밀번호 변경 | `ChangePassword` | `execute()` |
| 운영자 계정 초기화 | `BootstrapAccounts` | `execute()` |

공개 진입점이 하나인 유스케이스는 `execute()`를 사용한다. 같은 업무의 변형을 함께 제공할 때는 `registerCreator()`처럼 차이를 드러내는 동사형 메서드를 사용한다. 새 업무를 추가할 때 기존 클래스 이름이 포괄적이라는 이유만으로 관련 없는 진입점을 넣지 않는다.

호출부의 필드는 `registerAccount`, `changePassword`처럼 유스케이스 이름에 맞춘다. 테스트 클래스도 `RegisterAccountTest`처럼 대상 클래스 이름을 따른다. 요청 DTO는 `ChangePasswordRequest`처럼 용도를 명시하여 유스케이스 클래스와 이름이 충돌하지 않게 한다.

이 명명 규칙은 업무 유스케이스에 적용한다. 컨트롤러·리포지토리·포트·어댑터·공통 기술 컴포넌트는 각자의 역할을 나타내는 이름을 사용한다.

## 진입점과 설정의 역할

컨트롤러·리스너·스케줄러는 입력을 해석하고 유스케이스를 호출한다. 별도 조율이 필요하지 않으면 `core.service`를 직접 호출할 수 있다.

외부 이벤트는 `api.listener`의 모듈별 `*Mapper.from(...)`에서 봉투와 본문의 이벤트 ID·종류·메시지 키 일치를 검증한 뒤 내부 입력으로 변환한다. 업무 서비스와 도메인 모델은 `EventEnvelope`나 외부 이벤트 전체를 입력받지 않는다. 내부 입력의 필수 값과 값 자체의 불변식은 생성 시 보장하고, 기존 요청·소유자·금액·상태와 비교해야 알 수 있는 규칙은 업무 서비스와 도메인 모델에서 판단한다.

수신 입력에는 중복 판정·추적에 필요한 이벤트 ID·종류·발생 시각을 전송 방식과 무관한 값으로 포함할 수 있다. 순수 데이터인 공유 스냅샷은 MVP에서 재사용할 수 있다. 발행할 이벤트를 유스케이스에서 만들고 Outbox에 기록하는 것도 허용한다. 입력 변환을 위해 범용 공통 변환 계층이나 위임만 하는 서비스 클래스를 추가하지 않는다.

Inbox는 유스케이스의 같은 트랜잭션에서 처리한다. 중복 메시지를 먼저 생략하는 공통 래퍼로 업무별 동일 요청·동일 결과 비교를 건너뛰지 않는다. Catalog·Order의 내용 비교 순서와 Studio의 지연 결과 정책은 각 모듈의 규칙을 따른다.

설정과 시작 실행 클래스도 업무 로직을 유스케이스에 위임한다. 예를 들어 `config.BootstrapAccountsRunner`는 환경변수 값을 읽고 `core.service.BootstrapAccounts`를 호출하며, 계정 존재 확인·생성·역할 감사 기록은 유스케이스가 담당한다. 공개 가입과 운영자 초기화는 정책이 다르므로 저장 코드가 비슷해도 하나의 공개 가입 흐름으로 합치지 않는다.

## 트랜잭션과 검증

클래스 분리는 트랜잭션을 나누는 근거가 아니다. 함께 성공하거나 실패해야 하는 DB 변경은 유스케이스의 같은 트랜잭션으로 유지한다. 가입에서는 계정 생성·Outbox 등록 이벤트 기록·역할 감사 기록이 이에 해당한다. 이름 변경과 책임 추출만으로 기존 전파 방식이나 커밋 시점을 바꾸지 않는다.

외부 시스템의 호출은 DB 트랜잭션만으로 원자성을 보장할 수 없다. 외부 호출의 위치와 실패 처리는 기존 [트랜잭션·이벤트 설계](architecture.md#트랜잭션과-이벤트-전달)에 따라 결정한다.

리팩터링할 때 호출부·테스트·설정의 참조를 함께 변경한다. API 경로와 업무 동작을 바꿀 필요가 없는 변경에서는 기존 계약을 유지한다. 관련 모듈을 컴파일하고 기존 테스트로 동작을 확인하며, 정책이나 트랜잭션을 실제로 변경한 경우에는 해당 성공·실패 조건을 검증하는 테스트를 보완한다.
