# 측정 방법론 — 숫자를 믿어도 되는지 먼저 정한다

**부하를 거는 것은 k6 열 줄이면 된다. 어려운 것은 나온 숫자가 틀렸을 때 그걸 알아채는 것이다.**

이 리포는 그걸 비싸게 배웠다. [performance.md](performance.md) **7장은 통째로 무효 선언됐고**,
그걸 알아챈 유일한 이유는 대조군 한 줄이었다. 13장에서는 조건을 바꿨는데 차이가 안 나서
"영향 없음"으로 적을 뻔했는데, 실은 **부하가 아무것도 압박하지 않아 실험이 실패한 것**이었다.

아래 규칙은 전부 그런 사건에서 나왔다. 규칙마다 출처를 붙인다 —
**근거 없는 규칙은 다음 사람이 안 지키기 때문이다.**

측정 도구는 [scripts/perf/](../scripts/perf/), 결과와 판정은
[performance.md](performance.md) · [perf-tuning.md](perf-tuning.md) 에 있다.

---

## 0. 한 문장

**측정 스크립트가 하는 일의 대부분은 "얼마나 빠른가"가 아니라 "이 숫자를 믿어도 되는가"여야 한다.**

좋은 측정은 자기가 틀렸을 때 그걸 드러낸다. 아래 규칙은 전부 그 성질을 만드는 장치다.

---

## 1. 대조군이 **다른 숫자**를 내는지부터 확인한다

> **출처 — 7장.** 릴레이 개선 전후를 비교했더니 악화로 보였다.
> 그런데 **릴레이를 완전히 끄고 재도 같은 숫자가 나왔다.**
>
> ```
> 기준선 (개선 전)      74.1 RPS
> 개선 후               44.8 RPS   ← "개선이 성능을 망쳤다!"
> 릴레이 완전 비활성     44.9 RPS   ← 아니다. 측정이 망가진 것이다
> ```
>
> 대조군이 없었다면 **멀쩡한 수정을 되돌렸을 것이다.**

대조군은 결과를 확인하는 절차가 아니라 **측정이 살아 있는지 보는 계기판**이다.
비교를 시작하기 전에 이것부터 답해야 한다 — *두 조건이 실제로 달랐다는 증거가 무엇인가.*

9장은 그 증거를 `stove_outbox_pending` 으로 삼았다. 릴레이를 끈 조건에서 이 값이
**생성된 주문 수와 정확히 같아야** 한다.

```
릴레이 OFF   pending 5,398   = 생성된 주문 수 (하나도 발행되지 않았다)
릴레이 ON    pending 0
```

**두 조건이 서로 다른 숫자를 냈으므로 그 비교는 유효하다.** 7장에는 이 확인이 없었다.

대조군의 다른 형태로 **A → B → A** 가 있다. 마지막이 첫 번째와 같아야 한다 —
측정이 도는 동안 쌓이는 데이터의 효과를 배제한다.

```
12장   c=1 → c=3 → c=1     랙 최종 2,285 / 268 / 2,283
13장   c=1 → c=3 → c=1     랙 최종 5,756 /  353 / 5,741   (편차 0.3%)
```

## 2. "부하가 실제로 걸렸다"를 스크립트가 보장하게 한다

**"실패가 없다"와 "일이 일어났다"는 다른 명제다.** 전자만 확인하면 아무 일도 안 한 측정이 만점을 받는다.

k6 의 `check` 는 **세기만 하고 종료 코드를 바꾸지 않는다.**

```js
thresholds: {
  // 200 OK + 봉투 success:false 는 http_req_failed 에 안 잡힌다.
  // 이 줄이 없으면 전 주문이 거절돼도 지연 지표는 오히려 좋아지며 초록으로 통과한다.
  checks: ['rate>0.99'],

  // 도착률 기반에서 필수. maxVUs 가 모자라면 k6 는 요청을 아예 안 보낸다.
  // 목표 400 RPS 인데 실제로 120 만 나가도 http_req_duration 은 예쁘게 나온다.
  dropped_iterations: ['count<1'],
}
```

그리고 부하 형태는 **VU 기반이 아니라 도착률(arrival-rate) 기반**으로 짠다.
VU 기반은 응답이 느려지면 유입도 같이 줄어 **병목이 스스로를 가린다.**
적체는 유입을 고정해야 드러난다.

> **예외 — 재는 것이 처리량이 아닐 때.** `payment-callback.js` 는 "한 건이 끝까지 가는 데
> 걸리는 시간"을 재므로 VU 기반이다. 도착률로 두면 유입이 완료를 앞질러 VU 가 무한히 쌓인다.
> **시나리오의 executor 는 취향이 아니라 재려는 대상이 정한다.**

### 임계값은 1차 측정 후 다시 정해야 한다

처음 세우는 임계는 근거가 없다. 실측이 나오면 반드시 캘리브레이션한다.

> **아직 못 지킨 것.** `dropped_iterations: ['count<1']` 이 5회 중 4회 걸렸는데
> 실제 유실은 3,600건 중 **0~13건**이었다(12-7). 판정을 뒤집지 않지만
> **매번 빨간 임계값은 곧 아무도 안 보는 임계값이 된다.**

## 3. 판정 지표를 **측정 대상 밖에서** 가져온다

> **출처 — [D-026](defects.md#d-026).** 컨슈머 랙을 앱이 노출하는 지표로 판정했는데,
> 그 값은 컨슈머가 직전 fetch 응답에서 본 것이라 **fetch 가 멈추면 같이 멈춘다.**
> 실제 랙 113,517건 동안 **0** 을 보고했다.

```
앱 지표    "내가 마지막으로 본 랙"      ← 앱이 병들면 지표도 병든다
브로커     커밋 오프셋 vs 로그 끝       ← 앱이 죽어도 참
```

**측정 대상 자신에게 성적표를 맡기지 않는다.** 가능하면 한 계층 밖에서 잰다 —
큐는 브로커에게, DB 는 DB 에게, 지연은 클라이언트에서.

### 모르는 값을 0 으로 적지 않는다

D-026 을 만든 습관이 이것이다. `collect-lag.sh` 는 커밋 이력이 없는 파티션을
`unknown_partitions` 로 따로 센다. 0 으로 적는 순간 **"따라잡았다"와 "데이터가 없다"가
같은 그림**이 된다.

같은 이유로 랙과 **유입률**을 같이 남긴다 — 랙만 보면 "따라잡고 있다"와
"아무것도 안 왔다"가 구분되지 않는다. 11-2 의 "랙 0" 이 실은 후자였다.

## 4. 한계선 찾기와 비교하기를 분리한다

**포화 위에서 잰 값은 무엇을 바꾸든 "포화했다"만 알려준다.**

| 용도 | 부하 형태 | 쓰는 법 |
|---|---|---|
| 한계선 | 계단식 램프 (20→400 RPS) | 어디서 무너지는지 **찾기만** 한다 |
| 비교 | 고정 부하 | 관측된 한계선의 **절반 이하**에서만 판정 |

12장은 한계선 121.7 RPS 를 확인한 뒤 60 RPS 에서 비교했다. 이 순서를 지키지 않으면
두 조건이 둘 다 포화라 차이가 안 나거나, 잡음이 신호를 덮는다.

## 5. **압박 증거**를 같이 찍는다 — 없으면 음성 결과를 해석할 수 없다

> **출처 — 13-2.** `concurrency` 1 vs 3 을 팬아웃으로 쟀더니 완전히 똑같이 나왔다.
> 그런데 같이 찍어 둔 지표가 이유를 말해 줬다.
>
> ```
> 풀 active 최대   3 / 20      ← 커넥션이 남아돈다
> 풀 pending 최대  0           ← 기다린 스레드가 한 번도 없다
> 랙 최대          3           ← 컨슈머가 놀고 있다
> ```
>
> **압박이 없는데 노브를 돌린 것이다.** 이 상태의 "차이 없음"은
> "영향이 없다"가 아니라 **"이 실험은 질문에 답할 수 없다"**는 뜻이다.

조건을 바꿨는데 차이가 없을 때, 둘을 가를 수 있어야 한다.

- 정말 영향이 없다
- 부하가 그 자원을 건드리지 않았다

그래서 **바꾼 노브가 겨냥하는 자원의 포화도**를 항상 함께 남긴다.
풀이면 `pending`, 컨슈머면 랙, CPU 면 사용률.

### 포화도는 "꽉 찼나"가 아니라 "기다렸나"로 잰다

`hikaricp_connections_active` 가 최대치여도 `pending` 이 0 이면 풀은 충분한 것이다.
**대기가 서야 응답시간에 실린다.** 이 구분이 없어서 8-2 가 오래 열려 있었고,
`pending` 을 찍자 5회차 전부 0 으로 한 번에 닫혔다(13-5).

## 6. 조건마다 **동일한 초기 상태** — 그리고 지켰는지 확인할 수단

규칙은 9장이 세웠는데, **지켰는지 확인하는 수단**은 13장에서야 생겼다.

> **출처 — 13-8.** 회차 하나가 **시작 랙 5,686** 으로 출발했다(정상은 300 안팎).
> 컨슈머 오프셋 리셋이 그 회차에서 안 먹었다 — `--reset-offsets` 는 그룹에 활성 멤버가
> 없어야 하는데 `stop` 직후 브로커가 멤버를 아직 안 떨어낸 경합이다.
> 그 회차는 성공률 0% 가 됐고, 평균에 넣었으면 c=1 이 실제(50%)보다 나쁘게 나왔다.

**초기화는 DB 만이 아니다.** 큐·캐시·오프셋까지다. 그리고 DB 만 보면 깨끗해 보인다.
그래서 `run-session.sh` 는 `env.txt` 에 **시작 시점의 랙**을 남긴다.

**규칙을 세우는 것과 지켰는지 아는 것은 다른 일이다.** 확인 수단이 없는 규칙은
지켜졌다고 가정될 뿐이다.

### 사후 확인과 사전 확인은 다른 일을 한다

> **출처 — 14-6.** 같은 오염이 다시 났다. 시작 랙 21,971, 성공률 0%.
> 이번 원인은 경합이 아니라 드라이버의 변수 이름이었다 — `GROUPS` 는 **bash 내장 변수**라
> 대입이 먹지 않았고, 오프셋 리셋이 존재하지 않는 그룹에 **`rc=0` 으로 조용히 성공했다.**
> (같은 함정을 `collect-lag.sh` 가 `LAG_GROUPS` 로 피해 두었다. **적어 두었는데도 다시 밟았다.**)

13-8 은 회차가 **끝난 뒤** `env.txt` 로 알아챘다. 그것도 필요하지만, 그때는 이미 5분을 썼다.

```
사후 (env.txt 시작 랙)   →  회차를 버릴 수 있게 해 준다
사전 (부하 전 랙 측정)   →  회차를 낭비하지 않게 해 준다
```

**초기화 명령의 종료 코드는 초기화됐다는 증거가 아니다.** 되돌렸다고 가정하지 말고
되돌아갔는지 센다 — 리셋 직후 한 번, 부하 직전 한 번(재기동 구간에서 다시 설 수 있다).

## 7. 조건이 **실제로 걸렸는지** 매 회차 확인한다

**세 조건이 조용히 같은 값으로 돌면 비교가 통째로 거짓이 된다.**

`run-session.sh` 는 앱을 가리지 않고 컨테이너 환경변수를 훑어 `env.txt` 에 남긴다 —
릴레이 노브는 order 에, 컨슈머 노브는 payment 에 걸리므로 **하나만 보면 놓친다.**

환경변수 이름 규칙으로 표현할 수 없는 설정(`hibernate.jdbc.batch_size` 처럼 밑줄이 든 키)은
`SPRING_APPLICATION_JSON` 으로 주고 `/actuator/env` 로 **바인딩 소스까지** 확인한다
(perf-tuning.md 9절). 실제로 그렇게 확인했더니 **바인딩은 됐는데 효과가 없는** 경우가 나왔다 —
그 구분은 확인해야만 할 수 있다.

## 8. 환경을 **결과와 같은 폴더에** 남긴다

> **출처 — 10장.** "측정 환경이 변하면 그 전후 숫자는 비교가 아니라 무관한 값 두 개다."
> 그런데 그때 환경은 사람이 기억해서 문서에 적는 것이었다. **기억은 회차를 못 버틴다.**

환경이 결과를 얼마나 흔드는지는 이 리포에 사례가 셋 있다.

| | 같은 코드 개선의 개선폭 |
|---|---|
| 랩탑 (8GB) | **×3.08** |
| OCI Ampere (23GB) | **×5.25** |

같은 개선이 호스트에 따라 이렇게 다르다(perf-tuning 2절). 환경 기록이 없으면
이 둘은 그냥 모순이고, **느린 기계에서 잰 개선폭은 과소평가**였다는 결론에 도달할 수 없다.

## 9. 한 조건당 최소 2회 — 편차가 차이보다 작아야 유효하다

판정 기준은 하나다. **조건 안 편차 < 조건 사이 차이.**

```
9-3   조건 안 0.5ms / 1.7ms,  조건 사이 19ms       → 유효
12-4  조건 안 랙 2,119~2,285, 조건 사이 2,229 : 268 → 유효
13-7  조건 안 p95 160.7~180.8, c=3 이 그 안에 들어감 → 차이 없음
```

마지막 줄이 중요하다. **반복이 없으면 "차이 없음"을 말할 수 없다** —
비교 대상이 편차 범위 안에 있는지를 알 방법이 없기 때문이다.

## 10. 측정 중 호스트에 다른 부하를 올리지 않는다

> **출처 — 9장·10장.** 비교가 도는 중에 같은 호스트에서 CI 를 한 번 띄웠고,
> 그 회차의 p95 가 **59.66ms** 로 튀었다(같은 조건의 다른 회차는 42.60 / 43.12ms).
> 즉시 취소하고 그 회차를 버렸다.
>
> **규칙을 아는 것과 지키는 것은 별개였다.** 반복 측정이 그것을 잡아냈다 —
> 한 조건당 한 번만 쟀다면 오염된 값이 그대로 결론이 됐을 것이다.

측정 전에 `./gradlew --stop`, 잔여 JVM 정리, `load < 1.5` 확인.

## 절차 — 순서대로

```
1. 가설을 문장으로 적는다
     "X 를 바꾸면 Y 가 개선되고 대가는 Z 다"
     무엇이 나오면 가설이 틀린 것인지도 같이 적는다

2. 판정 지표를 고른다
     가급적 측정 대상 밖에서 (규칙 3)
     압박 증거를 같이 고른다 (규칙 5)

3. 스모크        경로가 살아 있나 — 여기서 깨지면 아래는 전부 무의미
4. 한계선        계단식. 찾기만 (규칙 4)
5. 조건 비교     한계선 절반 이하 고정 부하
     ├ 조건당 최소 2회                 (규칙 9)
     ├ 회차마다 동일 초기 상태 + 확인   (규칙 6)
     ├ 대조군 1회 — A → B → A          (규칙 1)
     └ 조건이 실제 걸렸는지 확인        (규칙 7)

6. 판정
     조건 안 편차 < 조건 사이 차이 인가
     압박 증거가 "부하가 걸렸다"를 말하는가
```

## 이 리포에서 각 규칙이 어디에 구현돼 있나

| 규칙 | 자리 |
|---|---|
| 부하가 걸렸는지 보장 | k6 시나리오의 `checks` · `dropped_iterations` 임계 |
| 판정 지표를 밖에서 | `collect-lag.sh` (브로커 오프셋), `kafka-exporter` |
| 압박 증거 | `collect-consumer.sh` 의 `pool_pending`, `collect-lag.sh` 의 랙 |
| 동일 초기 상태 + 확인 | `run-session.sh` 의 `RESET`, `env.txt` 의 시작 랙 **(사후)** |
| 〃 **사전** | `run-condition.sh` 가 리셋 직후·부하 직전 랙을 세고 넘으면 중단 |
| 압박 위에서 비교 | `run-condition.sh` 가 배경 부하를 깔고 `fanout` 을 겹친다 (13-2 의 실패에서) |
| 조건이 실제 걸렸는지 | `env.txt` 의 조건 오버라이드 (전 앱 훑기) |
| 환경 기록 | `env.txt` |
| 한 타임라인 | `run-session.sh` 가 수집기 넷을 k6 보다 먼저 켜고 나중에 끈다 |

## 아직 못 지키는 것

정직하게 남긴다. **규칙을 적어 두는 것과 지키는 것은 별개**라는 것이 9장의 교훈이다.

- **임계값 캘리브레이션** — `dropped_iterations` 가 과하게 빡빡하다(규칙 2).
  **다만 14장 4회차는 전부 0 이었다** — 재기동 뒤 45초를 두고 판정 구간을 시작한 회차들이다.
  임계가 빡빡한 것이 아니라 **워밍업을 안 준 회차가 걸렸던 것일 수 있다.** 아직 못 가렸다
- **한계선을 1회만 잰다** — 12장의 "60 RPS 는 절반 이하"라는 근거가 한 회차에 걸려 있었다.
  14-1 이 독립 회차로 120.91 RPS 를 냈다(12장 121.7). **이 항목은 이제 2회다**
- **측정 도구의 해상도** — perf-tuning 3절에서 종단 지연 중앙값이 안 변한 것처럼 보였는데,
  원인은 k6 시나리오의 폴링 간격 0.5초였다. `min` 이 네 회차 모두 517~522ms 로 같았던 것이 단서다.
  **도구가 결론을 가릴 수 있다** — 바닥값이 반복되면 그 자리를 의심한다
- **부하 시간 · 워밍업** — 13-7 이 12장을 뒤집은 이유가 60초 대 150초였다. 짧은 측정은
  재기동 직후 워밍업을 결과에 싣는다. **얼마나 길어야 충분한지는 아직 안 정했다.**
  14-5 가 여기에 정량적인 증거를 붙였다 — 같은 호스트·같은 조건인데 **배수 속도가 1.7배**
  차이 났고(c=1 19 → 33/s, c=3 52 → 75/s), 다른 것은 컨테이너가 얼마나 오래 떠 있었는가뿐이다.
  **지금 이 리포에서 가장 큰 측정 불확실성이 이것이다**
- **겹침 시점** — 14-4. 배경 부하와 팬아웃을 겹치는 시점이 c=1 성공률을 50% → 10~20% 로 바꿨다.
  **"압박 위에서 쟀다"는 것만으로는 조건이 특정되지 않는다** — 얼마나 밀린 위에서인지까지 적어야 한다

## 마지막 — 부정적 결과도 값이 있다

perf-tuning 5절이 JDBC 배치 튜닝을 시도했다가 **효과가 없다**는 것을 확인했다.
바인딩까지 검증한 부정적 결과였고, 그 덕에 배치당 고정비 20ms 와 건당 0.48ms 라는
비용 구조가 드러났다. **어디를 고쳐야 하는지는 안 되는 것을 지워서 알아냈다.**

13-5 도 같다. 커넥션 풀 가설이 기각됐다는 것은 "아무것도 못 얻었다"가 아니라
**자원 분리라는 큰 작업을 하지 않아도 된다는 것을 알아낸 것**이다.

무효 선언된 7장을 지우지 않고 남기는 이유도 이것이다 —
**무엇이 측정을 망쳤는지가 결론만큼 중요하다.**
