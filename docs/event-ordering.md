# 이벤트 순서는 어디서 깨지고, 어디서 지키는가

[D-013](defects.md#d-013)(발행 실패한 이벤트를 같은 애그리거트의 뒤 이벤트가 추월)을
고치면서 정리한 노트다. 결함 하나의 수정 기록은 `defects.md` 에 있고,
이 문서는 그 위층 질문을 다룬다.

> 순서 보장은 한 군데서 하는 일이 아니다. **어느 층에서 깨졌느냐에 따라 해법이 다르다.**

README 2절은 "메시지 키는 주문번호/상품코드 — 같은 애그리거트의 순서가 보장된다"고 말한다.
그 문장이 실제로 성립하려면 **세 층이 전부 제 몫을 해야 한다.** 한 층만 믿으면 조용히 뚫린다.

---

## 1. 순서가 깨질 수 있는 세 층위

```
[1] 프로듀서 층    send() 재시도가 앞선 in-flight 요청을 추월
[2] 발행자 층      Outbox 에서 꺼내 브로커로 보내는 순서가 틀림      ← D-013
[3] 컨슈머 층      받은 뒤 처리하는 순서가 틀림
```

세 층은 독립적이다. [1]을 막아도 [2]가 뚫리고, [2]를 막아도 [3]이 뚫린다.
아래에서 층마다 **무엇이 깨질 수 있고, 이 저장소가 현재 무엇으로 막고 있는지**를 적는다.

---

## 2. 먼저 — 주문 하나가 만드는 이벤트와 "짝"

순서가 쟁점이 되는 조건은 하나뿐이다.
**같은 토픽에 같은 파티션 키로 이벤트가 둘 이상 생길 때.** 그것을 여기서는 *짝* 이라고 부른다.

토픽은 애그리거트 단위이고 발행 주체가 곧 토픽 주인이다(`common/event/Topics.java`).
주문 하나가 살아 있는 동안 관여하는 것은 아래 셋이다.

| Outbox 주인 | 토픽 | 짝의 앞 (생성) | 짝의 뒤 (소멸) | 파티션 키 |
|---|---|---|---|---|
| order | `stove.order.v1` | `OrderCreated` | `OrderCanceled` | orderNo |
| payment | `stove.payment.v1` | `PaymentCompleted` | `PaymentCancelled` | orderNo |
| license | `stove.license.v1` | `LicenseIssued` | `LicenseRevoked` | orderNo |

세 줄이 전부 같은 모양이다 — **"만들었다" 다음에 "없앴다".**
순서가 뒤집히면 결과도 같다. 없는 것을 없애려다 실패하고, 그다음에 만들어서,
**없애려던 것이 살아남는다.**

정상 흐름에서는 짝이 동시에 PENDING 으로 놓일 일이 없다.
결제완료는 진작 발행돼 SENT 가 되고, 환불은 한참 뒤에 들어온다.
**창이 열리는 것은 앞 이벤트가 발행에 실패해 PENDING 으로 남아 있을 때뿐이다.**

```
payment 서비스의 outbox

id  | partition_key | event_type        | status
----|---------------|-------------------|--------
501 | ORD-1         | PaymentCompleted  | PENDING   ← 발행 실패, 재시도 대기
502 | ORD-1         | PaymentCancelled  | PENDING   ← 대기 중에 환불 요청이 들어옴
```

이 상태가 곧 [2]의 사고 조건이다.

서비스 **간** 순서는 Kafka 가 보장하지 않는다(토픽이 다르다).
그런데도 어긋나지 않는 이유는 **인과관계** 때문이다 —
license 는 `PaymentCompleted` 를 소비해야만 `LicenseIssued` 를 만들 수 있다.
앞 이벤트의 소비 결과로 뒤 이벤트가 태어나므로 순서가 자연히 잡힌다.
**따로 지켜야 하는 것은 언제나 한 Outbox 안의 짝이다.**

## 3. 층위 1 — 프로듀서: `enable.idempotence`

Kafka 프로듀서는 요청을 파이프라이닝한다.
`max.in.flight.requests.per.connection` 만큼 응답을 안 기다리고 연달아 보낸다.
여기서 1번 요청이 실패해 재시도되는 사이 2번이 먼저 브로커에 들어가면 **파티션 로그 순서가 뒤집힌다.**

```
전송:  [req1] [req2]  →  req1 실패 → 재시도
브로커 로그:  req2, req1        ← 순서 역전. 애플리케이션은 알 방법이 없다
```

전 서비스 `application.yml` 에 이미 걸려 있다.

```yaml
producer:
  acks: all
  retries: 3
  properties:
    enable.idempotence: true
```

`enable.idempotence: true` 면 프로듀서가 레코드마다 시퀀스 번호를 붙이고
브로커가 그 순서를 강제한다. 재시도가 일어나도 파티션 내 순서가 유지되고,
중복 기록도 브로커가 걸러낸다.

**이 층은 닫힌 문제다.** 다만 끄면 조용히 뚫리는 종류라, 설정에서 빠지지 않게 지켜야 한다.

## 4. 층위 2 — 발행자: D-013 과 키 웨이브

### 무엇이 문제였나

수정 전 릴레이는 배치를 id 순으로 돌면서 **실패한 건을 건너뛰고 계속 발행**했다.

```java
for (OutboxEvent event : batch) {
    try { kafkaTemplate.send(toRecord(event)).get(); event.markSent(); }
    catch (Exception e) { event.markFailed(...); }   // ← 기록만 하고 다음 건으로
}
```

2절의 501/502 가 한 배치에 들어오면 501 이 또 실패하고 502 만 나간다.
Kafka 는 **넣어준 순서대로만** 지켜주므로, 뒤집힌 순서를 충실히 보존한다.
license 는 발급되지 않은 라이선스를 회수하려다 `revoke()` 에서 그냥 `return` 하고,
뒤늦게 도착한 `PaymentCompleted` 로 라이선스를 **발급**한다.
**환불된 주문인데 라이브러리에 게임이 남는다.**

발행 실패는 브로커 장애만이 아니다. `acks: all` 단일 브로커 구성에서는
GC 한 번, 리더 선출 한 번에도 한 건이 실패할 수 있다.

[D-003](defects.md#d-003) 의 지수 백오프가 재시도 감내 시간을 10초에서 약 8분 30초로 늘렸는데,
그건 이벤트 유실을 막기 위해 필요한 수정이었다.
다만 **PENDING 이 살아 있는 시간이 그만큼 길어졌으니 추월 창도 같은 배율로 넓어졌다.**
결함 자체는 그 전부터 있었고, 백오프가 드러냈을 뿐이다.

### 무엇으로 고쳤나

발행 단위를 **한 건**에서 **한 키**로 바꿨다(`OutboxRelay#publishPreservingOrder`).

```
웨이브 1: [ORD-1의 1번, ORD-2, ORD-3, ...]  → 동시 발행, 1회 대기
웨이브 2: [ORD-1의 2번은 제외 — 1번이 실패했으므로 이번 회차 보류]
```

웨이브만으로는 **한 배치 안**까지다. 보류된 뒤 이벤트는 `next_attempt_at` 이 NULL 로 남는 반면
실패한 앞 이벤트는 백오프로 미래로 밀리므로, 다음 폴링에서 뒤 이벤트만 조회에 잡혀
그대로 추월이 일어난다([D-014](defects.md#d-014)). 그래서 실패 시
**같은 키의 뒤 이벤트에 앞의 `next_attempt_at` 을 전파해** 조회 대상에서 빠지는 시점까지 맞춘다.

파티션 키가 곧 **순서를 지켜야 하는 정확한 단위**라서, 이 구조가 두 가지를 한꺼번에 해결한다.

- **순서** — 앞이 실패한 키는 체인 전체가 다음 웨이브에서 빠진다. 추월이 구조적으로 불가능해진다.
- **처리량** — 대기 횟수가 *배치 크기(200)* 에서 *최장 체인 길이* 로 줄어든다.
  키가 주문번호라 한 배치에 같은 주문이 둘 이상 들어오는 일이 드물고, 대부분 길이 1 이다.

기존 코드는 **지켜야 할 순서는 깨면서, 안 지켜도 될 것까지 순차로 기다리고** 있었다.
정확히 거꾸로였고, 그래서 한 번의 수정으로 둘 다 풀렸다.

다만 **처리량에서 이 수정의 몫은 ×1.13 이다**(138.0 → 156.1 events/s). 고정 폴링 대기가
그대로 남아 있어서다 — 간판 수치 ×3.48 은 그 대기까지 걷어낸 뒤의 값이고,
그쪽은 순서와 무관한 별개 수정이다([performance.md](performance.md) 6장).

## 5. 층위 3 — 컨슈머: 지금은 안전하지만 조건부다

토픽은 파티션 3개다(`docker-compose.yml` 의 `KAFKA_NUM_PARTITIONS: 3`).
같은 키는 같은 파티션으로 가고, 파티션 안의 순서는 Kafka 가 보장한다.
리스너는 `concurrency` 를 지정하지 않아 컨테이너당 스레드가 1개이고,
`ack-mode: record` 로 한 건 처리할 때마다 커밋한다.

**현재 구성에서는 안전하다.** 깨지는 조건은 셋이다.

| 조건 | 왜 깨지나 | 대응 |
|---|---|---|
| 리스너 안에서 비동기 오프로드 | 스레드풀에 넘기는 순간 처리 순서가 도착 순서와 무관해진다 | 하지 않는다. 처리량이 필요하면 `concurrency` 를 올린다 |
| **파티션 수 증설** | `hash(key) % partitions` 가 바뀌어 같은 주문이 옛/새 파티션으로 갈라진다 | 증설 전에 해당 토픽을 완전히 배수하거나, 새 토픽 + 마이그레이션 |
| 논블로킹 재시도(`@RetryableTopic`) | 실패한 메시지가 재시도 토픽으로 빠져 뒤로 밀린다 | 쓰지 않는다. 이유는 [kafka-consumer-retry.md 6절](kafka-consumer-retry.md) |

`concurrency` 를 파티션 수까지 올리는 것은 **안전하다** — 스레드마다 파티션을 하나씩 맡으므로
같은 키는 여전히 한 스레드가 순서대로 처리한다. 파티션 수를 넘겨 올리면 노는 스레드만 생긴다.

파티션 증설이 위험하다는 점은 잊기 쉽다. 운영 중 "처리량이 부족하니 파티션을 늘리자"는
가장 자연스러운 대응인데, 키 기반 순서 보장에 의존하는 시스템에서는 그것만으로 순서가 깨진다.

## 6. 일반적인 해법 카탈로그

층위 2(발행 측)를 중심으로, 이 문제에 쓰이는 표준적인 접근들을 정리한다.
채택하지 않은 것도 **왜 안 골랐는지가 재사용되는 지식**이라 함께 적는다.

### A. 발행 측에서 순서를 지킨다

**A-1. 전면 중단 (stop-the-world)** — 실패하면 배치 전체를 멈추고, 다음 폴링에서 그 지점부터 다시 한다.
가장 단순하고 순서는 완전히 보장된다. 대신 **전역 head-of-line blocking** 이다 —
`ORD-1` 하나가 막히면 무관한 `ORD-2`~`ORD-500` 까지 멈춘다.
페이로드가 깨져 영구 실패하는 이벤트 하나가 서비스 전체의 발행을 정지시킬 수 있다.
이벤트 양이 적고 순서가 절대적인 도메인에서는 이게 정답일 수 있다.

**A-2. 키 단위 직렬화** ← **이 저장소의 선택**.
head-of-line blocking 의 범위를 키 하나로 좁힌다. A-1 의 안전성을 유지하면서 blast radius 를 줄인 것이고,
Kafka 의 파티션, Pulsar 의 `Key_Shared` 구독, SQS FIFO 의 `MessageGroupId` 가 전부 같은 아이디어다.
**대가**: 키 하나가 영구 실패하면 그 키는 계속 막힌다. 그래서 `maxRetry` 도달 시 DEAD 전이가
탈출구로 반드시 필요하고, **DEAD 알람이 그 짝이다.** `stove.outbox.dead` 에 Prometheus 알람 규칙이
걸려 있고(`infra/prometheus/alerts.yml`), DEAD 로 떨어진 이벤트는 운영 API 로 되살린다
(`/api/v1/ops/outbox/dead/{id}/requeue` — [decisions.md](decisions.md) 19번).

**A-3. 애그리거트별 발행 큐 (single-writer)** — 키를 워커에 결정적으로 배정해 한 키는 언제나 같은 워커가 맡는다.
릴레이를 다중화할 때 A-2 에 반드시 따라와야 하는 조건이다. 7절 참고.

### B. CDC — 로그 테일링

Outbox 테이블을 폴링하지 않고 **DB 트랜잭션 로그(binlog/WAL)를 읽어** 발행한다.
Debezium 의 Outbox Event Router 가 사실상 표준 구현이다.

순서 문제를 **원천적으로** 없애는데, binlog 가 커밋 순서 그대로 기록된 단일 로그이기 때문이다.
정렬할 대상이 없다. 읽은 순서가 곧 커밋 순서고, 실패하면 그 오프셋부터 다시 읽으므로
**건너뛸 방법 자체가 없다.**

| | 폴링 릴레이 | CDC |
|---|---|---|
| 순서 | 직접 관리 | 로그 순서 = 커밋 순서 (공짜) |
| 지연 | 폴링 주기만큼 | 거의 실시간 |
| DB 부하 | 주기적 SELECT + UPDATE | 없음 (복제 슬롯만) |
| 운영 | 앱 안에 전부 있음 | Kafka Connect 클러스터가 추가 운영 대상 |

교과서적으로는 CDC 가 정석이고 대규모 시스템은 대개 이쪽으로 간다.
**이 저장소가 폴링 릴레이를 유지하는 이유**는 순서·처리량·관측을 직접 다루는 것이
이 프로젝트의 목적에 부합하기 때문이다. CDC 를 썼다면 그 문제들이 커넥터 뒤로 숨었을 것이다.

### C. 수신 측에서 순서를 복원한다

발행 측이 완벽할 수 없다고 보고 컨슈머가 방어하는 계열. 발행 측 해법과 배타적이지 않다.

**C-1. 시퀀스 번호 + 재정렬 (Resequencer)** — 애그리거트별 단조 증가 번호를 싣고,
컨슈머가 기대보다 큰 번호를 받으면 처리하지 않고 보류한다.
확실하지만 비싸다 — 컨슈머마다 진행 상태 테이블, 보류 버퍼,
**영영 오지 않는 이벤트에 대한 타임아웃 정책**까지 필요하다.
앞 이벤트가 DEAD 로 죽으면 뒤 이벤트는 영원히 대기한다.

**C-2. 버전 기반 무시 (last-write-wins)** — 이벤트에 버전을 싣고 이미 더 최신을 처리했으면 버린다.
C-1 보다 훨씬 싸지만 **"버려도 되는" 이벤트에만** 쓸 수 있다.
상태 동기화(색인 갱신, 권한 사본)에는 완벽하고, 이벤트마다 별도 부수 효과가 있으면
(정산 원장에 행 추가 같은) 못 쓴다.

**C-3. 상태 전이 가드 + 보류 기록** — 불가능한 전이가 오면 거부하는 대신 기록해 둔다.
"회수" 가 왔는데 대상이 없으면 회수 예약을 남기고, 나중에 "발급" 이 도착하는 순간 즉시 적용한다.
[D-012](defects.md#d-012) 수정의 `orderNo` 대조가 이 계열의 축소판이다.

### D. 순서 의존 자체를 없앤다

위 셋은 전부 "순서를 지키는" 방법이다. 네 번째는 **순서가 상관없게 이벤트를 설계하는 것**이고,
가능하다면 이게 가장 강력하다.

**D-1. 상태를 싣는다 (event-carried state transfer)** — "무엇이 바뀌었다" 가 아니라 "지금 상태가 이렇다".

```
변화 전달:  "상품 3을 추가 지급"      → 순서가 중요. 놓치면 복구 불가
상태 전달:  "현재 보유 = [1, 2, 3]"   → 늦게 온 건 버리면 됨. 재처리로 복구 가능
```

[D-010](defects.md#d-010) 수정으로 `LicenseIssued` 가 이미 이렇게 되어 있다 —
"새로 지급된 것" 이 아니라 **현재 보유 전체**를 싣는다.
반대로 `LicenseRevoked` 는 [D-011](defects.md#d-011) 수정으로 **실제 변화만** 알린다.
지급은 상태를, 회수는 변화를 — 이 비대칭은 의도된 것이고 근거는 `defects.md` 에 있다.

**D-2. 멱등 + 교환법칙** — 어떤 순서로 적용해도 결과가 같게 만든다.
문서 ID 고정 upsert(store, download 의 색인·사본 갱신)가 그것이다.
다만 **"생성/소멸" 짝은 본질적으로 교환법칙이 성립하지 않는다** —
발급→회수와 회수→발급의 결과가 다르다. D-013 에는 쓸 수 없었던 이유다.

## 7. 남은 제약 — 릴레이를 다중화하면 A-2 가 무효가 된다

**릴레이는 현재 서비스당 1대여야 한다.** 문서로 남기는 이유는 이 제약이 코드에 드러나지 않기 때문이다.

`OutboxEventRepository#lockPendingBatch` 는 `FOR UPDATE SKIP LOCKED` 로 배치를 선점한다.
릴레이가 여러 대면 **같은 파티션 키의 이벤트가 서로 다른 릴레이로 갈라져 들어갈 수 있다.**

```
릴레이 A 가 선점: [501 ORD-1 PaymentCompleted]
릴레이 B 가 선점: [502 ORD-1 PaymentCancelled]   ← SKIP LOCKED 는 키를 모른다

A 에서 501 실패, B 에서 502 성공  →  D-013 이 그대로 재현된다
```

키 웨이브는 **한 릴레이가 그 키의 이벤트를 전부 들고 있을 때만** 성립한다.
다중화하려면 A-3 으로 가야 한다 — 키를 워커에 결정적으로 배정한다.

```sql
-- 예: 워커 인덱스로 키를 나눠 선점한다
WHERE status = 'PENDING'
  AND next_attempt_at <= NOW()
  AND MOD(CRC32(partition_key), :workerCount) = :workerIndex
```

이러면 워커 수를 바꿀 때 재배치 창이 생기므로(같은 키가 잠시 두 워커에 걸침)
무중단 스케일링에는 추가 설계가 필요하다. 지금 규모에서는 릴레이 1대로 충분하고,
처리량은 [performance.md](performance.md) 기준 480 events/s 로
전체 스택에서 관측된 API 한계선(132.5 RPS, 9-2 절)보다 훨씬 위에 있다.

**즉 다중화는 지금 필요하지 않다.** 필요해지는 시점에 이 문서로 돌아오면 된다.

## 8. 요약 카드

| 질문 | 답 |
|---|---|
| 순서가 깨지는 층은 | 프로듀서 / 발행자(Outbox 릴레이) / 컨슈머 — 셋이 독립적이다 |
| 순서가 쟁점이 되는 조건 | 같은 토픽 + 같은 파티션 키로 이벤트가 둘 이상 = *짝* |
| 이 도메인의 짝 | order/payment/license 각각의 "생성 → 소멸" 세 쌍 (2절) |
| 짝이 동시에 PENDING 이 되는 때 | 앞 이벤트가 발행 실패해 재시도 대기 중일 때뿐 |
| 프로듀서 층 방어 | `enable.idempotence: true` (전 서비스 적용) |
| 발행자 층 방어 | 키 단위 웨이브 발행 — 실패한 키의 뒤 이벤트를 보류 |
| 컨슈머 층 방어 | 단일 스레드 소비 + `ProcessedEventGuard` 멱등 흡수 |
| 설계 층 방어 | `LicenseIssued` 가 상태를 실어 순서 의존을 축소 (D-010) |
| 채택하지 않은 것 | CDC(운영 비용), 전면 중단(전역 blocking), 시퀀스 재정렬(컨슈머 비용) |
| 알려진 제약 | 릴레이 다중화 시 키 웨이브 무효 → A-3 필요 (7절) |
| 잊기 쉬운 함정 | 파티션 증설이 키→파티션 매핑을 바꿔 순서를 깬다 (5절) |

### 되새길 원칙

> **순서 보장은 범위를 좁힐수록 싸진다.**

전부의 순서를 지키려 하면 전역 blocking 을 사고, 아무것도 안 지키면 정합성을 잃는다.
**지켜야 하는 최소 단위를 정확히 지목하는 것**이 설계의 핵심이고, 여기서 그 단위는 파티션 키였다.
단위를 좁히고 나니 나머지를 동시에 보낼 수 있게 되어 처리량까지 따라왔다 —
순서와 처리량은 맞바꾸는 관계가 아니라, **범위를 잘못 잡았을 때만 충돌한다.**
