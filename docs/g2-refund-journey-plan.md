# G2 할인 거래 환불·이용권·다운로드 여정 계획

**2026-10-30 R3 실패·복구 계약 여정 완료:** 누적 구현·실제 수동 환불 기록을 `e11cfaa`로 커밋한 뒤, 같은 일곱 앱과 실제 Auth/Gateway·DB/Kafka를 루프백 PG HTTP 계약 픽스처에 연결했다. REQUESTED 미확정·실제 복구 전 재시도 409, 실제 ACTIVE/다운로드 복구, 명시적 재시도의 중복 수렴, Payment 재시작 후 같은 키·본문·최초 준비 유지와 성공 응답 유실 뒤 PG_QUERY_UNATTRIBUTED·COMPLETED를 확인했다. [증거 수준·관측·정리 기록](g2-refund-fault-journey-verification.md)을 따른다. 실제 PG 금융 동작은 0건이며 전용 환경은 정리하고 기존 23개·볼륨 57개를 보존했다. 다음 권장 논의는 P3 지급/지급 확인 누락의 근거 기반 복구다. 새 실제 TEST 자동 환불·재구매·G3 정산과 G2 전체 종료는 별도다.

2026-10-30. 사용자의 다음 작업 계획 수립 요청에 따라 작성했다. 기준 커밋은 `03cc89e`이며, 현재 작업본에는 [G2 구매·다운로드 완료 기록](g2-purchase-download-verification.md)과 관련 인계 문서의 미커밋 변경이 있다. 이 문서는 계획이다. 새 환불 정책의 합의, 구현·검증 완료, 추가 PG 승인·환불 실행을 뜻하지 않는다.

**후속 P1 확정:** 사용자는 **A안: 제공사 전액 취소 계약에 따른 반환, 할인 혜택 재사용은 제공사 정책**을 선택했다. [결정 35](decisions.md#provider-discount-full-refund)를 따른다. 플랫폼 별도 보전을 추가하지 않고 결제수단·사용 포인트 반환 근거를 확인한다. 아래 P1의 미결·추천 표현은 계획 당시 기록이며 같은 선택을 다시 묻지 않는다. P2의 후속 선택·검증은 아래 기록을 따른다.

**P1 내부 구현·검증 완료:** Payment의 원승인 금액 대조·포인트 근거 보존과 V33을 구현하고 OCI 최종 626건·bootJar를 통과했다. [구현·TDD·검증 경계](g2-discount-refund-implementation.md)를 따른다. 고객 조회 P2는 아래 후속 기록을 따르며 실제 할인 거래의 PG 취소·역할별 전체 여정은 남아 있다.

**후속 P2 확정:** 사용자는 환불 상세에서 주문·승인 금액과 확인된 반환 구성을 함께 제공하는 A안을 선택했다. [결정 36](decisions.md#refund-amount-details)을 따른다. 미확인 금액을 NULL로 표시하고 기존 금융 완료 상태를 유지하며, 합의한 범위의 이벤트·조회 사본·고객/관리자 응답을 구현·검증한다. 같은 선택을 다시 묻지 않는다.

**2026-10-30 P2 금액 상세 A안 구현·검증 완료:** [결정 36](decisions.md#refund-amount-details)에 따라 고객·관리자 환불 응답에 주문 총액·승인 PG 실결제/할인·확인 취소/포인트·미확인 목록을 연결했다. 기존 amount·COMPLETED를 유지하고 확인하지 않은 결제수단 반환액은 NULL로 남긴다. 공통 Kafka·Order·Payment·Gateway 최종 OCI **1,526건**과 Order·Payment bootJar를 통과했다. [이벤트·Order V27·TDD·역순/롤백·보존 기록](g2-refund-amount-details-implementation.md)을 따른다. 추가 실제 PG 승인/취소는 실행하지 않았으며, 다음은 구체적인 대상·금융 동작·관측 범위를 대조한 최신 할인 TEST 환불·이용권·다운로드 역할별 여정이다. 지급 복구·재구매·G3 정산은 별도 남은 범위다.

**2026-10-30 R3 실제 수동 환불 1건 완료:** 사용자의 `실행` 지시로 준비한 G2 TEST 거래의 실제 ADMIN 2차 승인→License SUSPENDED→PortOne CANCELLED·환불 COMPLETED를 검증했다. 새 구매 0건·성공 취소 1건이며 취소 총액 9,000원·제공사 보고 포인트 24원을 고객/관리자 상세에 보존하고 직접 근거가 없는 결제수단 반환액은 NULL로 유지했다. 새 다운로드 403, 기존 URL의 만료 전 200→자연 만료 후 403, 같은 명령/완료 이벤트 수렴과 웹훅을 확인했다. [실제 결과·관측 도구 보정·정리 기록](g2-refund-role-journey-verification.md)을 따른다. 전용 앱 일곱 개·컨테이너 네 개·웹훅 경로는 정리했고 기존 23개·볼륨 57개를 보존했다. 재개 기준은 새 경로의 환불 후 자료이며 과거 G2 원본은 환불 전 스냅샷이다. 같은 금융 스크립트를 반복하지 않는다. R3 실패/복구·자동 환불의 남은 검증, 지급 복구·재구매·G3 정산과 G2 전체 종료는 별도다.

## 1. 목표와 작업 순서

정상 구매 이후 고객이 환불을 요청하고, 필요한 관리자 판정과 실제 이용권 정지를 거쳐 PG 전액 취소·결과 조회·신규 다운로드 차단까지 이어지는 최신 여정을 완성한다. 확정 실패일 때는 실제 이용권 복구와 고객의 명시적 재시도까지 연결한다. 기존 정책을 유지하면서 **할인 거래의 금액 계약 → 필요한 구현과 관련 검증 → 실제 역할별 여정** 순서로 진행한다.

첫 구현 범위는 할인 거래의 전액 환불이다. [전체 일반화 계획](platform-generalization-plan.md)의 G2 전체 종료에는 지급 확인 누락 복구와 환불 후 재구매 정책도 필요하다. 이 두 항목은 아래 별도 단계에서 다루며, 할인 환불 여정 하나의 성공을 G2 전체 완료로 표시하지 않는다. 정산 조정은 G3로 이어간다.

## 3. 공식 계약에서 확인한 사실과 남은 확인

2026-10-30 공개 공식 문서를 대조했다. 실제 호출 경로는 기존 PortOne V2 `tosspay_v2` TEST다. 토스페이먼츠 문서를 토스페이의 계약으로 대신 사용하지 않는다.

| 근거 | 확인한 사실 | 이 사실만으로 확정할 수 없는 것 |
|---|---|---|
| [PortOne 현행 OpenAPI](https://developers.portone.io/api/schema/v2/openapi.json)의 CancelPaymentBody·PaymentAmount | amount 생략은 전액 취소이고 currentCancellableAmount는 요청 이전 잔액의 일치 검사다. discount에는 여러 할인과 적립형 포인트가 포함될 수 있다. | 할인 거래에서 각 요청·조회 금액의 채널별 대응, 할인 24원의 세부 종류와 고객 혜택 재사용 가능 여부. |
| [PortOne 취소 가이드](https://developers.portone.io/opi/ko/integration/cancel/v2/readme?v=v2) | 전액 취소와 부분 취소의 요청 예시를 구분하고, 직접 PG 취소로 생길 수 있는 상태 불일치를 설명한다. | 잔액 검사를 제거해도 된다는 근거나, 기존 고정 본문을 배포 시 다시 생성해도 된다는 허가는 아니다. |
| [PortOne 취소 완료 타입](https://portone-io.github.io/server-sdk/js/types/Payment.SucceededPaymentCancellation.html) | totalAmount와 easyPayDiscountAmount는 별도 필드이며, 후자는 적립형 포인트의 반환 금액으로 설명된다. 현행 OpenAPI와도 대조했다. | easyPayDiscountAmount를 승인 discount 전체와 같다고 보거나 현금 반환액으로 해석할 수 없다. |
| [토스페이 환불 API](https://docs-pay.toss.im/reference/common/refunds) | 환불 요청 총액, 반환된 할인·포인트·지불수단 금액과 환불 뒤 잔액을 구분한다. | 토스 직접 응답의 필드가 PortOne 응답에 어떤 형태로 보존되는지는 별도 확인이 필요하다. 직접 토스 API를 호출하는 구현을 추가하지 않는다. |
| [토스페이 상태 조회](https://docs-pay.toss.im/reference/common/status) | 즉시 할인과 사용 포인트를 구분하며 결제수단 승인액·환불 잔액·거래별 금액을 제공한다. | 현재 Payment의 합산 할인 스냅샷만으로 현금/포인트별 반환을 확정할 수 없다. |

먼저 PortOne의 취소 요청 amount·currentCancellableAmount, 조회 amount.cancelled, 취소 totalAmount·easyPayDiscountAmount 사이의 대응표를 만든다. 공개 계약과 비밀값을 제거한 기존 원자료로 확인되지 않는 항목은 미확인으로 남기고, 필요한 제공사 확인 질문과 실제 TEST 관측 항목을 적는다. 문의 발송·추가 금융 동작을 계획 작성에 포함하지 않는다.

**PG API 숫자를 사용자가 임의로 9,000원 또는 8,976원 중 선택하는 문제로 만들지 않는다.** 공급자의 총액·잔액 정의는 기술 계약으로 확인한다. 고객에게 보장하고 표시할 반환 범위·혜택 안내는 그 사실을 바탕으로 정할 제품 정책이다. 예시의 8,976원도 현재 기록의 PG 실결제액이며 실제 환불 완료 금액으로 미리 확정하지 않는다.

## 4. 유지할 합의와 정책 논의 순서

다음은 기존 합의이므로 다시 선택받지 않는다.

- Order는 환불 접수·심사·진행, Payment는 PG 실행·재조회·금융 근거, License는 실제 이용권을 소유한다. 원구매 PAID·주문 금액·구매 사실을 환불 상태로 덮어쓰지 않는다.
- 최초 결제 결과 시각부터 정확히 4시간 이내 접수는 자동 허용하고 이후는 수동 심사한다. 최초 접수·자격은 심사 지연·재시도로 바꾸지 않는다. 승인/자동 허용 뒤 지급 확인 → 실제 정지 → PG 실행 순서를 지킨다.
- 같은 실행의 attemptId·멱등 키·고정 UTF-8 본문·최초 준비 시각과 원래 3시간을 유지한다. 시간이 지났다는 이유로 실패·복구·새 시도를 만들지 않는다.
- 실제 확정 실패와 실제 복구 뒤 고객의 명시적 재시도, 반려 뒤 고객 재심사, 잘못된 승인 중단의 기존 경계와 감사 이력을 유지한다.
- 정지 상품의 라이브러리 노출, 신규 다운로드 거절, 이미 발급된 URL의 만료 전 사용과 이미 받은 파일 회수 제외를 유지한다.
- 주문 생성 30분·서버 승인·같은 주문의 검증된 개별 실패 재결제와 PG 할인 승인 A안은 재논의하지 않는다.

정책은 아래 순서로 **한 번에 하나씩** 설명하고 사용자의 선택과 이유를 기다린다. 다음 행의 정책을 앞 행의 승인에 포함하지 않는다.

| 순서 | 다룰 쟁점 | 결정 산출물 |
|---|---|---|
| P1 먼저 | 할인·포인트가 포함된 전액 환불의 고객 반환 범위와 안내. 기존 주문 총액과 실제 원 결제수단 반환을 어떻게 구분할지, 공급자 혜택 복원에 대해 무엇을 보장할지. | 9,000/8,976/24원 사례에 대한 고객 계약·공급자 확인 항목. 플랫폼의 별도 보전이나 쿠폰 재발급을 묵시적으로 추가하지 않는다. |
| P2 필요 시 | 확정한 반환 근거를 고객·관리자에게 제공하는 조회 방식과 미확인 값의 표현. | 원래 amount 보존, 추가 금액·출처·시점·미확인 표현과 모듈 간 전달의 최소 범위. |
| P3 후속 | PAID 뒤 지급 또는 지급 확인 누락의 근거 기반 복구 범위·주체. | 재전달/복구 계약과 같은 구매의 중복 지급·상태 역전 방지. |
| P4 후속 | 환불 완료 상품의 재구매 허용/불허. | 허용 시 새 구매 근거·권한과 과거 이벤트 격리, 불허 시 일관된 거절·안내. |

P1의 추천 방향은 **원 결제 전체를 취소하고 반환 구성은 공급자 근거대로 구분해 안내하는 것**이다. 고객이 주문 금액을 현금 반환액으로 오해하는 일을 줄이고, 근거 없는 할인·포인트 보전 비용과 지원 업무를 만들지 않기 때문이다. 조회의 세부 제공 방식은 P2에서 필요에 따라 좁혀 결정한다. 예를 들어 기존 결제 상세와 취소 영수증을 연결하는 안은 변경량이 작지만 고객이 여러 응답을 대조해야 하고, 환불 조회에 구성 정보를 보관하는 안은 안내가 명확하지만 이벤트·저장·명세 검증이 늘어난다. 어느 쪽도 이번 계획으로 확정하지 않는다.

### R2 구현 경계

- Payment가 가진 원승인 스냅샷과 원거래를 환불 내부 입력에서 검증한다. 모델·메서드의 정확한 형태와 새 컬럼은 R1 뒤 정한다. 이미 주문 금액을 아는 Order에 PG 숫자 계산을 떠넘기지 않는다.
- 외부 필드 해석과 HTTP는 기존 adapter 하위 패키지에 두고 호출 계약은 core.port, 설정 바인딩·조립은 config에 둔다. 외부 이벤트 전체를 서비스·도메인에 전달하지 않는다.
- 직접 성공과 조회로 확인한 전액 취소, 우리 실행의 성공 귀속은 기존처럼 구분한다. 할인 지원이 타인 거래·부분 취소·잔액 변경·불확실한 실패를 정상 완료로 넓히지 않도록 한다.
- 새 배포에서도 이미 준비한 본문·키·시각을 덮어쓰지 않는다. 금액 근거를 추가 저장해야 한다면 확인 가능한 자료만 사용한다. 과거 NULL을 주문 금액·0원 할인으로 임의 채우지 않고 실제 영향에 맞는 이행 경로를 정한다. 과거 특정 개발 주문을 위한 호환 정책을 새 요구로 만들지 않는다.
- 고객 조회를 확장할 경우 Payment의 검증된 사실을 어떤 최소 계약으로 전달할지 정한다. 기존 원구매 amount·이벤트 의미와 금융 원자성을 보존하고, 불필요한 조회 시 PG 호출은 추가하지 않는다.
- License와 Download는 금액을 계산하지 않는다. 이번 금액 변경이 권한 계약을 바꾸지 않는다면 관련 계약 검사와 실제 여정으로 확인하고 운영 코드를 이유 없이 수정하지 않는다.

## 6. 실제 여정과 검증 수준

| 여정 | 실행 방식과 관측 |
|---|---|
| 자동 환불 | 확정한 새 TEST 구매에서 자연 시각으로 4시간 이내 접수 → 지급 확인 → 실제 정지 → PortOne 취소/조회 → 고객 완료. 원구매와 취소 근거·Outbox/Inbox·새 다운로드 403을 대조한다. |
| 관리자 반려·승인 | 기존 config bootstrap으로 만든 실제 ADMIN과 별도 MEMBER가 Gateway BFF로 로그인한다. 자연스럽게 4시간을 경과한 합의된 검증 거래에서 심사 대기·권한 유지·반려/고객 재심사·회차 지정 승인과 감사 주체를 확인한다. |
| 확정 실패·복구·재시도 | PortOne HTTP 계약 픽스처가 재현 가능한 실패 영수증·미취소 조회를 제공하고 실제 업무 앱·DB·이벤트로 정지→복구→명시적 재시도를 검증한다. 실제 PortOne 장애 검증이라고 표시하지 않는다. |
| 미확정·응답 유실 | 재현 가능한 HTTP 경계 장애로 같은 키/본문·조회 복구·정지 유지·중복 금지와 조회 안내를 확인한다. 실제 금융 동작이 포함되는 별도 관측은 그 범위를 먼저 확정한다. |
| 다운로드 | 정지 전 ticket·원본 ZIP, 정지 뒤 새 ticket 거절, 복구 뒤 새 ticket·원본 일치를 확인한다. 기존 URL은 만료 전 허용·자연 만료 후 거절을 관측하며 전용 짧은 TTL 설정을 쓸 수 있다. 업무/PG 시각을 조작하지 않는다. |

ADMIN 검증을 자체 서명 테스트 JWT만으로 대체하지 않는다. 타인 MEMBER·비로그인 세션·CSRF 누락 대조도 독립 세션으로 실행한다. 원래 성공 거래의 상태·시각이나 환불 자격을 DB에서 바꿔 수동 심사를 만들지 않는다. 실제 거래가 자연 4시간을 지나야 하는 준비와 계약 픽스처의 즉시 검증을 분리해 진행한다.

기존 G2 성공 거래는 현재 PG 승인 근거와 업무 자료가 보존된 거래다. 이 계획을 해당 거래의 환불 실행 승인으로 해석하지 않는다. 실제 TEST 실행 전 대상 주문·현재 자격·금액 근거·수행할 승인/취소·예상 관측·횟수를 구체적인 표로 정하고 기존 실행 허가가 적용되는지 대조한다. 이미 완료한 금융 스크립트를 반복하지 않는다. 같은 지시에 대한 재확인은 요구하지 않는다.

## 7. OCI 실행과 검증 비용

코드·문서는 로컬에서 편집하고 **빌드·테스트·서비스 실행은 ssh sng OCI의 격리 작업본에서만** 수행한다. 실행 직전 HEAD·미커밋 변경·소스 해시와 원격 JAR를 대조한다. 이번 계획 작성에서는 OCI 서비스 기동·빌드·테스트를 실행하지 않았다.

1. 실제 컨테이너·볼륨·포트와 ID·시작 시각·재시작·health를 새로 수집한다. 과거 23개·57개를 현재값으로 가정하지 않는다.
2. 전용 작업 경로·DB·포트·토픽/소비 그룹·컨테이너·MinIO 자료와 실제 PG 경계를 격리한다. 보존한 검증 스택을 재사용한다면 사용 범위와 기존 데이터 재유입을 먼저 대조한다.
3. 관련 단위·아키텍처 → 관련 HTTP/DB/Kafka 통합 → 변경 정리 뒤 최종 게이트 순서로 진행한다. [검증 최적화 계획](test-verification-optimization-plan.md)을 따른다.
4. 최종 게이트는 Payment `check`·`bootJar`를 기본으로 하고, 실제 수정한 Order/Gateway·공통 이벤트 및 다른 소비자를 영향에 따라 추가한다. Order·Payment `check`에 일반 integrationTest와 migrationTest가 포함됨을 유지한다. 변경하지 않은 열한 앱 전체 검사를 자동 반복하지 않는다.
5. 같은 작업 디렉터리에 여러 Gradle 프로세스를 동시에 실행하지 않는다. 집중 Red·수정 반복·최종 게이트의 결과를 중복 합산하지 않는다.
6. 비밀 설정·토큰·쿠키·서명 URL을 Git·공개 문서·소스 묶음에서 제외한다. 원자료는 Git 제외 runs/에 보관하고 공유 자원·기존 nginx/웹훅 설정을 보존하며 이번 전용 자원만 정리한다.
