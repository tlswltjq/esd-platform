# 프로젝트 단순화 및 재구축 계획

작성일: 2026-10-11. 상태: 코드 조사에 기반한 실행 제안. 이 문서 작성으로 서비스·API·데이터가 변경되지는 않는다.

## 1. 목표와 기본 결정

**MSA의 데이터 소유권과 독립 배포는 유지하되, 게임 등록 → 공개 → 구매 → 이용권 → 다운로드 한 흐름만으로 기본 시스템을 다시 구성한다.** 서비스의 수, 저장소의 종류, 상태 전이, 필수 실행 도구를 함께 줄인다. 고도화 기능은 실제 요구가 생긴 서비스에만 추가한다.

기존 문서에 기능이나 규칙이 있다는 사실을 유지 이유로 삼지 않는다. 유지 이유는 기본 흐름에 필요하거나, 권한·금액·처리 결과의 정확성을 지키기 때문이어야 한다. 현재 구현을 보존한 채 새 추상화 계층을 덧붙이는 방식은 피한다.

계획의 기본 가정은 개발·실습용 플랫폼의 재정비다. 운영 중인 고객·실거래·보존 대상 데이터가 있는지는 확인되지 않았다. 먼저 이 여부를 확인하고, 개발 데이터의 초기화와 운영 데이터의 이관을 구분한다. 실서비스가 있다면 아래 기능 축소를 바로 적용하지 않고 사용 현황과 계약을 확인해 전환한다.

권장 기본 구성은 **업무 서비스 6개(Auth, Studio, Catalog, Order, Payment, License), 단순 reverse proxy, MySQL·Kafka·MinIO**다. Review·Settlement는 기본 실행에서 제외하고, Store·Download의 최소 기능은 원본을 소유한 서비스로 옮긴다. 이는 서로 다른 모든 도메인을 한 서비스로 합치는 계획이 아니다. 별도 조회 사본·업무 자동화가 필요한 시점에 다시 분리할 수 있게 한다.

Review·Settlement 제외는 개발용 기본 범위의 축소다. 실제 판매에 필요한 심의·정산 업무가 충족됐다는 의미가 아니다. 실제 운영을 계속해야 한다면 이 두 서비스의 필요한 기능은 유지하고 해당 운영 의존성을 별도로 표시한다. 기본 구성의 서비스 수를 목표로 업무 필수 조건을 삭제하지 않는다.

초기 가격은 KRW의 정수 금액, 상품은 단일 게임, 공개 파일은 게임당 현재 버전의 단일 산출물로 제한한다. 판매자는 회원과 연결된 단일 개인 판매 주체로 제한하되, 기존 `workspaceId`를 `memberId`로 그대로 바꾸지 않는다. 식별자 매핑과 기존 주문의 판매자 사본을 이관한다.

### 최소 공개 모델

게임 초안은 `DRAFT → SUBMITTED → APPROVED → PUBLISHED`, 반려는 `SUBMITTED → DRAFT`로 단순화한다. 제출 후에는 내용을 변경하지 못하게 하고 승인 대상을 고정한다. 공개된 버전은 불변으로 두며 변경은 새 초안의 승인·공개로 처리한다. 승인자·시각·대상 버전과 반려 사유는 남긴다. 모든 자료를 별도 revision 엔티티로 분리하지 않는다.

파일은 `PENDING → READY / FAILED` 정도의 상태만 둔다. Studio는 파일을 빌드하지 않는다. 외부에서 만든 완성 파일을 등록받고, 객체의 존재·크기·허용 형식을 확인한다. 초기 업로드는 크기 제한이 있는 **단일 presigned PUT**으로 정한다. 완료 확인과 만료된 미완료 객체 정리에 필요한 최소 처리만 유지한다. 작은 파일을 위해 multipart 상태 머신을 운영하지 않는다.

실행 검증·바이러스 검사·플랫폼별 패키징이 기본 환경에 포함되지 않으면 검사를 통과했다고 표시하지 않는다. 신뢰되지 않은 사용자의 파일을 실제 배포하는 요구가 생기면 그에 필요한 검증을 도입한다.

## 4. 인증과 진입점

**JWT는 유지하고 reactive Gateway를 없애는 것이 첫 단계다.** 기존 OAuth2 로그인까지 동시에 교체하지 않아 원인을 분리해서 검증한다. 최종 기본 인증은 단일 플랫폼의 가입/로그인 API와 짧은 수명의 access JWT로 줄인다.

- Auth는 Spring Security의 비밀번호 해시와 검증된 JWT 서명 도구를 사용한다. 토큰 파서·암호 알고리즘을 직접 만들지 않는다. 공개 가입에서 ADMIN 역할을 선택할 수 없게 하고 운영자 권한 부여 이력을 남긴다.
- 기존 `member_id`, `roles`, issuer, audience 계약은 가능한 한 유지한다. 서명 키는 재시작에도 유지하며 코드에 비밀을 넣지 않는다.
- 각 서비스가 Servlet Resource Server로 서명·issuer·audience·만료와 API 권한을 검증한다. proxy는 인증된 사용자 헤더를 생성하지 않는다. 사용자 식별용 외부 헤더는 제거하고 서비스는 JWT에서만 사용자를 식별한다.
- 소유권 검사는 Studio·Order·Payment·License가 담당한다. 내부 API는 proxy에 공개하지 않고 네트워크 접근 제한과 서비스 전용 자격으로 보호한다.
- 기본 access token 만료 후 다시 로그인한다. refresh token·SSO·즉시 폐기 요구가 생기면 별도 도입한다. 역할 변경/탈퇴 후 기존 토큰이 만료까지 유효할 수 있는 한계를 계약에 명시한다.
- 브라우저는 기본적으로 메모리에 token을 두고 Authorization 헤더로 전달한다. 쿠키 인증을 도입하면 CSRF 정책도 함께 설계한다. Swagger는 Bearer 입력으로 검증한다.
- PG 콜백은 사용자 JWT 대신 기존 공급자 서명과 금액/거래 검증을 유지한다.

전환 때는 새 로그인·기존 OAuth 토큰의 유효 기간과 issuer/JWKS 경로를 명시한다. 개발용 재구축에서는 새 환경에서 재로그인하는 방식으로 종료한다. 운영 전환에서는 기존 토큰 만료까지 제한된 호환 기간을 두고 구 인증 경로를 종료한다.

reverse proxy는 기존 보안 경계를 그대로 복사하지 않는다. **현재 Gateway에만 있는 차단 규칙을 먼저 담당 서비스 또는 내부 경로 제한으로 옮긴다.** issuer·redirect·forwarded header·CORS와 요청 종료 처리를 확인한 뒤 Gateway를 제거한다. proxy는 표준 Nginx 정적 설정으로 시작하고 새 Java MVC Gateway를 작성하지 않는다.

## 5. 데이터와 통신의 최소 구조

MySQL은 서비스별 스키마와 소유권을 유지한다. 다른 서비스 DB를 직접 읽거나 조인하지 않는다. MinIO는 객체 보관, Kafka는 커밋 이후 전달이 필요한 업무 이벤트에만 사용한다. Redis·Elasticsearch·MongoDB·ClamAV·Grafana·Tempo·Prometheus는 기본 기동 의존성에서 뺀다. 필요한 관측 도구는 별도 실행 구성으로 제공한다.

| 업무 | 기본 방식 | 남겨야 하는 실패 처리 |
|---|---|---|
| 게임 공개 → Catalog 반영 | Studio 변경과 Outbox를 한 트랜잭션에 저장, Kafka로 공개 스냅샷 전달 | Studio의 공개 결정과 Catalog 판매 반영을 구별. 동일 상품의 버전 증가와 중복 방어 |
| 상품 목록·상세 | Catalog MySQL 직접 조회 | 페이지 크기 제한, 필요한 인덱스, 출시 상품만 공개 |
| 주문 가격 확정 | Order → Catalog 동기 HTTP | 시간 제한, 실패 시 주문 미생성, 확정 가격 사본 보존 |
| 주문 → 결제 준비 | 기존 `OrderCreated` 이벤트 유지 | 아직 준비되지 않은 결제는 처리 대기 상태로 응답 |
| 결제 → 주문/이용권 반영 | 기존 결제·이용권 이벤트 유지 | 중복·지연·순서 역전·중단 후 재개 |
| 파일 다운로드 | License에서 이용권 원본 확인 → Studio 내부 API에서 공개 파일 정보 조회 → 짧은 URL 발급 | 권한 없음/상류 장애 시 발급 거부. 발급한 URL은 TTL 동안 접근 가능함을 명시 |

초기 비동기 계약은 기존 이름을 활용해 `ReleasePublished`, `OrderCreated`, `OrderCanceled`, `PaymentCompleted`, `PaymentFailed`, `PaymentCancelled`, `LicenseIssued`, `LicenseIssueFailed`의 8종을 기준으로 정리한다. 현재 Payment가 처리하지 않는 `OrderCanceled`는 결제 전 취소 반영에 연결한다. `ReleasePublished`는 단일 공개 스냅샷만 담는다. 비활성 기능의 빌드·심사·웹훅·할인 이벤트는 기본 경로에서 발행하거나 구독하지 않는다. 기존 payload를 축소할 때는 계약 버전과 소비자 전환을 같이 처리한다.

공개·결제·환불은 DB 저장 후 단순 HTTP 호출로 바꾸지 않는다. 두 번째 작업 전에 중단되면 공개 반영이나 이용권이 누락되기 때문이다. 해당 경로에는 최소 Outbox/중복 처리 기록과 필요한 재시도를 남긴다. 모든 변경을 이벤트로 표현하거나 모든 서비스에 Kafka를 주입할 필요는 없다.

결제 실패와 결제 전 주문 취소는 금전 이동이 없고, 결제 후 취소는 Payment의 전액 환불로만 처리한다. Order의 상태 변경만으로 환불 완료라고 응답하지 않는다. 결제 전 취소와 승인 콜백이 경합하면 상태 조건부 갱신과 늦은 승인 보상으로 최종 결과를 맞춘다. 취소 이벤트가 먼저 와도 이후 생성 이벤트가 결제를 다시 열지 못하게 한다. 이용권 지급이 영구 실패하면 환불로 보상한다. 늦은 지급 이벤트가 환불 후 권한을 되살리지 못하도록 취소 기록/버전 가드를 유지한다. 이를 위해 필요한 취소·재개 상태는 서비스 기본 기능에 포함한다.

Outbox·Inbox·DLT는 이름 때문에 삭제하지 않는다. 발행 실패·소비 실패를 찾아 재처리하는 최소 수단과 보존/정리 기준을 유지한다. 초기 릴레이를 단일 인스턴스로 제한한다면 배포 설정에도 그 제약을 반영하고, 다중 인스턴스 배포 시에는 claim/lease나 키 순서 보장을 먼저 해결한다. 광범위한 운영 콘솔과 자동 복구 프레임워크는 뒤로 미룬다.

## 6. 코드와 규칙을 다시 정하는 방식

서비스 기본 구조는 `controller → service → repository`로 충분하다. HTTP·저장소 어댑터가 필요하면 `client`, `storage` 등 기능에 맞는 패키지를 둔다. 엔티티와 도메인을 별도 객체로 복제하지 않고, 단순 위임만 하는 Facade·Port·Mapper는 제거한다. 기존 패키지 전부를 이름만 바꾸는 작업은 하지 않는다.

PG·객체 저장소처럼 mock과 실제 구현을 바꿔야 하는 경계에는 작은 인터페이스를 유지한다. 외부 호출과 DB 트랜잭션을 나눌 때 필요한 조율도 남긴다. 인터페이스를 모든 서비스·리포지토리·클라이언트에 의무적으로 만들지 않는다.

공통 코드에는 실제 두 곳 이상에서 반복되는 기술 요소만 둔다. DTO·도메인·리포지토리는 서비스 소유다. 작은 `common/core`, `web`, `jpa`를 따로 유지할 가치가 없으면 합치고, security/event/messaging과 테스트 지원은 실제 의존성에 따라 정리한다. 공통 모듈을 합친다는 이유로 Auth에 JPA 외 Kafka까지 따라오게 만들지 않는다.

| 유지할 규칙 | 제거하거나 선택 사항으로 전환할 규칙 |
|---|---|
| 다른 서비스의 구현/DB에 직접 의존하지 않기 | 모든 클래스의 패키지 위치 고정 |
| 사용자·상품·주문의 소유권과 금액을 서버에서 검증 | 모든 외부 호출에 Port/Facade 강제 |
| 외부 I/O를 긴 DB 트랜잭션 밖에서 수행 | 공통 규칙을 위한 불필요한 계층·DTO 분리 |
| 금전·권한의 중복 및 재처리 결과 보장 | 모든 기능의 이벤트화·CQRS·캐시 적용 |
| 비밀 관리, 마이그레이션, 필수 오류·상태 관측 | 기본 CI의 전 서비스 성능·장애·mutation 검사 |

기존 [설계 결정](decisions.md)은 당시 근거로 보존한다. 구현 단계에서 바뀐 결정에는 대체됨 표시를 넣고 현재 규칙으로 계속 참조되지 않게 한다. 이전 도메인 문서도 현재 기본 범위와 확장 기능 설명을 구분한다. 이 계획 문서의 선택을 또 수십 개 규칙 문서로 분해하지 않는다.

## 7. 실행 순서와 완료 조건

기간은 팀 규모와 운영 데이터 여부가 확인되지 않아 확정하지 않는다. 아래 단계는 각각 검증 가능한 PR 단위로 나누고, 완료 조건을 충족한 뒤 다음 단계로 넘어간다.

| 단계 | 구체 작업 | 완료 조건 |
|---|---|---|
| 0. 기준선과 범위 고정 | 현재 Git 기준점 보존, 실제 사용 API/운영 데이터 확인, 기본 시나리오와 기능 삭제 목록 확정. 기존 E2E에서 핵심 검증만 추출 | 정상 구매·환불 및 권한/중복의 현재 결과 기록. 새 기본 범위와 이관 대상이 한 목록으로 정리됨 |
| 1. 규칙과 개발 환경 축소 | 패키지 강제 규칙 완화, 기본/확장 실행 구성 분리, 공통 전이 의존성 제거. 이때 기존 기능은 여전히 실행 가능하게 유지 | Auth 등 단일 서비스가 관계없는 Kafka/검색/관측 인프라 없이 기동. 기본 CI와 확장 검증 경로 분리 |
| 2. Gateway와 인증 단순화 | 서비스 권한을 먼저 보완, 정적 proxy로 교체하고 기존 OAuth 검증. 그다음 가입/로그인 JWT로 전환 | Flux/Gateway 앱 의존성 제거. 만료/변조 토큰, 타인 자원, 내부 경로 접근 거부. proxy 경유 로그인/콜백/요청 종료 통과 |
| 3. 창작·공개 흐름 재구축 | Studio의 단일 초안/승인/파일 모델, 단일 PUT, 즉시 공개와 Catalog 반영 구현. 수동 승인 연결 후 Review를 기본 구성에서 제외 | 하나의 창작 경로만 존재. 파일 누락·타인 파일·미승인 공개 거부. 공개 이벤트 재전달/순서 역전에도 상품 상태 보존 |
| 4. 조회·다운로드 통합 | Catalog에 목록/검색, License에 티켓 발급 추가. 계약·보안 검증 후 Store/Download와 관련 저장소 제거 | 목록·가격·구매 파일이 새 경로로 조회됨. 환불 후 새 URL 발급 거부. ES/Redis/Mongo 없이 동일 기본 흐름 통과 |
| 5. 커머스·정산 범위 축소 | 단일 상품/KRW/전액 환불로 정리. 할인·복합 상품 제거, Settlement 기본 실행 제외. 취소/환불·지급 실패 보상 검증 | 중복 콜백은 1회 승인 효과, 중복 환불은 1회 환불 효과. 재시작 후 처리 재개. 기존 주문 금액/판매자 사본 보존 |
| 6. 삭제와 문서 정리 | 소비자 전환과 잔여 이벤트 처리 후 구 코드·테이블·의존성·스케줄러·테스트·설정 제거. 시작 안내와 서비스 명세를 새 기본 흐름으로 갱신 | 새 clone에서 기본 구성만으로 가입→등록→공개→구매→다운로드→환불 재현. 구 API/모듈이 기본 빌드·기동 경로에 없음 |

단순화 브랜치에서 **유지할 코드를 골라 축소하는 방식**을 우선한다. 기존 문제 해결 코드까지 전면 폐기하는 새 저장소 재작성은 하지 않는다. Studio의 과도한 모델은 같은 서비스 안에서 최소 모델로 교체한다. 개발 환경은 새 스키마로 검증해도 되지만 기존 Flyway 이력을 수정하지 않는다.

운영 데이터가 있다면 단계 3~5에서 다음 전환 절차를 적용한다. 기존 API를 한시적으로 새 처리로 연결하고 데이터 이관을 검증한 뒤 새 경로로 전환한다. 주문/PG 거래/회원/판매자/이용권 식별자를 보존한다. 기존 Outbox·DLT·소비 지연을 정리하고 소비자 전환이 끝나기 전에는 구 이벤트·테이블을 삭제하지 않는다. 전환 전 백업과 읽기 대사를 준비하고, 새 환경에서 생긴 거래를 고려하지 않은 구 DB 복원은 롤백 수단으로 쓰지 않는다.

현재 확인되지 않은 정책 중 [주문 취소와 환불(Q9)](domain/open-questions.md#q9), [실패한 롤백의 완료 표시(Q10)](domain/open-questions.md#q10), [환불 금액 반올림(Q12)](domain/open-questions.md#q12)는 처리 방향을 분리한다. Q9는 새 기본 커머스에서 해결하고, Q10은 롤백 기능 제거로 기본 경로에서 사라진다. Q12는 Settlement가 운영에 남거나 기존 정산을 이관하면 회귀 검증이 필요하며, 서비스 비활성화만으로 결함이 수정됐다고 기록하지 않는다.

## 8. 검증과 성공 기준

기본 CI는 유지 서비스의 컴파일·단위 테스트·필수 통합 테스트와 다음 인수 시나리오로 구성한다. 기존 테스트는 새 범위에 맞게 정리하되 정확성을 지키는 회귀 테스트를 패키지 규칙과 함께 삭제하지 않는다.

1. 가입·로그인 → 창작자 파일 등록 → 운영자 승인 → 상품 공개 → 구매 → 이용권 → 다운로드.
2. 미인증/만료/변조 token, 타인 프로젝트·주문·파일 접근, 미승인 상품 공개 거부.
3. 가격 불일치, 서명 없는 PG 콜백, 금액/거래 불일치 거부.
4. 중복 이벤트·콜백·환불, 환불 후 늦은 지급, 공개 버전 역전에도 결과 보존.
5. 결제 완료 후 소비 중단·재시작, 환불 착수 후 중단·재시작, 상류 장애 시 다운로드 발급 거부.

성능·chaos·mutation 검사는 관련 변경이나 별도 실험에서 실행한다. 관측은 구조화 로그, 요청 ID, health, 실패/미처리 이벤트 수, 주문별 결제·이용권 상태 조회부터 남긴다. 추가 관측 스택 없이도 막힌 업무를 찾아야 한다.

구조적 완료 기준은 업무 앱 10개에서 기본 6개, Java Gateway 제거, 기본 저장소/메시징 6종에서 3종으로 축소다. 기본 흐름에 CI 자격증명·multipart·release channel·별도 Store/Download 사본이 등장하지 않아야 한다. 기동 시간·메모리·기본 테스트 시간·수동 API 단계 수는 단계 0에서 측정하고 최종 결과와 같은 환경에서 비교한다. 측정 전 임의의 개선율을 약속하지 않는다.

## 9. 고도화를 다시 허용하는 조건

기능 추가 시에는 **현재 생긴 문제, 최소 구현, 검증 결과**를 한 PR에 적는다. 아직 구현하지 않는 확장을 위한 범용 프레임워크·빈 서비스·모든 옵션의 feature flag를 미리 만들지 않는다.

| 확장 | 도입을 검토할 증거 | 확장할 위치 |
|---|---|---|
| multipart/재개 업로드 | 지원해야 하는 파일이 단일 PUT의 제한을 넘거나 재시도 비용이 실제 문제 | Studio 업로드 어댑터. 기존 단일 업로드는 계속 지원 |
| CI OIDC·웹훅 | 반복 업로드를 자동화할 실제 팀/파이프라인과 보안 요구 | Studio의 별도 연동 기능. 일반 창작자 API와 독립 |
| 예약·채널·롤백 | 운영에서 필요한 공개 일정/시험 배포/복구 사례 | Studio 공개 모델. 즉시 공개 기본 흐름 유지 |
| 검색 서비스/Elasticsearch | MySQL 인덱스와 쿼리 개선으로 해결되지 않는 검색 품질·부하 | Catalog 계약에서 Store 분리. 원본 소유권 유지 |
| Redis 캐시 | 측정된 반복 조회 병목과 허용 가능한 만료/불일치 조건 | 병목이 있는 서비스에만 추가 |
| Download 분리·매니페스트 | 다중 파일/패치 또는 파일 접근 트래픽의 독립 배포 필요 | License의 권한 조회 계약과 Studio의 공개 파일 계약 사용 |
| Review 분리 | 수동 승인으로 감당할 수 없는 심사 업무·외부기관 연동 | Studio 제출/승인 경계를 이벤트 계약으로 추출 |
| Settlement 활성화 | 실제 판매자 지급·마감·대사가 제품 범위에 포함 | 구매 당시 확정 금액/판매자와 환불 원본을 기반으로 활성화 |
| OAuth2/OIDC·refresh token | 외부 클라이언트/SSO 또는 재로그인 방식으로 충족 못 하는 세션 요구 | Auth. 업무 서비스의 JWT 검증 계약 유지 |

첫 구현 묶음은 **기준선 확보 → 형식 규칙 완화 → 관계없는 인프라 의존성 제거**로 시작한다. 인증·업무 모델·이벤트를 한 번에 교체하지 않는다. 이후 가장 복잡한 Studio를 단순화하고 원본 조회를 중심으로 기본 서비스 구성을 완성한다.
