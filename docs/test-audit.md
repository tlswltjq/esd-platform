### F1 — 10배로 곱해지는 컨테이너가, 유일하게 방어가 없는 컨테이너다

PR #22 는 `:apps:settlement:test` 에서 깨졌다. Kafka 컨테이너가 `exit 126` 으로 죽고
대기 전략이 시한을 넘겼다. settlement 는 그 PR 이 한 줄도 건드리지 않은 모듈이라
"플레이크" 로 넘길 수 있었는데, **이 리포가 이미 이 실패를 예언해 뒀다.**

```
gradle.properties
  org.gradle.workers.max=2
  # "워커 수만큼 스택이 동시에 뜨므로, CPU 코어 수를 그대로 쓰면
  #  Kafka 가 기동 시한 안에 못 올라와 죽는다."

.github/workflows/ci.yml
  # "워커 수와 힙은 러너의 ~/.gradle/gradle.properties 가 정한다(4 / 6g)"
  runs-on: [self-hosted, Linux, ARM64]   # 4코어 / 23GB
```

리포가 "2 가 한계" 라고 적어 둔 축에서 CI 는 4 로 돈다.
그리고 빌드 1회가 띄우는 컨테이너를 세어 보면 왜 Kafka 가 먼저 죽는지가 분명해진다.

| 이미지 | 기동 수 | 기동 시한 | 재시도 |
|---|---:|---|---|
| `confluentinc/cp-kafka` | **10** | **기본 60초** | **없음** |
| `mysql:8.0` | 8 | 기본 | 없음 |
| `redis:7-alpine` | 3 | 기본 | 없음 |
| `elasticsearch:8.18.6` | 1 | 명시 3분 | 없음 |
| `mongo:7` | 1 | 기본 | 없음 |

**가장 많이 뜨는 것이 가장 안 지켜진다.** Elasticsearch 는 느리다는 이유로
`withStartupTimeout(3분)` 을 받았는데 딱 1번 뜬다. Kafka 는 10번 뜨고,
최대 4개가 동시에 뜨고, 기본 60초를 쓴다. 4코어에서 4스택이 겹치면 60초는 넉넉한 값이 아니다.

#### 뿌리는 타임아웃이 아니라 경계다

`withStartupAttempts(2)` 를 붙이면 이 실패는 사라진다. 그런데 그건 증상을 덮는 것이고,
진짜 문제는 **실행 정책이 그레이들 모듈 경계를 따라간다** 는 것이다.
지금 `:apps:catalog:test` 하나에 컨테이너가 필요 없는 도메인 테스트와
MySQL·Kafka·Redis 를 띄우는 통합 테스트가 **같은 태스크에 섞여 있다.**

```
지금  test 태스크 1개 = 컨테이너 무관 51클래스 + 컨테이너 의존 34클래스
      → 전체가 가장 느리고 가장 취약한 쪽의 실행 프로파일을 물려받는다
      → 도메인 테스트 한 줄 고쳐도 Kafka 기동을 기다린다
      → 병렬도를 올리면 컨테이너가 죽고, 낮추면 단위 테스트까지 느려진다

구조  test            컨테이너 없음 · 최대 병렬 · 수 초
      integrationTest 컨테이너 있음 · 병렬 제한 · 기동 방어
      → 실행 정책이 "어느 모듈인가" 가 아니라 "무엇을 필요로 하는가" 로 정해진다
```

소스셋을 가르면 병렬도 문제가 **둘로 분리돼 각각 옳은 값을 가질 수 있다.**
지금은 하나의 `workers.max` 가 양쪽을 동시에 만족시켜야 해서 어느 쪽도 제대로 못 맞춘다 —
로컬 2, 러너 4 로 서로 다른 값을 쓰면서 주석으로 그 이유를 설명하고 있는 것 자체가
이 경계가 없다는 증거다.

> **조치** — 소스셋을 `test` / `integrationTest` 로 가른다. `build` 는 단위를 먼저 돌려
> 빠르게 실패하고, 통합은 병렬 제한과 함께 뒤에 붙는다. Kafka 기동 방어
> (`withStartupAttempts`·`withStartupTimeout`)는 이 구조 안의 세부로 들어간다 —
> 단독으로 쓰면 다음번엔 MySQL 이 같은 이유로 죽는다.

### F3 — 오류 응답의 HTTP 상태를 지키는 것이 CI 밖의 셸 스크립트뿐이다

`common/core` 에는 **테스트 디렉터리 자체가 없다.**
`ErrorCode` 가 어떤 `HttpStatus` 로 나가는지를 단언하는 자동 테스트가 저장소 전체에 없다.

```
있는 것   assertThat(e.errorCode()).isEqualTo(ErrorCode.CONFLICT)
없는 것   그 CONFLICT 가 실제로 409 로 나가는가

409/403/400/404 를 실제로 확인하는 자리 = smoke-stack.sh 7건
그런데 CI 는 smoke-stack.sh 를 돌리지 않는다.
```

스모크가 기대-실패 7건(`PRICE_MISMATCH` 409, `PAYMENT_TX_MISMATCH` 409,
미보유 403, result 누락 400 …)을 상태코드로 판정하므로 **이 계약을 지키는 것은 스모크 하나다.**
그리고 스모크는 사람이 `remote.sh smoke` 로 손수 부를 때만 돈다.

결과적으로 `ErrorCode` 의 상태 매핑을 잘못 바꿔도 `./gradlew build` 는 초록이다.
[testing.md](testing.md) 6.3 이 "여전히 무테스트" 라고 인정한 항목인데,
**대가가 문서에 적힌 것보다 크다** — 그 공백을 CI 밖의 스크립트가 떠받치고 있다는 사실이 문서에 없다.

> **조치** — `ErrorCode` ↔ `HttpStatus` 를 **열거 전수로** 고정한다. 값 몇 개를 집어 단언하면
> *새로 추가되는* 코드는 계속 무방비다. `ErrorCode.values()` 를 돌며 매핑이 선언돼 있는지까지
> 보는 형태여야 "상수를 추가하면 테스트가 먼저 막는" 구조가 된다.
> `OpenApiSnapshot` 이나 `EventContractTest` 가 목록을 스캔해 대조하는 것과 같은 성질이고,
> 이 리포는 이미 그 패턴을 두 번 썼다.

### F5 — 부하는 쓰기 경로 한 줄만 보고, 사용자가 느끼는 지연은 재지 않는다

k6 시나리오 셋이 전부 **주문 생성 한 경로** 를 민다.
릴레이를 주 지표로 고른 근거(9개 서비스의 단일 병목)는 타당하고,
`pending` 기울기를 판정 기준으로 삼은 것도 좋은 선택이다. 다만 덮이지 않은 면이 넓다.

| 경로 | 부하 시나리오 | 비고 |
|---|---|---|
| 주문 생성 (쓰기) | ✅ smoke · throughput · soak | 3종 전부 여기 |
| Outbox 릴레이 | ✅ `relay-drain.sh` | HTTP 와 분리해 측정 |
| 검색·읽기 (store + Redis) | **없음** | 8-4 가 미측정으로 인정 |
| 결제 콜백 (팬아웃 최대) | ✅ `payment-callback.js` | `PaymentCompleted` → 4개 서비스 |
| 컨슈머 측 처리 | ✅ `collect-consumer.sh` | 랙·소비율·처리시간·리스너 예외 |
| 종단 지연 | ✅ `e2e_fulfillment_latency` | 아래 참고 |

가장 아픈 것이 마지막 줄이다. **"주문을 넣고 몇 초 뒤에 게임을 받는가" 를 재는 지표가 없다.**
`http_req_duration` 은 주문 API 응답까지고, `pending` 은 적체의 대리 지표다.
둘 다 초록인데 종단 지연이 30초일 수 있다 — 결제 완료에서 라이선스 지급까지
Kafka 홉이 두 번, 릴레이 폴링이 두 번 끼기 때문이다.
그리고 그 숫자가 사용자가 실제로 느끼는 유일한 숫자다.

> **✅ 조치했다** — `scripts/perf/payment-callback.js` 가 결제 콜백을 밀고 `orderNo` 로 라이브러리를
> 폴링해 **지급까지의 벽시계 시간을 `e2e_fulfillment_latency` 트렌드로 기록**한다.
> e2e 쪽에도 같은 구간을 재는 자리를 뒀다(5절 5번).
>
> 재면서 하나 배웠다 — 폴링이 조건 성립 전에 받는 404 가 `http_req_failed` 에 잡혀 **18.6%** 가 나왔다.
> 전부 정상 대기였다. 폴링 요청에만 `expectedStatuses(200, 404)` 를 줘서
> **아직 도착하지 않은 것**과 **시스템이 틀린 것**을 갈랐다(지금 0.00%).

### F6 — 단위·구조 층은 손댈 곳이 없다

점검하면서 반증을 찾으려 했는데 나오지 않았다. 몇 가지는 이 규모에서 드물게 좋다.

- **ArchUnit 규칙을 검사하는 메타 테스트가 있다.** `ArchRuleEnforcementTest` 가 위반 픽스처
  (`GuardlessService`, `MisnamedEndpoint` …)로 규칙이 실제로 실패하는지 본다.
  규칙이 공허 통과하는 것은 흔한 함정인데 여기선 막혀 있고, 실제로 [D-021](defects.md#d-021) 을 잡아냈다
- **커버리지 대신 뮤테이션을 쓴다.** 그리고 `targetTests` 미지정 때문에 `api.*` 테스트가
  판정에 참여하지 못하고 있던 것까지 찾아내 고쳤다 — 측정 도구의 사각지대를 의심한 흔적이다
- **OpenAPI 스냅샷이 응답 계약을 고정한다.** 31개 엔드포인트에 `jsonPath` 를 손으로 붙이는 대신
  명세를 커밋해 대조하는 판단은 유지비 대비 효과가 좋다
- **테스트 격리를 삭제가 아니라 키 공간 분리로 한다.** 병렬에서도 안전하고
  "내 데이터만 보인다" 가 테스트 안에서 자명해진다

남은 미커버는 [testing.md](testing.md) 6.2 가 이미 전수로 적어 두었고,
등급도 "미커버" 로 정직하게 매겨져 있다. **여기에 보탤 것이 없다.**

## 4. 스모크와 e2e — 언제 도는가

PR #22 의 관찰은 정확하다. `smoke-stack.sh` 는 이름과 달리 스모크가 아니다 —
58건 중 7건이 실패를 기대하고, 수수료 30% 를 직접 계산해 대조하고,
중복 콜백 전후의 라이선스 수를 세어 멱등을 확인한다. 인수 테스트가 하는 일이다.

### 4.1 "스모크" 라는 한 단어가 둘을 가리키고 있다

| 구분 | 건수 | 내용 | 필요 조건 | 언제 |
|---|---:|---|---|---|
| **게이트** | 13 → **14** | 0장 컨테이너 · 4장 인프라 도달성 · 5장 게이트웨이 차단 · 6장 액추에이터 10종 | 데이터 불필요 · 수 초 | 스택 배포 직후 자동 |
| **인수** | 45 → **42** | 1장 트랙A · 2장 트랙B · 3장 트랙C · 3-B 실패경로 | 데이터 생성 + 전파 대기 · 36초 | main push |

둘 다 갈라 놓았다. 게이트는 `scripts/stack-wait.sh` 로(4.2), 인수는 `:e2e` 모듈로(5절 4번).

건수가 움직인 이유는 성질이 다르다. 게이트는 **늘었다** — kafka 직접 프로브가 더해졌고,
브로커가 죽어도 나머지 열세 건이 전부 초록이던 자리다. 인수는 **합쳐졌다** —
한 번의 호출을 두 번 판정하던 세 자리가 한 테스트의 여러 단언이 됐다(5절 4번의 대응표).

두 개는 **언제 돌아야 하는지가 애초에 다르다.** 한 파일에 있어서 같은 시점에 묶여 있었을 뿐이다.

### 4.2 게이트 14건 — 배포의 일부다

CI 이야기가 아니다. `remote.sh stack` 직후에 자동으로 도는 것이고,
사람이 따로 부를 일이 아니다. PR #22 가 이미 `stack_wait` 추출 계획을 적어 뒀으므로
**아래 1번과 같이 처리할 수 있다** — 소스셋 분리와 겹치지 않고 e2e 모듈을 기다릴 이유도 없다.

다만 선행 조건이 하나 있다. **지금 0장은 게이트 역할을 못 한다.**

```bash
unhealthy=$(docker ps --filter health=unhealthy --format '{{.Names}}')
[ -n "$unhealthy" ] && bad ... || ok "unhealthy 없음"

→ 컨테이너가 0개여도 통과한다 (빈 결과를 "정상" 으로 읽는다)
→ OCI 20개 중 7개가 헬스체크 미정의 · 거기에 kafka·redis·mongodb 가 있다
→ 브로커가 죽어도 이 장은 초록이다
```

게이트로 세우려면 게이트가 실제로 막아야 한다.
액추에이터 10종을 맨 앞으로 옮겨 `exit 2` 로 세우는 것이 선행이다.

> **✅ 처리됨** — `scripts/stack-wait.sh` 로 옮기면서 고쳤다([defects.md](defects.md#d-023) D-023).
> 대기(`remote.sh` 의 `stack_wait`)와 판정(0·4·5·6장)이 갈라져 있던 것을 한 파일로 합쳤고,
> 기대 컨테이너 20종을 이름으로 대조하며, 부트에 지표가 없는 kafka 는 직접 찌른다.
> 게이트 14건 · `stack up` 이 자동으로 부르고 불통과면 `exit 2` 로 배포를 세운다.
> **깨뜨려서 확인했다** — 앱 10종을 내리면 12건이, 브로커만 내리면 2건이 빨개진다.
> (판정이 13 → 14 로 는 것은 kafka 직접 프로브가 더해졌기 때문이다)

### 4.3 인수 45건 — PR 마다가 아니라 main push

| | PR 마다 | main push |
|---|---|---|
| 스택 재기동 | 필요 | 필요 |
| CI 시간 | 6분 → 12분 | 6분 → 12분 |
| 빈도 | PR 수만큼 | 하루 몇 번 |
| 러너 1대 | **큐가 생긴다** | 감당된다 |
| 실패했을 때 | 머지 차단 | revert |

러너가 1대인 것이 결정적이다. 그리고 e2e 가 잡는 것은 서비스 *사이* 의 결함이라
PR 단위보다 통합 시점에 의미가 있다.
급할 때 PR 에 붙이는 문은 `workflow_dispatch` 나 라벨로 열어 둔다.

### 4.4 "CI 에 스모크 태우기" 는 건너뛴다

PR #22 는 3단계를 제안했다 — ① CI 에 태운다 → ② `:e2e` 모듈로 승격 → ③ curl 이 못 보는 것.
방향은 맞는데 **①은 건너뛰기를 권한다.** 두 가지가 겹친다.

**부하** — 스모크는 20컨테이너 스택이 이미 떠 있어야 돈다. CI 에 붙이려면 같은 잡에서
그 스택을 올려야 한다.

```
현재      Testcontainers 23개 (최대 4스택 동시)          → 여기서 Kafka 가 죽었다
①이후    Testcontainers 23개 + compose 스택 20개       → 같은 4코어 / 23GB
```

방금 빌드를 깨뜨린 경합에 20컨테이너를 더 얹는 셈이다. 방어선이 인프라 경합으로
간헐 실패하기 시작하면 **사람들이 빨간불을 무시하는 법을 배운다.**
그건 방어선이 없는 것보다 나쁘다.

**버려질 작업** — PR #22 본문이 스스로 적어 뒀다. "`smoke-stack.sh` 는 2단계에서 사라진다."
즉 ①은 **지워질 예정인 셸 스크립트에 CI 배관을 놓는 일** 이다.
`stack_wait` 추출은 어차피 재사용되니 남지만, 스크립트를 잡에 태우고
종료 코드 3 을 CI 가 해석하게 만드는 배관은 2단계에서 통째로 버려진다.

①의 값어치는 "지금 당장 회귀 방어선이 생긴다" 인데, 그 값어치의 상당 부분은
**F3 를 제대로 하면 컨테이너 없이 회수된다.**

```
BUILD SUCCESSFUL in 1s
```

`CI` 환경변수가 있을 때뿐이고, 로컬을 열어 둔 근거는 "반복 루프에서는 캐시가 맞다" 였다.
그 근거가 이 층에서는 성립하지 않는다 — **e2e 의 진짜 입력은 소스가 아니라 떠 있는 스택**이라
그레이들이 볼 수 없고, 앱을 재배포하고 다시 부르는 것이 기본 사용법이기 때문이다.

실행 건수 보고만으로는 못 막혔다는 점이 더 중요하다. 건너뛴 태스크는 `afterSuite` 자체를 부르지 않아
**요약 줄이 아예 안 나온다** — 요약이 없는 것과 0건인 것이 화면에서 같아 보인다.
`outputs.upToDateWhen { false }` 를 조건 없이 걸어 막았다.

지연만 임계값을 세우지 않는다. 러너 부하에 따라 흔들리는 숫자를 게이트로 세우면
간헐 실패가 나고, 그러면 사람들이 빨간불을 무시하는 법을 배운다 — 4.4 에서 ①을 건너뛴 것과 같은 논리다.
상한은 전파가 **끊긴 것**을 잡는 선으로만 둔다. 추세는 k6 가 본다
(`scripts/perf/payment-callback.js` 의 `e2e_fulfillment_latency` — 실측 avg 926ms).

#### 트레이스 — 자랑에 방어선을 붙였다

`decisions.md` 17번이 메운 간극(Outbox 가 발행을 다른 스레드로 미뤄 끊기던 Kafka 구간 추적)에
회귀 방어선이 하나도 없었다. **깨뜨려서 확인했다.**

```
payment 에 SPRING_KAFKA_TEMPLATE_OBSERVATION_ENABLED=true 를 주고 재기동

관측 — Kafka 를 건너는 트레이스 연결 > traceId 가 6개 서비스에 걸친다  FAILED
  Tempo 에서 traceId=1b8c97… 조회 — 60초 안에 성립하지 않았다.

```

자동 계측이 릴레이의 복원 헤더를 덮어쓰자 컨슈머들이 **새 트레이스를 시작했다** —
17번이 예고한 그대로다. 되돌리고 46/46 초록을 다시 확인했다.

여섯이 되는 것은 **게이트웨이를 거치기 때문**이다
(gateway → payment → license·order·settlement → download). 직접 부르면 다섯이다.

#### 적체 판정에서 전제 하나가 틀렸다

처음에는 아홉 종 전부에 적체 0 을 요구했다가 `store`·`download` 의 404 로 빨개졌다.
**둘은 순수 컨슈머다** — 받은 것을 색인과 권한 사본에 쓰고 끝나므로 `outbox_event` 도 릴레이도 없다.

404 를 조용히 0 으로 읽었다면 편했겠지만, 그러면 **발행하는 앱에서 릴레이 구성이 빠져 404 가 되는 것**도
같이 초록이 된다. 그래서 목록을 발행 7종으로 좁혔고, 그 목록에서의 404 는 실패로 남겼다.
DLT 쪽 404 는 의미가 정반대라(카운터가 첫 유입에서야 생긴다) 0 으로 세되 화면에 남긴다.

### 시점표

```
✅ 1번 직후   게이트 14건 → 배포에 붙는다      ← 0장 공허 통과(D-023) 수정이 선행이었다
✅ 2번 직후   PR 이 오류 응답 계약을 컨테이너 없이 지킨다
✅ 4번 직후   인수 42건 → main push 에 붙는다
✅ 5번 직후   관측 4건이 같은 하네스에 얹힌다 (총 46건)
```

**수동으로 남은 관통 검증은 없다.** 게이트는 `stack up` 이, 인수는 main push CI 가 부른다.
사람이 손으로 부르는 길(`remote.sh gate` · `remote.sh e2e`)은 커밋 전에 확인하려는 경우에만 쓴다.

1·2 를 앞에 둔 이유가 순서 자체에 있었다.
**1은 뒤의 전부가 올라앉을 바닥이고, 2는 4를 미룰 수 있게 해 주는 대가 지불이었다.**
이 둘 없이 4로 직행했다면 e2e 가 설 때까지 오류 응답 계약이 무방비였고,
e2e 가 서고 나서도 컨테이너 경합 위에서 간헐 실패했을 것이다.

**PR #22 의 본체 가치는 CI 투입과 무관하게 이미 확보돼 있었다.**
그 PR 이 한 일은 스크립트가 거짓말하지 않게 만든 것이고, 그래서 손으로 불러도 결과를 믿을 수 있었다.
자동화 여부보다 이쪽이 먼저인 것이 맞았다.

## 6. 소견을 구조의 언어로 다시 쓰면

| 소견 | 없는 경계 |
|---|---|
| F1 | 실행 정책이 **필요 자원** 이 아니라 모듈 경계를 따라간다 |
| F3 | 도메인 오류 → HTTP 상태 계약에 **주인이 없다** (셸이 대신 지킨다) |
| F2 · F4 | 문서와 실물을 **맞물리게 하는 장치가 없다** (스냅샷·전수 대조를 이미 쓰는데 여기엔 안 썼다) |
| F5 | 측정이 **서비스 단위** 에서 끝나고 흐름 단위로 올라가지 않는다 |

그래서 개별 증상을 하나씩 막는 것보다 **경계를 세우는 순서로 가는 편이 낫다.**
`withStartupAttempts` 두 줄로 F1 을 덮을 수 있지만, 그러면 다음번엔 MySQL 이
같은 이유로 죽고 같은 자리에 또 두 줄을 붙이게 된다. 소스셋을 가르면 그 부류가 통째로 닫힌다.

나머지 셋도 성질이 같다 — 이 리포는 **전수 대조로 계약을 고정하는 패턴을 이미 세 번 썼다**
(OpenAPI 스냅샷, `EventContractTest`, `ArchRuleEnforcementTest`).
F3 와 F2 는 그 패턴을 안 쓴 자리일 뿐이다.
