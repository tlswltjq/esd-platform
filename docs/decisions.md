# 설계 결정 기록

구조를 바꾸며 내린 판단과 그 근거를 남긴다.
**무엇을 했는지는 커밋이 말하고, 여기서는 왜 그렇게 했고 무엇을 포기했는지를 적는다.**

각 항목은 배경 → 결정 → 근거 → 버린 선택지 순이다.

과거 기록의 `infrastructure` 패키지 표기는 당시 명칭이다. 2026-10-18 명칭 변경 이후의 기준은 [결정 26](#26-외부-연동-구현-패키지를-adapter로-부른다)과 [패키지 변경 기록](adapter-package-rename-plan.md)을 따른다.

과거 기록의 CI·E2E Compose 파일명과 포트 구분은 당시 구성이다. 2026-10-21 이후 실행은 [결정 27](#27-compose는-기본-정의와-로컬-접속-오버라이드만-둔다)과 [Compose 실행 구성](compose-layout.md)을 따른다.

## 1. 모듈을 core 와 api 로 가른다

**배경** — 서비스마다 `api` / `application` / `domain` / `infrastructure` 로 나뉘어 있었지만
경계를 강제하는 장치가 없었다. 실제로 응답 DTO 를 서비스가 반환하고, 서비스가 어댑터를
직접 참조하는 코드가 섞여 있었다.

**결정** — `core`(단일 도메인)와 `api`(바깥과의 접점)로 가르고, ArchUnit 으로 강제한다.

```
core/{domain, port, service}     api/{controller, listener, scheduler, application}     infrastructure/
```

**근거** — 규칙이 없으면 경계는 시간이 지나며 반드시 흐려진다.
규칙을 처음 돌렸을 때 위반이 **166건**이었고, 그중 상당수는 눈으로 읽어서는 보이지 않던 것이다.

**버린 선택지** — 관례로만 정하고 리뷰에서 잡기. 이미 흐려진 뒤였으므로 설득력이 없었다.

---

## 2. 인바운드 어댑터는 컨트롤러만이 아니다

**배경** — 최초 구상은 진입점을 `api/controller` 하나로 뒀는데, 실제 진입점은 셋이었다 —
HTTP 9개, Kafka 리스너 10개, 스케줄러 1개.

**결정** — `api/listener`, `api/scheduler` 를 컨트롤러와 동급으로 둔다.

**근거** — Kafka 리스너는 컨트롤러와 성격이 같다(봉투를 풀어 유스케이스를 부른다).
`infrastructure` 에 두면 "core 는 api 를 모른다"는 핵심 규칙이 리스너에는 적용되지 않는다.

---

## 3. 파사드를 강제하지 않는다

**결정** — 인바운드가 `core.service` 를 직접 불러도 된다. 조율이 필요한 곳에만 파사드를 둔다.

**근거** — 9개 모듈 중 실제 조율이 있는 곳은 order 하나뿐이었다.
전부 강제하면 위임만 하는 껍데기가 8개 생긴다.

**대가** — "언제 파사드를 두는가"가 판단의 영역으로 남는다.
기준은 트랜잭션이다 — 외부 동기 호출을 트랜잭션 밖에 두어야 하면 파사드를 만든다(order 가 그 경우다).

---

## 4. 도메인 객체와 엔티티를 분리하지 않는다

**결정** — `core/domain` 에 JPA 어노테이션과 Spring Data 리포지토리를 허용한다.

**근거** — 모듈당 애그리거트가 1~3개다. 매핑 계층을 두는 비용이 얻는 것보다 크다.
DDD 의 "리포지토리 인터페이스는 도메인 계층에" 해석과도 일관된다.

**대가** — `core` 가 완전히 순수하지는 않다. 대신 규칙을 "전송 기술(HTTP/Kafka)을 모른다"로
좁혀서 지킨다. 영속성은 예외로 두되 그 예외를 명시한다.

---

## 5. 모든 포트는 core 에 둔다

**배경** — 처음에는 외부 **시스템** 포트(PG·CDN·스토리지)는 `core/port` 에,
외부 **도메인** 포트(catalog)는 `api/application/port` 에 두었다.

**결정** — 예외 없이 `core/port` 한 곳.

**근거** — 포트를 찾을 곳이 둘이면 "어디 있더라"가 매번 판단이 된다.
"확정된 가격이 필요하다"는 것도 주문 도메인의 요구이지 어댑터의 사정이 아니다.
DDD 가 리포지토리 인터페이스를 도메인에 두는 것과 같은 자리다.

**따라오는 규칙** — 포트 패키지에는 인터페이스만 둔다.
포트가 주고받는 값은 `core/domain` 의 모델이다(리포지토리가 도메인 객체를 반환하는 것과 같다).

---

## 6. 트랜잭션과 멱등 가드는 서비스가 소유한다

**배경** — 리스너 10개 중 7개가 `@Transactional` 을 달고 `ProcessedEventGuard` 를 직접 불렀다.
나머지 3개는 서비스가 했다. 두 방식이 공존했다.

**결정** — 서비스로 통일한다. 리스너는 역직렬화와 위임만 한다.

**근거** — 취향이 아니라 **필수**였다. 리스너가 트랜잭션을 열면 Saga 보상 경로가 성립하지 않는다.
내부에서 예외가 나면 바깥 트랜잭션이 rollback-only 로 마킹되고, `catch` 로 삼켜도 커밋 시점에
`UnexpectedRollbackException` 이 난다. license 가 리스너에 트랜잭션을 안 단 이유가 그것이었다.

부수 효과로 어댑터를 갈아끼워도(Kafka → SQS, 운영툴 재처리 API) 멱등성 보장이 따라가고,
Kafka 없이 서비스 단위로 멱등성을 테스트할 수 있게 됐다.

**대가** — 서비스 시그니처에 `eventId`, `eventType` 이 올라온다.
core 가 알게 되는 것은 Kafka 가 아니라 "이 호출은 중복될 수 있고 식별자가 따라온다"는 사실뿐이고,
멱등성은 도메인 서비스의 정당한 관심사이므로 감당할 만하다고 판단했다.

payment 에서만 진입점을 나눴다 — 환불은 HTTP 와 이벤트 양쪽에서 오는데
HTTP 경로에는 넘길 `eventId` 가 없다.

**규칙** — `멱등_가드는_서비스가_소유한다` 가 인바운드에서 `ProcessedEventGuard` 로 가는 의존을 막는다.
트랜잭션 위치만 검사해서는 부족했다 — 트랜잭션이 서비스에 있어도
"이 메시지를 이미 처리했는가"의 판정만 어댑터로 새어 나갈 수 있다.

## 7. 캐시에 실리는 값은 API 응답이 아니다

**배경** — catalog·store 의 조회 서비스가 응답 DTO 를 반환했다. `core → api` 역방향이었고,
실제로 `api ↔ application` 순환으로 잡혔다.

**결정** — core 가 읽기 모델(`ProductView`, `StoreProductView`)을 반환하고 컨트롤러가 응답으로 옮긴다.

**근거** — 방향 문제만이 아니었다. 이 값은 `GenericJackson2JsonRedisSerializer` 로 Redis 에 실린다.
엔티티는 setter 가 없어 역직렬화가 깨지므로 **애초에 엔티티를 반환할 수도 없었다.**
읽기 모델을 따로 두면 캐시 페이로드가 API 계약과 분리되어, 응답 필드를 바꿔도 캐시 스키마가 그대로다.

---

## 8. 멱등성은 두 겹으로, 다만 막는 대상이 다르다

**결정** — Inbox 가드 `(event_id, consumer_group)` 와 도메인 유니크를 함께 건다.
store·download 는 둘 다 두지 않는다.

**근거** — 두 겹이 같은 것을 두 번 막는 게 아니다.

| 층 | 막는 것 |
|---|---|
| Inbox 가드 | **같은 메시지**의 재전달 |
| 도메인 유니크 | **경위가 어떻든 같은 결과** (이벤트 재발급, 수동 재처리) |

store·download 는 문서 ID 고정 upsert 라 연산 자체가 멱등이다.
멱등성은 인프라가 주는 보장이 아니라 연산의 성질이므로, 멱등한 연산에는 장치를 얹지 않는다.

**전제** — Outbox 릴레이는 at-least-once 다. 중복 발행을 막지 않고 소비 측에서 흡수한다.
exactly-once 전달보다 싸고, 이 선택의 대가가 곧 멱등성이다.

## 9. 스텁은 프로파일로 격리한다

**배경** — 외부 연동 5개 중 4개가 스텁인데 전부 무조건적인 `@Component` 였다.
실제 어댑터를 붙이면 같은 포트에 빈이 둘이 되어 기동이 실패했을 것이다.

**결정** — 스텁에 `@Profile("!prod")`. 교체 대상이 둘인 포트는 `@ConditionalOnProperty`.

**근거** — `prod` 에서 구현이 없으면 "no qualifying bean" 으로 즉시 실패하는 편이 낫다.
운영에서 스텁이 조용히 도는 것만은 일어나면 안 된다.

**규칙** — `스텁_어댑터는_격리한다` 가 `Mock*`/`Stub*`/`Fake*` 로 시작하는 어댑터에
`@Profile` 또는 `@ConditionalOnProperty` 를 요구한다. 조건을 거는 것이 관례가 아니라 통과 조건이다.

**대가** — 이름으로 스텁을 식별하는 검사라 완벽하지 않다. `LocalPgClient` 처럼 다르게 지으면 놓친다.
대신 규칙이 이름을 강제하는 셈이 되고, 놓치는 경우도 "조건 없는 스텁" 이라는 가장 흔한 실수는 아니다.

## 10. 머신별 값은 리포에 적지 않고 계산한다

**배경** — 작업 장소가 자주 바뀌는데, `~/.testcontainers.properties` 에 이 머신의 홈 경로가
박혀 있었다. 다른 머신에서는 없는 소켓을 가리키며 실패한다 — 설정하지 않은 것보다 나쁘다.

**결정** — 값이 아니라 계산식을 커밋한다.

```sh
export DOCKER_HOST="$(docker context inspect --format '{{.Endpoints.docker.Host}}')"
```

JDK 는 foojay 리졸버가 조달한다.

**검증** — `~/.testcontainers.properties` 를 비우고 파생된 `DOCKER_HOST` 만으로 테스트가 통과했다.
CI 는 이 머신의 흔적이 없는 환경에서 매번 같은 것을 증명한다.

> 이 계산식은 처음에 `.envrc`(direnv)로 커밋했다가 12번에서 뺐다.
> 계산식이 틀려서가 아니라, 그것을 실어 나르는 도구가 리포의 요구사항이 되기 때문이다.

## 11. 개발 환경은 로컬 Docker와 Gradle Wrapper를 기준으로 한다

**결정 (2026-09-16)** — 개발 컨테이너와 호스트 소켓 래퍼를 제거한다. 로컬은 JDK·Docker와
`./gradlew`를, 인프라가 필요한 최종 검증은 원격 러너를 사용한다.

**근거** — 로컬과 CI에 Docker가 준비되어 있어 별도 개발 환경 계층을 유지할 실익이 없다.
도구 구성은 필요해질 때 검증 가능한 형태로 다시 만든다.

## 12. 로컬 경로에서 mise 와 direnv 를 뺀다

**배경** — 11번의 "로컬 직접" 경로는 `.mise.toml`(JDK 조달)과 `.envrc`(DOCKER_HOST 계산)를
전제로 했다. 정작 주 랩탑을 확인하니 **둘 다 설치되어 있지 않았다.**
그런데도 빌드는 멀쩡히 돌고 있었다.

**결정** — `.mise.toml` 과 `.envrc` 를 지운다. 리포가 요구하는 설치 도구를 0개로 만든다.

**근거** — 측정이 `.mise.toml` 의 전제를 깼다.

```
$ env -u JAVA_HOME ./gradlew --version
Launcher JVM:  17.0.18 (Homebrew)          # 21 아니어도 돈다

$ env -u JAVA_HOME ./gradlew -q javaToolchains
Microsoft JDK 21.0.10  ...  Detected by: IntelliJ    # mise 아닌 IDE 가 조달했다
```

주석에 적어둔 "Gradle 런처 JVM 이 미리 있어야 한다"는 닭과 달걀은 맞다.
틀린 것은 **그 JVM 이 21 이어야 한다**는 부분이다 — Gradle 8.14 는 17 이상이면 뜨고,
컴파일은 toolchain 이 따로 잡는다. JDK 가 0개인 머신은 이미 A·B 경로가 덮는다.

`.envrc` 는 계산식 자체는 옳지만(10번), 그 세 줄을 위해 direnv 설치를 요구한다.
`DOCKER_HOST` 는 README 에 한 줄로 적으면 되고, 자동화하고 싶은 사람은 `~/.zshrc` 에 둔다.

**대가** — macOS 사용자는 셸마다 `DOCKER_HOST` 를 직접 export 해야 한다.
자동화를 리포에서 개인 환경으로 옮긴 것이고, 그 대신 리포의 설치 요구가 사라진다.

**더 큰 교훈** — 10번은 *검증되지 않은 머신별 값* 이 없느니만 못하다고 했다.
같은 것이 **검증되지 않은 조달 경로**에도 성립한다.
`.mise.toml` 은 커밋된 그날부터 한 번도 실행되지 않은 채 "이 리포는 mise 를 쓴다"고 말하고 있었다.
설정은 자기가 도는지 스스로 증명하지 않는다. 실행되는 것만이 증명한다 — CI 가 그 자리다.

## 13. `@ConfigurationProperties`는 config에서 바인딩한다

**2026-10-16 변경.** 기존 결정은 설정값을 사용하는 계층에 바인딩 객체를 두는 것이었다.
당시에는 설정 객체를 config로 옮기면 core가 config에 의존한다고 보았다. 이번 변경에서는 객체 조립도 함께 옮겨 그 의존을 제거한다.

**결정** — 환경변수·YAML을 읽는 `@ConfigurationProperties`와 `@Value`는 앱의 config에 둔다.
config가 기본값·범위를 검증하고 서비스·모델·어댑터에는 필요한 일반 값이나 구성된 클라이언트만 전달한다.
공통 라이브러리의 Properties 정의도 config에 두고 기존 AutoConfiguration이 값을 추출해 실행 객체를 조립한다.
스케줄러의 실행 간격·활성화 조건은 진입점의 실행 설정이며 core에 전달하지 않는다.

```text
환경 설정 → config의 바인딩·검증·객체 조립
                   → 서비스: 처리 수·재시도 간격·업로드 제한
                   → 도메인 정책: 수수료율·기준 식별자
                   → 어댑터: HTTP/SDK 클라이언트·서명 값
```

**근거** — 설정 키·프로필·바인딩 방식의 변경 이유와 업무 규칙의 변경 이유를 나눈다.
수수료율 자체는 도메인 값이지만 그 값을 환경변수에서 읽는 방식까지 도메인의 책임은 아니다.
바인딩 객체의 위치만 바꾸면 core → config 의존이 생긴다. config의 Bean 팩토리가 일반 값을 생성자에 전달하도록 함께 바꾼다.
MVP에서는 값 몇 개를 전달하기 위해 별도의 설정 포트·정책 계층을 의무적으로 만들지 않는다.

**유지하는 것** — 설정 키·환경변수·기본값·단위와 업무 동작, 각 업무 트랜잭션은 유지한다.
설정값의 Properties 네이밍과 불변 record 규칙도 유지한다.

**검사** — ModulePackageRules는 Properties의 config 배치, 바인딩 객체의 외부 전달 금지,
config 밖의 Environment/Binder 사용·Value 주입을 검사한다. CommonLibraryRules는 공통 Properties 배치와 실행 객체의 바인딩 의존을 검사한다.
규칙 자체는 위반 픽스처와 올바른 설정 픽스처로 검증한다.
전역 적용 내역과 실제 실행 근거는 [설정 경계 개선 기록](core-boundary-audit.md#설정-바인딩과-내부-입력-경계-개선)을 따른다.

## 14. `libs/` 를 `common/` 으로 바꾸고 접두사를 뗀다

**배경** — 공용 모듈이 `libs/common-core` 였고 그 패키지는 `com.stove.common.core` 다.
모듈명 하나가 패키지 두 조각을 하이픈으로 눌러 담고 있었다.
`apps/order` → `com.stove.order` 는 조각 대 조각인데 이쪽만 규칙이 달랐다.

**결정** — `common/core`. 디렉터리가 곧 패키지 조각이다.

**근거** — 셋이 같은 방향을 가리켰다.

1. 경로가 패키지와 1:1 이 된다. 두 트리가 다른 규칙을 쓸 이유가 없었다.
2. `libs` 는 Gradle 이 이미 쓰는 이름이다 — `build/libs` 가 산출물 디렉터리이고
   Dockerfile 이 `apps/*/build/libs/*.jar` 를 집는다. 한 리포에서 같은 단어가 두 뜻이었고,
   실제로 참조를 세려고 `libs/` 를 grep 했을 때 소스와 jar 경로가 섞여 나와 걸러내야 했다.
3. 접두사가 부모 디렉터리와 중복이다. `common/common-core` 라고 쓰지 않는 것과 같은 이유다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| `libs/core` — 디렉터리는 두고 접두사만 제거 | `com.stove.common.core` 의 `common` 이 경로에서 사라진다. 지금보다 나쁘다 |
| `common/testing` — `:common:test:test` 가 어색해서 | 패키지도 따라가야 하고 import 15개가 바뀐다. 이 변경의 명분(경로 = 패키지)을 스스로 깨는 값이다. 어색함은 아무도 치지 않는 명령어에만 나타나고 `./gradlew test` 는 그대로다 |

**대가** — `apps`/`libs` 는 종류 대 종류였는데 `apps`/`common` 은 종류 대 역할이 된다.
분류 기준이 섞이는 것은 맞다. 다만 "배포하는 것 / 그들이 공유하는 것" 으로 읽히고,
매일 얻는 것은 경로-패키지 일치 쪽이 크다고 봤다.

**산출물 이름은 유지했다** — `:common:core` 를 그냥 두면 jar 가 `core-0.0.1-SNAPSHOT.jar` 로 나온다.
`core.jar` / `web.jar` / `test.jar` 는 클래스패스에서 어느 프로젝트 건지 알 수 없다.
`archivesName` 으로 `common-` 을 되살려 **공용 jar 7개가 리네이밍 전 이름 그대로다**
(`common-core-0.0.1-SNAPSHOT.jar` 등). 산출물 이름은 하나도 바뀌지 않았다.
**사람이 읽는 경로에서는 중복을 없애고, 기계가 뱉는 이름에서는 유일성을 지킨다.**

> CI 는 통과했지만 앱 테스트 10개가 전부 `FROM-CACHE` 였다 — Gradle 이 입력이 같다고 판단해
> 실제로 돌지 않았다. 리네이밍이 no-op 이라는 간접 증거이긴 하나 그것만 믿지 않고
> 캐시를 끄고 61개 태스크를 전부 실행해 확인했다(4분 49초). 12번의 교훈과 같은 자리다 —
> **돌지 않은 검사는 통과한 것이 아니다.**

## 15. 인프라가 필요한 검증은 원격 러너로 옮긴다

**배경** — 주 랩탑은 RAM 8GB 이고 Docker 에 준 것은 **3.83GB** 다.
`gradle.properties` 의 `workers.max=2` 는 성능 선택이 아니라 그 한계에 대한 항복이었고
(주석이 "코어가 아니라 Docker 에 준 메모리가 한계선"이라고 적고 있다),
**전체 스택을 한 번도 동시에 띄운 적이 없었다.**

그 대가는 이미 치러져 있었다. `performance.md` 의 HTTP 경로 측정이 무효였다 —
릴레이를 **완전히 끈** 구성이 개선 구성과 같은 숫자(44.9 RPS)를 냈다.
`pageouts` 150만, 스와핑 중에 잰 값이었다. 코드가 아니라 환경을 측정하고 있었다.

**결정** — 로컬 직접 실행과 원격 러너로 역할을 나눈다.

| 경로 | 호스트 가정 | 용도 |
|---|---|---|
| 로컬 직접 | JDK + Docker | 단위 테스트·ArchUnit |
| **OCI self-hosted 러너** | **없음 (push 하면 돈다)** | **인프라가 필요한 전부** |

경계는 **무엇이 컨테이너를 요구하는가**다 —
단위 테스트는 로컬이 빠르고 CI 를 기다릴 이유가 없다.

**측정** — 첫 self-hosted 빌드 (Ampere A1, 4코어 23GB, aarch64):

| | |
|---|---|
| 동시 컨테이너 최대 | **15** |
| 최저 available 메모리 | 16,127 MiB |
| 러너 cgroup 피크 | 5,264 MiB |
| swap 사용 | **0** |

로컬 Docker 총량이 3,919 MiB 다. 15개가 동시에 뜨면서 스왑을 한 번도 건드리지 않았다.
`workers.max` 를 4로 올린 것은 러너의 `~/.gradle/gradle.properties` 이고,
**리포의 2/2g 는 그대로 두었다** — 그 값은 3.83GB 머신의 값이고 그 머신은 여전히 존재한다(10번).

**대가 1 — 격리가 없다.** self-hosted 러너는 docker 그룹을 요구하고 docker 그룹은 사실상 root 다.
리포가 PRIVATE 이라 fork PR 이 러너에서 도는 경로가 없다는 것이 전제다.
**공개 리포였다면 이 구성은 금지다.** 전용 사용자(`runner`)와 홈 밖 워크스페이스로 완화했을 뿐,
격리했다고 말할 수는 없다.

**대가 2 — 잡 사이에 상태가 남는다. 그래서 CI 가 조용히 거짓말을 했다.**

`ubuntu-latest` 는 매 잡이 새 머신이라 `~/.gradle` 이 남지 않는다.
self-hosted 는 남는다. 그것이 `org.gradle.caching=true` 와 만나 이렇게 됐다.

| 실행 | 소요 | 태스크 |
|---|---|---|
| 1회차 | 5분 57초 | **84 executed** |
| 2회차 | 23초 | 41 executed, **43 from cache** |
| 3회차 | 23초 | 41 executed, **43 from cache** |

**2·3회차의 23초 동안 테스트는 한 줄도 돌지 않았다.** 그린이었다.
14번이 기록한 것과 같은 함정인데, 이번에는 우연이 아니라 **구조가 되어 있었다** —
입력이 같은 한 앞으로 영원히 그럴 것이었다.

캐시 자체는 정직하다. 입력이 같으면 결과도 같다는 전제가 옳기 때문이다.
**앱 테스트에서 그 전제가 성립하지 않는 것이 문제다.** Testcontainers 컨텍스트 로딩
테스트의 결과는 소스 입력이 아니라 환경(Docker 버전·이미지·메모리·네트워크)에 달려 있고,
그 환경을 검증하는 것이 이 테스트의 존재 이유다. compose 파일이나 러너 설정만 바꾼
변경에서 CI 가 그린인데 Docker 를 한 번도 안 건드리는 상태가 만들어진다.

**해법 — CI 에서만 테스트 결과를 캐시에서 꺼내지 않는다**(`build.gradle`).

```groovy
if (providers.environmentVariable('CI').isPresent()) {
    outputs.upToDateWhen { false }
    outputs.cacheIf { false }
}
```

컴파일 캐싱은 유지한다 — 컴파일 결과는 입력만으로 결정되므로 전제가 성립한다.
로컬도 건드리지 않는다. 반복 루프에서는 캐시가 맞고,
**실제로 도는지 증명하는 자리는 CI 다**(12번). 느려지는 것은 테스트뿐이다.

**버린 선택지** — `--no-build-cache`. 간단하지만 컴파일 캐시까지 버린다.
전제가 성립하는 곳의 캐시까지 끌 이유가 없다.

**대가 3 — 상한을 스스로 걸어야 한다.** GitHub-hosted 는 잡이 죽어도 남의 일이지만
self-hosted 는 같은 커널을 공유한다. swap 이 0 인 채로 스파이크가 나면 OOM killer 가
무엇을 죽일지 `oom_score` 가 정한다. swap 8GB 와 러너 cgroup `MemoryMax` 를 함께 건다.
상한값은 추정이 아니라 위 실측(5.3GB)의 2배로 정했다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| `ubuntu-latest` 유지 | 2코어 7GB. Testcontainers 스택을 병렬로 못 띄운다. 애초의 문제가 그대로다 |
| MCP 서버로 원격을 도구화 | 먼저 만들면 순서가 뒤집힌다 — CI 를 써보기 전에는 커밋 전 반복 루프가 얼마나 답답한지 모른다 |
| CI 전용 인스턴스 분리 | 격리는 얻지만 Always Free 한도를 넘고 용량 확보 싸움을 다시 해야 한다 |
| 포트를 publish 한 채로 | 이 호스트는 공개 IP 다. ES(`xpack.security.enabled: false`)·Grafana(익명 허용)·MinIO·MySQL 이 인증이 없거나 기본 자격증명이다 |

**포트를 열지 않는다** — `docker-compose.ci.yml` / `docker-compose.apps.ci.yml` 가
`ports` 를 지운다. Compose 는 오버라이드에서 `ports` 를 **덮어쓰지 않고 이어붙이므로**
`ports: []` 로는 지워지지 않는다 — `!reset` 태그가 필요하다(Compose 2.24+).
스모크 테스트는 호스트가 아니라 `stove_default` 네트워크 안에서 돈다.

## 16. 컨슈머 그룹 이름은 한 곳에서만 정한다

**배경** — 같은 이름이 앱마다 세 곳에 살고 있었다.

| 자리 | 예 (license) | 실제로 쓰이나 |
|---|---|---|
| `application.yml` 의 `group-id` | `license` | **아니오** — 아래가 덮어쓴다 |
| `@KafkaListener(groupId=)` | `"license"` | 예 (Kafka 그룹) |
| 서비스의 `CONSUMER_GROUP` | `"license"` | 예 (Inbox 멱등 키, 8번) |

리스너 12개가 전부 `groupId` 를 명시하므로 **yml 값은 9개 앱 전부에서 한 번도 읽히지 않았다.**
표기도 이미 갈려 있었다 — 8개 리스너는 자기 `GROUP` 상수를 두고, license·store 는 리터럴을 직접 썼다.
그룹 이름 문자열이 프로덕션 코드에 **26곳** 있었다.

**결정** — 가드를 쓰는 7개 서비스에서 `CONSUMER_GROUP` 을 `public` 으로 열고 리스너가 그것을 참조한다.
yml 의 `group-id` 는 지운다. `ConsumerGroupRules` 가 값 일치와 `groupId` 명시를 검사한다.
26곳이 9곳(가드 서비스 7 + store·download 각 1)이 됐고, **가드를 쓰는 앱은 전부 1곳**이다.

**근거** — **결함을 고친 것이 아니다.** 중복을 없앤 것이고, 이득도 딱 그만큼이다.
읽히지 않는 설정이 9개 앱에 하나씩 있었고, 같은 뜻의 상수가 두 가지 표기로 갈려 있었다.
14번과 같은 자리다 — 사람이 읽는 경로에서 중복을 없앤다.

죽은 `group-id` 를 남겨두지 않은 이유는 따로 있다. **읽히지 않는 값이 조종 손잡이처럼 보이는 것**
자체가 함정이다. 컨슈머 그룹을 바꾸려는 사람이 가장 먼저 여는 파일이 `application.yml` 인데,
거기를 고쳐도 아무 일도 일어나지 않는다.

**의미상으로도 한 값이 맞다** — 멱등 키가 "이 이벤트를 누가 처리했는가"를 뜻한다면
그 "누가"의 정체는 컨슈머 그룹이다. 전에는 두 값이 우연히 같았고, 이제는 같은 것을 가리킨다.
다만 이건 설계 취향의 논거이지 급한 이유는 아니었다.

**규칙이 참조가 아니라 값을 보는 이유** — 애노테이션 속성은 컴파일 타임 상수라
바이트코드에는 값만 남고 **"무엇을 참조했는가"가 지워진다.**
"리터럴 대신 상수를 참조하라"는 정적으로 검사할 수 없고, 값 대조가 유일한 방법이다.

**대가 1 — 멱등 키가 Kafka 토폴로지를 따라 움직이게 됐다.** 이게 이 결정의 진짜 대가다.

전에는 `processed_event.consumer_group` 이 Kafka 와 독립이었다. 가드는 자기가 쓴 값과
자기가 읽는 값만 비교하므로(`ProcessedEventGuard:32,36`), 그 값이 Kafka 그룹명과 달라도
**일관되기만 하면 멱등은 완전하게 동작했다.** 묶고 나면 그룹명을 바꾸는 모든 경우에
과거 처리 기록이 통째로 안 보이게 되고, `auto-offset-reset: earliest` 와 만나 전량이 재실행된다.

| 그룹명을 바꾸는 이유 | 묶기 전 | 묶은 뒤 |
|---|---|---|
| 재처리하려고 | 재처리가 안 된다 | **의도대로 재처리된다** |
| 환경 접두사·명명 규칙 등 무관한 이유 | **아무 일도 없다** | 전량 재실행된다 |

**이 저장소에서는 아랫줄이 더 현실적이다.** 계획된 재처리 수단은 그룹 rename 이 아니라
DLT + 운영툴이고(README 7절, 6번의 "운영툴 재처리 API"), 그 경로에는 컨슈머 그룹이 없다.
윗줄을 근거로 삼아 이 변경을 정당화하지 않는다.

전량 재실행이 실제 사고가 되지 않는 것은 8번의 두 번째 층이 받아내기 때문이다 —
`Order.markPaid():93`(상태 가드), `GameProject.approve()`(상태 불일치 시 무시),
license 의 `existsByOrderNoAndProductId`, settlement 원장 유니크. **위층을 흔들어도
아래층이 버틴다는 것이지, 위층을 흔든 것이 안전하다는 뜻은 아니다.**

**대가 2** — 리스너가 `core.service` 의 상수를 참조한다. payment 의 `LicenseEventListener` 는
`RefundFacade` 만 알던 것이 `PaymentService` 를 import 하게 됐다.
계층 방향은 허용 범위이고(`Inbound → CoreService`, 1번) 컴파일 타임 상수라 바이트코드에
의존이 남지도 않지만, 소스에는 남는다.

store·download 는 제외한다. Inbox 가드가 없어(8번) 대조할 두 번째 출처가 아예 없다.
**다만 제외 여부는 `ProcessedEventGuard` 주입으로 판정하고, 이름 목록으로 적지 않는다.**
처음 쓴 규칙은 `CONSUMER_GROUP` 상수의 부재로 제외를 판정했는데, 그러면 "가드를 안 쓰는 앱"과
"상수가 사라진 앱"이 같은 문으로 빠져나간다 — 검사할 것이 없는 것과 검사 대상이 사라진 것을
구별하지 못한 채 초록으로 보인다. [D-021](defects.md#d-021) 과 같은 부류의 공허 통과다.
이름 목록으로 적지 않는 이유도 같다. 목록은 낡고, 낡은 목록은 침묵으로 낡는다.

그래서 규칙 자신을 검사하는 테스트를 함께 붙였다(`ArchRuleEnforcementTest$ConsumerGroup`).
앱 하나를 모사한 픽스처 다섯 개로 **갈라진 그룹·상수 없는 가드·groupId 누락**은 잡는지,
**한 상수에서 나온 그룹·가드 없는 앱**은 통과시키는지 양쪽을 본다.
`ArchRule` 이 아니라 `JavaClasses` 를 받는 메서드라서 — 앱 전체를 모아 집합끼리 비교해야 하는데
`ArchRule` 은 클래스 단위로 돈다 — 기존 위반/준수 픽스처 두 벌을 재사용하지 못하고 앱 단위로 만들었다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| yml 을 단일 출처로 (애노테이션에서 `groupId` 생략) | 그룹명이 컴파일 타임 상수가 아니게 되어 서비스는 `@Value` 주입이 필요하고 `core` 에 스프링 설정 의존이 들어온다. **컴파일 에러가 기동 실패보다 강하다** |
| 기동 시 `KafkaListenerEndpointRegistry` 와 대조 | yml 까지 반영된 최종 런타임 값을 보는 유일한 방법이지만, 서비스가 그룹명을 밖으로 알리는 통로가 따로 필요하다. 정상 경로를 상수로 이미 막았으므로 걸릴 일이 없다 |
| yml 의 `group-id` 유지 | 운영 가시성을 위해 남기자는 안. 읽히지 않는 값이 **"여기가 그룹을 정하는 자리"처럼 보이는 것**이 손해다 |
| 그대로 두기 | 가장 진지한 후보였다. 결함이 없었고 재현된 사고도 없다. 중복 제거의 값이 대가 1을 넘는다고 봤지만 **아슬아슬한 판단이고, 반대로 정해도 틀리지 않는다** |

> **이 항목은 결함 수정이 아니다.** 처음 잡았던 근거는 "그룹명을 바꿔 재처리할 때
> Inbox 가 조용히 무력화한다"였는데, 그 조작은 이 저장소의 어느 문서·스크립트에도 없고
> 계획된 재처리 경로도 아니다. 일어날 예정이 없는 사고를 1순위 근거로 삼았던 것이라
> 근거를 중복 제거로 낮추고, 대신 대가 1을 적었다. 커밋도 `refactor:` 로 단다.

## 17. 추적 컨텍스트를 이벤트와 함께 저장한다

**배경** — `correlationId` 는 HTTP 구간에서만 이어졌다. 주문 하나가
order → payment → license → settlement 로 흐를 때 order 이후 로그가 `[payment,]` 로 빈칸을 찍었고,
`EventHeaders.CORRELATION_ID` 는 "규약만 적어두고 미룬다"는 주석과 함께 **아무도 참조하지 않는 상수**였다.
그 주석의 미룬 근거는 "Micrometer Tracing 이 들어오면 손으로 만든 헤더는 중복이 된다"였다.

**결정** — Micrometer Tracing + OTLP 를 도입하고, **적재 시점에 붙잡은 `traceparent` 를
`outbox_event` 에 컬럼으로 저장했다가 발행 시점에 헤더로 되살린다.**

**근거** — 미룬 근거의 절반은 맞고 절반은 틀렸다. 표준 헤더로 가는 것은 옳았지만,
**자동 계측만으로는 이 시스템에서 트레이스가 이어지지 않는다.**

Kafka 자동 계측은 `send()` 를 호출한 **스레드**에 매달린 컨텍스트를 싣는다.
그런데 Outbox 는 발행을 일부러 뒤로 미루므로 실제 발행자는 요청 스레드가 아니라 릴레이 스케줄러다.

```
[요청 스레드]      주문 생성 → outbox INSERT → 커밋 → 스레드 반납 (컨텍스트 소멸)
                       ⋮  최대 1초
[스케줄러 스레드]  폴링 → kafka.send()   ← 자동 계측은 여기의 컨텍스트를 싣는다
```

맡겨두면 컨슈머가 **"릴레이가 돈 폴링 회차"를 부모로 삼는다**(아래 8번에서 실측했다). 배치에 여러 애그리거트가 섞이면
무관한 주문들이 같은 traceId 를 공유하는, 없느니만 못한 상태가 된다.
`EventHeaders` 주석이 MDC 를 두고 적어둔 "적재 시점에 담아 두지 않으면 릴레이에서는 이미 없다"가
추적 컨텍스트에도 **글자 그대로** 적용된다 — 스레드 로컬이라는 메커니즘이 같기 때문이다.

그래서 이벤트 본문에 적용한 논리(지금 커밋하고 나중에 보낸다)를 컨텍스트에도 적용했다.
**Transactional Outbox 와 분산 추적의 충돌은 구현 실수가 아니라 두 패턴의 전제가 어긋나는 지점이고,
그 간극은 이 저장소가 메워야 한다.**

**따라오는 것들**

| 바뀐 것 | 이유 |
|---|---|
| `CorrelationIdFilter` → `TraceIdResponseFilter` | 하던 일 셋 중 식별자 생성·MDC 적재는 라이브러리가 더 잘 한다. 응답 헤더로 돌려주는 것만 남겼다 |
| `X-Correlation-Id` 헤더 이름은 유지 | 밖에서 보이는 계약이다. 내부 구현이 바뀌었다고 따라 바꿀 이유가 없다 — **값의 출처만 traceId 로 일원화됐다** |
| order 의 `RestClientConfig` 삭제 | `RestClient` 빌더에 옵저베이션이 이미 걸려 있어 `traceparent` 가 자동으로 실린다. 예고된 "중복"이 실제로 그 자리에 있었다 |
| `EventHeaders.CORRELATION_ID` 삭제 | 위와 같다. 이름을 우리가 정하지 않는 헤더(`traceparent`)로 대체했다 |
| 릴레이가 헤더를 **직접** 넣는다 | 자동 계측에 맡기면 스케줄러의 컨텍스트가 실린다. `spring.kafka.template.observation-enabled` 를 켜면 이 복원이 덮어써진다(부트 기본값이 꺼짐이라 지금은 안전하다) |

**대가**

1. **`outbox_event` 에 이벤트와 무관한 컬럼이 하나 생겼다.** 이 표에서 유일하게 "이벤트에 관한 것이
   아닌" 값이다. 스레드 로컬이라는 제약이 강제한 것이고, 대안은 전부 더 나빴다(아래).
2. **전파 형식이 W3C 라는 전제가 코드에 박혔다.** B3 로 바꾸면 `MicrometerTraceContextCapture` 가
   값을 못 찾는다. 그때 **Kafka 구간 추적만 조용히 끊기고** 처리 자체는 계속된다 —
   테스트로 그 동작을 못 박아 뒀다.
3. **마이그레이션이 7벌 복제됐다.** 스키마 복제는 이미 있던 문제이고 이 결정이 만든 것은 아니지만,
   같은 파일을 7번 붙여 넣을 때마다 그 비용이 다시 확인된다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| 자동 계측만 켜고 끝낸다 | **틀린 트레이스가 생긴다.** 없는 것보다 나쁘다 — 무관한 주문들이 한 트레이스로 묶인다. **추론이 아니라 실측이다(아래 8번)** |
| `correlationId` 헤더를 손으로 만든다(원래 백로그) | 표준을 두고 사설 규약을 유지하게 된다. 구간별 소요 시간과 부모-자식 관계도 못 얻는다 |
| traceparent 를 payload 에 넣는다 | 이벤트 계약이 관측 도구를 알게 된다. 컨슈머가 body 를 파싱하기 전에 헤더만 보고 판단한다는 규약도 깨진다 |
| 릴레이에서 스팬을 새로 열고 부모로 잇는다 | 폭포수에 "발행 지연"이 한 칸으로 보이는 이점이 있지만, 릴레이 hot path 에 스팬 수명 관리가 들어온다. 지금은 부모 스팬 종료와 컨슈머 스팬 시작 사이의 **간격**으로 같은 정보가 읽힌다 |
| `tracestate` 까지 저장한다 | 벤더 확장 값이라 트레이스 트리를 그리는 데 필요 없다. 컬럼 하나(55자 고정)로 끝나는 것을 JSON 으로 키울 이유가 없다 |

**8. 이 판단을 실측했다** (2026-08-21, OCI Ampere A1 전체 스택)

버린 선택지의 첫 줄("자동 계측만 켜면 틀린 트레이스가 생긴다")은 **켜 보지 않고 적은 것**이었다.
`spring.kafka.template.observation-enabled` 는 부트 기본값이 꺼짐이라 이 저장소에서 한 번도 켜진 적이 없다.
근거가 추론뿐인 채로 코드 주석·이 문서·포트폴리오 세 곳에 단정으로 적혀 있었으므로, 플래그만 뒤집어 쟀다.

**조건** — payment 만 `poll-interval-ms=10000` 으로 두어 승인 콜백 3건이 반드시 한 배치에 들어가게 하고,
`observation-enabled` 만 바꿔 두 조건을 만들었다. 네 회차 전부 릴레이가 `outbox relay 처리 3건` 을 찍어
**배치 조건이 같았음을 확인**했다. 판정은 license 의 지급 로그 한 줄이다 —
`[license,traceId,spanId] ... 라이선스 지급 orderNo=...` 이 둘을 같은 줄에 찍는다.

| 조건 | 회차 | 릴레이 배치의 traceId | 주문 3건의 컨슈머 traceId |
|---|---|---|---|
| **off** (현재 동작) | 1 | `1c821b29…` | `ad737b86…` · `03a96e64…` · `b6fd9329…` — **셋 다 다르고 릴레이와도 무관** |
| **off** | 2 | `5912f31a…` | `030b4996…` · `ee1833df…` · `89d89440…` — **셋 다 다름** |
| **on** | 1 | `0fbf7905…` | **셋 다 `0fbf7905…`** — 릴레이 배치와 동일 |
| **on** | 2 | `25209d79…` | **셋 다 `25209d79…`** — 릴레이 배치와 동일 |

**세 가지가 한꺼번에 확인됐다.** ① 자동 계측이 릴레이가 복원해 둔 `traceparent` 헤더를 **덮어쓴다**
② 컨슈머의 트레이스가 원 요청이 아니라 **릴레이 폴링 회차**에 붙는다
③ 한 배치에 섞인 **무관한 주문 셋이 같은 traceId 를 공유한다**.

원복까지 마쳤다(오버라이드 제거, 컨테이너 21개 복귀). 측정 중에는 같은 호스트의 CI 러너를 멈췄다 —
[performance.md](performance.md) 9장이 "비교 도중 CI 가 붙어 회차가 튀었다" 로 남긴 규칙을 그대로 적용했다.

## 18. API 명세를 생성하고, 그 명세를 테스트로 고정한다

**배경** — 엔드포인트 31개의 목록이 어디에도 없었다. 파악하려면 README 의 curl 예제를 읽거나
컨트롤러 9개를 여는 수밖에 없었다. 더 나쁜 것은 **응답 형식을 지키는 장치가 없었다**는 점이다 —
[testing.md](testing.md) 6.3 이 적어둔 대로 저장소 전체에 `jsonPath` 단언이 하나도 없어서,
DTO 필드를 지우거나 컨트롤러 시그니처를 바꿔도 컴파일과 테스트가 전부 통과한다.

**결정** — springdoc 으로 명세를 생성하고, **그 명세를 스냅샷으로 커밋해 테스트가 대조한다.**

**근거** — 문서를 손으로 쓰면 코드와 어긋난다. 13번에서 이미 겪은 문제다("문서는 자기가
사실인지 확인하지 않는다"). 생성하면 어긋날 수 없고, 생성물을 고정하면 **계약 변경이 diff 로 드러난다.**

ArchUnit 이 구조에 대해 하는 일을 계약에 대해 한다. 규칙이 없으면 흐려지는 것은 경계만이 아니다.

`@Min(1)`, `@NotEmpty` 같은 이미 있는 Bean Validation 이 그대로 스키마 제약(`minimum`, `minItems`)이
되므로 애노테이션을 새로 달 필요가 없었다. 실제 변경은 의존성 한 줄과 설정이 거의 전부다.

**대가와 그 처리**

| 문제 | 처리 |
|---|---|
| 스냅샷이 임의 포트 때문에 매 실행 달라진다 | `servers` 노드를 지운다. 거기에만 포트가 들어간다 |
| 필드 순서가 바뀌면 전체가 diff 로 뜬다 | 키를 정렬해 저장한다. 순서는 계약이 아니다 |
| 컨텍스트를 9벌 더 띄우면 CI 가 두 배가 된다 | **기존 `*ContextTest` 에 얹었다.** 이미 뜬 서버에 요청 하나를 더하는 비용뿐이다 |
| 의도한 변경마다 손으로 고쳐야 한다 | `-Dstove.openapi.update=true` 로 갱신한다. 그 diff 를 리뷰에 넣는 것이 목적이다 |

**신원 헤더를 명세에 드러낸다** — `X-Member-Id`/`X-Seller-Id` 는 클라이언트가 그대로 보내고
서버가 검증하지 않는다. 문서를 만들면 이 사실이 밖에서 보인다. 숨기지 않고 `ApiDocumentationCustomizer`
가 **"스켈레톤 한정, 서버가 검증하지 않는다"** 를 파라미터 설명으로 붙인다.
설명이 없으면 의도한 스켈레톤이 아니라 빠뜨린 인증으로 읽히고, 4곳 중 하나만 빠져도 마찬가지다.
그래서 서비스마다 적지 않고 `common:web` 한 곳에서 붙인다.

> 2026-09-27, 이슈 #75: 커머스의 `X-Member-Id`는 폐지했다. 주문·결제·라이브러리·다운로드는
> 검증된 access token의 `member_id`를 사용하며 OpenAPI에도 OAuth2 요구사항을 표시한다.
> 이 절의 헤더 설명은 당시 스켈레톤 설계 기록이다. `X-Seller-Id` 설명만 남아 있다.

**게이트웨이가 9개 명세를 모은다** — Swagger UI 를 게이트웨이가 서빙하므로 명세도 같은 출처여야 한다
(이 저장소에는 CORS 설정이 없어 다른 포트를 직접 부르면 브라우저가 막는다).
그래서 `/v3/api-docs/<service>` 프록시 라우트 9개를 **라우팅 표에 명시적으로 올렸다.**

이 저장소의 외부 노출 통제는 필터가 아니라 **라우트의 부재**로 표현돼 있고(`GatewayRouteTest`),
문서 프록시는 그 표를 넓히는 변경이다. 그래서 같은 테스트로 성질을 못 박았다 —
GET 전용이고, `/v3/api-docs/<service>` 한 경로씩만 열리며, 하위 경로로 넓어지지 않는다.
**명세에 보인다고 호출할 수 있는 것은 아니다** — 도달 가능성은 여전히 라우팅 표가 정한다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| 문서를 손으로 쓴다(마크다운) | 코드와 어긋난다. 13번에서 이미 겪었다 |
| 스냅샷 없이 Swagger UI 만 | 편의만 얻고 계약 방어는 못 얻는다. 이쪽이 본편이다 |
| 엔드포인트마다 `jsonPath` 단언 | 31개에 손으로 붙여야 하고, 새 엔드포인트에는 저절로 붙지 않는다 |
| 전용 스냅샷 테스트 클래스 9개 | 컨텍스트를 9벌 더 띄운다. CI 시간의 대부분이 컨텍스트 기동이다 |
| 게이트웨이 대신 서비스별 Swagger UI 만 | 9개 포트를 오가야 하고, 컨테이너 구성에서는 게이트웨이만 진입점이라는 전제와 어긋난다 |

## 19. 포기한 메시지를 버리지 않고, 되살릴 문을 단다

**배경** — 실패한 메시지가 사라지는 자리가 두 군데 있었다.

| 자리 | 그때 무슨 일이 | 남는 것 |
|---|---|---|
| 컨슈머 재시도 소진(7초) | 기본 recoverer 가 로그 찍고 건너뜀, 오프셋 커밋 | 로그 한 줄 |
| Outbox 발행 재시도 소진 | `DEAD` 로 전이, 더 시도하지 않음 | DB 행 — **되살릴 방법이 없음** |

두 번째가 특히 이상했다. `OutboxEvent#requeue()` 는 처음부터 있었고 주석도 정확했다 —
"회수 경로가 없으면 장애가 길어진 순간 유실 방지 장치가 유실의 원인이 된다."
그런데 **그 메서드를 부르는 프로덕션 코드가 하나도 없었다.** 전수로 확인했고 호출처는 테스트 4곳뿐이었다.
되살리려면 운영자가 프로덕션 DB 에 직접 UPDATE 를 쳐야 했다는 뜻이다.

**결정** — 컨슈머 실패는 DLT 로 보내고, 두 경로 모두 **HTTP 로 되살릴 수 있게** 한다.

**근거** — "파티션을 막지 않는다"는 판단은 옳았다. 계약 위반 메시지 한 건이 뒤의 정상 메시지를
전부 세우는 것은 더 나쁘다. 문제는 그 대가로 **유실**을 골랐다는 점이고, 그럴 필요가 없었다.

DLT 는 파티션을 막지 않으면서 메시지를 남긴다 — **맞바꿈이 아니라 순수 개선이다.**
"관측 가능한 포기"가 "관측 가능한 연기"가 된다. 실패 원인·원본 토픽/파티션/오프셋이 헤더로 보존되고,
계약 헤더와 `traceparent`(17번)도 따라가므로 DLT 레코드에서 그 요청의 전 구간 트레이스로 바로 간다.

**license 만 다르게 한다** — 지급 실패는 DLT 로 보내지 **않는다.**
그 경로는 Saga 보상이 이미 최종 처리이기 때문이다. 그런데 리스너가 실패했으므로 Inbox 가드 행은
롤백돼 있다 — 즉 **재투입하면 멱등 가드가 막아주지 않고 지급이 다시 시도된다.**
이미 환불된 결제에 라이선스를 발급하게 된다. 보상 대상이 아닌 실패와 봉투를 못 푸는 레코드는
보상이 걸리지 않으므로 DLT 로 보낸다. 이 갈림을 테스트로 못 박았다.

**컨슈머 정책을 `common:kafka` 로 뺐다** — 적용하다 보니 **store 와 download 에는 재시도 정책도
DLT 도 붙지 않는다**는 것이 드러났다. 둘은 `common:messaging` 을 의존하지 않기 때문이다(Outbox 가 없다).
그래서 스프링 기본값(`FixedBackOff(0ms, 9회)` = 수 밀리초)으로 돌고 있었고,
색인 동기화와 권한 사본 갱신 이벤트가 그렇게 사라질 수 있었다.

정책만 쓰려고 Outbox 와 JPA 까지 딸려오는 것이 문제였으므로 모듈을 갈랐다.
`common:kafka` 는 수신 측 정책(재시도·DLT·DLT 운영 API)만 담고 JPA 를 모른다.
**9개 서비스가 전부 같은 실패 처리를 갖게 된 것은 이 분리 덕분이다.**

**운영 API 를 어디에 둘지**

| | 자리 | 이유 |
|---|---|---|
| `/api/v1/ops/outbox/**` | `common:messaging` | `outbox_event` 를 쓰는 7개 서비스 |
| `/api/v1/ops/dlt/**` | `common:kafka` | **9개 전부** — 보낼 수 있으면 되돌릴 수도 있어야 한다 |

게이트웨이는 이 경로를 라우팅하지 않는다. 도달 불가가 곧 통제라는 이 저장소의 방식(18번)을 그대로 따른다.

**화면은 만들지 않았다** — 운영툴에 프론트를 붙일 자리라고 봤지만, 18번으로 각 서비스에
Swagger UI 가 생겼다. 목록 조회와 버튼 두 개가 전부인 도구에는 그것으로 충분하고,
화면을 따로 만들면 **명세와 화면 두 벌을 유지**하게 된다.

**대가**

1. **DLT 도 쌓인다.** 아무도 안 보면 유실과 운영상 다르지 않아 `stove.kafka.dead-lettered` 카운터를
   더하고 Prometheus 알람 규칙을 붙였다. `promtool check rules` 로 검증했다.
2. **재투입은 중복 수신이다.** Inbox 멱등 가드가 막아주지만, 가드가 없는 서비스(store·download)는
   자연 멱등(문서 ID 고정 upsert)에 기댄다 — 8번의 전제가 여기서 한 번 더 쓰인다.
3. **원인을 안 고치고 재투입하면 그대로 돌아온다.** 도구가 대신 판단할 수 없어서
   조회를 먼저 하게 만들었다(조회는 커밋하지 않으므로 몇 번을 봐도 상태가 안 변한다).
4. **모듈이 하나 늘었다.** `common/*` 이 7개에서 8개가 됐다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| 실패 시 파티션을 세운다(재시도 무한) | 계약 위반 한 건이 뒤의 정상 메시지를 전부 막는다. 원래 판단이 옳았다 |
| store·download 에 정책을 복제한다 | 재시도 숫자가 서비스마다 갈리면 장애 때 무슨 일이 벌어질지 예측할 수 없다 |
| store·download 가 `common:messaging` 을 의존한다 | JPA 가 딸려와 DataSource 자동 구성이 붙는다. ES·Mongo 서비스에 RDB 를 요구하게 된다 |
| DLT 를 상주 리스너로 자동 재투입 | 원인을 고치기 전에 되돌아가는 사고가 가능해진다. 재투입은 사람이 누르는 작업이다 |
| 운영 화면(Thymeleaf)을 만든다 | Swagger UI 와 두 벌이 된다. 화면이 필요해지는 시점은 목록에 필터가 필요해질 때다 |

## 20. 테스트 실행 정책을 모듈이 아니라 필요 자원으로 가른다

**배경** — 한 모듈의 `test` 태스크에 두 종류가 섞여 있었다.
컨테이너가 필요 없는 도메인·어댑터·ArchUnit 테스트와, MySQL·Kafka 를 띄우는 통합 테스트다.
그래서 **전체가 가장 느리고 가장 취약한 쪽의 실행 프로파일을 물려받았다.**

증상이 `gradle.properties` 에 그대로 적혀 있었다.

```
org.gradle.workers.max=2
# "워커 수만큼 스택이 동시에 뜨므로, CPU 코어 수를 그대로 쓰면
#  Kafka 가 기동 시한 안에 못 올라와 죽는다."
```

이 값 하나가 두 가지를 동시에 정했다 — 컴파일·단위 테스트의 병렬도와 동시 컨테이너 스택 수.
컨테이너를 지키려 2 로 누르면 인프라가 필요 없는 816개 테스트까지 함께 느려지고,
올리면 Kafka 가 죽는다. **어느 쪽도 제대로 맞출 수 없는 값**이었고,
로컬 2 / CI 러너 4 로 갈라 쓰면서 주석으로 이유를 설명하고 있던 것이 그 증거다.
실제로 CI 가 이 축에서 깨졌다 — settlement 의 Kafka 컨테이너가 `exit 126`.

**결정** — 소스셋을 `test` / `integrationTest` 로 가르고,
동시 컨테이너 스택 수는 공유 빌드 서비스(`InfraTestThrottle`)가 따로 센다.

**근거 — 경계는 규약이 아니라 클래스패스가 지킨다**

`common:test` 를 둘로 갈랐다.

| 모듈 | 무엇이 있나 | 어느 소스셋에 걸리나 |
|---|---|---|
| `common:test` | `EventRecords`, `OpenApiSnapshot` — 인프라 불필요 | 양쪽 |
| `common:testcontainers` | `InfraContainers`, `SharedContainers` | **`integrationTest` 만** |

그래서 `src/test` 의 클래스는 `InfraContainers` 를 **임포트조차 할 수 없다.**
컨테이너 테스트를 빠른 소스셋에 잘못 두면 사람의 검토가 아니라 컴파일이 막는다.

**태그(`@Tag("integration")`)를 버린 이유가 여기 있다.** 태그는 붙이는 것을 잊을 수 있고,
잊으면 예전 상태로 조용히 돌아간다. 이 저장소가 반복해서 피해 온 실패 방식이다 —
강제할 수 없는 문장은 대개 사실이 아니다(13번).

그리고 실제로 값을 했다. 분리 작업 중에 `InfraContainers` 를 쓰지 않고 Testcontainers 를
직접 쓰던 테스트 2건(`S3PresignedUrlSignerTest`·`S3BuildStorageTest`)이 나왔는데,
찾아낸 것은 검토가 아니라 **컴파일 실패**였다. 태그로 갈랐으면 그대로 남았다.

**대가**

1. **모듈이 하나 늘었다.** `common/*` 이 8개에서 9개가 됐다.
2. **소스셋이 늘어 태스크가 늘었다.** `defectTest` 와 pitest 가 양쪽을 다 봐야 한다 —
   한쪽만 보면 그쪽 테스트가 조용히 판정에서 빠진다. 둘 다 명시적으로 맞췄다.
3. **`build` 가 여전히 둘 다 돈다.** 기본 빌드에서 통합을 빼면 아무도 안 돌린다.
   대신 `shouldRunAfter` 로 단위가 먼저 돌게 해 컨테이너를 띄우기 전에 깨질 것은 먼저 깨진다.
4. **OpenAPI 스냅샷 경로가 바뀌었다**(`src/integrationTest/resources/openapi/`).
   `OpenApiSnapshot` 이 파일 경로를 직접 쓰므로 같이 옮겼다.

**결과 — 자원 사용량을 실측했다**

원격 러너(CI 와 같은 OCI Ampere A1 4코어 23GB)에서 `build --rerun-tasks`,
양쪽 다 `--max-workers=4`(러너의 실제 설정), 상주 스택 20개를 같은 기준선으로 두고
3초 간격 샘플링, **조건당 2회 반복**.

| | 이전 r1 | 이전 r2 | 이후 r1 | 이후 r2 | 평균 변화 |
|---|---:|---:|---:|---:|---:|
| 최대 동시 테스트 컨테이너 | 14 | 14 | 8 | 7 | **−46%** |
| 평균 동시 테스트 컨테이너 | 7.9 | 7.9 | 4.3 | 4.4 | **−45%** |
| 컨테이너 메모리 증분 | 2,972 MB | 2,666 MB | 1,991 MB | 1,897 MB | **−31%** |
| 호스트 여유 최소 | 8,952 MB | 8,793 MB | 10,516 MB | 10,679 MB | **+19%** |
| 동시 8개 이상이던 시간 | 99s | 102s | 9s | 0s | **100s → 4.5s** |
| 빌드 소요 | 335s | 333s | 346s | 344s | **+3%** |

**조건 안의 편차가 조건 사이의 차이보다 훨씬 작다** — 최대 컨테이너 수는 회차 간 0~1,
조건 사이는 6.5다. 이번 비교는 유효하다(10번의 규칙).

숫자가 설계와 정확히 맞는다. 이전에는 워커 4개가 각자 스택을 띄워
4 × (컨테이너 2~3 + Ryuk) ≈ 14, 이후에는 throttle 이 2로 조여
2 × (컨테이너 2~3 + Ryuk) ≈ 8 이다.

**속도는 목표가 아니었고, 실제로 조금 느려졌다(+3%).**
통합 태스크를 2개로 조이면 그만큼 직렬화되기 때문이다.
**얻은 것은 시간이 아니라 여유**다 — 최대 부하 시점의 호스트 여유가 1.7 GB 늘었고,
컨테이너가 8개 이상 겹쳐 있던 시간이 100초에서 4.5초로 줄었다.
PR #22 를 깨뜨린 것이 바로 그 겹침 구간이었다.

피드백 루프는 따로 짧아졌다. 인프라가 필요 없는 816건이 컨테이너를 기다리지 않는다.

> **재측정 여지 — throttle 기본값 2 는 아직 근거가 얇다.**
>
> 2 를 고른 것은 예전 `workers.max=2` 가 실제로 견디던 값이라는 것뿐이고,
> 러너(4코어 23GB)에서 그 값이 최적이라는 근거는 없다. 위 실측에서 이후 조건의
> 호스트 여유 최소가 10.6 GB 였으므로 **아직 여유가 남아 있다.**
>
> 3 으로 올리면 +3% 의 시간 손실을 되찾으면서도 이전(최대 14)보다는 훨씬 낮게 유지될
> 가능성이 크다. 같은 하네스로 그대로 잴 수 있다 —
> `./gradlew build --rerun-tasks --max-workers=4 -Pstove.infraTest.maxParallel=3`,
> 3초 간격 샘플링, 조건당 2회, 상주 스택을 같은 기준선으로.
>
> 판정 기준은 시간이 아니라 **최대 동시 컨테이너와 호스트 여유 최소**다.
> 여유가 이전 수준(8.9 GB)까지 내려가면 되돌린다 — 그 구간이 PR #22 를 깨뜨린 자리다.
>
> 로컬(Docker 3.83 GB 랩탑)은 별개다. 거기서는 2 도 넉넉하지 않을 수 있고,
> 머신별 값은 머신에 두는 것이 이 저장소의 방식이다(10번).

```
./gradlew test              816건 · Docker 불필요 · 수 초
./gradlew integrationTest   175건 · Testcontainers
./gradlew build             둘 다 (단위가 먼저)
```

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| `withStartupAttempts(2)` 만 붙인다 | 증상만 덮는다. 다음번엔 MySQL 이 같은 이유로 죽고 같은 자리에 또 두 줄을 붙이게 된다 |
| `@Tag("integration")` 으로 가른다 | 붙이는 것을 잊으면 조용히 예전 상태로 돌아간다. 위의 2건이 실제 사례다 |
| 모듈 간 Kafka 컨테이너를 공유한다 | 토픽 이름이 같아 모듈끼리 서로의 이벤트를 집는다. 격리가 깨지는 값이 절약보다 크다 |
| `common:test` 를 통째로 통합 전용으로 돌린다 | `EventRecords` 를 쓰는 리스너 테스트 9개는 브로커가 필요 없다. 그것까지 느려진다 |
| `org.gradle.workers.max` 를 CI 에서만 낮춘다 | 머신마다 다른 값을 계속 관리하게 된다. 문제는 값이 아니라 **한 값이 두 가지를 정하는 것**이었다 |

## 21. 인수 시나리오를 위해 포트를 열되, 루프백에만 연다

**배경** — `scripts/smoke-stack.sh` 의 인수 45건을 `:e2e` 모듈로 옮기면서 막힌 자리다.
셸은 같은 네트워크에 curl 컨테이너를 띄워 서비스 이름(`http://gateway:8080`)으로 불렀다.
**그레이들 테스트 JVM 은 그 네트워크에 넣을 수 없다** — 스택 밖에 있는 것이 이 층의 전제이기도 하다.

그런데 CI compose 는 호스트 포트를 **의도적으로** 열지 않는다(`docker-compose.ci.yml`).
15번이 원격 러너를 세우며 내린 결정이고, 근거는 편의가 아니라 보안이었다 —
CI 호스트는 공개 IP 를 가지는데 이 스택의 Elasticsearch(`xpack.security.enabled: false`),
Grafana(`GF_AUTH_ANONYMOUS_ENABLED: true`), MinIO 콘솔, MySQL, MongoDB 는 인증이 없거나 기본 자격증명을 쓴다.

**결정** — `docker-compose.apps.e2e.yml` 로 앱 10종만 `127.0.0.1:1808X` 에 연다.

```
docker compose -f docker-compose.apps.yml \
               -f docker-compose.apps.ci.yml \    # ports: !reset []
               -f docker-compose.apps.e2e.yml     # 127.0.0.1:1808X 로 다시 연다
```

**근거** — 원래 결정을 뒤집는 것이 아니다. **위험한 것은 포트를 여는 행위가 아니라 `0.0.0.0` 에 붙이는 것**이었고,
그 문장은 원문에도 그렇게 적혀 있다. 루프백 바인딩은 호스트 안에서만 닿는다.
그리고 호스트에 들어올 수 있는 사람은 이미 `docker exec` 로 무엇이든 할 수 있으므로,
이 오버라이드가 새로 여는 공격면은 없다.

인프라는 **Tempo 의 조회 API 하나만** 연다(`docker-compose.e2e.yml`, `127.0.0.1:13200`).
근거가 가장 강했던 대상(ES·Grafana·MinIO 콘솔·MySQL·MongoDB)은 그대로 닫혀 있다.

Tempo 를 여는 이유는 **"하나의 traceId 가 여섯 서비스에 걸치는가"를 물어볼 문이 필요해서**다.
17번이 메운 간극(Outbox 가 발행을 미뤄 끊기던 Kafka 구간 추적)에 회귀 방어선이 하나도 없었고,
그것을 세우려면 스팬을 조회할 수 있어야 한다. 스팬 **수신**(4318)은 열지 않는다 —
앱이 컨테이너 네트워크 안에서 보내므로 밖에서 넣을 일이 없다.

**오프셋을 쓰는 이유** — `+10000` 이 규칙이라 서비스가 늘어도 계산할 것이 없다.
그리고 이 호스트에는 traefik 이 `127.0.0.1:8080` 을 잡던 자리가 있어(`docker-compose.apps.ci.yml` 주석)
같은 번호를 그대로 쓰면 sng 스택을 되살릴 때 충돌한다.

**대가**

1. **compose 파일이 하나 더 늘었다.** 앱 오버라이드가 셋이 됐고(기본·ci·e2e), 적용 순서가 의미를 가진다 —
   ci 가 `!reset` 으로 지운 뒤에 e2e 가 열어야 한다. 순서를 바꾸면 조용히 포트가 닫힌다.
2. **로컬과 원격의 주소가 다르다.** 로컬 개발은 `8080`, e2e 는 `18080` 이다.
   그래서 주소를 코드에 박지 않고 `stove.e2e.*` 시스템 프로퍼티로 덮을 수 있게 뒀다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| 테스트 JVM 을 컨테이너로 띄워 `stove_default` 에 붙인다 | 그레이들·JDK·소스를 담은 이미지를 따로 관리하게 된다. 그리고 **e2e 는 스택 밖에 있어야 한다** — 안에서 도는 것은 통합 테스트가 이미 한다 |
| `0.0.0.0` 으로 그냥 연다 | 15번의 근거를 정면으로 뒤집는다. 인증 없는 ES·Grafana 가 공개 IP 에 붙는다 |
| 게이트웨이 하나만 연다 | 적체 0 수렴·DLT 0 판정이 앱별 `/actuator/metrics` 를 읽는다. 나중에 다시 여느니 지금 규칙으로 연다 |
| Prometheus 를 열어 지표를 한 곳에서 읽는다 | 스크레이프 주기(10초)만큼 값이 늦다. 적체가 0 인지 묻는데 10초 전 값을 보게 된다 — 앱을 직접 읽으면 지금 값이다 |
| SSH 터널로 로컬에서 원격 스택을 두드린다 | CI 에서는 터널을 열 대상이 자기 자신이라 의미가 없고, 경로가 로컬/CI 로 갈린다 |

## 22. 실패 분류는 두 번째 사례가 나올 때까지 license 안에 둔다

2026-10-17 변경: License MVP에서 지급 실패 자동 보상과 전용 오류 핸들러를 제거했다. 현재는 공통 재시도·DLT를 사용한다. 아래는 재작성 전 결정 기록이다. [현재 범위](license-mvp-plan.md).

**배경** — [D-027](defects.md#d-027) 이 `isStorageFailure` 를 만들었다. "저장소가 답을 못 준 것은
*처리 불가*가 아니라 *판단 불가*" 라는 구분이고, 그 판정 자체는 license 전용이 아니다 —
어느 컨슈머에나 적용된다. `common:kafka` 로 올리자는 제안이 [#45](https://github.com/tlswltjq/stove/issues/45) 로 열려 있었다.

**결정** — **올리지 않는다.** `apps/license` 안에 둔다.
조건을 정하고 그 조건이 충족될 때 다시 본다.

**근거** — 실측으로 확인했다. 커스텀 에러 핸들러를 가진 서비스는 **여전히 license 하나뿐**이다.

```
$ grep -rl "KafkaErrorHandlerConfig|DefaultErrorHandler" apps/ --include=*.java
apps/license/.../KafkaErrorHandlerConfig.java     ← 유일한 커스텀
common/kafka/.../KafkaConsumerAutoConfiguration.java  ← 기본 핸들러
```

나머지 8개 서비스는 기본 핸들러로 **무조건 DLT** 다. 원인이 저장소든 아니든 결과가 같다.
지금 올리면 **아무 데서도 동작이 바뀌지 않는 코드**가 공용 모듈에 생긴다.

근거 없이 공용 모듈에 규칙을 올리면 되돌리기 어렵다 — 쓰는 쪽이 늘어난 뒤에는
"이게 왜 여기 있나" 를 아무도 답할 수 없게 된다. **공용화의 비용은 코드 줄 수가 아니라
그 규칙을 나중에 바꾸지 못하게 되는 것**이다.

**올릴 조건** — 다른 서비스에서 재시도 소진 후 종결이 갈리는 경로가 생길 때. 구체적으로 셋 중 하나다.

- Saga 참여자가 하나 더 늘거나
- DLT 말고 다른 종결(스킵·보류·알람만)이 필요한 컨슈머가 생기거나
- 저장소 장애일 때만 재시도를 더 하고 싶은 경로가 생길 때

**올릴 때 같이 옮길 것** — `ConsumerRetryPolicy` 옆이 자리다(둘 다 "실패를 어떻게 볼 것인가" 다).
그리고 **예외 분류를 넓게 잡은 판단(비용 비대칭)도 같이 옮겨 적어야 한다** —
그 근거가 없으면 다음 사람이 좁힌다.

**버린 선택지**

| | 왜 버렸나 |
|---|---|
| 지금 올린다 | 동작이 바뀌는 곳이 없다. 재사용이 아니라 **재사용의 예고**일 뿐이고, 예고는 결정이 아니다 |
| 이슈를 닫지 않고 계속 열어 둔다 | 조건이 적혀 있는 질문은 **판단이 끝난 것**이다. 열어 두면 "아직 못 정했다" 로 읽힌다 |

> 이 항목이 15번(`remote.sh`)과 같은 성격이다 — **증명되지 않은 계획은 결정이 아니다.**
> 다만 방향이 반대다. 그쪽은 "해 보고 나서 적었다" 이고 여기는 **"하지 않기로 한 것을 적었다"** 다.
> 둘 다 나중 사람이 같은 자리에서 다시 고민하지 않게 하는 것이 목적이다.

## 23. 서비스 분해의 단위는 메서드가 아니라 트랜잭션이다

**배경** — `core/service` 를 "한 클래스 한 기능" 으로 쪼개고 조율은 전부 `api/application` 에 두자는
계획이 있었다. 구조 자체(`core/domain`·`core/port`·`infrastructure`·`api/application`)는
1~5번이 이미 정한 것이라 계획에서 실제로 새로 정해지는 것은 그 둘이었다.

**결정** — 분해는 하되 **단위를 트랜잭션 하나로** 정한다. 조율의 자리는 3번을 그대로 둔다 —
트랜잭션 밖에 두어야 할 것이 있을 때만 파사드다.

**근거** — 하한선이 이미 코드에 박혀 있다. `OutboxRecorder` 와 `ProcessedEventGuard` 가
`Propagation.MANDATORY` 다. 이벤트를 적재하거나 멱등 마킹을 하는 유스케이스는 `core.service` 가
연 트랜잭션 안에서 끝나야 한다. 그보다 잘게 쪼개면 조각을 다시 묶을 자리가 파사드밖에 없는데,
파사드는 트랜잭션을 열 수 없다(`트랜잭션_경계는_core_service_다`).
**더 쪼개는 순간 규칙을 어기지 않고는 원자성을 되찾을 수 없다.**

**적용** — 애그리거트를 둘 이상 만지던 세 곳만 갈랐다.

| 모듈 | 전 | 후 |
|---|---|---|
| download | `DownloadService` — 애그리거트 3, 트랜잭션 없음(Mongo) | `ManifestService` · `EntitlementService` · `ProductRefService` · `DownloadTicketService` |
| studio | `StudioService` — 애그리거트 2 | `GameProjectService` · `GameBuildService` |
| settlement | `SettlementService` — 애그리거트 2 | `SettlementRecordService` · `SellerSettlementService` |

payment 는 손대지 않았다. 공개 메서드가 12개지만 전부 `Payment` 하나의 상태기계다 —
쪼개면 전이 규칙이 클래스마다 흩어지고 얻는 것은 파일 수뿐이다.
나머지 여섯 서비스는 애그리거트가 하나고 100줄 안팎이라 대상이 아니다.

**드러난 것 — 규칙은 이 계획의 반대편을 막지 않는다.**
`계층_접근_방향` 은 같은 레이어 안의 의존을 검사 대상에서 뺀다
(ArchUnit 1.3.0 `Architectures.originMatchesIfDependencyIsRelevant` 가 `ownLayer` 를 허용에 더한다).
그래서 `core.service → core.service` 는 통과한다 — 이번 분해가 셋 다 그 형태인데 규칙 36개가 그대로 초록이다.
**"조율은 파사드에서" 를 규약으로 적어도 강제되지 않는다**는 뜻이고,
강제되지 않는 경계가 어떻게 되는지는 1번이 이미 답했다.
그래서 규약을 늘리지 않고 **트랜잭션이라는 강제되는 선**만 남겼다.

**포트를 여는 기준도 같이 좁힌다** — 도메인 간 협업의 기본값은 이벤트다.
포트 6개 중 다른 도메인은 `CatalogPort` 하나뿐이고 나머지 다섯은 외부 시스템(PG·CDN·S3·등급위·세금계산서)이다.
"다른 도메인이 필요하면 포트를 판다" 로 읽으면 동기 호출이 기본이 되어 Saga·Outbox 설계와 반대로 간다.
**상태 변경 전파는 이벤트, 포트는 이 트랜잭션 전에 확정된 값이 필요할 때만**
(order → catalog 가격 확정이 그 예이자 유일한 사례다).

**대가** — 애그리거트를 가로지르는 유스케이스는 서비스가 서비스를 부른다
(`GameBuildService → GameProjectService`, `SellerSettlementService → SettlementRecordService`,
`DownloadTicketService → 셋`). 부르는 쪽 트랜잭션에 참여하므로 경계는 그대로지만
**한 클래스만 읽어서는 트랜잭션 범위가 안 보인다.** 대신 애그리거트마다 접근 소유자가 하나로 정해졌다 —
settlement 의 마감이 원장을 "집으면서 닫는" 한 호출이 된 것이 그 결과다.

**버린 선택지**

| | 왜 버렸나 |
|---|---|
| 공개 메서드마다 클래스 하나 (68개) | 트랜잭션 하한선 아래로 내려간다. 원자성을 되찾을 자리가 없다 |
| 조율을 전부 `api/application` 으로 | 3번이 이미 기각했다. 현행 파사드 5개는 전부 "트랜잭션 밖에 둘 것" 이 있어서 존재하고, 나머지는 위임 껍데기가 된다 |
| 규칙으로 못 박기 (예: 서비스당 리포지토리 1개) | 정당한 예외가 규칙보다 먼저 나온다 — 마감 한 건이 원장과 확정본을 함께 만진다. 사례가 하나 더 쌓일 때까지 두는 편이 낫다(22번과 같은 판단) |

**따라온 것** — studio 의 통합 테스트가 둘로 갈렸다(`GameProjectServiceTest`·`GameBuildServiceTest`).
애노테이션 조합이 같아 **컨텍스트는 한 벌 그대로**이며, 실행 로그에서 Hikari 풀이 늘지 않은 것으로 확인했다
(testing.md 의 커넥션 한계선). 테스트 수는 그대로 15개다.
테스트 수와 소요 시간은 CI 실행 결과로만 판단한다. 지금 값을 손으로 고치지는 않는다.

## 24. 도메인 정의·현재 구현·합의 기록을 함께 관리한다

2026-10-01, [#89](https://github.com/tlswltjq/esd-platform/issues/89)의 문서 구성 방침을 적용한다.
문서 구조에 대한 기록이며, 개별 업무 정책의 합의 상태는 각 정의와 검토 기록에서 관리한다.

**배경:** 코드의 `PUBLISHED`가 상점 자료 확정과 릴리스 공개에 모두 사용되고,
프로젝트·상품, 이용권 원본·다운로드 사본도 비슷한 이름으로 설명되어 업무 경계가 흐려졌다.
구현에서 발견한 동작을 그대로 합의된 정책으로 기록하면 미지원 기능과 의도한 규칙을 구별하기 어렵다.

**적용:** [용어집](domain-glossary.md)을 시작점으로 업무 흐름과 두 상세 정의 문서를 연결한다.
각 핵심 정의에 업무 규칙 제안, 현재 구현, 정상·거절 사례, 코드·기존 테스트 근거,
합의 상태를 함께 적는다. 서비스 배포 경계는 바운디드 컨텍스트 후보를 찾는 출발점으로 사용한다.
불일치와 미정 정책은 [미결 질문](domain/open-questions.md)에 남기고 담당자 결정 후 정의에 반영한다.
API 예제와 외부 연동 명세는 기존 문서를 참조한다.

**이유와 유지 비용:** 업무 시나리오에서 의미를 먼저 읽고 코드로 근거를 확인할 수 있다.
한 개념을 바꿀 때 흐름·정의·미결 질문·테스트 링크를 함께 확인해야 하므로
[유지 관리 규칙](domain-glossary.md#유지-관리)을 변경 PR에 적용한다.
클래스·DB 필드만 나열하는 사전은 행위와 조건을 설명하기 부족하고,
서비스별 명세에 정의를 반복하면 같은 용어의 의미가 서로 달라질 수 있어 채택하지 않았다.

## 25. 본인용 단일 구매의 출처는 License에 함께 보존한다

2026-10-17. 본인용 동일 상품은 한 번만 구매하고 선물·추가 수량은 후속 범위로 정했다.
Order가 자기 주문의 PENDING·PAID로 추가 구매를 차단하며 최종 FAILED 이후 새 요청만 허용한다.
License 조회 결과는 비동기 전달에 뒤처질 수 있으므로 주문 생성의 판단 근거로 사용하지 않는다.

`LicensePurchase`와 권한의 서로 다른 생명주기를 관리할 요구가 없는 현재 범위에서는 출처를 `License`에 통합한다.
두 객체의 구매자·상품 중복과 FK 연결 검사를 줄이고, OrderPaid의 13개 값 전체 비교·출처 식별자 유일성·Inbox 원자성은 유지한다.
이 선택으로 License의 컬럼은 늘지만 업무 엔티티·저장소·지급 쓰기 경로는 각각 하나가 된다.

Order의 동시 주문은 PENDING·PAID에만 적용되는 DB 유일 제약으로 막는다. License도 상품별 유일 제약을 최종 방어로 둔다.
기존 반복 구매 자료를 임의로 한 출처로 축약하지 않는다. 적용 전 1:1 전환 조건을 확인하고, 기존 구매 근거 테이블은 과거 자료로 보존한다.
세부 범위·자료 전환·검증은 [License 통합 계획](license-mvp-plan.md#통합-및-중복-구매-제한-수정-계획)을 따른다.

## 26. 외부 연동 구현 패키지를 adapter로 부른다

**배경** — `infrastructure`에 S3 같은 기술 연동과 다른 업무 도메인의 HTTP 호출 구현을 함께 두어, 패키지 이름만으로 후자의 역할을 이해하기 어려웠다.

**결정** — 2026-10-18 Java 업무 패키지 이름을 `adapter`로 변경한다. 호출 모듈이 `core.port`의 계약을 소유하고, `adapter`가 외부 기능을 그 계약에 맞춘다. 설정 바인딩·클라이언트 구성·객체 조립은 `config`에 둔다. 기존 하위 패키지와 클래스·업무 계약은 유지하며 ArchUnit의 패키지·접근 경계도 함께 변경한다.

**근거** — 구현의 역할을 표현하면 다른 서비스의 HTTP 클라이언트와 저장소·PG·프레임워크 연동을 같은 기준으로 설명할 수 있다. 명칭 변경만으로 새 계층이나 업무 포트를 늘릴 이유는 없다. 실제 이동 범위와 검증 결과는 [변경 기록](adapter-package-rename-plan.md)에 남긴다.

**버린 선택지** — 연결 도메인별 패키지나 `adapter.in/out`을 추가하는 세분화. 현재 구조에서는 이름 변경만으로 목적을 달성할 수 있다.

## 27. Compose는 기본 정의와 로컬 접속 오버라이드만 둔다

**배경** — Jib 전환 후에도 루트 Compose 파일이 7개 남았다. 기본 파일이 연 포트를 CI 파일이 지우고 E2E 파일이 다시 열어, 적용 순서와 중복 포트를 관리해야 했다.

**결정** — 2026-10-21 인프라·앱의 기본 파일에서 호스트 포트를 제거한다. 각각 local 오버라이드 하나만 두어 총 4개로 줄인다. 로컬·호스트 JVM E2E·원격 검증은 같은 local 구성을 사용하고, 내부 네트워크 실행은 기본 파일만 사용한다.

**근거** — 호스트 접속은 실행 환경의 선택이다. 기본 파일의 서비스·이미지·데이터 설정을 유지하면서 포트 선택을 한 번만 적용할 수 있다. 로컬 오버라이드의 포트는 모두 `127.0.0.1`로 제한한다. 앱은 기존 E2E의 `+10000` 포트, MinIO S3는 `19000`, Tempo 조회는 `13200`을 사용한다.

**대가와 검증** — 기존 일반 로컬 구성의 Gateway·Auth·Tempo 포트가 E2E 주소로 통일된다. 원격 local 구성은 이전 E2E 전용 구성보다 많은 인프라 포트를 루프백에 제공한다. 기본 구성은 기존 CI 구성과, 앱 local 구성은 기존 CI+E2E 구성과 동일함을 정규화 결과로 확인했다. 실행 방법과 실제 검증 결과는 [Compose 실행 구성](compose-layout.md)에 기록한다.

**버린 선택지** — CI·E2E 파일을 유지한 채 별칭만 추가하기. 포트를 지웠다 다시 여는 순서 의존성과 같은 목적의 중복 정의가 남는다.

## 28. 내구 접수의 추적 부모를 저장하고 처리 시도마다 복원한다

2026-10-24, [#99](https://github.com/tlswltjq/esd-platform/issues/99). 17번의 Outbox 저장·발행 시 복원 원칙을 Payment의 내구 접수 경계까지 확장한다.
요청 접수 트랜잭션과 결과 Outbox 생성 트랜잭션은 다른 스레드·프로세스에서 실행될 수 있다. 트랜잭션 안이라는 사실만으로 원래 요청 컨텍스트가 남아 있지는 않는다.

Payment가 소유하는 작은 메타데이터 테이블에 최초 W3C v00 부모를 요청·Inbox와 함께 저장한다. 재전달은 업무 입력을 비교하지만 최초 추적 부모는 바꾸지 않는다.
메타데이터 저장·조회 및 건별 추적 실행은 Payment의 core.port, JDBC·Micrometer 구현은 adapter, 조립은 config가 맡는다. 업무 입력·이벤트 본문과 도메인에는 추적 라이브러리를 넣지 않는다.
처리 시도마다 저장된 부모의 새 자식 span을 만들고 PG 호출·결과·Outbox 적재를 같은 scope로 연결한다. scope 종료 시 외부 컨텍스트를 복원한다. 부모가 없으면 무관한 스케줄러 trace를 상속하지 않는 새 root로 처리한다.

HTTP 전파에는 자동 구성된 RestClient.Builder를 사용한다. 여러 공급자 클라이언트는 builder를 복제해 주소·키가 섞이지 않게 조립한다.
Tempo는 기존 독립 인프라로 유지한다. 실제 tracer·MySQL·Kafka 통합과 별도 Tempo E2E를 구분하고, 샘플링 0·수집기 중단의 업무 지속도 검사한다.
저장 비용은 접수당 작은 행 한 건과 처리 시도당 조회 한 번이다. TTL이나 임의 삭제로 미확정 요청의 부모를 잃지 않게 하며, 이번 로컬 범위에서는 결제 행의 수명과 함께 보존한다.
구현 범위·실제 검증 근거는 [Tempo 도입·검증 기록](tempo-tracing-plan.md)을 따른다.

이 선택도 격리 발행·재전달의 인프라 의존성을 없애지는 않는다. 정지 완료 전용 소비 경계에서 근거 불일치는 업무 재시도 없이 DLT로 보내고, DB 등 일시 실패는 기존 제한 재시도를 거친다. DLT 발행이 실패하면 원본 소비 완료로 처리하지 않는다. 운영자는 근거를 복구·대조한 뒤 재투입할 수 있어야 하며 Tempo만을 업무 복구 근거로 사용하지 않는다.
같은 토픽·키만으로 업무 발생 순서부터 License 반영까지 보장되지는 않는다. 현재 Outbox의 배치 밖·재시도 대기 중 선행 이벤트 추월 방지 과제가 남아 있으므로 발행·소비 경계의 순서도 별도로 검증한다.

확정 실패 후 재실행은 사용자의 명시적 재시도로 진행하는 방향을 선택했다. 최초 접수에서 확보한 자동 환불 자격은 유지한다.
2026-10-26, 현재 결과만 갱신하는 A안 대신 환불 한 건에 실행 시도별 기록을 남기는 B안을 선택했다. 고객·운영자에게 지연 경위·실패 사유·재시도 과정을 설명할 근거를 업무 DB에 남긴다. Refund는 최초 접수 시각과 당시 자격을 보존하고, RefundAttempt는 별도 attemptId·실행 순번·시작 시각·미확정/확정 결과·결과 시각·실패 사유를 보존한다. 새 시도의 기록으로 이전 실패를 덮어쓰지 않는다.
이 결정은 내부 이력 관리 요구다. PG 멱등 키를 attemptId와 같게 할지는 결정하지 않았다. 내부 시도 ID와 외부 키 매핑을 구분하고, PG의 실패 보존·중복 처리·재실행 계약에 맞춰 어댑터를 설계한다. 시도별 기록 저장·결과 연결과 현재 유효한 시도를 검증하는 비용을 감수한다.
먼저 Order의 실행 이력 모델·저장소·V14 테이블을 구현했다. 도메인 12건의 Red·Green 뒤 OCI에서 Order 단위 197건·통합 54건을 통과했다. 과거 실패·최초 자격 보존, DB 식별자·순번 제약과 롤백을 확인했다. 이 모델 검증 시점에는 정지 완료 수신과 실제 실행·재시도 허용을 연결하기 전이었다. 근거는 [검증 기록](testing.md#order-full-refund-tdd)을 따른다.
미확정·응답 유실의 자동 확인은 같은 시도를 이어서 처리한다. 새 시도 기록이 존재한다는 사실만으로 PG 실행을 허용하지 않으며, 새 실행의 허용·정지 확인·이전 결과 대조는 업무 서비스가 보장해야 한다. 어떤 확정 실패에 사용자 재시도가 유효한지와 구체적인 결과·복구 계약은 추가 설계가 필요하다.
같은 키의 확정 결과를 보존하는 PG 계약이라면, 확정 거절에 동일 키를 반복 전송하는 것만으로 결과가 달라지지는 않는다.

2026-10-27, PG 멱등 키도 실행 시도별로 구분하는 B안을 선택했다. 모의 PG에는 `Idempotency-Key=attemptId`를 사용한다. 같은 시도의 응답 유실·자동 확인·재호출은 같은 키를 유지하고, 확정 거절 뒤 업무상 허용된 새 실행만 새 attemptId와 키를 사용한다. refundId는 여러 실행을 묶는 환불 업무 식별자로 유지한다. 같은 키·같은 요청은 최초 확정 결과를 보존·반환하고, 같은 키에 다른 결제·금액·통화 등 변경된 근거가 오면 거절한다. 확정 거절도 같은 키를 재호출해 성공으로 바꾸지 않는다.
키가 달라도 원결제의 전액 환불 성공은 한 번만 허용해야 한다. 이 보호는 환불 업무별 키를 쓰는 대안에도 필요하며, 시도별 키의 고유 비용으로만 계산하지 않는다. 모의 PG의 원장·동시성 구현 비용을 제외하면, 이미 선택·구현한 시도별 이력에 PG 결과를 연결하고 별도의 키 매핑을 만들지 않을 수 있다는 것이 Codex의 추천 근거였다. 실제 PG에서는 해당 계약의 지원 여부·보존 기간·원결제 중복 방지 보장을 확인해야 한다.
이 선택은 계약 결정이며 PG 환불 구현·검증 완료가 아니다. 서로 다른 키가 이미 환불된 원결제를 가리킬 때의 응답, 승인·조회 필드와 실패 분류는 후속 논의한다. 원결제 초과 환불 방지에 성공하더라도 이를 일반적인 환불 확정 실패로 처리해 보유권을 복구해서는 안 된다. 결과 유실만으로 새 실행을 만들 수 없고, 새 키를 사용할 수 있다는 사실만으로 고객 재시도·재정지를 허용하지 않는다.

이어 사용자는 모의 PG를 가까운 시일 안에 교체할 예정이므로 모의 PG에 드는 비용을 최소화하고 싶다고 밝혔다. 앞서 제시한 '이미 환불된 원결제에 다른 시도 키가 온 경우의 응답'은 아직 선택하지 않았다. 다음 논의는 실제 제공사 테스트 환경으로 지금 전환을 시작할지와 대상 제공사·작업 범위다. 제공사 고유 응답·오류·결과 보존 계약을 새로 만드는 모의 PG 확장은 우선하지 않는다. 지금 전환하라는 사용자 승인이나 특정 제공사 선택으로 해석하지 않는다. 시도별 키라는 내부 결정은 유지하되, 외부 헤더 형식·멱등 보장 기간·조회·취소 결과는 선택한 제공사의 공식 계약을 확인해 연결한다. 우리 업무 이력의 보존과 제공사의 멱등 응답 보장 기간은 구분한다.

이어 사용자는 PG 테스트 환경 연결을 진행하겠다고 선택했다. 모의 PG의 환불 계약 확장보다 실제 제공사 테스트 연동을 먼저 진행한다. 대상 제공사는 아직 선택하지 않았다. 현재 소스에는 실제 PG 어댑터·구매자 인증 결제 화면·인증 결과를 받는 쓰기 API가 없으므로 기존 자동 승인 어댑터 교체만으로 완료되지 않는다. 첫 검증 범위와 현재 코드 영향은 [PG 테스트 연동 계획](pg-test-integration-plan.md)에 정리했다. 과거 포트원 V2 계획인 GitHub #82는 not_planned로 닫혔으며 현재 제공사 선택이나 구 구현의 호환성 요구로 삼지 않는다.

이어 사용자가 포트원 테스트 채널 설정 사진을 제공했다. 화면의 PG Provider는 `tosspay_v2`이며 토스페이 간편결제 채널이다. 준비 비용을 줄이기 위해 이 포트원 V2 채널을 활용하는 방향으로 진행한다. 처음 제안한 토스페이먼츠 카드 채널과 구분하고, 실제 연결·승인 성공으로 기록하지 않는다. 채널에 입력된 PG API Key를 포트원 서버 인증용 V2 API Secret으로 사용하지 않는다. 로컬 비밀 설정의 빈 파일을 준비했으며 사진 속 키 원문은 코드·문서에 옮기지 않았다.

이후 사용자가 전달한 Store ID·Secret을 Git에서 제외한 로컬 설정에 저장하고 실제 포트원 서버의 테스트 결제 목록을 읽기 전용 조회했다. 지정 Store ID·`isTest=true` 필터로 HTTP 200·정상 응답·반환 0건을 확인했다. 원자료는 [연동 계획의 인증 확인 기록](pg-test-integration-plan.md#2026-10-27-읽기-전용-api-인증-확인)을 따른다. 채널 키 원문·실제 채널 사용은 아직 확인 전이고, 결제·취소 생성과 업무 앱 연동은 수행하지 않았다.

이어 채널 키를 준비하고 독립 테스트 결제 9,000원·전액 취소를 검증한 뒤, 사용자는 웹훅·주기 조회 병행의 B안부터 진행하기로 선택했다. 서명 검증·연결값 mapper·DB 내구 접수·재조회 예약·조회로 확인된 PAID의 기존 결과/Outbox 반영을 구현했다. 접수 응답은 결제 확정이 아니고, 알림·브라우저 응답의 도착 순서나 중복에 의존하지 않는다. 외부 조회 중 DB 잠금을 유지하지 않으며 기존 확정 결제를 알림으로 되돌리지 않는다.
로컬 140건·OCI 단위 140건/통합 57건(신규 9건)의 근거는 [PG 연동 계획](pg-test-integration-plan.md#2026-10-27-b안-웹훅-접수주기-조회-기반)을 따른다. 실제 SDK의 로컬 주문 연결·공개 HTTPS 수신 주소·포트원 웹훅 실전달, PAID 이외 상태와 실제 환불·복구·정산은 후속이다. 웹훅 서명 시크릿도 로컬 비밀 설정에만 보관했다. 기존 주소를 찾기 위한 Cloudflare CLI는 미인증이어서 도메인 존재 여부를 아직 판단할 수 없다.

이어 사용자가 OCI 공개 IP 사용을 제안하고 실행을 승인했다. 도메인 구매·Cloudflare 인증 없이 공개 신뢰 IP 인증서와 8시간 간격 갱신 확인을 구성했다. 전용 nginx에서 웹훅 경로만 공개하며 비밀값은 로컬에 두고 SSH로 로컬 Payment·격리 OCI DB를 연결한다. 실제 TEST 준비 웹훅과 재발송을 200으로 수신하고 DB 중복 방지를 확인했다. 이 Mac과 연결이 실행 중이어야 수신되는 검증 환경이며 24시간 운영 배포나 실제 Order 결제 성공·환불 완료와 구분한다. 상세 근거는 [공개 IP 구성 기록](pg-test-integration-plan.md#oci-공개-ip-https-구성실제-웹훅-수신)을 따른다.

이어 사용자는 결제창 정보를 전용 API로 묶어 제공하는 A안을 선택했다. 기존 본인 결제의 고정 paymentId·순결제액·주문 연결값과 서버의 공개 채널·웹훅 주소를 반환한다. 조회는 새 결제 생성·승인·예약이 아니며 본인 PENDING·PORTONE_TEST만 대상으로 한다. 브라우저 변조 가능성·응답 후 상태 변경은 남으므로 최종 PG 조회를 계속 사용한다. Payment 접수 전 404와 고객의 대기 안내·실제 PG 실패 분류는 별개다. 계약과 검증은 [결제창 정보 API 기록](pg-test-integration-plan.md#2026-10-27-a안-본인-결제창-정보-전용-api)을 따른다.

이후 실제 TEST 주문·결제를 PAID로 확인한 뒤, 사용자는 장기 미확정 환불의 자동 재전송 정책에서 A안을 선택했다. 기존 attemptId 멱등 키는 유지하며 최초 송신 준비의 내구 저장 시각부터 3시간이 되면 자동 취소 명령의 재전송을 막는다. 조회는 허용하고 PENDING·원래 시도를 보존해 운영 확인 대상으로 다룬다. 시간 경과로 실패·보유권 복구·새 실행을 만들지 않는다. 최초 준비가 커밋된 뒤에만 권한을 반환하고 HTTP 직전에도 기한을 다시 검사한다. 준비 이후 실제 전송 전 프로세스가 종료된 경우에도 시간이 진행되는 보수성·고객 대기·운영 확인 비용을 포함한다. 상세 구현 범위와 아직 없는 PG 실행기/조회 작업자는 [재전송 A안 기록](pg-test-integration-plan.md#2026-10-27-장기-미확정-환불의-자동-재전송-a안)을 따른다.


이후 A안의 완료 거절·격리 정책을 반영해 Order의 정지 완료 수신을 구현했다. Refund가 실제 정지 요청 ID를 보존하고 Order·지급 확인·환불·원래 요청과 완료를 대조한다. 일치하면 PENDING_PAYMENT_REFUND로 전이하며 첫 실행 이력·Inbox·RefundExecutionRequested Outbox를 같은 트랜잭션으로 저장한다. 실행 요청은 Order 토픽·주문번호 키로 환불/시도/주문/결제/구매자·전액 금액·통화·정지 완료 이벤트 ID를 전달한다. Payment 접수·PG 실행과 최종 환불 완료는 후속이다.
도메인 7건·서비스 16건의 Red·Green, 로컬 단위·계약 424건과 OCI DB·Kafka·마이그레이션 검증을 완료했다. 최종 통합 근거는 전체 실행에서 통과한 64건과 Kafka 선별 재검증 4건으로 구분했다. 운영 코드 해시·초기 실패와 테스트 조립 수정·공유 자원 보존은 [검증 기록](testing.md#order-full-refund-tdd)을 따른다. 격리된 건의 복구·재투입 책임과 DLT 가용성 의존은 남는다.

Payment는 Order의 환불 허용 조건을 다시 판정하지 않지만, 실행 요청을 자신의 결제 사실과 대조해야 한다.
주문번호·결제 식별자·금액·통화와 같은 연결 근거가 맞는지, 이미 처리한 환불 시도인지 검증하는 책임은 Payment에 있다.
Order가 허용했다는 사실만으로 다른 결제나 다른 금액의 실행을 받아들이지 않는다.
2026-10-27, Payment의 내구성 있는 실행 요청 접수를 추가했다. 환불 허용 시각·자격을 다시 계산하지 않고 로컬 PAID 결제의 주문·결제 ID·구매자·실제 청구액·통화를 대조한다. 같은 paymentId 행을 잠가 같은 실행의 동시 접수를 순차 처리하고 refund_execution·Inbox·시도별 추적 부모를 같은 트랜잭션으로 저장한다. PG 호출은 접수 서비스의 의존성에 포함하지 않는다.
Order의 refundId·attemptId·요청 이벤트·정지 완료 이벤트 ID와 본문을 보존한다. 같은 시도의 변경된 재전달과 요청 ID 재사용은 거절한다. 현재 실행이 미확정이면 새 시도를 받지 않으며 DB의 PENDING 결제/환불 유일 제약도 둔다. 현재 구현의 상태는 PENDING뿐이다. 확정 실패 뒤 새 시도 허용·PG 키 매핑·PG 결과·복구는 별도 후속 계약으로 남긴다.
결제 승인 흐름의 기존 추적 부모를 덮어쓰지 않도록 환불 시도 ID를 키로 별도 추적 저장소를 사용한다. 잘못된 선택적 추적 헤더는 기존 PaymentTraceMapper 규칙대로 무시하고 업무를 진행한다. 이 접수는 추적 부모의 내구성 있는 보존까지이며 PG 재개 span·Tempo 전체 흐름 검증을 뜻하지 않는다.
잘못된 환불 실행 입력은 완료된 Payment 모듈의 기존 입력 거절·제한 Kafka 재시도 후 DLT 처리를 유지한다. 입력 불일치를 PG의 확정 환불 실패로 바꾸거나 결과·복구 이벤트를 추정 발행하지 않는다. Order 정지 완료의 전용 즉시 격리 설정을 다른 소비자 전체로 확대하지 않는다.
도메인 13건·서비스 15건의 Red·Green 뒤 로컬 Payment 단위 123건, OCI Payment 단위 123건·통합 48건과 공통 Kafka 183건을 검증했다. 실제 공급자 중단 중 접수·전체 롤백·동시성·메시지 중복·추적 부모 보존과 잘못된 금액의 DLT 경계를 확인했다. 공유 컨테이너 18개·볼륨 55개는 보존했다. 구체적인 범위와 원자료는 [검증 기록](testing.md#order-full-refund-tdd)을 따른다.
이 분리에는 Order와 Payment 사이의 요청·결과 계약과 진행 상태를 조율하는 비용이 따른다.
License 장애나 정지 완료 확인 지연은 PG 실행도 지연시킨다. 정지 완료 통지·중단 후 재개가 필요하다.
접수 응답은 보유권 정지 완료를 보장하지 않는다. 저장 후 응답 직후 서버가 재시작돼도 정지 요청·완료 확인과 PG 실행을 누락 없이 이어갈 수 있어야 한다.

**추적 기반의 역할** — [Tempo 도입·검증](tempo-tracing-plan.md)은 기존 구매 흐름의 Outbox 헤더 전달과 Payment 접수·예약·재시작·재시도의 부모 복원을 확인했다.
환불의 새 이벤트와 별도 재개 작업에서도 컨텍스트가 이어지는지 추가 검증해야 한다. 기존 도입만으로 새 환불 흐름의 추적 완전성이 보장되지는 않는다.
수집된 span은 호출 관계·오류·지연을 조사하는 근거다. 환불 단계·실행 결과·재처리 여부의 정본은 업무 DB에 보존하고, 환불·주문·결제·이벤트의 업무 식별자로 연결한다.
현재 로컬 Tempo 보존 설정은 1시간이며 샘플링·수집기 장애로 trace가 없을 수 있다. trace 부재를 미실행이나 환불 실패의 근거로 사용하지 않는다.
메시지 중복·순서 역전·미전달·장기 대기와 복구 절차는 별도로 구현·검증한다.

**대가와 반례** — License 지급이 늦어져도 자동 환불 기한은 연장되지 않는다.
이미 저장한 ZIP을 회수할 수 없으며 기존 URL의 남은 유효시간 동안 파일 접근이 가능하다.
PG 응답 유실은 환불 실패의 근거가 아니며, 미확정이 길어지면 고객이 돈도 돌려받지 못하고 상품도 이용하지 못하는 기간이 길어질 수 있다.
PG 전체 가용성이 높아도 개별 거래의 결과 확인은 지연될 수 있다. 미해결 건 추적·고객 안내·운영 대응의 책임은 서비스에 남으며 구체적인 개입 기준은 추가로 결정한다.
PG의 환불 성공 후 로컬 저장에 실패하는 경우도 있어 우리 DB의 중복 방지만으로는 외부 환불의 멱등성을 보장할 수 없다.

**선택하지 않은 대안** — PG 성공을 확인할 때까지 보유권을 유지하는 방식, 기존 presigned URL의 즉시 무효화를 위한 다운로드 경로 변경,
미확정·일시 장애의 결과 확인을 사용자 재시도에만 맡기는 방식, License 정지 요청과 PG 실행을 완료 확인 없이 병행하는 방식.

남은 정책과 계약 질문은 [Q9](domain/open-questions.md#q9)에서 관리한다. 각 쟁점은 담당자의 선택과 이유, 반례·비용 검토 후 결정한다.

## 검증하며 드러난 것

정적 검증이 잡는 것과 못 잡는 것이 뚜렷하게 갈렸다. 기록해 둔다.

| 발견 | 잡은 수단 | 정적 검증이 놓친 이유 |
|---|---|---|
| `api ↔ application` 순환 12건 | ArchUnit 순환 검사 | import 를 눈으로 읽어서는 안 보인다 |
| 어댑터가 자기 포트를 못 보는 규칙 결함 | 실제 적용 | 규칙을 쓸 때는 몰랐다 |
| 빈 모듈에서 터지는 규칙 2건 | **규칙을 안 쓰던 모듈에 적용** | 9개 앱이 전부 비지 않아서 가려져 있었다 |
| javadoc 이 코드와 어긋난 것 (13번) | **규칙으로 옮겨 적기** | 문서는 자기가 사실인지 확인하지 않는다 |
| `catalogRestClient` 빈 이름 충돌 | **애플리케이션 기동** | 컴파일·규칙 23개 모두 통과했다 |
| Docker 29 가 Testcontainers 를 거부 | 개발 환경 빌드 | 업스트림이 바뀐 것이라 코드에 흔적이 없다 |
| self-hosted CI 가 테스트를 건너뛰고 그린 | **소요 시간이 5분 57초 → 23초** | 빌드는 성공했다. 로그를 열지 않으면 보이지 않는다 |
| 컨테이너 재사용이 Flyway 검증을 깨뜨림 | 통합 테스트 | 모듈 간 상태 누수라 한 모듈만 보면 안 보인다 |
| 추적이 꺼진 구성에서 **빈 응답 헤더**를 내보냄 (17번) | **없던 자리에 테스트를 붙임** | `Tracer.NOOP` 은 null 이 아니라 빈 traceId 를 가진 스팬을 준다. null 검사는 통과한다 |
| store·download 에 재시도 정책도 DLT 도 없었음 (19번) | **다른 작업을 적용하다가** | 두 서비스는 `common:messaging` 을 의존하지 않는다. 없는 것은 규칙 위반으로 잡히지 않는다 |
| 운영 컨트롤러가 자동 구성 스위치를 우회 (19번) | **컨텍스트 로딩 테스트** | `@RestController` 가 `@Component` 를 품는다. 스캔 범위가 겹치는 컨텍스트에서만 드러난다 |

> `self-hosted CI` 줄은 **초록불이 신호가 아닐 수 있다**는 사례다.
> 실패는 스스로 알리지만 "돌지 않음"은 알리지 않는다 —
> 통과 개수도, 결과 파일도, 종료 코드도 전부 정상으로 보인다.
> 이번에 그것을 드러낸 유일한 값이 **소요 시간**이었다.

`catalogRestClient` 건이 컨텍스트 로딩 테스트를, Docker 29 건이 Docker 호환성 검증을 추가한 계기다.
**"컴파일되고 규칙도 통과하는데 안 뜨는" 부류가 실재한다.**

표의 위쪽 세 건은 성격이 다르다. 셋 다 **규칙을 쓰거나 옮기는 과정 자체**가 잡아냈다 —
검사가 통과한다고 검사가 옳다는 뜻은 아니다.

### 한 번 띄워 보고 나온 것 (17~19번 적용 직후)

전체 스택을 원격에 올려 스모크를 돌렸다. **테스트 977개가 전부 통과한 상태에서 결함이 8건 나왔다.**
공통점은 하나다 — 전부 *컴파일·단위 테스트·컨텍스트 로딩의 사각지대*, 즉
**설정과 바깥 세계의 접점**이다.

| 발견 | 증상 | 왜 테스트가 못 잡았나 |
|---|---|---|
| `grafana/tempo:latest` 가 v3.0.0 을 받아옴 | 기동 즉시 사망 — 3.x 는 `ingester`/`compactor` 를 최상위에서 안 받는다 | 이미지 태그는 코드가 아니다. 어제 되던 것이 오늘 안 된다 |
| `springdoc.api-docs.enabled=false` | **Swagger UI 전체가 404.** 그 속성은 명세 하나가 아니라 구성 전체의 스위치였다 | 게이트웨이에는 컨트롤러가 없어 스냅샷 테스트 대상이 아니다 |
| DLT 접미사가 `-dlt` | 우리 토픽은 점으로 끊는데 `stove.payment.v1-dlt` 가 생겼다 | 스프링 기본값이다. 우리 코드에 그 문자열이 없으니 검색으로도 안 보인다 |
| license 가 이름 규칙을 우회 | 자기 `DeadLetterPublishingRecoverer` 를 만들어 **DLT 토픽이 두 개** 생겼다 | 두 경로 모두 각자는 정상 동작한다. 갈렸다는 사실은 토픽 목록에서만 보인다 |
| license 가 계측도 우회 | 이름을 고친 뒤에도 license 의 DLT 유입만 지표에 없었다 | 카운터를 에러 핸들러 쪽에서 올려서 자기 recoverer 경로가 비껴갔다 |
| Prometheus 가 `host.docker.internal` 을 긁음 | **타깃 10개가 전부 down.** 지표도 규칙도 있는데 알람이 울릴 수 없었다 | 규칙이 조용한 것과 대상이 없는 것이 겉보기에 같다 |
| 파일 단위 bind mount 가 상함 | 호스트 파일은 갱신됐는데 컨테이너는 옛 내용 — rsync 가 inode 를 바꾼다 | 로컬에서는 파일을 제자리 수정해서 드러나지 않는다 |
| `increase()` 가 첫 1건을 놓침 | Micrometer 는 카운터를 첫 증가 때 등록한다 → 시계열이 값 1 로 생기고 증가분은 0 | 지표는 정상이고 규칙도 유효하다. 둘의 **조합**만 틀렸다 |

앞의 다섯은 고치면서 장치를 하나씩 남겼다 — 태그 고정,
`DeadLetterTopics`(이름 규칙 단일 출처), `DeadLetterPublisher`(발행과 계측을 한 덩어리로),
그리고 `앱은_DLT_발행자를_직접_만들지_않는다` 규칙. **같은 종류로 다시 갈리지 않게 하는 것이 목적이다.**

뒤의 셋은 남길 장치가 마땅치 않다. 컨테이너 배선과 PromQL 의미론은 코드 규칙으로 강제할 대상이
아니라 **한 번 띄워서 확인할 대상**이다. 그래서 이 표 자체가 그 자리를 대신한다.

> 이 절 맨 위의 "초록불이 신호가 아닐 수 있다"가 여기서 한 번 더 반복됐다.
> 이번에는 초록불이 **거짓말을 한 것이 아니라 그 영역을 보지 않았을 뿐**이다 —
> 그런데 결과는 같다. **관측 장치 전체가 죽어 있는데 아무도 몰랐다.**


2026-10-27 후속으로 사용자는 **PG 조회로 같은 결제의 전액 취소를 확인하면 환불 업무를 완료하는 A안**을 선택했다. 취소 주체·현재 실행 시도의 성공 여부를 입증할 때까지 고객 업무도 보류하는 B안은 선택하지 않았다. 고객의 환불 업무와 우리 실행의 결과를 분리한다. PG_QUERY_UNATTRIBUTED 근거·성공 취소별 ID/금액/제공된 시각·PG 최종 취소 시각·최초 확인 시각·이벤트를 보존한다. 실행 상태 PENDING·결과 미확정은 유지하고, Order의 실행에는 reconciliationRequired를 저장한다. 이를 SUCCEEDED나 FAILED로 바꾸지 않는다. 다른 결제·원 PG 거래·상점·채널·TEST 모드·통화·금액의 불일치, 요청 접수/부분 취소·중복 취소 ID·성공 합계 불일치는 완료 근거가 아니다. 여러 성공 취소의 합계가 원결제액과 일치해 전액 취소가 증명된 경우도 인정한다. 선택한 채널 범위의 할인 없는 원결제 검증을 유지한다.

A안은 수동 취소로 환불 API의 장애가 가려질 수 있다는 비용이 있다. 그래서 업무 완료와 별개로 실행 조사 표시를 남긴다. 조사 화면·알림·조사 종결 절차는 미구현이며 완료했다고 하지 않는다. 3시간 경과 후에도 조회로 전액 취소를 확인할 수 있지만 새 취소 명령·새 시도·보유권 복구로 바꾸지 않는다. PG 취소 POST의 응답 분류·확정 실패·사용자 재시도 허용은 이번 선택으로 확정하지 않는다.


2026-10-27 사용자는 ‘자동은 최대한 명확하고 간단한 케이스에만 적용하는 것이 맞다’는 이유로 원결제 전액 잔액 조건 A안을 선택했다. PG에 원액을 amount/currentCancellableAmount로 고정하고 일부 취소나 명시적 잔액 변화가 있으면 추가 자동 취소를 멈춘다. 남은 금액의 자동 보완은 하지 않는다. 잔액 변화는 실패·복구·새 시도의 근거가 아니며 전액 취소 조회 확인에 의한 업무 완료는 유지한다. 같은 시도는 최초 실제 본문·키·준비 시각을 보존한다. 예외의 수동 처리와 고객 대기 비용을 받아들이고 최소 자동 범위를 유지한다. 상세 구현·검증과 아직 연결하지 않은 스케줄/API/실제 PG 범위는 PG 테스트 연동 계획의 최신 A안 기록을 따른다.


2026-10-27 사용자는 검증된 SUCCEEDED 취소 응답으로 후속 조회를 기다리지 않고 실행 성공과 환불 업무를 완료하는 A안을 선택했다. 2026-10-27 사용자는 REQUESTED 후 결과 조회 간격으로 B안(최초 준비 후 5·15·35초, 이후 1분)을 선택했다. 초기에 빠르게 확인하고 장기 대기의 PG 호출을 줄인다. 정상 취소 웹훅은 조기 GET을 깨우며 같은 알림 재전달은 다시 깨우지 않는다. 주기와 임대는 DB에 보존하고 재시작/긴 HTTP 후 밀린 조회는 건너뛴다. 3시간은 기존 POST의 자동 재송신 한계이며 GET 종료 시점이 아니다. 조회 대기/장애는 실패·복구·새 시도를 만들지 않는다. 1분까지의 발견 지연과 일정/동시 작업 관리 비용을 받아들인다. 기존 미확정 송신 직후 1회 조회는 유지하며, 자동 취소 POST 시작/재시도 주기는 후속 결정이다.


2026-10-27 사용자는 환불 실패 후 권한 복구의 B안을 선택했다. 우리 시도에 연결된 PG 취소 ID의 FAILED와 원결제 전액 미취소·진행 중 취소 없음이 추가 조회로 함께 검증될 때만 복구를 요청한다. 다른 경로의 취소를 보지 않고 복구할 위험을 줄이는 대신 조회 장애 시 이용 정지 지속과 추가 대조 비용을 받아들인다. 2026-10-27 사용자는 복구 완료 뒤 고객의 명시적 재시도를 추가 운영 승인 없이 허용하는 A안을 선택했다. 원래 환불 자격·refundId·실패/복구 이력은 보존하고, 검증된 실패와 실제 복구를 확인한 시도에만 새 정지 요청→새 실제 정지 완료→다음 순번/새 attemptId로 이어간다. 같은 이전 실패 번호를 지정한 중복 요청은 같은 재시도 접수이며 뒤늦게 다시 실행을 만들지 않는다. 자동 새 시도는 하지 않는다. 실패 원인이 남아 반복 실패하거나 재처리 동안 권한이 다시 정지될 수 있는 비용을 받아들이고 운영 승인 비용을 추가하지 않는다. Payment는 명시적 이전 실패 연결과 단일 후행 실행을 검증하며, PG 송신은 저장된 이전 FAILED 이력과 현재 전액 잔액을 대조한 경우에만 허용한다.
