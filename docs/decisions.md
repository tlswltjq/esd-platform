# 설계 결정 기록

구조를 바꾸며 내린 판단과 그 근거를 남긴다.
**무엇을 했는지는 커밋이 말하고, 여기서는 왜 그렇게 했고 무엇을 포기했는지를 적는다.**

각 항목은 배경 → 결정 → 근거 → 버린 선택지 순이다.

---

## 1. 모듈을 core 와 api 로 가른다

**배경** — 서비스마다 `api` / `application` / `domain` / `infrastructure` 로 나뉘어 있었지만
경계를 강제하는 장치가 없었다. 실제로 응답 DTO 를 서비스가 반환하고, 서비스가 어댑터를
직접 참조하는 코드가 섞여 있었다.

**결정** — `core`(단일 도메인)와 `api`(바깥과의 접점)로 가르고, ArchUnit 으로 강제한다.

```
core/{domain, port, service}     api/{controller, listener, scheduler, application}     infrastructure/
```

**근거** — 규칙이 없으면 경계는 시간이 지나며 반드시 흐려진다.
규칙을 처음 돌렸을 때 위반이 **166건**이었고, 그중 상당수는 눈으로 읽어서는 보이지 않던 것이다.

**버린 선택지** — 관례로만 정하고 리뷰에서 잡기. 이미 흐려진 뒤였으므로 설득력이 없었다.

---

## 2. 인바운드 어댑터는 컨트롤러만이 아니다

**배경** — 최초 구상은 진입점을 `api/controller` 하나로 뒀는데, 실제 진입점은 셋이었다 —
HTTP 9개, Kafka 리스너 10개, 스케줄러 1개.

**결정** — `api/listener`, `api/scheduler` 를 컨트롤러와 동급으로 둔다.

**근거** — Kafka 리스너는 컨트롤러와 성격이 같다(봉투를 풀어 유스케이스를 부른다).
`infrastructure` 에 두면 "core 는 api 를 모른다"는 핵심 규칙이 리스너에는 적용되지 않는다.

---

## 3. 파사드를 강제하지 않는다

**결정** — 인바운드가 `core.service` 를 직접 불러도 된다. 조율이 필요한 곳에만 파사드를 둔다.

**근거** — 9개 모듈 중 실제 조율이 있는 곳은 order 하나뿐이었다.
전부 강제하면 위임만 하는 껍데기가 8개 생긴다.

**대가** — "언제 파사드를 두는가"가 판단의 영역으로 남는다.
기준은 트랜잭션이다 — 외부 동기 호출을 트랜잭션 밖에 두어야 하면 파사드를 만든다(order 가 그 경우다).

---

## 4. 도메인 객체와 엔티티를 분리하지 않는다

**결정** — `core/domain` 에 JPA 어노테이션과 Spring Data 리포지토리를 허용한다.

**근거** — 모듈당 애그리거트가 1~3개다. 매핑 계층을 두는 비용이 얻는 것보다 크다.
DDD 의 "리포지토리 인터페이스는 도메인 계층에" 해석과도 일관된다.

**대가** — `core` 가 완전히 순수하지는 않다. 대신 규칙을 "전송 기술(HTTP/Kafka)을 모른다"로
좁혀서 지킨다. 영속성은 예외로 두되 그 예외를 명시한다.

---

## 5. 모든 포트는 core 에 둔다

**배경** — 처음에는 외부 **시스템** 포트(PG·CDN·스토리지)는 `core/port` 에,
외부 **도메인** 포트(catalog)는 `api/application/port` 에 두었다.

**결정** — 예외 없이 `core/port` 한 곳.

**근거** — 포트를 찾을 곳이 둘이면 "어디 있더라"가 매번 판단이 된다.
"확정된 가격이 필요하다"는 것도 주문 도메인의 요구이지 어댑터의 사정이 아니다.
DDD 가 리포지토리 인터페이스를 도메인에 두는 것과 같은 자리다.

**따라오는 규칙** — 포트 패키지에는 인터페이스만 둔다.
포트가 주고받는 값은 `core/domain` 의 모델이다(리포지토리가 도메인 객체를 반환하는 것과 같다).

## 6. 트랜잭션과 멱등 가드는 서비스가 소유한다

**배경** — 리스너 10개 중 7개가 `@Transactional` 을 달고 `ProcessedEventGuard` 를 직접 불렀다.
나머지 3개는 서비스가 했다. 두 방식이 공존했다.

**결정** — 서비스로 통일한다. 리스너는 역직렬화와 위임만 한다.

**근거** — 취향이 아니라 **필수**였다. 리스너가 트랜잭션을 열면 Saga 보상 경로가 성립하지 않는다.
내부에서 예외가 나면 바깥 트랜잭션이 rollback-only 로 마킹되고, `catch` 로 삼켜도 커밋 시점에
`UnexpectedRollbackException` 이 난다. license 가 리스너에 트랜잭션을 안 단 이유가 그것이었다.

부수 효과로 어댑터를 갈아끼워도(Kafka → SQS, 운영툴 재처리 API) 멱등성 보장이 따라가고,
Kafka 없이 서비스 단위로 멱등성을 테스트할 수 있게 됐다.

**대가** — 서비스 시그니처에 `eventId`, `eventType` 이 올라온다.
core 가 알게 되는 것은 Kafka 가 아니라 "이 호출은 중복될 수 있고 식별자가 따라온다"는 사실뿐이고,
멱등성은 도메인 서비스의 정당한 관심사이므로 감당할 만하다고 판단했다.

payment 에서만 진입점을 나눴다 — 환불은 HTTP 와 이벤트 양쪽에서 오는데
HTTP 경로에는 넘길 `eventId` 가 없다.

**규칙** — `멱등_가드는_서비스가_소유한다` 가 인바운드에서 `ProcessedEventGuard` 로 가는 의존을 막는다.
트랜잭션 위치만 검사해서는 부족했다 — 트랜잭션이 서비스에 있어도
"이 메시지를 이미 처리했는가"의 판정만 어댑터로 새어 나갈 수 있다.

## 7. 캐시에 실리는 값은 API 응답이 아니다

**배경** — catalog·store 의 조회 서비스가 응답 DTO 를 반환했다. `core → api` 역방향이었고,
실제로 `api ↔ application` 순환으로 잡혔다.

**결정** — core 가 읽기 모델(`ProductView`, `StoreProductView`)을 반환하고 컨트롤러가 응답으로 옮긴다.

**근거** — 방향 문제만이 아니었다. 이 값은 `GenericJackson2JsonRedisSerializer` 로 Redis 에 실린다.
엔티티는 setter 가 없어 역직렬화가 깨지므로 **애초에 엔티티를 반환할 수도 없었다.**
읽기 모델을 따로 두면 캐시 페이로드가 API 계약과 분리되어, 응답 필드를 바꿔도 캐시 스키마가 그대로다.

---

## 8. 멱등성은 두 겹으로, 다만 막는 대상이 다르다

**결정** — Inbox 가드 `(event_id, consumer_group)` 와 도메인 유니크를 함께 건다.
store·download 는 둘 다 두지 않는다.

**근거** — 두 겹이 같은 것을 두 번 막는 게 아니다.

| 층 | 막는 것 |
|---|---|
| Inbox 가드 | **같은 메시지**의 재전달 |
| 도메인 유니크 | **경위가 어떻든 같은 결과** (이벤트 재발급, 수동 재처리) |

store·download 는 문서 ID 고정 upsert 라 연산 자체가 멱등이다.
멱등성은 인프라가 주는 보장이 아니라 연산의 성질이므로, 멱등한 연산에는 장치를 얹지 않는다.

**전제** — Outbox 릴레이는 at-least-once 다. 중복 발행을 막지 않고 소비 측에서 흡수한다.
exactly-once 전달보다 싸고, 이 선택의 대가가 곧 멱등성이다.

## 9. 스텁은 프로파일로 격리한다

**배경** — 외부 연동 5개 중 4개가 스텁인데 전부 무조건적인 `@Component` 였다.
실제 어댑터를 붙이면 같은 포트에 빈이 둘이 되어 기동이 실패했을 것이다.

**결정** — 스텁에 `@Profile("!prod")`. 교체 대상이 둘인 포트는 `@ConditionalOnProperty`.

**근거** — `prod` 에서 구현이 없으면 "no qualifying bean" 으로 즉시 실패하는 편이 낫다.
운영에서 스텁이 조용히 도는 것만은 일어나면 안 된다.

**규칙** — `스텁_어댑터는_격리한다` 가 `Mock*`/`Stub*`/`Fake*` 로 시작하는 어댑터에
`@Profile` 또는 `@ConditionalOnProperty` 를 요구한다. 조건을 거는 것이 관례가 아니라 통과 조건이다.

**대가** — 이름으로 스텁을 식별하는 검사라 완벽하지 않다. `LocalPgClient` 처럼 다르게 지으면 놓친다.
대신 규칙이 이름을 강제하는 셈이 되고, 놓치는 경우도 "조건 없는 스텁" 이라는 가장 흔한 실수는 아니다.

## 10. 머신별 값은 리포에 적지 않고 계산한다

**배경** — 작업 장소가 자주 바뀌는데, `~/.testcontainers.properties` 에 이 머신의 홈 경로가
박혀 있었다. 다른 머신에서는 없는 소켓을 가리키며 실패한다 — 설정하지 않은 것보다 나쁘다.

**결정** — 값이 아니라 계산식을 커밋한다.

```sh
export DOCKER_HOST="$(docker context inspect --format '{{.Endpoints.docker.Host}}')"
```

JDK 는 foojay 리졸버가 조달한다.

**검증** — `~/.testcontainers.properties` 를 비우고 파생된 `DOCKER_HOST` 만으로 테스트가 통과했다.
CI 는 이 머신의 흔적이 없는 환경에서 매번 같은 것을 증명한다.

> 이 계산식은 처음에 `.envrc`(direnv)로 커밋했다가 12번에서 뺐다.
> 계산식이 틀려서가 아니라, 그것을 실어 나르는 도구가 리포의 요구사항이 되기 때문이다.

## 11. 개발 환경 진입 경로를 셋으로 나눈다

**배경** — 주 작업은 M1 랩탑, 이동 시에는 빌려 쓰는 x86 Mac(OrbStack 만 보장).

**결정**

| 경로 | 호스트 가정 | 용도 |
|---|---|---|
| devcontainer (docker-in-docker) | 없음 | 아무것도 못 믿을 때 |
| `scripts/dev.sh` (호스트 소켓) | Docker Desktop / OrbStack | 빌린 머신, 빠름 |
| 로컬 직접 (`./gradlew`) | JDK + Docker 있음 | 주 랩탑 |

**근거** — docker-outside-of-docker 로 통일하는 안은 버렸다.
그 방식은 호스트의 `/var/run/docker.sock` 을 마운트하는데, macOS + OrbStack 에서는
그 경로가 admin 권한으로만 생긴다. 호스트 가정을 없애려다 더 취약한 가정을 들이게 된다.

`scripts/dev.sh` 는 소켓 경로를 활성 docker 컨텍스트에서 계산하므로 그 문제를 피한다.

**중첩의 비용** — 격리 자체가 아니라 호스트 이미지 캐시를 못 쓴다는 점이다.
`/var/lib/docker` 를 이름 붙은 볼륨에 두어 머신당 한 번만 내게 했다.

## 12. 로컬 경로에서 mise 와 direnv 를 뺀다

**배경** — 11번의 "로컬 직접" 경로는 `.mise.toml`(JDK 조달)과 `.envrc`(DOCKER_HOST 계산)를
전제로 했다. 정작 주 랩탑을 확인하니 **둘 다 설치되어 있지 않았다.**
그런데도 빌드는 멀쩡히 돌고 있었다.

**결정** — `.mise.toml` 과 `.envrc` 를 지운다. 리포가 요구하는 설치 도구를 0개로 만든다.

**근거** — 측정이 `.mise.toml` 의 전제를 깼다.

```
$ env -u JAVA_HOME ./gradlew --version
Launcher JVM:  17.0.18 (Homebrew)          # 21 아니어도 돈다

$ env -u JAVA_HOME ./gradlew -q javaToolchains
Microsoft JDK 21.0.10  ...  Detected by: IntelliJ    # mise 아닌 IDE 가 조달했다
```

주석에 적어둔 "Gradle 런처 JVM 이 미리 있어야 한다"는 닭과 달걀은 맞다.
틀린 것은 **그 JVM 이 21 이어야 한다**는 부분이다 — Gradle 8.14 는 17 이상이면 뜨고,
컴파일은 toolchain 이 따로 잡는다. JDK 가 0개인 머신은 이미 A·B 경로가 덮는다.

`.envrc` 는 계산식 자체는 옳지만(10번), 그 세 줄을 위해 direnv 설치를 요구한다.
`DOCKER_HOST` 는 README 에 한 줄로 적으면 되고, 자동화하고 싶은 사람은 `~/.zshrc` 에 둔다.

**대가** — macOS 사용자는 셸마다 `DOCKER_HOST` 를 직접 export 해야 한다.
자동화를 리포에서 개인 환경으로 옮긴 것이고, 그 대신 리포의 설치 요구가 사라진다.

**더 큰 교훈** — 10번은 *검증되지 않은 머신별 값* 이 없느니만 못하다고 했다.
같은 것이 **검증되지 않은 조달 경로**에도 성립한다.
`.mise.toml` 은 커밋된 그날부터 한 번도 실행되지 않은 채 "이 리포는 mise 를 쓴다"고 말하고 있었다.
설정은 자기가 도는지 스스로 증명하지 않는다. 실행되는 것만이 증명한다 — CI 가 그 자리다.

## 13. `@ConfigurationProperties` 의 자리는 정하지 않는다

**배경** — `ModulePackageRules` javadoc 은 `config/` 를 "스프링 설정, `@ConfigurationProperties`"
자리라고 적어 두었다. 정작 `config/` 에는 **하나도 없었다** —
`infrastructure/` 에 4개, `core/domain/` 에 2개. 어느 쪽도 규칙이 없었다.
문서와 코드가 어긋났으니 코드를 문서에 맞추고 규칙으로 굳히려 했다.

**결정** — 자리를 정하지 않는다. 설정값은 **그 값을 쓰는 계층 안**에 둔다. 고친 것은 javadoc 쪽이다.

**근거** — 옮기려고 열어 보니 전제가 틀려 있었다.

```java
// review/core/domain, settlement/core/domain
public record SettlementProperties(Long selfSellerId, BigDecimal partnerFeeRate) { }
//                                                    ^ 중개 수수료율 0.3 — FeePolicy 가 쓴다
```

수수료율은 "어떤 DB 를 쓰는가" 같은 기술 설정이 아니라 정산 도메인 그 자체다.
자동 승인 여부(`ReviewProperties`)도 마찬가지로 `ReviewService` 가 읽는 정책이다.

그리고 이것을 `config/` 로 빼면 `core → config` 가 되어 **1번의 핵심 규칙이 깨진다.**
즉 자리를 강제하는 규칙은 애초에 성립할 수가 없었다 —
계층 규칙이 이미 답을 정하고 있고, 그 위에 위치 규칙을 얹으면 둘이 싸운다.

**버린 선택지** — 전부 `config/` 로 모으기. 5번("포트를 찾을 곳이 하나여야 한다")과 같은 논리로
보였지만 같은 논리가 아니다. 포트는 전부 인터페이스라 소속 계층이 하나로 정해진다.
설정값은 **값마다 소속 계층이 다르다** — 타임아웃은 어댑터의 사정이고 수수료율은 도메인의 사정이다.
찾을 곳을 하나로 만드는 대가가 5번에서는 없었지만 여기서는 규칙 위반이다.

**대신 넣은 규칙** — 위치 대신, 그때까지 아무것도 막지 않던 것을 막는다.

| 규칙 | 막는 것 |
|---|---|
| 설정값은 `api/` 에 두지 않는다 | 진입점마다 같은 값을 따로 읽어 갈리는 것 |
| 이름은 `~Properties` | 컨트롤러·리스너와 같은 결의 네이밍 |
| 설정값은 불변(record)이다 | setter 달린 설정 = 런타임에 조용히 바뀌는 전역 가변 상태 |

7개가 이미 전부 그렇게 되어 있어 프로덕션 클래스는 하나도 옮기지 않았다.
**지키고 있을 때 굳히는 것이 요점이다.**

**대가** — "이 값이 도메인 정책인가 어댑터 설정인가"가 판단으로 남는다.
기준은 읽는 쪽이다 — `core` 가 읽으면 `core` 에 둔다.

**더 큰 교훈** — 12번은 실행되지 않는 설정이 사실이 아닌 것을 말한다고 했다.
문서도 같다. javadoc 은 코드가 자기를 따르는지 확인하지 않는다.
어긋난 것을 발견했을 때 **틀린 쪽이 코드라는 보장은 없다.**
이번에는 문서가 틀렸고 코드가 옳았으며, 그것을 드러낸 것은 읽기가 아니라
**규칙으로 옮겨 적으려는 시도**였다. 강제할 수 없는 문장은 대개 사실이 아니다.

## 14. `libs/` 를 `common/` 으로 바꾸고 접두사를 뗀다

**배경** — 공용 모듈이 `libs/common-core` 였고 그 패키지는 `com.stove.common.core` 다.
모듈명 하나가 패키지 두 조각을 하이픈으로 눌러 담고 있었다.
`apps/order` → `com.stove.order` 는 조각 대 조각인데 이쪽만 규칙이 달랐다.

**결정** — `common/core`. 디렉터리가 곧 패키지 조각이다.

**근거** — 셋이 같은 방향을 가리켰다.

1. 경로가 패키지와 1:1 이 된다. 두 트리가 다른 규칙을 쓸 이유가 없었다.
2. `libs` 는 Gradle 이 이미 쓰는 이름이다 — `build/libs` 가 산출물 디렉터리이고
   Dockerfile 이 `apps/*/build/libs/*.jar` 를 집는다. 한 리포에서 같은 단어가 두 뜻이었고,
   실제로 참조를 세려고 `libs/` 를 grep 했을 때 소스와 jar 경로가 섞여 나와 걸러내야 했다.
3. 접두사가 부모 디렉터리와 중복이다. `common/common-core` 라고 쓰지 않는 것과 같은 이유다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| `libs/core` — 디렉터리는 두고 접두사만 제거 | `com.stove.common.core` 의 `common` 이 경로에서 사라진다. 지금보다 나쁘다 |
| `common/testing` — `:common:test:test` 가 어색해서 | 패키지도 따라가야 하고 import 15개가 바뀐다. 이 변경의 명분(경로 = 패키지)을 스스로 깨는 값이다. 어색함은 아무도 치지 않는 명령어에만 나타나고 `./gradlew test` 는 그대로다 |

**대가** — `apps`/`libs` 는 종류 대 종류였는데 `apps`/`common` 은 종류 대 역할이 된다.
분류 기준이 섞이는 것은 맞다. 다만 "배포하는 것 / 그들이 공유하는 것" 으로 읽히고,
매일 얻는 것은 경로-패키지 일치 쪽이 크다고 봤다.

**산출물 이름은 유지했다** — `:common:core` 를 그냥 두면 jar 가 `core-0.0.1-SNAPSHOT.jar` 로 나온다.
`core.jar` / `web.jar` / `test.jar` 는 클래스패스에서 어느 프로젝트 건지 알 수 없다.
`archivesName` 으로 `common-` 을 되살려 **공용 jar 7개가 리네이밍 전 이름 그대로다**
(`common-core-0.0.1-SNAPSHOT.jar` 등). 산출물 이름은 하나도 바뀌지 않았다.
**사람이 읽는 경로에서는 중복을 없애고, 기계가 뱉는 이름에서는 유일성을 지킨다.**

> CI 는 통과했지만 앱 테스트 10개가 전부 `FROM-CACHE` 였다 — Gradle 이 입력이 같다고 판단해
> 실제로 돌지 않았다. 리네이밍이 no-op 이라는 간접 증거이긴 하나 그것만 믿지 않고
> 캐시를 끄고 61개 태스크를 전부 실행해 확인했다(4분 49초). 12번의 교훈과 같은 자리다 —
> **돌지 않은 검사는 통과한 것이 아니다.**

## 15. 인프라가 필요한 검증은 원격 러너로 옮긴다

**배경** — 주 랩탑은 RAM 8GB 이고 Docker 에 준 것은 **3.83GB** 다.
`gradle.properties` 의 `workers.max=2` 는 성능 선택이 아니라 그 한계에 대한 항복이었고
(주석이 "코어가 아니라 Docker 에 준 메모리가 한계선"이라고 적고 있다),
**전체 스택을 한 번도 동시에 띄운 적이 없었다.**

그 대가는 이미 치러져 있었다. `performance.md` 의 HTTP 경로 측정이 무효였다 —
릴레이를 **완전히 끈** 구성이 개선 구성과 같은 숫자(44.9 RPS)를 냈다.
`pageouts` 150만, 스와핑 중에 잰 값이었다. 코드가 아니라 환경을 측정하고 있었다.

**결정** — 11번의 진입 경로 표에 D 를 더한다.

| 경로 | 호스트 가정 | 용도 |
|---|---|---|
| A. devcontainer | 없음 | 아무것도 못 믿을 때 |
| B. `scripts/dev.sh` | Docker Desktop / OrbStack | 빌린 머신 |
| C. 로컬 직접 | JDK + Docker | 단위 테스트·ArchUnit |
| **D. OCI self-hosted 러너** | **없음 (push 하면 돈다)** | **인프라가 필요한 전부** |

A·B·C 는 "이 머신의 Docker 를 어떻게 빌리는가"의 변주였고 셋 다 같은 천장 아래 있었다.
D 는 천장을 바꾼다. 경계는 **무엇이 컨테이너를 요구하는가**다 —
단위 테스트는 로컬이 빠르고 CI 를 기다릴 이유가 없다.

**측정** — 첫 self-hosted 빌드 (Ampere A1, 4코어 23GB, aarch64):

| | |
|---|---|
| 동시 컨테이너 최대 | **15** |
| 최저 available 메모리 | 16,127 MiB |
| 러너 cgroup 피크 | 5,264 MiB |
| swap 사용 | **0** |

로컬 Docker 총량이 3,919 MiB 다. 15개가 동시에 뜨면서 스왑을 한 번도 건드리지 않았다.
`workers.max` 를 4로 올린 것은 러너의 `~/.gradle/gradle.properties` 이고,
**리포의 2/2g 는 그대로 두었다** — 그 값은 3.83GB 머신의 값이고 그 머신은 여전히 존재한다(10번).

**대가 1 — 격리가 없다.** self-hosted 러너는 docker 그룹을 요구하고 docker 그룹은 사실상 root 다.
리포가 PRIVATE 이라 fork PR 이 러너에서 도는 경로가 없다는 것이 전제다.
**공개 리포였다면 이 구성은 금지다.** 전용 사용자(`runner`)와 홈 밖 워크스페이스로 완화했을 뿐,
격리했다고 말할 수는 없다.

**대가 2 — 잡 사이에 상태가 남는다. 그래서 CI 가 조용히 거짓말을 했다.**

`ubuntu-latest` 는 매 잡이 새 머신이라 `~/.gradle` 이 남지 않는다.
self-hosted 는 남는다. 그것이 `org.gradle.caching=true` 와 만나 이렇게 됐다.

| 실행 | 소요 | 태스크 |
|---|---|---|
| 1회차 | 5분 57초 | **84 executed** |
| 2회차 | 23초 | 41 executed, **43 from cache** |
| 3회차 | 23초 | 41 executed, **43 from cache** |

**2·3회차의 23초 동안 테스트는 한 줄도 돌지 않았다.** 그린이었다.
14번이 기록한 것과 같은 함정인데, 이번에는 우연이 아니라 **구조가 되어 있었다** —
입력이 같은 한 앞으로 영원히 그럴 것이었다.

캐시 자체는 정직하다. 입력이 같으면 결과도 같다는 전제가 옳기 때문이다.
**앱 테스트에서 그 전제가 성립하지 않는 것이 문제다.** Testcontainers 컨텍스트 로딩
테스트의 결과는 소스 입력이 아니라 환경(Docker 버전·이미지·메모리·네트워크)에 달려 있고,
그 환경을 검증하는 것이 이 테스트의 존재 이유다. compose 파일이나 러너 설정만 바꾼
변경에서 CI 가 그린인데 Docker 를 한 번도 안 건드리는 상태가 만들어진다.

**해법 — CI 에서만 테스트 결과를 캐시에서 꺼내지 않는다**(`build.gradle`).

```groovy
if (providers.environmentVariable('CI').isPresent()) {
    outputs.upToDateWhen { false }
    outputs.cacheIf { false }
}
```

컴파일 캐싱은 유지한다 — 컴파일 결과는 입력만으로 결정되므로 전제가 성립한다.
로컬도 건드리지 않는다. 반복 루프에서는 캐시가 맞고,
**실제로 도는지 증명하는 자리는 CI 다**(12번). 느려지는 것은 테스트뿐이다.

**버린 선택지** — `--no-build-cache`. 간단하지만 컴파일 캐시까지 버린다.
전제가 성립하는 곳의 캐시까지 끌 이유가 없다.

**대가 3 — 상한을 스스로 걸어야 한다.** GitHub-hosted 는 잡이 죽어도 남의 일이지만
self-hosted 는 같은 커널을 공유한다. swap 이 0 인 채로 스파이크가 나면 OOM killer 가
무엇을 죽일지 `oom_score` 가 정한다. swap 8GB 와 러너 cgroup `MemoryMax` 를 함께 건다.
상한값은 추정이 아니라 위 실측(5.3GB)의 2배로 정했다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| `ubuntu-latest` 유지 | 2코어 7GB. Testcontainers 스택을 병렬로 못 띄운다. 애초의 문제가 그대로다 |
| MCP 서버로 원격을 도구화 | 먼저 만들면 순서가 뒤집힌다 — CI 를 써보기 전에는 커밋 전 반복 루프가 얼마나 답답한지 모른다 |
| CI 전용 인스턴스 분리 | 격리는 얻지만 Always Free 한도를 넘고 용량 확보 싸움을 다시 해야 한다 |
| 포트를 publish 한 채로 | 이 호스트는 공개 IP 다. ES(`xpack.security.enabled: false`)·Grafana(익명 허용)·MinIO·MySQL 이 인증이 없거나 기본 자격증명이다 |

**포트를 열지 않는다** — `docker-compose.ci.yml` / `docker-compose.apps.ci.yml` 가
`ports` 를 지운다. Compose 는 오버라이드에서 `ports` 를 **덮어쓰지 않고 이어붙이므로**
`ports: []` 로는 지워지지 않는다 — `!reset` 태그가 필요하다(Compose 2.24+).
스모크 테스트는 호스트가 아니라 `stove_default` 네트워크 안에서 돈다.

## 16. 컨슈머 그룹 이름은 한 곳에서만 정한다

**배경** — 같은 이름이 앱마다 세 곳에 살고 있었다.

| 자리 | 예 (license) | 실제로 쓰이나 |
|---|---|---|
| `application.yml` 의 `group-id` | `license` | **아니오** — 아래가 덮어쓴다 |
| `@KafkaListener(groupId=)` | `"license"` | 예 (Kafka 그룹) |
| 서비스의 `CONSUMER_GROUP` | `"license"` | 예 (Inbox 멱등 키, 8번) |

리스너 12개가 전부 `groupId` 를 명시하므로 **yml 값은 9개 앱 전부에서 한 번도 읽히지 않았다.**
표기도 이미 갈려 있었다 — 8개 리스너는 자기 `GROUP` 상수를 두고, license·store 는 리터럴을 직접 썼다.
그룹 이름 문자열이 프로덕션 코드에 **26곳** 있었다.

**결정** — 가드를 쓰는 7개 서비스에서 `CONSUMER_GROUP` 을 `public` 으로 열고 리스너가 그것을 참조한다.
yml 의 `group-id` 는 지운다. `ConsumerGroupRules` 가 값 일치와 `groupId` 명시를 검사한다.
26곳이 9곳(가드 서비스 7 + store·download 각 1)이 됐고, **가드를 쓰는 앱은 전부 1곳**이다.

**근거** — **결함을 고친 것이 아니다.** 중복을 없앤 것이고, 이득도 딱 그만큼이다.
읽히지 않는 설정이 9개 앱에 하나씩 있었고, 같은 뜻의 상수가 두 가지 표기로 갈려 있었다.
14번과 같은 자리다 — 사람이 읽는 경로에서 중복을 없앤다.

죽은 `group-id` 를 남겨두지 않은 이유는 따로 있다. **읽히지 않는 값이 조종 손잡이처럼 보이는 것**
자체가 함정이다. 컨슈머 그룹을 바꾸려는 사람이 가장 먼저 여는 파일이 `application.yml` 인데,
거기를 고쳐도 아무 일도 일어나지 않는다.

**의미상으로도 한 값이 맞다** — 멱등 키가 "이 이벤트를 누가 처리했는가"를 뜻한다면
그 "누가"의 정체는 컨슈머 그룹이다. 전에는 두 값이 우연히 같았고, 이제는 같은 것을 가리킨다.
다만 이건 설계 취향의 논거이지 급한 이유는 아니었다.

**규칙이 참조가 아니라 값을 보는 이유** — 애노테이션 속성은 컴파일 타임 상수라
바이트코드에는 값만 남고 **"무엇을 참조했는가"가 지워진다.**
"리터럴 대신 상수를 참조하라"는 정적으로 검사할 수 없고, 값 대조가 유일한 방법이다.

**대가 1 — 멱등 키가 Kafka 토폴로지를 따라 움직이게 됐다.** 이게 이 결정의 진짜 대가다.

전에는 `processed_event.consumer_group` 이 Kafka 와 독립이었다. 가드는 자기가 쓴 값과
자기가 읽는 값만 비교하므로(`ProcessedEventGuard:32,36`), 그 값이 Kafka 그룹명과 달라도
**일관되기만 하면 멱등은 완전하게 동작했다.** 묶고 나면 그룹명을 바꾸는 모든 경우에
과거 처리 기록이 통째로 안 보이게 되고, `auto-offset-reset: earliest` 와 만나 전량이 재실행된다.

| 그룹명을 바꾸는 이유 | 묶기 전 | 묶은 뒤 |
|---|---|---|
| 재처리하려고 | 재처리가 안 된다 | **의도대로 재처리된다** |
| 환경 접두사·명명 규칙 등 무관한 이유 | **아무 일도 없다** | 전량 재실행된다 |

**이 저장소에서는 아랫줄이 더 현실적이다.** 계획된 재처리 수단은 그룹 rename 이 아니라
DLT + 운영툴이고(README 7절, 6번의 "운영툴 재처리 API"), 그 경로에는 컨슈머 그룹이 없다.
윗줄을 근거로 삼아 이 변경을 정당화하지 않는다.

전량 재실행이 실제 사고가 되지 않는 것은 8번의 두 번째 층이 받아내기 때문이다 —
`Order.markPaid():93`(상태 가드), `GameProject.approve()`(상태 불일치 시 무시),
license 의 `existsByOrderNoAndProductId`, settlement 원장 유니크. **위층을 흔들어도
아래층이 버틴다는 것이지, 위층을 흔든 것이 안전하다는 뜻은 아니다.**

**대가 2** — 리스너가 `core.service` 의 상수를 참조한다. payment 의 `LicenseEventListener` 는
`RefundFacade` 만 알던 것이 `PaymentService` 를 import 하게 됐다.
계층 방향은 허용 범위이고(`Inbound → CoreService`, 1번) 컴파일 타임 상수라 바이트코드에
의존이 남지도 않지만, 소스에는 남는다.

store·download 는 제외한다. Inbox 가드가 없어(8번) 대조할 두 번째 출처가 아예 없다.
**다만 제외 여부는 `ProcessedEventGuard` 주입으로 판정하고, 이름 목록으로 적지 않는다.**
처음 쓴 규칙은 `CONSUMER_GROUP` 상수의 부재로 제외를 판정했는데, 그러면 "가드를 안 쓰는 앱"과
"상수가 사라진 앱"이 같은 문으로 빠져나간다 — 검사할 것이 없는 것과 검사 대상이 사라진 것을
구별하지 못한 채 초록으로 보인다. [D-021](defects.md#d-021) 과 같은 부류의 공허 통과다.
이름 목록으로 적지 않는 이유도 같다. 목록은 낡고, 낡은 목록은 침묵으로 낡는다.

그래서 규칙 자신을 검사하는 테스트를 함께 붙였다(`ArchRuleEnforcementTest$ConsumerGroup`).
앱 하나를 모사한 픽스처 다섯 개로 **갈라진 그룹·상수 없는 가드·groupId 누락**은 잡는지,
**한 상수에서 나온 그룹·가드 없는 앱**은 통과시키는지 양쪽을 본다.
`ArchRule` 이 아니라 `JavaClasses` 를 받는 메서드라서 — 앱 전체를 모아 집합끼리 비교해야 하는데
`ArchRule` 은 클래스 단위로 돈다 — 기존 위반/준수 픽스처 두 벌을 재사용하지 못하고 앱 단위로 만들었다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| yml 을 단일 출처로 (애노테이션에서 `groupId` 생략) | 그룹명이 컴파일 타임 상수가 아니게 되어 서비스는 `@Value` 주입이 필요하고 `core` 에 스프링 설정 의존이 들어온다. **컴파일 에러가 기동 실패보다 강하다** |
| 기동 시 `KafkaListenerEndpointRegistry` 와 대조 | yml 까지 반영된 최종 런타임 값을 보는 유일한 방법이지만, 서비스가 그룹명을 밖으로 알리는 통로가 따로 필요하다. 정상 경로를 상수로 이미 막았으므로 걸릴 일이 없다 |
| yml 의 `group-id` 유지 | 운영 가시성을 위해 남기자는 안. 읽히지 않는 값이 **"여기가 그룹을 정하는 자리"처럼 보이는 것**이 손해다 |
| 그대로 두기 | 가장 진지한 후보였다. 결함이 없었고 재현된 사고도 없다. 중복 제거의 값이 대가 1을 넘는다고 봤지만 **아슬아슬한 판단이고, 반대로 정해도 틀리지 않는다** |

> **이 항목은 결함 수정이 아니다.** 처음 잡았던 근거는 "그룹명을 바꿔 재처리할 때
> Inbox 가 조용히 무력화한다"였는데, 그 조작은 이 저장소의 어느 문서·스크립트에도 없고
> 계획된 재처리 경로도 아니다. 일어날 예정이 없는 사고를 1순위 근거로 삼았던 것이라
> 근거를 중복 제거로 낮추고, 대신 대가 1을 적었다. 커밋도 `refactor:` 로 단다.

## 17. 추적 컨텍스트를 이벤트와 함께 저장한다

**배경** — `correlationId` 는 HTTP 구간에서만 이어졌다. 주문 하나가
order → payment → license → settlement 로 흐를 때 order 이후 로그가 `[payment,]` 로 빈칸을 찍었고,
`EventHeaders.CORRELATION_ID` 는 "규약만 적어두고 미룬다"는 주석과 함께 **아무도 참조하지 않는 상수**였다.
그 주석의 미룬 근거는 "Micrometer Tracing 이 들어오면 손으로 만든 헤더는 중복이 된다"였다.

**결정** — Micrometer Tracing + OTLP 를 도입하고, **적재 시점에 붙잡은 `traceparent` 를
`outbox_event` 에 컬럼으로 저장했다가 발행 시점에 헤더로 되살린다.**

**근거** — 미룬 근거의 절반은 맞고 절반은 틀렸다. 표준 헤더로 가는 것은 옳았지만,
**자동 계측만으로는 이 시스템에서 트레이스가 이어지지 않는다.**

Kafka 자동 계측은 `send()` 를 호출한 **스레드**에 매달린 컨텍스트를 싣는다.
그런데 Outbox 는 발행을 일부러 뒤로 미루므로 실제 발행자는 요청 스레드가 아니라 릴레이 스케줄러다.

```
[요청 스레드]      주문 생성 → outbox INSERT → 커밋 → 스레드 반납 (컨텍스트 소멸)
                       ⋮  최대 1초
[스케줄러 스레드]  폴링 → kafka.send()   ← 자동 계측은 여기의 컨텍스트를 싣는다
```

맡겨두면 컨슈머가 **"릴레이가 돈 폴링 회차"를 부모로 삼는다.** 배치에 여러 애그리거트가 섞이면
무관한 주문들이 같은 traceId 를 공유하는, 없느니만 못한 상태가 된다.
`EventHeaders` 주석이 MDC 를 두고 적어둔 "적재 시점에 담아 두지 않으면 릴레이에서는 이미 없다"가
추적 컨텍스트에도 **글자 그대로** 적용된다 — 스레드 로컬이라는 메커니즘이 같기 때문이다.

그래서 이벤트 본문에 적용한 논리(지금 커밋하고 나중에 보낸다)를 컨텍스트에도 적용했다.
**Transactional Outbox 와 분산 추적의 충돌은 구현 실수가 아니라 두 패턴의 전제가 어긋나는 지점이고,
그 간극은 이 저장소가 메워야 한다.**

**따라오는 것들**

| 바뀐 것 | 이유 |
|---|---|
| `CorrelationIdFilter` → `TraceIdResponseFilter` | 하던 일 셋 중 식별자 생성·MDC 적재는 라이브러리가 더 잘 한다. 응답 헤더로 돌려주는 것만 남겼다 |
| `X-Correlation-Id` 헤더 이름은 유지 | 밖에서 보이는 계약이다. 내부 구현이 바뀌었다고 따라 바꿀 이유가 없다 — **값의 출처만 traceId 로 일원화됐다** |
| order 의 `RestClientConfig` 삭제 | `RestClient` 빌더에 옵저베이션이 이미 걸려 있어 `traceparent` 가 자동으로 실린다. 예고된 "중복"이 실제로 그 자리에 있었다 |
| `EventHeaders.CORRELATION_ID` 삭제 | 위와 같다. 이름을 우리가 정하지 않는 헤더(`traceparent`)로 대체했다 |
| 릴레이가 헤더를 **직접** 넣는다 | 자동 계측에 맡기면 스케줄러의 컨텍스트가 실린다. `spring.kafka.template.observation-enabled` 를 켜면 이 복원이 덮어써진다(부트 기본값이 꺼짐이라 지금은 안전하다) |

**대가**

1. **`outbox_event` 에 이벤트와 무관한 컬럼이 하나 생겼다.** 이 표에서 유일하게 "이벤트에 관한 것이
   아닌" 값이다. 스레드 로컬이라는 제약이 강제한 것이고, 대안은 전부 더 나빴다(아래).
2. **전파 형식이 W3C 라는 전제가 코드에 박혔다.** B3 로 바꾸면 `MicrometerTraceContextCapture` 가
   값을 못 찾는다. 그때 **Kafka 구간 추적만 조용히 끊기고** 처리 자체는 계속된다 —
   테스트로 그 동작을 못 박아 뒀다.
3. **마이그레이션이 7벌 복제됐다.** 스키마 복제는 이미 있던 문제이고 이 결정이 만든 것은 아니지만,
   같은 파일을 7번 붙여 넣을 때마다 그 비용이 다시 확인된다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| 자동 계측만 켜고 끝낸다 | **틀린 트레이스가 생긴다.** 없는 것보다 나쁘다 — 무관한 주문들이 한 트레이스로 묶인다 |
| `correlationId` 헤더를 손으로 만든다(원래 백로그) | 표준을 두고 사설 규약을 유지하게 된다. 구간별 소요 시간과 부모-자식 관계도 못 얻는다 |
| traceparent 를 payload 에 넣는다 | 이벤트 계약이 관측 도구를 알게 된다. 컨슈머가 body 를 파싱하기 전에 헤더만 보고 판단한다는 규약도 깨진다 |
| 릴레이에서 스팬을 새로 열고 부모로 잇는다 | 폭포수에 "발행 지연"이 한 칸으로 보이는 이점이 있지만, 릴레이 hot path 에 스팬 수명 관리가 들어온다. 지금은 부모 스팬 종료와 컨슈머 스팬 시작 사이의 **간격**으로 같은 정보가 읽힌다 |
| `tracestate` 까지 저장한다 | 벤더 확장 값이라 트레이스 트리를 그리는 데 필요 없다. 컬럼 하나(55자 고정)로 끝나는 것을 JSON 으로 키울 이유가 없다 |

## 18. API 명세를 생성하고, 그 명세를 테스트로 고정한다

**배경** — 엔드포인트 31개의 목록이 어디에도 없었다. 파악하려면 README 의 curl 예제를 읽거나
컨트롤러 9개를 여는 수밖에 없었다. 더 나쁜 것은 **응답 형식을 지키는 장치가 없었다**는 점이다 —
[testing.md](testing.md) 6.3 이 적어둔 대로 저장소 전체에 `jsonPath` 단언이 하나도 없어서,
DTO 필드를 지우거나 컨트롤러 시그니처를 바꿔도 컴파일과 테스트가 전부 통과한다.

**결정** — springdoc 으로 명세를 생성하고, **그 명세를 스냅샷으로 커밋해 테스트가 대조한다.**

**근거** — 문서를 손으로 쓰면 코드와 어긋난다. 13번에서 이미 겪은 문제다("문서는 자기가
사실인지 확인하지 않는다"). 생성하면 어긋날 수 없고, 생성물을 고정하면 **계약 변경이 diff 로 드러난다.**

ArchUnit 이 구조에 대해 하는 일을 계약에 대해 한다. 규칙이 없으면 흐려지는 것은 경계만이 아니다.

`@Min(1)`, `@NotEmpty` 같은 이미 있는 Bean Validation 이 그대로 스키마 제약(`minimum`, `minItems`)이
되므로 애노테이션을 새로 달 필요가 없었다. 실제 변경은 의존성 한 줄과 설정이 거의 전부다.

**대가와 그 처리**

| 문제 | 처리 |
|---|---|
| 스냅샷이 임의 포트 때문에 매 실행 달라진다 | `servers` 노드를 지운다. 거기에만 포트가 들어간다 |
| 필드 순서가 바뀌면 전체가 diff 로 뜬다 | 키를 정렬해 저장한다. 순서는 계약이 아니다 |
| 컨텍스트를 9벌 더 띄우면 CI 가 두 배가 된다 | **기존 `*ContextTest` 에 얹었다.** 이미 뜬 서버에 요청 하나를 더하는 비용뿐이다 |
| 의도한 변경마다 손으로 고쳐야 한다 | `-Dstove.openapi.update=true` 로 갱신한다. 그 diff 를 리뷰에 넣는 것이 목적이다 |

**신원 헤더를 명세에 드러낸다** — `X-Member-Id`/`X-Seller-Id` 는 클라이언트가 그대로 보내고
서버가 검증하지 않는다. 문서를 만들면 이 사실이 밖에서 보인다. 숨기지 않고 `ApiDocumentationCustomizer`
가 **"스켈레톤 한정, 서버가 검증하지 않는다"** 를 파라미터 설명으로 붙인다.
설명이 없으면 의도한 스켈레톤이 아니라 빠뜨린 인증으로 읽히고, 4곳 중 하나만 빠져도 마찬가지다.
그래서 서비스마다 적지 않고 `common:web` 한 곳에서 붙인다.

**게이트웨이가 9개 명세를 모은다** — Swagger UI 를 게이트웨이가 서빙하므로 명세도 같은 출처여야 한다
(이 저장소에는 CORS 설정이 없어 다른 포트를 직접 부르면 브라우저가 막는다).
그래서 `/v3/api-docs/<service>` 프록시 라우트 9개를 **라우팅 표에 명시적으로 올렸다.**

이 저장소의 외부 노출 통제는 필터가 아니라 **라우트의 부재**로 표현돼 있고(`GatewayRouteTest`),
문서 프록시는 그 표를 넓히는 변경이다. 그래서 같은 테스트로 성질을 못 박았다 —
GET 전용이고, `/v3/api-docs/<service>` 한 경로씩만 열리며, 하위 경로로 넓어지지 않는다.
**명세에 보인다고 호출할 수 있는 것은 아니다** — 도달 가능성은 여전히 라우팅 표가 정한다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| 문서를 손으로 쓴다(마크다운) | 코드와 어긋난다. 13번에서 이미 겪었다 |
| 스냅샷 없이 Swagger UI 만 | 편의만 얻고 계약 방어는 못 얻는다. 이쪽이 본편이다 |
| 엔드포인트마다 `jsonPath` 단언 | 31개에 손으로 붙여야 하고, 새 엔드포인트에는 저절로 붙지 않는다 |
| 전용 스냅샷 테스트 클래스 9개 | 컨텍스트를 9벌 더 띄운다. CI 시간의 대부분이 컨텍스트 기동이다 |
| 게이트웨이 대신 서비스별 Swagger UI 만 | 9개 포트를 오가야 하고, 컨테이너 구성에서는 게이트웨이만 진입점이라는 전제와 어긋난다 |

## 19. 포기한 메시지를 버리지 않고, 되살릴 문을 단다

**배경** — 실패한 메시지가 사라지는 자리가 두 군데 있었다.

| 자리 | 그때 무슨 일이 | 남는 것 |
|---|---|---|
| 컨슈머 재시도 소진(7초) | 기본 recoverer 가 로그 찍고 건너뜀, 오프셋 커밋 | 로그 한 줄 |
| Outbox 발행 재시도 소진 | `DEAD` 로 전이, 더 시도하지 않음 | DB 행 — **되살릴 방법이 없음** |

두 번째가 특히 이상했다. `OutboxEvent#requeue()` 는 처음부터 있었고 주석도 정확했다 —
"회수 경로가 없으면 장애가 길어진 순간 유실 방지 장치가 유실의 원인이 된다."
그런데 **그 메서드를 부르는 프로덕션 코드가 하나도 없었다.** 전수로 확인했고 호출처는 테스트 4곳뿐이었다.
되살리려면 운영자가 프로덕션 DB 에 직접 UPDATE 를 쳐야 했다는 뜻이다.

**결정** — 컨슈머 실패는 DLT 로 보내고, 두 경로 모두 **HTTP 로 되살릴 수 있게** 한다.

**근거** — "파티션을 막지 않는다"는 판단은 옳았다. 계약 위반 메시지 한 건이 뒤의 정상 메시지를
전부 세우는 것은 더 나쁘다. 문제는 그 대가로 **유실**을 골랐다는 점이고, 그럴 필요가 없었다.

DLT 는 파티션을 막지 않으면서 메시지를 남긴다 — **맞바꿈이 아니라 순수 개선이다.**
"관측 가능한 포기"가 "관측 가능한 연기"가 된다. 실패 원인·원본 토픽/파티션/오프셋이 헤더로 보존되고,
계약 헤더와 `traceparent`(17번)도 따라가므로 DLT 레코드에서 그 요청의 전 구간 트레이스로 바로 간다.

**license 만 다르게 한다** — 지급 실패는 DLT 로 보내지 **않는다.**
그 경로는 Saga 보상이 이미 최종 처리이기 때문이다. 그런데 리스너가 실패했으므로 Inbox 가드 행은
롤백돼 있다 — 즉 **재투입하면 멱등 가드가 막아주지 않고 지급이 다시 시도된다.**
이미 환불된 결제에 라이선스를 발급하게 된다. 보상 대상이 아닌 실패와 봉투를 못 푸는 레코드는
보상이 걸리지 않으므로 DLT 로 보낸다. 이 갈림을 테스트로 못 박았다.

**컨슈머 정책을 `common:kafka` 로 뺐다** — 적용하다 보니 **store 와 download 에는 재시도 정책도
DLT 도 붙지 않는다**는 것이 드러났다. 둘은 `common:messaging` 을 의존하지 않기 때문이다(Outbox 가 없다).
그래서 스프링 기본값(`FixedBackOff(0ms, 9회)` = 수 밀리초)으로 돌고 있었고,
색인 동기화와 권한 사본 갱신 이벤트가 그렇게 사라질 수 있었다.

정책만 쓰려고 Outbox 와 JPA 까지 딸려오는 것이 문제였으므로 모듈을 갈랐다.
`common:kafka` 는 수신 측 정책(재시도·DLT·DLT 운영 API)만 담고 JPA 를 모른다.
**9개 서비스가 전부 같은 실패 처리를 갖게 된 것은 이 분리 덕분이다.**

**운영 API 를 어디에 둘지**

| | 자리 | 이유 |
|---|---|---|
| `/api/v1/ops/outbox/**` | `common:messaging` | `outbox_event` 를 쓰는 7개 서비스 |
| `/api/v1/ops/dlt/**` | `common:kafka` | **9개 전부** — 보낼 수 있으면 되돌릴 수도 있어야 한다 |

게이트웨이는 이 경로를 라우팅하지 않는다. 도달 불가가 곧 통제라는 이 저장소의 방식(18번)을 그대로 따른다.

**화면은 만들지 않았다** — 운영툴에 프론트를 붙일 자리라고 봤지만, 18번으로 각 서비스에
Swagger UI 가 생겼다. 목록 조회와 버튼 두 개가 전부인 도구에는 그것으로 충분하고,
화면을 따로 만들면 **명세와 화면 두 벌을 유지**하게 된다.

**대가**

1. **DLT 도 쌓인다.** 아무도 안 보면 유실과 운영상 다르지 않아 `stove.kafka.dead-lettered` 카운터를
   더하고 Prometheus 알람 규칙을 붙였다. `promtool check rules` 로 검증했다.
2. **재투입은 중복 수신이다.** Inbox 멱등 가드가 막아주지만, 가드가 없는 서비스(store·download)는
   자연 멱등(문서 ID 고정 upsert)에 기댄다 — 8번의 전제가 여기서 한 번 더 쓰인다.
3. **원인을 안 고치고 재투입하면 그대로 돌아온다.** 도구가 대신 판단할 수 없어서
   조회를 먼저 하게 만들었다(조회는 커밋하지 않으므로 몇 번을 봐도 상태가 안 변한다).
4. **모듈이 하나 늘었다.** `common/*` 이 7개에서 8개가 됐다.

**버린 선택지**

| 안 | 버린 이유 |
|---|---|
| 실패 시 파티션을 세운다(재시도 무한) | 계약 위반 한 건이 뒤의 정상 메시지를 전부 막는다. 원래 판단이 옳았다 |
| store·download 에 정책을 복제한다 | 재시도 숫자가 서비스마다 갈리면 장애 때 무슨 일이 벌어질지 예측할 수 없다 |
| store·download 가 `common:messaging` 을 의존한다 | JPA 가 딸려와 DataSource 자동 구성이 붙는다. ES·Mongo 서비스에 RDB 를 요구하게 된다 |
| DLT 를 상주 리스너로 자동 재투입 | 원인을 고치기 전에 되돌아가는 사고가 가능해진다. 재투입은 사람이 누르는 작업이다 |
| 운영 화면(Thymeleaf)을 만든다 | Swagger UI 와 두 벌이 된다. 화면이 필요해지는 시점은 목록에 필터가 필요해질 때다 |

## 검증하며 드러난 것

정적 검증이 잡는 것과 못 잡는 것이 뚜렷하게 갈렸다. 기록해 둔다.

| 발견 | 잡은 수단 | 정적 검증이 놓친 이유 |
|---|---|---|
| `api ↔ application` 순환 12건 | ArchUnit 순환 검사 | import 를 눈으로 읽어서는 안 보인다 |
| 어댑터가 자기 포트를 못 보는 규칙 결함 | 실제 적용 | 규칙을 쓸 때는 몰랐다 |
| 빈 모듈에서 터지는 규칙 2건 | **규칙을 안 쓰던 모듈에 적용** | 9개 앱이 전부 비지 않아서 가려져 있었다 |
| javadoc 이 코드와 어긋난 것 (13번) | **규칙으로 옮겨 적기** | 문서는 자기가 사실인지 확인하지 않는다 |
| `catalogRestClient` 빈 이름 충돌 | **애플리케이션 기동** | 컴파일·규칙 23개 모두 통과했다 |
| Docker 29 가 Testcontainers 를 거부 | **devcontainer 빌드** | 업스트림이 바뀐 것이라 코드에 흔적이 없다 |
| self-hosted CI 가 테스트를 건너뛰고 그린 | **소요 시간이 5분 57초 → 23초** | 빌드는 성공했다. 로그를 열지 않으면 보이지 않는다 |

> 마지막 줄은 **초록불이 신호가 아닐 수 있다**는 사례다.
> 실패는 스스로 알리지만 "돌지 않음"은 알리지 않는다 —
> 통과 개수도, 결과 파일도, 종료 코드도 전부 정상으로 보인다.
> 이번에 그것을 드러낸 유일한 값이 **소요 시간**이었다.
| 컨테이너 재사용이 Flyway 검증을 깨뜨림 | 통합 테스트 | 모듈 간 상태 누수라 한 모듈만 보면 안 보인다 |
| 추적이 꺼진 구성에서 **빈 응답 헤더**를 내보냄 (17번) | **없던 자리에 테스트를 붙임** | `Tracer.NOOP` 은 null 이 아니라 빈 traceId 를 가진 스팬을 준다. null 검사는 통과한다 |
| store·download 에 재시도 정책도 DLT 도 없었음 (19번) | **다른 작업을 적용하다가** | 두 서비스는 `common:messaging` 을 의존하지 않는다. 없는 것은 규칙 위반으로 잡히지 않는다 |
| 운영 컨트롤러가 자동 구성 스위치를 우회 (19번) | **컨텍스트 로딩 테스트** | `@RestController` 가 `@Component` 를 품는다. 스캔 범위가 겹치는 컨텍스트에서만 드러난다 |

`catalogRestClient` 건이 컨텍스트 로딩 테스트를, Docker 29 건이 devcontainer 검증을 추가한 계기다.
**"컴파일되고 규칙도 통과하는데 안 뜨는" 부류가 실재한다.**

표의 위쪽 세 건은 성격이 다르다. 셋 다 **규칙을 쓰거나 옮기는 과정 자체**가 잡아냈다 —
검사가 통과한다고 검사가 옳다는 뜻은 아니다.

### 한 번 띄워 보고 나온 것 (17~19번 적용 직후)

전체 스택을 원격에 올려 스모크를 돌렸다. **테스트 977개가 전부 통과한 상태에서 결함이 8건 나왔다.**
공통점은 하나다 — 전부 *컴파일·단위 테스트·컨텍스트 로딩의 사각지대*, 즉
**설정과 바깥 세계의 접점**이다.

| 발견 | 증상 | 왜 테스트가 못 잡았나 |
|---|---|---|
| `grafana/tempo:latest` 가 v3.0.0 을 받아옴 | 기동 즉시 사망 — 3.x 는 `ingester`/`compactor` 를 최상위에서 안 받는다 | 이미지 태그는 코드가 아니다. 어제 되던 것이 오늘 안 된다 |
| `springdoc.api-docs.enabled=false` | **Swagger UI 전체가 404.** 그 속성은 명세 하나가 아니라 구성 전체의 스위치였다 | 게이트웨이에는 컨트롤러가 없어 스냅샷 테스트 대상이 아니다 |
| DLT 접미사가 `-dlt` | 우리 토픽은 점으로 끊는데 `stove.payment.v1-dlt` 가 생겼다 | 스프링 기본값이다. 우리 코드에 그 문자열이 없으니 검색으로도 안 보인다 |
| license 가 이름 규칙을 우회 | 자기 `DeadLetterPublishingRecoverer` 를 만들어 **DLT 토픽이 두 개** 생겼다 | 두 경로 모두 각자는 정상 동작한다. 갈렸다는 사실은 토픽 목록에서만 보인다 |
| license 가 계측도 우회 | 이름을 고친 뒤에도 license 의 DLT 유입만 지표에 없었다 | 카운터를 에러 핸들러 쪽에서 올려서 자기 recoverer 경로가 비껴갔다 |
| Prometheus 가 `host.docker.internal` 을 긁음 | **타깃 10개가 전부 down.** 지표도 규칙도 있는데 알람이 울릴 수 없었다 | 규칙이 조용한 것과 대상이 없는 것이 겉보기에 같다 |
| 파일 단위 bind mount 가 상함 | 호스트 파일은 갱신됐는데 컨테이너는 옛 내용 — rsync 가 inode 를 바꾼다 | 로컬에서는 파일을 제자리 수정해서 드러나지 않는다 |
| `increase()` 가 첫 1건을 놓침 | Micrometer 는 카운터를 첫 증가 때 등록한다 → 시계열이 값 1 로 생기고 증가분은 0 | 지표는 정상이고 규칙도 유효하다. 둘의 **조합**만 틀렸다 |

앞의 다섯은 고치면서 장치를 하나씩 남겼다 — 태그 고정,
`DeadLetterTopics`(이름 규칙 단일 출처), `DeadLetterPublisher`(발행과 계측을 한 덩어리로),
그리고 `앱은_DLT_발행자를_직접_만들지_않는다` 규칙. **같은 종류로 다시 갈리지 않게 하는 것이 목적이다.**

뒤의 셋은 남길 장치가 마땅치 않다. 컨테이너 배선과 PromQL 의미론은 코드 규칙으로 강제할 대상이
아니라 **한 번 띄워서 확인할 대상**이다. 그래서 이 표 자체가 그 자리를 대신한다.

> 이 절 맨 위의 "초록불이 신호가 아닐 수 있다"가 여기서 한 번 더 반복됐다.
> 이번에는 초록불이 **거짓말을 한 것이 아니라 그 영역을 보지 않았을 뿐**이다 —
> 그런데 결과는 같다. **관측 장치 전체가 죽어 있는데 아무도 몰랐다.**
